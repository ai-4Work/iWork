## 0. 为什么设计 L1/L2/L3 三层记忆

在深入 L3 之前,先回答一个更根本的问题:为什么要设计 L1、L2、L3 三层记忆?因为单层记忆解决不了"上下文有边界、检索会失手、事实会过时"这三个并存的问题,分层是对三个真问题的逐层回应。

### 0.1 一句话哲学

README_CN 的原话最能概括动机:

> 不追求"存下所有东西",而是解决三个问题:**什么值得留下、谁可以使用、下一次怎样少拿但拿对。**

核心矛盾是:**记忆存太多 → 上下文被占满、召回噪声大;存太少 → 关键信息丢、检索不到**。分层就是在这条"从原始到凝练"的频谱上逐级沉淀,每一层解决一层矛盾。

### 0.2 逐层回答"为什么多一层"

```
L0 对话记录(原始)  →  L1 原子(结构化)  →  L2 场景(情景)  →  L3 画像(语义)
  核对原话/时间      精确召回事实       快速恢复情境       进入用户/团队语境
```

- **L0 → L1:解决"什么值得留下"**。L0 是全量原文,太吵。L1 做严格质量门("宁缺毋滥""记忆必须跳出当前对话依然成立"),把对话提炼成**单条结构化事实碎片**(persona / episodic / instruction)。但碎片有两个天生缺陷:会**无限累积、互相矛盾**;召回**依赖检索措辞**——top-N 检索偏一次,关键事实就丢了。
- **L1 → L2:解决"碎片凑不成全景"**。L2 把碎片原子记忆按"团队+agent"聚合成**跨会话的连贯场景叙事**(不是清单,是文档)。它的出现是为了补 L1 的召回弱点:场景导航**全量注入**系统提示词末尾,用"几行摘要的冗余换召回可靠性",避免一次检索偏差丢掉整个情境。这就是 README 说的分层权衡:"平时用 L2/L3 快速进入语境,需要具体事实时再回到 L1/L0。"
- **L2 → L3:解决"场景是情境,不是人"**。L2 的场景再连贯也是"某段时间在干嘛",不是"这个人/这支团队整体是谁"。L1 虽有 persona 型记忆,但它是单条原子事实,无限累积、可能互相矛盾。L3 读 L2 的场景叙事做**综合分析**,产出一份**稳定、自洽、有界**的身份文档(核心原型 + 兴趣图谱 + 交互协议 + 认知内核),有 2000 字符硬上限——把"无限的事实"压缩成"永远在场的身份"。

### 0.3 为什么是三层而非一层

关键在于三层**形态不同、召回方式不同、无法互相替代**:

| 层 | 形态 | 召回方式 | 特点 |
|----|------|----------|------|
| L1 | 事实碎片 | 向量/关键词 **top-N** 检索 | 精确、可执行,但依赖检索措辞 |
| L2 | 场景叙事 | **整份**导航注入 | 可靠、有全景,但逐场景累积会膨胀 |
| L3 | 身份画像 | **整份**注入系统提示词末尾 | 稳定、可缓存、有界,但不含细节 |

最关键的证据是**召回侧的分工**:L1 动态拼到用户消息前缀(随问题变),L2 导航 + L3 画像拼到系统提示词末尾(基本不变、命中提示词缓存)。如果只有 L1,缓存友好和精确召回只能二选一;如果只有 L3,细节和情境全没了。三层正好覆盖"精确事实 / 连贯情境 / 长期身份"三个不同粒度的需求。

### 0.4 一句话总结

**上下文有边界、检索会失手、事实会过时**——一层记忆做不到面面俱到。L1 用检索换精确,L2 用冗余换可靠,L3 用压缩换稳定,三层互补构成一条从"原始对话"到"可复用认知"的沉淀链路。

## 1. 概述

L3 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L2 生成的场景块与场景索引(**不是 L1 记忆**)
- **输出**:一份凝练、稳定、有界的"画像"文档,回答"这个人是谁、喜欢什么、该怎么服务"
- **形态**:同一份文件,内容形态由提示词模式决定——对话模式下是**个人画像**(Persona Architect,四层深度扫描);团队工作模式下是**团队 Operating Doctrine**(可复用工作原则)
- **注入**:整份读入,包在"用户画像"标签里,拼到**系统提示词末尾**(稳定部分,缓存友好)

一句话:L1 给"和当前问题相关的事实",L2 给"进行中的情境全景",L3 给"这个用户/这支团队整体是谁"——一份稳定注入、永远在场的身份文档。

### 1.1 L3 的数据来源

L3 的输入是 **L2 的产出**,不是 L1 的原子记忆。这是理解 L3 的关键:**L1 已经有 persona 类型的记忆提取了,为什么还要 L3?** 因为两者吃的原料不同、产出的层级不同:

- **L1 的 persona 记忆**是单条原子事实("用户喜欢日本料理"),从逐轮对话里直接抽取,会无限累积、可能互相矛盾
- **L3 画像**读的是 L2 拼好的**连贯场景叙事**(跨会话、按"团队+agent"累积),从中做**综合分析**,推断出"这个人整体是谁"(核心原型、兴趣图谱、交互协议、认知内核),输出一份**稳定、自洽、有界**的身份文档

**读取方式是增量的**:每次生成只读"上次画像之后更新过的场景"完整原文(含元信息与正文),不是把所有场景重读一遍;场景索引提供了"哪些场景更新了"的判断依据。

**隔离范围是跨会话的**:画像按"团队 + agent"隔离累积,刻意忽略用户/会话/任务维度——横跨几十个会话沉淀的是"这一位用户"或"这一支团队"的长期画像,而不是某次对话的临时状态。

### 1.2 抽取时机

L3 不是独立定时任务,而是**由 L2 级联触发的**:每次 L2 场景抽取完成后才轮到评估 L3;L2 首次被跳过时不触发。真正"要不要生成"由五个优先级依次判断,命中任一即触发:

| 优先级 | 触发条件 | 典型来源 |
|--------|----------|----------|
| P1 主动请求 | 场景抽取时 LLM 输出了"请求立即更新画像"的带外信号 | 场景抽取过程中发现重大变化,主动要求画像跟进 |
| P2 冷启动 | 已抽取过场景、但从未生成过画像、且有场景文件 | 首次积累出场景后 |
| P2.5 恢复 | 曾生成过画像、但画像文件正文丢失或为空(只剩导航) | 文件损坏 / 被误删,需要重建 |
| P3 首个场景 | 只完成过 1 次场景抽取、且画像之后有新记忆 | 首个场景块落盘 |
| P4 阈值 | 自上次画像以来新增的记忆数达到阈值(默认 50 条) | L1 持续抽取,记忆数累积到阈值 |

评估按优先级从高到低:先看 P1 主动请求,再看 P2 冷启动、P2.5 恢复、P3 首个场景,最后看 P4 阈值。

一句话:**平时靠阈值(P4)周期性沉淀画像;场景抽取中如有重大变化,可主动插队(P1);冷启动和文件损坏有专门兜底(P2 / P2.5 / P3)**。

**两种部署模式的级联差异**:独立模式在进程内"L2 完成后立即评估 L3",用全局互斥 + 待办标记去重,避免同时跑多个;服务模式走任务队列——L2 任务完成后直接入队一个 L3 任务,用分布式锁保证**同一 agent 的画像文件不并发写**。

### 1.3 与主会话、上下游的关系

L3 处于级联链的**末端**:`会话 → L0 存档 → L1 抽取 → L2 场景聚合 → L3 画像生成`。它只消费 L2 的产出,不直接碰 L0 对话、也不直接读 L1 记忆;画像的"真相源"是场景——场景不变,画像就不重算。

反馈闭环:**画像生成后进入稳定注入**,此后每一轮会话开始前,AI 都带着"这个人是谁"工作;画像什么时候更新?取决于 L2 什么时候产生了新场景变化。所以 L2 是 L3 的"上游时钟",L3 是这条记忆链路的"语义收口"。

## 2. 核心处理流程

L3 的处理逻辑非常"轻":**判定环节全是规则,生成环节一次 LLM 调用,收尾环节全是确定性操作**。先从整体看一遍流程,再分节详解。

### 2.1 完整流程总览

从 L2 完成,到画像真正落地,一次 L3 处理走完下面十一步。全流程只有一步调用 LLM(第 ⑧ 步),其余都是规则、文件操作或存储操作。

```
L2 完成
  → ① 触发判断:按五个优先级评估要不要生成(见 1.2)
  → ② 读检查点 + 读现有画像(剥掉导航,看有没有正文)
  → ③ 读场景索引,筛出自上次画像后更新过的场景
  → ④ 读变化场景的完整原文(含元信息)
  → ⑤ 定模式:首次(无画像)/ 增量(已有画像)
  → ⑥ 组装提示词(系统提示词 + 用户提示词)
  → ⑦ 备份旧画像
  → ⑧ 一次 LLM 调用:LLM 用文件工具直接把画像写进画像文件
  → ⑨ 读回 + 确定性后处理(剥导航、转义危险标签)
  → ⑩ 追加最新场景导航 + 写回
  → ⑪ 级联收尾:推进检查点 + 上报指标
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 触发判断 | 评估五优先级 | 规则 | 命中任一即生成;不命中则本次不跑 |
| ② 读现状 | 读检查点与现有画像 | 规则 | 画像正文是否为空决定后续模式 |
| ③ 筛变化场景 | 按时间筛选 | 规则 | 更新晚于上次画像时间的才算变化;日期不可解析按变化处理 |
| ④ 读场景原文 | 预加载完整内容 | 规则 | 变化场景的全文都喂给 LLM,供深度分析 |
| ⑤ 定模式 | 首次 / 增量 | 规则 | 由"有没有画像正文"自动决定 |
| ⑥ 组装提示词 | 拼系统 + 用户提示词 | 规则 | 可选追加自定义策略 |
| ⑦ 备份 | 备份旧画像 | 存储 | 默认保留 3 份;对象存储模式下跳过 |
| ⑧ 生成 | 一次 LLM 调用 | **LLM** | LLM 用文件工具直接写画像文件,沙箱限定数据目录 |
| ⑨ 后处理 | 剥导航、转义 | 规则 | 转义注入边界标签,防逃逸 |
| ⑩ 落地 | 追加导航、写回 | 存储 | 画像 = 正文 + 导航,一体落地 |
| ⑪ 收尾 | 推进检查点、上报 | 规则/存储 | 清主动请求信号、记录生成时间 |

按阶段读这张表:

- **① → ⑦ 准备**:纯规则 + 存储,判定要不要跑、把输入和备份准备好
- **⑧ 生成**:唯一一次 LLM 调用,LLM 以"文件代理"身份直接产出画像
- **⑨ → ⑪ 收尾**:确定性后处理、落地、推进检查点

下面 2.2–2.7 按这十一步的顺序展开详述。

### 2.2 增量读取与输入构造

L3 **不重读全部历史**,每次只处理"上次画像之后变化的部分":

- **读现有画像**:读画像文件,剥掉尾部场景导航,判断正文是否为空。有正文 → 后续走"增量";无正文 → 走"首次"
- **读场景索引**:拿到当前全部场景的清单(每个场景含文件名、摘要、热度、创建与更新时间)
- **筛变化场景**:逐个对比"场景最近更新时间"与"上次画像生成时间",更新晚于画像时间的就是变化场景;**任一日期无法解析时按"变化"处理**(保守,宁多不少)
- **读变化场景完整原文**:把每个变化场景的完整内容(含元信息与正文)原样读出来,预加载给 LLM

**一个重要的短路**:如果没有任何变化场景、但画像已经存在,本次直接跳过——所有场景都在上次画像时分析过了,没有必要重复生成。只有当"有变化场景"或"还没有画像"时才继续。

### 2.3 两种模式:首次与增量

模式由"有没有画像正文"**自动决定**,不是配置项:

- **首次生成**:没有旧画像。基于当前所有变化场景从零提炼,输出完整模板文档(核心原型 + 基本信息 + 长期偏好 + 四个章节)
- **增量更新**:已有旧画像。把旧画像全文 + 变化场景全文一起给 LLM,在旧版基础上迭代。增量时提示词会附一段**迭代决策指南**,让 LLM 自主判断该用哪种方式处理变化场景:

| 方式 | 含义 |
|------|------|
| 强化 | 新场景只是佐证已有洞察,压缩进原句或不改 |
| 补充 | 出现新维度,新增内容 |
| 修正 | 旧洞察与新场景矛盾,以新为准 |
| 重构 | 文档变散、变长、结构失衡,整体压缩重写 |
| 不改 | 新场景没有有用的新增内容 |

关键约束:**不要把每次变化都追加成新条目**。画像是"持续压缩、少而准"的文档,不是累积的流水账。

### 2.4 LLM agent 执行

这是 L3 唯一调用 LLM 的一步,也是画像生成的"创作环节"。LLM 不是返回文本等工程侧写入,而是**以"文件代理"身份,用文件工具直接把结果写进画像文件**:

- **文件工具约束**:必须用文件工具写入最终内容;**只准操作画像文件这一个文件**,禁止读取或写入任何其他文件(包括场景块目录、元数据目录等);首次/大幅重写用整体写入,局部修改用精确替换;现有画像全文已在用户消息里提供,无需再读
- **沙箱隔离**:工作目录限定在数据目录,工具被沙箱限制在画像文件范围内
- **写入内容必须纯粹**:只写最终画像文档,不夹带思考过程、分析步骤
- **四层深度扫描**(对话模式):基础锚点(确凿事实)→ 兴趣图谱(投入时间/金钱/注意力的事物,区分活跃度)→ 交互协议(沟通习惯、雷区、工作流偏好)→ 认知内核(决策逻辑、矛盾点、终极驱动力)。强调"叙事连贯性",禁止简单的罗列
- **输出模板**(对话模式):核心原型一句话 + 基本信息 + 长期偏好 + 四个章节(全景语境 / 生活的肌理 / 交互与认知协议 / 深层洞察与演变)
- **长度上限**:对话模式整份不超过 **2000 字符**;团队工作模式不超过 **1200 字**(持续压缩)
- **团队工作模式的提炼对象**:可复用 SOP / 长期原则 / 决策逻辑 / 边界 / 反模式 / Agent 规则;每条都要过"通用性、完整性、可执行性、稳定性、精炼性"五条过滤,任一不满足就不写
- **禁止事项**:
  - 禁止过长、禁止把每次变化追加成新条目
  - **禁止过度推测**:没提到的信息不要臆想,尤其是冷启动阶段,没有相关信息完全可以不填
  - **禁止使用非场景来源的信息**:画像内容必须且只能来自提供的场景数据,不许从工作区目录结构、文件路径、系统信息等技术元数据里提取任何个人信息
  - **禁止添加场景导航**:场景导航由工程自动追加,LLM 不许写

### 2.5 工程侧确定性后处理

LLM 写完后,工程侧做三道确定性处理:

1. **剥导航**:LLM 若在文件里写了场景导航区块(理论上被禁止,但不排除),先按分界标记剥掉,只留画像正文
2. **转义危险标签**:把正文里可能出现的"注入边界标签"(如用户画像、相关记忆、场景导航这类包裹标签的闭合写法)转义掉——防止画像内容被人为塞入恶意闭合标签、逃逸出注入区块(标签注入防御)。LLM 写完的正文只有"转义后"才算数
3. **空内容判定**:剥离导航并转义后,如果正文为空,本次视为失败,不落地

### 2.6 落地写入与备份

- **备份**:LLM 运行之前,先把旧画像备份一份(默认保留最近 3 份);这样即使 LLM 把画像写坏,也能找回上一版。对象存储模式下本地不做备份,恢复由存储后端快照负责
- **写回**:后处理完成后的最终内容(画像正文 + 最新场景导航)写回画像文件
- **失败判定**两条:
  - LLM 跑完但没有写画像文件(文件不存在)→ 生成失败
  - LLM 写了但内容是空的 → 生成失败
  - 只有这两条之外的正常路径才落地

画像文件的最终形态是"**正文 + 场景导航**"一体:正文是画像本身,导航是给 AI 用的"场景目录"。召回注入时再剥掉导航只取正文。

### 2.7 级联收尾

画像落地后做三件事:

- **推进检查点**:记录本次画像生成时间、当前已处理记忆总量快照;清零"自上次画像以来新增记忆计数"(P4 阈值据此重新累计);清除 P1 主动请求信号(消费掉这次插队)。**无论本次生成成功还是失败,检查点都会推进**——避免失败后对同一批数据反复重试
- **上报生成事件**:触发原因、生成模式(首次 / 增量)、新画像内容与长度、整体耗时
- **上报延迟与画像变化指标**:生成延迟、更新前后画像长度、**画像漂移比**(用行级差异衡量"这次到底改了多少",0 到 1 之间;没生成或前后都为空时不报)

## 3. 召回:画像怎么回到对话里

第 2 章讲的是"入"——把场景综合成画像写进文件;召回讲的是"出"——把画像拿回对话,让 AI 记得"这个人是谁"。画像在召回里属于**稳定注入**部分,与 L1 的动态召回分工明确。

### 3.1 时机:每轮对话前预取

和 L1 一样,AI 处理**每一条新的用户消息之前**,宿主先调一次召回接口,把三层记忆一起预取回来,再让 LLM 干活。画像作为三层之一被同步读取,失败或超时**不阻塞对话**(非关键路径)。

### 3.2 注入方式:整份稳定注入

画像的注入方式很直接:

- **整份读取**:读画像文件,剥掉尾部场景导航,只留正文
- **标签包裹**:用"用户画像"标签把正文包起来
- **位置固定**:拼到**系统提示词末尾**,与 L2 场景导航、记忆工具指南放在同一个稳定区

因为画像的"主要变量"不在召回侧(它不按当前用户输入检索或过滤),所以这段内容在两次画像更新之间**字节级不变**——正好命中模型提供商的提示词缓存,省 token 省成本。

### 3.3 与 L1、L2 的分工

一次召回同时拿三层,却放在两个不同的位置,分工如下:

| 部分 | 内容 | 位置 | 特点 |
|------|------|------|------|
| 动态部分 | L1 相关记忆 | **用户消息前缀** | 每轮随问题变化,检索 top-N |
| 稳定部分 | L2 场景导航 + **L3 画像** + 记忆工具指南 | **系统提示词末尾** | 基本不变,命中缓存 |

其中画像与场景导航都是**整份读取/生成**,不按输入做过滤——由 LLM 自行判断相关性。区别在于:场景导航是"目录"(一行一个场景,给 AI 索引),画像是"这个人是谁"(一份完整身份文档)。两者都是"兜底保证",不依赖当轮检索措辞。

**一个与 L1 不同的点:画像没有召回侧的长度裁剪**。L1 相关记忆有单条字符上限、总预算上限,超长截断;画像则整份注入、不做截断。画像的"有界"是靠生成侧保证的——对话模式 2000 字符、团队模式 1200 字的上限,让画像天生是一份精炼、自洽、塞得进上下文的文档。

### 3.4 控制与兜底

- **生成侧兜底**:画像内容有硬性长度上限与"只来自场景证据"的约束,保证注入的内容精简可信
- **召回侧兜底**:画像不是万能的,当注入的画像或导航不足以回答问题时,AI 可以主动调工具深入——读场景文件进具体情境、搜 L1 结构化记忆、搜 L0 原文对话(搜索工具每轮合计限 3 次,防止无休止地搜)

### 3.5 一句话总结

每轮 AI 开口前,宿主把三层记忆预取好拼进上下文:**画像(L3)整份注入系统提示词末尾,稳定、可缓存;L1 相关记忆动态拼到用户消息前缀;L2 场景导航同区给出目录**。画像更新靠 L2 场景变化驱动,注入的内容永远是有界、精简、基于场景证据的综合身份判断。

### 两套提示词的来源与选择

L3 的 prompt 分两套,对应两种画像形态:

```text
- ✅ 求精不求多，能不写就不写，能合并就合并

- ✅ 只操作 `persona.md`
```

### 4.3 画像生成 · 用户提示词模板

运行时把动态数据填进固定框架(下方 `${...}` 为模板变量):

```text
**输出语言**：`persona.md` 使用下方变化场景内容的主导语言。

**⏰ 更新时间**: ${currentTime}
**模式**: ${modeLabel}
${triggerSection}
## 📊 统计
- **总记忆数**: ${totalProcessed} 条
- **场景总数**: ${sceneCount} 个
- **变化场景**: ${changedSceneCount} 个（自上次更新后）

---
${changedScenesContent}

${existingPersonaSection}
${iterationGuide}
```

变量说明:

- `${modeLabel}`:`🆕 首次生成` 或 `🔄 迭代更新`
- `${triggerSection}`:有触发原因时输出一段"触发信息"小节,没有则整段为空
- `${changedScenesContent}`:变化场景的完整内容(每个场景一段,含元信息与正文),由工程预加载组装;无变化场景时替换为"无变化场景、本次可全局审视"的提示
- `${existingPersonaSection}`:增量模式下预加载现有画像全文;首次模式为空
- `${iterationGuide}`:增量模式下的一段"迭代决策指南";首次模式为空
