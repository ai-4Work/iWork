# iWork Agent 系统 — 面试·真实使用话术

> **定位**：这份文档是 `interview-questions-answers.md`（设计视角）的姊妹篇。
> 那份回答"系统**怎么工作、为什么这么设计**"；这份回答"这套系统在**真实世界跑起来**是什么样、我踩过什么坑、怎么演进"。
> 面试官一旦追问"**真实的使用情况**"，就用这份。

---

## 〇、一句话定位（背下来，开场 30 秒用）

> 我自己从零搭了一套**本地运行的 Agent 平台**——约 1.7 万行 Python（FastAPI 服务端 + Electron 客户端）。
> 它不是我练手的 demo，是我**日常真在用的工具**：最常拿它做**办公文档处理**（Word 编写、PDF 阅读、扫描件/发票 OCR、Excel 统计）和**日常查询**（天气、地图、搜索、车次）。

**为什么这个开场有效**：
- "日常真在用 + 办公场景"是大多数候选人没有的**区分度**——多数人是拿现成 CLI/IDE 工具，或只做了纯 coding-agent demo。
- 一句话同时立住两件事：**做得出来**（1.7 万行工程代码）+ **用得上**（真实场景），直接化解面试官对"是不是 AI 生成的文档 / 纸上谈兵"的默认怀疑。
- 面向 **Agent 平台/架构师**岗，重点不在"我用它写了多少代码"，而在"我搭了一个平台，并且每天用它在真实场景里干活"。

## 一、讲述心法：三段式节奏

面试官问"真实使用"时，**不要一股脑背设计**。按系统真实状态分三档讲：

| 档位 | 怎么讲 | 覆盖模块 |
|---|---|---|
| **真做了** | 讲**取舍、踩坑、迭代、数据**——真实使用痕迹是最强说服力 | Query Loop 引擎、上下文管理、可观测性、MCP 集成、简单版记忆 |
| **部分做了** | 主动讲**缺口 + 演进方向**——诚实 + 展示架构判断力 | 记忆（→L1/L2/L3）、多 Agent（→星型拓扑）、成本（→接真实计费） |
| **纸面设计** | 讲**为什么这么设计 + 为什么还没落地**——展示思考深度，绝不冒充已实现 | 单回合工具并发、权限 Policy Engine、L1/L2/L3 完整实现 |

**核心原则**：面试官最怕的是你吹"已实现"结果被追问拆穿。**主动承认"这块我设计了、还没落地"反而加分**——资深岗位看的就是"想得清不清楚、对自己系统的诚实度"。真做了的部分才往里放具体数字和踩坑。

## 三、模块真实使用口径卡

每张卡 = **STAR（场景→行动→结果→数据）+ 能扛追问的代码级细节**。
面试**只挑 2–3 张主推**（架构、Query Loop、上下文管理，或对你岗位最相关的），其余当弹药。

---

### 卡 1｜架构总览 — 治理集中、执行本地

**场景**：一个自用 Agent 不该是单机玩具——我想要企业级的可管控、可审计、可量化、可复用。
**行动**：拆成 FastAPI 服务端（大脑 + 政策制定者）+ Electron 客户端（手）。
- 服务端集中：Query Loop、上下文、记忆、Skill/MCP 注册、多 Agent 编排、Hooks、权限、审计、成本。
- 客户端执行：bash / 文件 / glob/grep、客户端 MCP、skill 脚本——因为文件、进程、凭证都在本机，**执行必须贴近资源**。
**取舍（要主动讲）**：代价是**单点故障、离线不可用**。
**数据/细节**：通信用 MCP Streamable HTTP（一个 HTTP 请求完成"发消息 + 收 NDJSON 流"，断线走 `GET /stream?since_seq=N` 回放，重连逻辑简单可靠）。
**扛追问**：单点故障怎么缓解？→ 断线重连 + StreamBuffer 回放已落地；服务端本地兜底是明确没做的部分，我列为架构演进方向。

---

### 卡 2｜Query Loop 引擎（最扎实，主推）

**场景**：多用户/多会话要串行不丢消息、崩溃能恢复——这是平台的地基。
**行动**：每个会话一个 `QueryLoopEngine` 协程：消息 FIFO 队列（≤10）+ 状态机（IDLE/PROCESSING/WAITING_SYNC）+ 三模式（Ask/Plan/Build）+ 每消息 turn≤25、总超时 300s。
**关键决策**：队列用 **DB + asyncio.Event** 混合——`SELECT … FOR UPDATE SKIP LOCKED` 原子出队，**服务器崩溃后 pending 消息能恢复，不靠纯内存队列**。
**踩坑**：服务器重启后正在处理的消息重置为 pending 从头执行 → **副作用重复**（如重复写文件）是真实风险；我的应对方案是幂等注解，但尚未全量落地。
**细节（背下来）**：
- StreamBuffer 断线重放（NDJSON chunk，回放不丢流）。
- DeepSeek 的 `reasoning_content` 与 `tool_calls` 必须同一条消息——这是真实调多模型踩出来的兼容坑。
- 断线重连、指数退避重试、循环检测（连续 3 次相同工具调用）都落地了。

---

### 卡 3｜上下文管理（主推）

**场景**：对话一长，模型开始"丢中间信息"（Lost in the Middle）——这是我真实观察到的退化现象，逼我做上下文管理。
**行动**：三层堆栈（raw / compressed / meta-summary）+ 双粒度压缩 + 按 `retention_score` 四维打分把低热度块**卸载到 pgvector**（外部记忆）+ TF-IDF 召回（`offload.py`，`recall` 工具）。
**数据（设计值，可讲）**：压缩阈值 ask=0.55、build/plan=0.80；`retention_score` 权重 = precision 0.45 / reference heat 0.30 / one-shot 0.15 / token cost 0.10。
**踩坑/缺口（要主动讲）**：语法层引用检测（UUID 正则 + 文件路径）做了；**语义层 embedding 召回（0.78 阈值）没做**，整体覆盖约 60–70%。
**扛追问**："卸载的块怎么找回来？" → TF-IDF 关键词召回，`recall` 工具把块重新注入上下文。

---

### 卡 4｜可观测性

**场景**：多轮工具调用像黑盒——**出了问题不知道是模型想错了还是工具坏了**，所以我给平台配了可观测体系。
**行动**：OpenTelemetry（tracing + metrics）+ structlog + EventBus（Stream/Audit 订阅）+ 审计日志落库（`audit_logs` 表）+ Grafana 栈（Tempo/Prometheus/Loki）。
**细节**：指标清单含 `agent_tool_permission_denied_total`（权限拒绝可量化）；支持零外部依赖启动。
**缺口（要主动讲）**：`llm_cost` 指标定义了但没接线——成本这块只差最后一步。
**用法**：面试可以反客为主——"我加 span 之后，能定位某次工具失败是超时、权限还是命令本身的问题"。

---

### 卡 5｜MCP 工具集成

**场景**：真实接入了 5 个 MCP（`mcp-hub.json`）：和风天气、高德地图、百度地图、百度搜索、12306——**都是日常真在用的**。
**行动**：MCP 进程由**客户端**托管（凭证 env 注入、每用户 `mcp_servers.yaml` 隔离）；工具名加 `{server_id}_` 前缀防重名；三种传输 **stdio / SSE / streamable-http 都写过代码**；通过 `client.tool_request` 回传执行。
**踩坑（主推点）**：文档里列了 **G1–G5 五个真实缺陷**——
- G1 初始连接失败**不触发重连**（`_schedule_reconnect()` 未实现，服务卡在 ERROR，标记"待修复"）
- G2 `notify("notifications/initialized")` 失败会中断整个连接
- G3 SSE 断流后 pending 请求不清醒，硬等 120s
- G4 stdio 的 JSON 解析异常裸抛，raw traceback 直接进 LLM 上下文
- G5 notify 无 null check（Http/SSE 有、stdio 没有）

**扛追问**："为什么 MCP 工具在服务端、客户端工具在 Electron 端？" → MCP 服务是外部生态，注册/命名/凭证治理放服务端；客户端工具操作本地文件，执行必须贴近资源。

---

### 卡 6｜记忆（简单版已落地 → L1/L2/L3 设计）

**真实状态（先说清楚）**：**简单版已落地**：`memories` 表四类（user/feedback/project/reference）+ `rules` 表（AI 只读）+ MEMORY.md 动态索引（LIMIT 200）+ `load_memory/write_memory/delete_memory` 三工具 + 1 分钟写入冷却 + protected 标志。
**演进设计（未落地）**：L1 原子记忆 → L2 场景记忆 → L3 画像记忆四层体系，含质量门预筛、冲突判断（store/update/merge/skip 四动作）、热度管理、画像漂移比指标——**这是完整设计，还没实现**（文档明确标注"未实现"，测试用例文档也写明"功能尚未实现：设计级验收用例"）。
**话术**："我先做了一个**够用**的版本——事实碎片 + 规则 + 索引，现在真的在跑；然后我把'更聪明'的记忆——分层提炼、冲突合并、画像稳定——**完整设计好**作为演进路线。**因为我想先要个能用的，再要个更聪明的。**"
**细节**：简单版的写路径有 1 分钟冷却，防 LLM 高频刷记忆。

---

### 卡 7｜成本控制（设计完整，计费没落地）

**真实状态**：成本公式（input/output/cache_read/cache_write）、三级预算（session/user/global）、软/硬限额、D1–D4 降级阶梯（thinking_budget → 激进压缩 → 禁用重工具 → 换更便宜模型）——**全部设计好了**。
**缺口（要主动讲）**：`pricing.json` 没加载、`llm_cost` 指标没接线——**公式是设计，真实计费差最后一步**。
**话术**："我做完整的设计和降级策略，但真实计费还差定价表和指标接线，这是我下一步的事。"（把缺口讲成"下一步"，反而显得 roadmap 清晰）

---

### 卡 8｜多 Agent（task 委派已落地 → 星型拓扑设计）

**真实状态**：**task 委派已落地**：`task_handler` 派子 agent、child session、`<final_output>` 提取；`plugins/experts/` 有真实插件（senior-developer 等）。
**演进设计（未落地）**：星型拓扑 + 单 `task` 工具 + `agent_name` 枚举 + 先串后并 + 子 agent 硬限制（不可调 task、不可改 rules/memories、文件限父 workspace）。文档标注"**状态：设计中，方案讨论稿**"。
**话术**："我从可用的'串行委派'做起；在此基础上把'并发编排'的拓扑、隔离边界、资源上限想清楚了，但那是设计稿。"

---

### 卡 9｜单回合工具并发（纸面设计，主打"痛点→设计动机"）

**真实状态（诚实）**：现状是**串行执行**——遗留问题 6.2：LLM 一轮返回多个独立工具调用时逐个 await，总耗时 = 各 I/O 之和。**这是我最想落地的痛点**。
**设计**：**分段调度（segmented scheduling）**：
- 工具着色：只读内置判"读"；`apply_batch` 判"写"（同文件排队、异文件并行）；`exec_command` 用读白名单 `command_is_read_only()` 判定（如 cat/grep/ls，**排除重定向/管道/链式命令，没把握就串行**）；MCP 按 `supports_parallel_tool_calls` / `readOnlyHint` 数据驱动。
- 连续段划分：**读段内全并行、写段内保序，段间严格按模型发出顺序串行，不重排**。
**为什么是这个方案（核心卖点）**：相对"两阶段（读全先、写全后）"，**保留模型发出顺序** → 天然满足"写后读 / 读后写"的副作用依赖；相对 per-file 读写锁表，简单得多。
**量化（设计推演）**：3 个独立读操作从串行 `3×t` 降到并行 `t`。
**话术**："真实痛点是串行太慢，我把方案想透了——包括**不解析命令**、用白名单判定读，没把握就串行，**拿并发换安全**。这是我下一步最想落地的一块。"

## 四、高频"真实使用"追问对答口径

### Q1："你每天用它干什么？"
**A（办公主线，30–60 秒）**：
"最常做的是办公文档处理。比如**扫描件发票**——交给 paddleocr 的 skill 转成结构化 Markdown，表格数据提取出来进 Excel 统计；一堆 PDF 要合并/加密/表单填充，用 pdf skill；写 Word 文档用 doc-generator。平时随手问天气、查地图、查车次，走 MCP。**它是我的工作台，不是玩具。**"
> 备选：如果面试官是技术向，补一句"我也用它处理代码，但占比不如文档多——这反而证明它不是只能写代码的 demo。"

### Q2："真实使用中最常出什么问题？"
**A（诚实三连，收尾亮可观测性）**：
"三个真实的：**① 对话一长上下文退化**，丢中间信息——所以我做了上下文压缩和卸载；**② 工具调用串行慢**——所以我设计了分段调度并发；**③ 已知缺陷还没修**——MCP 连接失败不重连（G1），还有另外四个我列在文档里的。但这些问题我都能定位，因为我有 OTel span 和审计日志，**能区分是模型想错了还是工具坏了。**"

### Q3："XX 你实现了吗？"（对 L1/L2/L3、多 agent 并发、权限引擎、成本计费、并发）
**A（统一话术）**：
"这里我要先说清楚，避免你误以为 B 已经跑在生产里：**我实现的是可用的 A**（X 的基础版，落地在跑）；**B 是我完整设计好、还没落地的演进版**。设计 B 是因为真实的痛点 Y（串行慢 / 记忆太浅 / 只能串行委派）。核心设计点是 Z（讲 1–2 个：比如分段调度保序、L2 用受限 agent 只开放 read/write/edit、子 agent 硬限制）。"
> 这句话术同时完成三件事：**诚实**（不冒充）、**展示深度**（Z）、**展示演进路线**（A→B）。

### Q4："这文档是不是 AI 生成的？"
**A（不回避，三连证据 + 坦白排版）**：
"设计文档的**排版和表述**有一部分是 AI 帮我整理的——我不藏着。但我要说明三件事：**① 文档里有 G1–G5 缺陷、llm_cost 缺口、语义召回没做**这类'自我批评'内容——AI 生成的包装文档不会自黑，只有真做过的人才会；**② 代码是可运行的**，有日志轮转、有指标快照；**③ 我可以现场讲任何一个模块的取舍和踩坑。**核心的每一处设计决策、缺陷、取舍，都是我的。"

### Q5："重新做一遍你会改什么？"
**A（用遗留问题清单，真实且系统）**：
"四个我记在遗留清单里的：
**① 工具目录膨胀**——工具一多 LLM 就选不对，候选方案是 RAG 工具选择 / 硬上限 ≤30 / LLM router；
**② 单 turn 串行执行**——落地分段调度；

架构层面还想消掉**单点故障**——服务端挂了客户端没有本地兜底。"

## 五、避坑清单（绝不能冒充已实现）

面试中主动说清楚，**一旦被追问实现细节就会露馅**：

| 模块 | 现状（可说的） | 不能说成 |
|---|---|---|
| 记忆 | 简单版（memories/rules + 3 工具）已落地 | L1/L2/L3 四层记忆已实现 |
| 多 Agent | task 委派 + child session 已落地 | 星型拓扑 / 并发编排已实现 |
| 权限 | 仅 Build 模式静态 `_check_tool_permission()` | Policy Engine（permissions.yaml 规则引擎）已实现 |
| 成本 | 公式 + 三级预算 + 降级设计 | 真实计费（pricing.json 加载、llm_cost 接线）已实现 |
| 并发 | 现状串行 | 分段调度已实现 |

**主动澄清话术模板**：
> "这块我要先说清楚：**我实现的是 A（可用版本），B 是我完整设计、还没落地的演进版**。我不想让你误以为 B 已经跑在生产里。设计 B 是因为真实的 X 痛点……"

**为什么这套避坑逻辑在资深岗面试反而是优势**：
- 面试官最擅长追问实现细节，吹"已实现"是最容易翻车的。
- 主动声明边界，等于告诉他"**我对系统每个部件的真实状态都有清晰认知**"——这正是架构师的核心素质：**知道自己系统里什么是真的、什么是计划**。
