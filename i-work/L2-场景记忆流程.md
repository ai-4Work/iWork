> 本文档梳理 TencentDB-Agent-Memory 项目中 **L2 层场景记忆**的处理流程,内容来自对源码的研读。包含:处理流程概述(数据来源与抽取时机)、核心处理流程详解、召回机制(记忆怎么回到对话),以及 chat / code 两套场景抽取 prompt 的完整原文。
>
> **核心理解**:L2 把 L1 中**方向/主题一致**的记忆整合进**同一个场景文件**,但这不是机械归档——由 LLM 以受限 agent 的方式主动决策(UPDATE / MERGE / CREATE),把新记忆**重写融合**进已有场景的连贯叙事(明确禁止简单追加列表),产物是"叙事文档"而非"清单"。方向一致是分组依据,整合重写才是落笔方式。
>
> **召回口径**:对话召回时 L1 与 L2 不会字面重复——L1 按相似度检索 top-N 原子记忆正文,动态拼到用户消息前缀;L2 只全量注入"场景导航"(路径/热度/摘要,不过滤),拼到系统提示词末尾(稳定、命中缓存),场景全文按需 read、不进提示词。两者有少量语义重叠(场景摘要由 L1 聚合而来),这是设计使然——用几行摘要的冗余换召回可靠性,避免一次 L1 检索偏差就丢掉整个场景。

## 1. 概述

L2 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L1 抽取并落库的结构化记忆记录
- **输出**:结构化的**场景叙事文档**,跨会话累积,既是召回时让 AI"记得"情境的载体,也是 L3 画像生成的重要素材

L2 和 L1 最大的区别在"怎么抽":L1 是**一次 LLM 调用输出结构化 JSON**;L2 则是**让 LLM 像一个受限 agent 一样,在沙箱里用读/写/改工具自主整合场景文件**——新增、更新、合并、删除都让 LLM 自己决定,工程侧只做确定性的收尾(清理、重建索引、更新导航)。

### 1.1 L2 的数据来源

L2 的输入就是 **L1 落库的结构化记忆记录**,不是 L0 原始对话。

**L1 记忆存在哪里、L2 怎么读**

- L1 抽出的原子记忆记录在记忆库的 L1 记录表,L2 按**游标增量**拉取——游标记录"上次 L2 抽到哪条",即上次处理完成时最新一条 L1 记录的更新时间;每次只读游标之后新产生或更新的记录,保证每条记忆只被聚合一次
- 记忆库不可用时**直接报错,不静默降级**——让上层明确知道发生了什么
- 没有新记录时直接跳过、不推进游标;冷启动第一次被跳过时不记录运行时间,避免挡住下一次触发

**一条 L1 记录长什么样**

L1 落库的是一条结构化的原子记忆记录。仍以文档 4.3 的 Billing 超时排查为例,一条 L1 记录大致如下(节选核心字段):

```json
{
  "id": "m_1755571800000_a1b2c3d4",
  "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
  "type": "episodic",
  "priority": 85,
  "scene_name": "我（AI）在和用户王小明排查 Billing API 超时",
  "source_message_ids": ["msg_c", "msg_d"],
  "metadata": {
    "activity_start_time": "2026-08-18T02:00:00.000Z",
    "activity_end_time": "2026-08-18T02:10:00.000Z"
  },
  "timestamps": ["2026-08-18T02:10:00.000Z"],
  "createdAt": "2026-08-18T02:10:00.000Z",
  "updatedAt": "2026-08-18T02:10:00.000Z",
  "version": 1,
  "teamId": "team_xxx",
  "userId": "user_xxx",
  "agentId": "agent_xxx"
}
```

要点:

- **content / type / priority / scene_name**:L1 抽取的核心字段。`type` 按模式取 persona/episodic/instruction(对话)或 work_fact/work_task/work_method/work_artifact(团队);`metadata` 存类型相关附加信息(episodic 为活动时间区间)
- **id / timestamps / version**:id 全局唯一;`timestamps` 记录时间戳轨迹(合并时取并集);`version` 单调递增(update/merge 后 +1)
- **teamId / userId / agentId / sessionId**:隔离与归属维度,其中 L2 按"teamId + agentId"分组(见下文)
- **createdAt / updatedAt**:落库时间,`updatedAt` 正是 L2 游标推进的依据

> 落到检索库的 L1 表会把上述字段平铺成列(record_id/content/type/priority/…/metadata_json),`source_message_ids` 只留在产出文档里、检索库不存;且传给 L2 LLM 时只保留 content / created_at / id 三字段(见 2.2)。

**L2 读出来的记录怎么分组**

L2 属于**跨会话、跨用户的聚合层**:读出来的 L1 记录按"**teamId + agentId**"的隔离作用域分成组,每组独立做一次场景整合。这里刻意**忽略**用户、会话、任务这些维度(仅当 teamId 缺省时才退化为 userId 兜底)——同一 teamId + agentId 的记忆可以跨多个会话、多个用户持续累积。

**L1 与 L2 的游标关系**

L2 的游标落在 L1 记录上,但 L2 处理的是"teamId + agentId"聚合后的记录集合,和 L1 的"按会话"是两套维度。只要 L1 持续产出新记忆,L2 的游标就会持续推进。

### 1.2 抽取时机

L2 抽取**不是固定定时任务**,由"L1 完成后级联 + 保底轮询 + 频率限制"三部分共同决定。

| # | 时机 | 触发方式 | 说明 |
|---|------|----------|------|
| ① | L1 完成后级联(主) | L1 抽取成功 → 为该作用域调度一个延迟计时器 | 默认延迟 10 秒;同一作用域的计时器"只提前不推迟",保证尽快聚合新记忆 |
| ② | 保底轮询(辅) | 上一次 L2 完成后,挂一个最大间隔计时器 | 默认 3600 秒兜底,保证一直有新记忆但没被级联到的场景也能被聚合 |
| ③ | 最小间隔保护(约束) | L2 触发时间的下限 | 同一作用域两次 L2 至少间隔默认 900 秒,防止连续 L1 把 L2 触发打爆 |

边界情况:

- **冷会话**:超过 24 小时未活跃的会话,保底轮询会跳过,不再空转
- **downward-only 定时器**:计时器只允许提前、不允许推迟——新消息来了尽快抽,但也不违背最小间隔
- **无新数据**:轮询到点后发现没有新 L1 记录,直接跳过且不更新运行时间

**两种部署模式的等价逻辑**:单进程内嵌模式与多副本服务模式的调度器实现不同,但语义一致——L1 完成后通过计时器级联 L2,外加最大间隔保底轮询;服务模式由中心化的任务扫描器消费到期计时器,并用分布式锁保证多副本不会重复执行同一个 L2 任务。

一句话:L1 一完成就延迟抽(主),长时间没触发就兜底抽(辅),最小间隔和冷会话做护栏。

### 1.3 正常会话与 L2 的关系

会话走**主路**,L2 走**支路**——两者**互不阻塞,但严格依赖,最终闭环**。

```
正常会话(主路):  会话进来 → 消息落库 L0 → L1 抽取原子记忆 → 会话继续正常进行

记忆抽取(支路):  L1 完成后级联触发 L2 → 按游标读新 L1 记录 → 聚合进场景
```

为什么不是"互不相干",有三个耦合点:

1. **数据上游**:L2 吃的就是 L1 抽出的记忆——没有 L1,就没有 L2 可聚合
2. **启动通知**:L1 每完成一批抽取,都会给调度器记一笔,据此安排 L2 何时跑(延迟触发或保底轮询)
3. **反馈回路**:L2 聚合出的场景通过"场景导航"被召回、注入 AI 的上下文,让 AI"记得"跨会话聊过哪些主题、做过哪些事

所以完整链路其实是一个循环:

```
会话 → L0 存档 → L1 原子记忆 → L2 场景聚合 → 下次会话召回(含场景导航) → 会话
```

一句话:**主路负责实时对话;L2 是 L1 之后的二级聚合支路,把碎片化原子记忆沉淀成可复用的场景;场景最终回到会话里发挥作用,并成为 L3 画像的重要素材**。

## 2. 核心处理流程

L2 的处理分两大段:**先"增量读取 + LLM agent 场景整合",再"确定性收尾 + 落地级联"**。先从整体看一遍流程,再分节详解。

### 2.1 完整流程总览

从一批新增 L1 记忆,到场景真正沉淀,一次 L2 处理走完下面九步。全流程只有一处调用 LLM(第 ⑤ 步),而且是"agent 式"调用——LLM 通过读/写/改工具在沙箱里自主完成场景文件的增改合并。

```
L1 新增记忆记录
  → ① 增量读取:按游标只读上次之后更新的记录;无新记录直接跳过
  → ② 作用域分组:按"teamId+agentId"拆组,每组独立处理
  → ③ 备份:本地模式把整个场景目录快照备份(服务模式交给存储后端)
  → ④ 读索引 + 组提示词:新记忆列表 + 已有场景摘要 + 当前时间,外加场景数量预警
  → ⑤ 一次 LLM agent 执行:沙箱内用读/写/改工具自主新增/更新/合并场景文件(失败从备份还原)
  → ⑥ 确定性收尾:清理软删/空/残留文件 → 规范化文件名 → 全量重建场景索引
  → ⑦ 更新导航:把场景导航追加到画像文件末尾;解析 LLM 的画像更新请求信号
  → ⑧ 落地收尾:单调修复处理计数 → 变化场景以画像形态同步进记忆库 → 写生成血缘日志
  → ⑨ 级联:推进 L3 画像调度
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 增量读取 | 只读新的 L1 记录 | 规则/存储 | 游标=上次完成时最新更新时间;无新记录跳过 |
| ② 作用域分组 | 拆组隔离 | 规则 | teamId+agentId 维度,刻意忽略用户/会话/任务 |
| ③ 备份 | 场景目录快照 | 存储 | 仅本地模式;服务模式由存储后端负责 |
| ④ 组提示词 | 拼输入 | 规则 | 三输入 + 数量预警 + 可读文件清单 |
| ⑤ 场景整合 | 增改合并场景文件 | LLM agent | 唯一一次 LLM;沙箱;自主决策 |
| ⑥ 确定性收尾 | 清理/规范化/重建索引 | 规则 | 索引只由工程侧写,LLM 不可见 |
| ⑦ 导航更新 | 画像追加导航 + 解析信号 | 规则 | 画像不存在/只剩导航时跳过 |
| ⑧ 落地 | 计数修复/同步/血缘 | 存储 | 计数单调取大,不整体覆盖 |
| ⑨ 级联 | 推进 L3 | 调度 | L3 由触发器按优先级二次判断 |

其中 LLM 只出现在第 ⑤ 步,其余环节全部确定性执行。工程侧在 LLM 之后做四件"收拾残局"的事(⑥⑦ 里),这是 L2 与 L1 的显著差异——L1 的 LLM 输出结构化 JSON 后基本直接落库,而 L2 的 LLM 在文件系统里自由操作,必须有一层规则来清理、校验、重建。

下面 2.2–2.8 按这九步的顺序展开详述。

### 2.2 增量读取与输入构造

L1 已按游标持续产出记忆,L2 **不处理全量历史**——每次只读"上次游标之后新增的那批记录",按作用域分组后送给整合器。

传给 LLM 的记忆**只保留文本内容**,不携带类型、优先级等 L1 结构字段——因为 L2 要让 LLM 自由整合,而不是按类型机械搬运。

一次 L2 处理的输入由三部分组成:

| 输入 | 内容 | 作用 |
|------|------|------|
| **新记忆列表** | 本次新增的 L1 记忆文本 | 唯一整合来源 |
| **已有场景摘要** | 当前所有场景文件的文件名、热度、摘要 | 供 LLM 判断该更新哪个场景;顶部带"当前场景总数 n/上限"计数 |
| **当前时间戳** | 生成时间 | 供 LLM 填写场景文件头里的创建/更新时间 |

另外还附一份"**已有场景文件清单**"——LLM 只能读取清单里的文件,不能猜测或编造不存在的文件名。

一次 L2 处理的输入实例(仍以 Billing 超时排查为例,与 4.3 渲染示例同源):

**① 新记忆列表**(本次增量读取的 L1 记忆,只保留文本,JSON 数组):

```json
[
  {
    "id": "mem_1",
    "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
    "created_at": "2026-08-18T02:10:00.000Z"
  },
  {
    "id": "mem_2",
    "content": "用户(王小明)决定将 api-gateway 的超时告警阈值调整为 2 秒",
    "created_at": "2026-08-18T02:15:00.000Z"
  }
]
```

**② 已有场景摘要**(顶部带"当前场景总数 n/上限",下面按场景列出文件名/热度/更新/摘要):

```text
**当前场景总数:2 / 15**

### 技术研究-Billing超时排查.md
**热度**: 5 | **更新**: 2026-08-17T10:00:00.000Z
**summary**: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

### 日常生活-日本旅行计划.md
**热度**: 2 | **更新**: 2026-07-01T08:00:00.000Z
**summary**: 计划五月去日本旅行,偏好京都路线
```

**③ 当前时间戳**:

```text
2026-08-18T02:16:00.000Z
```

**附:已有场景文件清单**(LLM 只能 read 清单里的文件,不能猜测或编造别的文件名):

```text
- `技术研究-Billing超时排查.md`
- `日常生活-日本旅行计划.md`
```

> 以上是送入 LLM 的输入;完整渲染 Prompt 见 4.3。

### 2.3 场景数量上限与分级预警

L2 对场景总数有**硬性上限(默认 15 个)**,通过提示词里的**三级预警**约束 LLM:

| 预警级别 | 触发条件 | 强制要求 |
|----------|----------|----------|
| 红色 | 场景数 ≥ 上限 | **必须先 MERGE**:把最相似的 2-4 个场景合并为 1 个并删除旧文件,直到数量 < 上限,再处理新记忆 |
| 橙色 | 场景数 = 上限 - 1 | **只能 UPDATE,不能 CREATE** 新场景 |
| 黄色 | 场景数接近上限 | 建议优先 UPDATE 或主动 MERGE 相似场景 |

工程侧**不强制裁剪**文件数量——上限靠 LLM 自觉遵守,工程侧只负责事后清理 LLM 留下的脏文件(见 2.6)。如果 LLM 违反规则,数量可能会暂时超限,但下一轮的红/橙预警会再次要求它合并。

### 2.4 LLM agent 执行

这是 L2 唯一一次 LLM 调用,也是与 L1 架构差异最大的地方。LLM 不是"输出一段 JSON 就结束",而是被当作一个**受限的文件操作 agent**:

- **沙箱隔离**:LLM 的工作目录被钉在场景文件目录,索引、检查点、画像等系统文件对 LLM **物理不可见**,它改不了自己看不见的东西
- **工具白名单**:只开放**读、写、改**三个文件工具,没有命令执行等越权能力
- **删除的唯一方式**:把文件内容写成 `[DELETED]` 标记(写空字符串会被工具拒绝),由工程侧随后真正清理
- **服务模式**:LLM 的文件工具走对象存储,而不是本地文件系统
- **失败恢复**:LLM 执行异常时,本地模式从备份把整个场景目录**整体还原**,防止 LLM 半途写入或清空沙箱泄漏到下一轮召回;恢复失败只记日志,绝不掩盖原始错误

一句话:给 LLM 一个"只装了三个文件工具的沙箱工作台",让它自己决定怎么整合场景。

### 2.5 动作模型与热度管理

LLM 在沙箱里对场景文件可以做四类动作,按**优先级**排列:

| 动作 | 含义 | 触发条件 / 约束 |
|------|------|-----------------|
| **UPDATE(更新)** | 锁定已有场景,整体重写或局部修改 | **首选策略**;按摘要/文件名相似性锁定目标 |
| **MERGE(合并)** | 把 2-4 个相似场景合并成 1 个概括性更强的 | 强制(超限时)或主动(同一条叙事弧线);**合并后必须删除旧文件** |
| **CREATE(新建)** | 创建全新场景文件 | **最后手段**;须先读 ≥2 个最相似场景验证无法融入;每批最多新增 1 个 |
| **删除(软删)** | 标记文件待清理 | 唯一方式:把文件内容写成 `[DELETED]` 标记 |

几个关键约束:

- **默认策略是 UPDATE 不是 CREATE**:犹豫时选 UPDATE,避免场景无限膨胀
- **MERGE 必须删旧文件**:被合并的旧文件必须写 `[DELETED]` 标记,否则文件总数不减、合并无效(打 `[ARCHIVE]` 之类的标记不算删除)
- **热度管理(重要度)**:新建 heat=1;更新 heat=旧+1;合并 heat=所有相关场景热度之和+1。热度是"被记忆命中的累计次数",也是召回侧导航排序的依据

### 2.6 工程侧确定性收尾

LLM 执行完之后,工程侧做四件**确定性**的事(都是规则,不再调 LLM):

1. **软删清理**:扫描场景目录,把内容为 `[DELETED]` 标记、空白,以及"只有文件头没有正文"的残留文件真正删除。后者是 LLM 合并时没删干净旧文件的产物
2. **文件名规范化**:LLM 偶发产出带空格/括号等非法字符的文件名,会破坏下游解析。在重建索引前统一重命名(空格→短横线、去括号等),保证后续所有读取方只见规范名
3. **全量重建索引**:重扫剩余场景文件,从每个文件的文件头解析出摘要/热度/时间,重建场景索引。索引**只由工程侧维护**,LLM 在沙箱外看不到
4. **更新导航 + 画像信号**:
   - 读最新索引生成"场景导航",剥离画像里旧的导航后追加重写;如果画像文件还不存在、或画像只剩导航没有正文,则跳过,等画像生成
   - 解析 LLM 文本输出里的 `[PERSONA_UPDATE_REQUEST]` 标记(重大价值观转变、跨场景突破性洞察时 LLM 会主动输出),写入检查点,供后续 L3 画像刷新优先触发

### 2.7 落地写入

一次 L2 处理的产出会写到多个目标,各目标**独立容错,失败互不阻塞**:

| 目标 | 内容 | 由谁写 |
|------|------|--------|
| **场景文件** | 场景叙事正文 + 文件头(创建/更新时间、摘要、热度) | LLM 工具 |
| **场景索引** | 所有场景的文件名/摘要/热度/时间的清单 | 工程侧 |
| **画像文件** | 画像正文 + 追加的场景导航 | 工程侧 |
| **检查点** | 处理计数、画像更新请求 | 工程侧 |
| **记忆库镜像** | 变化的场景以"画像"形态同步进记忆库(只做镜像,不建向量检索) | 工程侧 |
| **血缘日志** | 本次场景产出由哪批 L1 记忆生成 | 工程侧 |

其中"记忆库镜像"要说明一点:L2 场景**本体不直接进向量检索**——记忆库里的 L1 记录承担检索职责,L2/L3 的画像只是以"内容镜像"的形式同步过去,用于多副本共享与恢复。

### 2.8 级联收尾

L2 任务完成后做两件事:

- **单调修复计数**:在并发临界区内重读检查点,只对"处理计数"做取大,绝不整体覆盖——否则会抹掉并发节点推进的 L1 游标,导致重复抽取
- **推进 L3(画像)调度**:触发下一层画像生成。但 L3 是否真正执行由画像触发器按优先级**二次判断**(主动请求、冷启动、记忆阈值等),L2 只是发出请求

## 3. 召回:场景记忆怎么回到对话里

第 2 章讲的是"入"——把 L1 记忆聚合成场景;召回讲的是"出"——把场景信息拿回对话,让 AI"记得"跨会话累积的情境。两条线合起来就是 1.3 里说的闭环。

### 3.1 时机:每轮对话前预取

与 L1 完全一致:AI 处理每一轮对话之前,宿主先调一次召回接口,把三层记忆(相关记忆、场景导航、画像)预取好拼进上下文,再让 LLM 开始干活。它是同步的、非关键路径的——召回失败不阻塞对话。

### 3.2 一次召回同时做三件事

1. **L1 记忆检索**(核心):拿当前用户消息当查询,去记忆库搜相关原子记忆
2. **L2 场景导航**:读场景索引,列出有哪些历史情境,供 AI 判断跟当前话题的关联
3. **L3 画像注入**:读画像文件,把"这个人是谁、有什么偏好"塞进上下文

其中 L2 的部分就是"场景导航"。

### 3.3 场景导航怎么生成与注入

- **全量注入、不过滤**:场景导航**不按当前用户输入检索或过滤**,一次把全部历史场景列出来,由 LLM 自行判断与当前话题的关联——与 L1 记忆"按相似度检索 top-N"是完全不同的策略
- **按热度降序排序**:每个场景一条,包含**路径、热度、摘要**
- **热度分档**:≥50 单火,≥100 双火,≥200 三火,≥500 四火,≥1000 五火——让 AI 一眼看出哪些场景最重要
- **使用说明**:导航底部附带提示,告诉 AI 需要细节时用什么工具按路径读完整场景

一个场景导航的片段示例(画像文件末尾追加的稳定内容):

```text
---
## 🗺️ Scene Navigation (Scene Index)
*以下是当前场景记忆的索引,可根据需要 read 读取详细内容。*

### Path: {数据目录}/scene_blocks/技术研究-Billing超时排查.md
**热度**: 5 | **更新**: 2026-08-17T10:00:00.000Z
Summary: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

### Path: {数据目录}/scene_blocks/日常生活-日本旅行计划.md
**热度**: 2 | **更新**: 2026-07-01T08:00:00.000Z
Summary: 计划五月去日本旅行,偏好京都路线

📌 使用说明:
- Path 是场景块的路径,可直接使用 read 工具读取完整内容
- 热度:该场景被记忆命中的累计次数,越高越重要
- Summary:场景的核心要点摘要
```

### 3.4 注入方式:拆成两半,缓存友好

和 L1 的召回一样,召回结果被刻意拆成两部分:

- **动态部分**(每轮都变):召回的 L1 相关记忆,拼到**用户消息前缀**
- **稳定部分**(基本不变):画像 + 场景导航 + 一份"记忆工具使用指南",拼到**系统提示词末尾**

这样拆的原因:稳定部分能命中模型提供商的**提示词缓存**——不会被每轮变化的记忆打爆缓存,省 token 省成本。场景导航尤其如此:只要 L2 没有新增/合并/删除场景,这段内容字节级不变,一直命中缓存;一旦场景索引变化(新场景、热度更新、场景合并),导航才会跟着更新。

### 3.5 控制与兜底

- **渐进式披露**:导航**只给路径、热度、摘要,不塞全文**。AI 需要某个场景的完整画像、事件经过或阶段结论时,才按路径主动读取完整场景文件——省 token,也避免上下文被不相关的长叙事占满
- **主动检索兜底**:注入不够用时,AI 可以主动调工具——"记忆搜索"搜 L1、"对话搜索"搜 L0 原文、"读场景文件"进具体情境;其中两个搜索工具**每轮合计限 3 次**,防止 AI 无休止地搜

### 3.6 一句话总结

每轮 AI 开口前,宿主把三层记忆预取好:相关原子记忆动态拼接,**场景导航全量注入**(只给路径/热度/摘要,按需深入),画像进稳定区走缓存;注入不够时 AI 还能主动读场景文件,但搜索限次。

## 4. 附录:完整 Prompt 原文

以下为 L2 场景抽取的完整 prompt,按"对话 / 团队工作"两种场景,各一套系统提示词 + 一个用户提示词模板。

### 两套提示词的来源与选择

L2 的 prompt 分两套,对应两种场景口径:

- **对话模式(chat)**:个人场景叙事,面向个人对话,把碎片化记忆整合成"数字第二大脑"的场景日记(用户基础信息/核心特征/偏好/隐性信号/核心叙事/演变轨迹)
- **团队工作模式(code)**:可复用工作方法场景,面向团队协作,沉淀 SOP/判断逻辑/禁忌/原则/经验(工作场景/适用条件/核心 SOP/判断逻辑/禁忌与反模式)

用哪套由一个配置项 `promptMode` 决定,只认 `chat` / `code` 两个值,**默认 `chat`**,配置写成其它值一律回退 `chat`。设置位置:顶层 `promptMode` 或 `prompts.mode` 定全局;`extraction` 组可单独覆盖 L1/L2 的抽取,`persona` 组可单独覆盖 L2/L3,不设则继承全局。它是**纯静态配置**:不按团队、agent 或会话自动切换。

> 提示:以下原文中的 `${maxScenes}` 是运行时参数(场景数量上限),**默认值为 15**。

### 4.1 抽取 · 对话模式系统提示词

````text
# Memory Consolidation Architect

**输出语言**:`.md` 场景文件的所有自然语言内容(文件名、章节标题、正文)使用与"New Memories List"中记忆相同的语言;META 字段名(created/updated/summary/heat)和 `[DELETED]` 等标记保持英文。模板中给出的中文章节标题(`## 用户核心特征` 等)作为结构骨架——非中文输出时请用目标语言的等价表达替换。

## 角色定义 (Role Definition)
你是记忆整合架构师。你的目标是为用户构建一个"数字第二大脑"。你不仅仅是在记录数据,你更像是一位人类学家和心理学家,负责分析原始记忆,从中提取核心特征、捕捉隐性信号,并构建不断演变的叙事。


## 架构模型

### Layer 1 (Input): Raw Memories
- **来源**:API 分批召回(每批 20 条)
- **状态**:碎片化、无序

### Layer 2 (Processing): Scene Diaries
- **形态**:**不是清单,是连贯的叙事文档**
- **逻辑**:将 L1 碎片融合进特定场景文件
- **动作**:Create(创建)、Integrate(整合)、Rewrite(重写)
- **禁止**:简单追加列表

你主要负责L1到L2的生成任务

## 输入环境 (Input Context)
你将接收三个输入:
1. 新增记忆 (New Memory): 一段原始的、非结构化的新近回忆信息。
2. 现有 Block 映射表 (Existing Blocks Map): 包含当前所有记忆块(Markdown 文件)的文件名和摘要的列表。
3. 当前时间 (Current Time): 用于生成元数据的具体时间戳。

**⚠️ 场景文件数量上限:${maxScenes} 个。处理完成后目录中的场景文件数量必须严格小于此上限。**

## ⛔ 文件操作约束(必须严格遵守)
1. **所有文件操作使用相对文件名**(如 `技术研究-Rust学习.md`),当前工作目录已设为场景文件目录
2. **read 只能读取用户消息中"已有场景文件清单"列出的文件**,禁止猜测或编造不在清单中的文件名
3. **创建新场景文件时**,使用 **write** 工具。参数:`path`=文件名, `content`=完整内容
4. **局部更新场景文件**:使用 **edit** 工具。参数:`path`=文件名, `edits`=[{`oldText`: 旧内容, `newText`: 新内容}]。对于大范围重写或结构性变更,建议使用 **read** + **write** 整体重写。
5. **场景索引和系统配置由工程系统自动维护**,你只需专注于操作 `.md` 场景文件
6. **删除文件的唯一方式**:使用 **write** 工具将文件内容写为 `[DELETED]` 标记(`path`=文件名, `content`=`[DELETED]`)。系统会自动清理带有此标记的文件。**禁止**写入空字符串(会被系统拒绝)。**禁止**用 `[ARCHIVE]`、`[CONSOLIDATED]` 等其他标记替代删除——只有 `[DELETED]` 标记会触发系统清理。
7. **禁止创建报告/整合/汇总类文件**。你的输出必须是有意义的场景叙事文件(如"技术架构与工程实践.md"、"日常生活与工作节奏.md")。禁止创建以 BATCH、REPORT、CONSOLIDATION、INTEGRATION、ARCHIVE、SUMMARY 等为前缀的文件。

## 📛 文件命名规范(强制)

为保证下游工具(场景导航、健康检查、对象存储同步等)能正确解析路径引用,**新建文件**或 **MERGE 后的目标文件**必须遵守以下命名规则:

- **允许字符**:英文字母、数字、CJK 中日韩文字、短横线 `-`、下划线 `_`、点号 `.`
- **必须以 `.md` 结尾**(小写)
- **❌ 禁止包含**:空格、全角空格、引号、括号 `( ) [ ] { }`、斜杠 `/ \`、冒号 `:`、分号 `;`、问号 `?`、感叹号 `!`、星号 `*`、竖线 `|`、其他标点
- **多词分隔**:使用 `-`(短横线)连接,不要用空格
- **更新现有文件**时,沿用清单中给出的文件名,不要改名

✅ 正确示例:
- `Daily-Rhythm-in-Shanghai.md`
- `日常生活-健康管理.md`
- `技术研究-Rust学习.md`
- `Coffee-Yirgacheffe.md`

❌ 错误示例(每次都会触发工程兜底重命名):
- `Daily Rhythm in Shanghai.md`(含空格)
- `Coffee (Yirgacheffe).md`(含括号)
- `Q1 Milestone?.md`(含空格和问号)

> 提示:即使你没遵守,工程系统会自动归一化文件名(空格替换为短横线、删除括号等),但这会增加日志噪音和潜在冲突。请在 `write` 时直接使用合规名字。


## 工作流与逻辑 (Workflow & Logic)
在生成输出之前,你必须执行以下"思维链"过程:

### ⚠️ 阶段 0:强制检查场景总数(必须先执行)

**在处理任何记忆之前,你必须:**

1. **统计当前场景总数**:查看 "Existing Scene Blocks Summary" 顶部标注的当前场景总数
2. **最终目标**:处理完成后,目录中的场景文件数量必须 **严格小于 ${maxScenes}**
3. **遵守分级预警**:
   - 红色预警(≥ ${maxScenes}):**必须先通过 MERGE 减少文件数量**,将最相似的 2-4 个场景合并为 1 个,**并删除被合并的旧文件**,直到文件数 < ${maxScenes} 后,再处理新记忆
   - 橙色预警(= ${maxScenes - 1}):**只能 UPDATE 现有场景,不能 CREATE 新场景**
   - 黄色预警(接近 ${maxScenes}):**优先 UPDATE 或主动 MERGE 相似场景**

**合并优先级**(当需要合并时,按以下顺序选择):
1. **主题高度重叠**:如"Python后端开发"和"Go后端开发" → 合并为"后端开发技术栈"
2. **叙事弧线相同**:如"求职材料-JD匹配"和"职业发展-能力对齐" → 合并为"职业发展与求职"
3. **热度最低的场景**:如果没有明显重叠,合并或删除 heat 最低的 2-3 个场景

### 阶段 1:分析与分类
分析 新增记忆。它的核心领域是什么?(例如:编程风格、情绪状态、职业轨迹、人际关系)。
提取事实事件链(触发 -> 行动 -> 结果)以及底层的心理状态。

### 阶段 2:检索与策略选择
将新记忆与 现有 Block 映射表 进行比对。
需要时使用 **read** 工具读取完整场景文件内容
**只能读取用户消息中"已有场景文件清单"列出的文件,禁止猜测其他文件路径。**

**核心原则:默认策略是 UPDATE,不是 CREATE。** 当犹豫于 UPDATE 和 CREATE 之间时,选择 UPDATE。

策略选择(按优先级排序):
1. **UPDATE(更新)**【首选策略】: 如果存在相关的 Block(基于摘要或文件名的相似性),先用 **read** 读取文件内的具体信息,再锁定该 Block 进行更新(**write** 整体重写 或 **edit** 局部替换)
2. **MERGE(合并)**:
   - 合并的新 block 应该是生成概括性更强的场景,包含已有的多个相似场景
   - **强制合并**:当前 Block 总数 **≥ ${maxScenes}** 时,必须先将多个相似记忆合并
   - **主动合并**:即使未达上限,如果两个 Block 属于同一叙事弧线,也应合并以增加深度
   - **⚠️ 合并后必须删除旧文件**:被合并的旧场景文件必须通过 **write** 写入 `[DELETED]` 标记。**仅仅打标记(如 [ARCHIVE]、[CONSOLIDATED])不算删除,文件仍会占用配额。**
3. **CREATE(新建)**【最后手段】:
   - **前提条件**:当前场景总数 < ${maxScenes}
   - **CREATE 前的强制验证**:必须先用 **read** 检查至少 2 个最相似的现有场景,确认新记忆确实无法融入后才能 CREATE。跳过验证直接 CREATE 是被禁止的
   - 如果话题是全新的且与现有内容区分度高,可以创建新 Block
   - **每次批处理最多新增 1 个场景**

**示例 A:新记忆整合进已有 block(UPDATE - 原地更新)**
**具体操作步骤(工具调用)**:
1. **read**(`path`='Python后端开发.md') → 获取已有内容 A
2. 分析新记忆 + 已有内容 A → 整合生成新内容 B(`heat = 旧heat + 1`)
3. **write**(`path`='Python后端开发.md', `content`=B) → **整体重写该场景文件**
   或 **edit**(`path`='Python后端开发.md', `edits`=[{`oldText`: 旧章节, `newText`: 新章节}]) → **局部更新某部分**

**示例 B:合并多个 block(MERGE — 合并后必须删除旧文件)**
**具体操作步骤(工具调用)**:
1. **read**(`path`='Python后端开发.md') → 获取内容 A
2. **read**(`path`='Go后端开发.md') → 获取内容 B
3. 整合 A + B + 新记忆 → 生成新内容 C(`heat = heatA + heatB + 1`)
````

````text
- 使用 **read** 读取需要更新的场景文件。

- 使用 **edit** 对场景文件进行局部更新。
- **删除文件**:使用 **write**(`path`=文件名, `content`='[DELETED]') 写入删除标记。系统会自动清理这些文件。**重要**:只有 `[DELETED]` 标记会触发系统清理。写入空字符串会被系统拒绝,写入 `[ARCHIVE]`、`[CONSOLIDATED]` 等标记不会删除文件。
````
