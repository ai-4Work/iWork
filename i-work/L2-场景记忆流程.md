> 本文档梳理 iWork 中 **L2 层场景记忆**的处理流程(实现见 `server/memory/l2/`)。包含:处理流程概述(数据来源与抽取时机)、核心处理流程详解、召回机制(记忆怎么回到对话),以及抽取系统提示词、用户提示词模板与场景工具指南的完整原文。
>
> **核心理解**:L2 把 L1 中**方向/主题一致**的记忆整合进**同一个场景**,但这不是机械归档——由 LLM 主动决策(UPDATE / MERGE / CREATE),把新记忆**重写融合**进已有场景的连贯叙事(明确禁止简单追加列表),产物是"叙事文档"而非"清单"。方向一致是分组依据,整合重写才是落笔方式。
>
> **召回口径**:对话召回时 L1 与 L2 不会字面重复——L1 按相似度检索 top-N 原子记忆正文,动态拼到用户消息前缀;L2 只全量注入"场景导航"(名字/热度/摘要,不过滤),拼到系统提示词末尾(稳定、命中缓存),场景全文由 `scene_read` 工具按名取、不进提示词。两者有少量语义重叠(场景摘要由 L1 聚合而来),这是设计使然——用几行摘要的冗余换召回可靠性,避免一次 L1 检索偏差就丢掉整个场景。

## 1. 概述

L2 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L1 抽取并落库的结构化记忆记录
- **输出**:结构化的**场景叙事文档**,跨会话累积,既是召回时让 AI"记得"情境的载体,也是 L3 画像生成的重要素材

L2 和 L1 最大的区别在"怎么抽":L1 是**一次 LLM 调用输出结构化 JSON**,把对话拆成一条条原子记忆;L2 也是**一次 LLM 调用**,但它输出的是一批**动作**(UPDATE / MERGE / CREATE)——工程侧按动作把新记忆的正文**重写融合**进已有场景,而不是给每条记忆找个位置。新增、更新、合并由 LLM 决策,落地与收尾由工程侧确定性执行(名字规范化、热度与 version 计算、单事务写入)。

### 1.1 L2 的数据来源

L2 的输入就是 **L1 落库的结构化记忆记录**,不是 L0 原始对话。

**L1 记忆存在哪里、L2 怎么读**

- L1 抽出的原子记忆记录在记忆库的 L1 记录表,L2 按**游标增量**拉取——游标记录"上次 L2 抽到哪条",即上次处理完成时最新一条 L1 记录的更新时间;每次只读游标之后新产生或更新的记录,保证每条记忆只被聚合一次
- 记忆库不可用时**直接报错,不静默降级**——让上层明确知道发生了什么
- 没有新记录时直接跳过、不推进游标;冷启动第一次被跳过时不记录运行时间,避免挡住下一次触发

**一条 L1 记录长什么样**

L1 落库的是一条结构化的原子记忆记录。仍以文档 4.3 的 Billing 超时排查为例,一条 L1 记录大致如下(节选核心字段):

```json
{
  "id": "m_1755571800000_a1b2c3d4",
  "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
  "type": "episodic",
  "priority": 85,
  "scene_name": "我（AI）在和用户王小明排查 Billing API 超时",
  "source_message_ids": ["msg_c", "msg_d"],
  "metadata": {
    "activity_start_time": "2026-08-18T02:00:00.000Z",
    "activity_end_time": "2026-08-18T02:10:00.000Z"
  },
  "timestamps": ["2026-08-18T02:10:00.000Z"],
  "createdAt": "2026-08-18T02:10:00.000Z",
  "updatedAt": "2026-08-18T02:10:00.000Z",
  "version": 1,
  "teamId": "team_xxx",
  "userId": "user_xxx",
  "agentId": "agent_xxx"
}
```

要点:

- **content / type / priority / scene_name**:L1 抽取的核心字段。`type` 按模式取 persona/episodic/instruction(对话)或 work_fact/work_task/work_method/work_artifact(团队);`metadata` 存类型相关附加信息(episodic 为活动时间区间)
- **id / timestamps / version**:id 全局唯一;`timestamps` 记录时间戳轨迹(合并时取并集);`version` 单调递增(update/merge 后 +1)
- **teamId / userId / agentId / sessionId**:隔离与归属维度,其中 L2 按"userId + agentId"分组(见下文)
- **createdAt / updatedAt**:落库时间,`updatedAt` 正是 L2 游标推进的依据

> 落到检索库的 L1 表会把上述字段平铺成列(record_id/content/type/priority/…/metadata_json),`source_message_ids` 只留在产出文档里、检索库不存;且传给 L2 LLM 时只保留 content / created_at / id 三字段(见 2.2)。

**L2 读出来的记录怎么分组**

L2 属于**跨会话的聚合层**:读出来的 L1 记录按"**userId + agentId**"的隔离作用域分成组,每组独立做一次场景整合。这里刻意**忽略**会话、任务这些维度——同一作用域的记忆可以跨多个会话持续累积。(上游按"teamId + agentId"分组、teamId 缺省退化为 userId;本仓库没有 teams 表,直接用 userId。)

**L1 与 L2 的游标关系**

L2 的游标落在 L1 记录上,但 L2 处理的是"userId + agentId"聚合后的记录集合,和 L1 的"按会话"是两套维度。只要 L1 持续产出新记忆,L2 的游标就会持续推进。

### 1.2 抽取时机

L2 抽取**不是固定定时任务**,由"L1 完成后级联 + 保底轮询 + 频率限制"三部分共同决定。

这三条**没有计时器**:L2 是一个 60 秒轮询的后台 sweep(与 L1 同款),每轮只看 DB 现算——游标落在 `l2_checkpoints`,重启不丢断点。

| # | 时机 | 判据(每轮 sweep 现算) | 说明 |
|---|------|------------------------|------|
| ① | L1 完成后级联(主) | 游标之后有新的 L1 记忆,且**本批最新那条**距今 ≥ 10 秒 | 等 10 秒是为了让 L1 的这一批落定 |
| ② | 保底轮询(辅) | 同样非空,且距上次整合 ≥ 3600 秒 | 记忆持续零星落库、级联一直被推迟时的兜底 |
| ③ | 最小间隔保护(约束) | 距上次整合 < 900 秒 | 是约束不是触发:先判它,防止连续 L1 把 L2 打爆 |

L1 侧**不需要发任何信号**:轮询架构下"L1 落定 → 等 10 秒 → 整合"退化成一句 DB 判定——L1 还在追积压时它的 `updated_at` 一直在翻新,① 自然不满足;L1 收工 10 秒后即触发。

边界情况:

- **冷启动**:游标从 epoch 起算,但每轮只吃 20 条新记忆,不会把历史全量重抽一遍;且第一次不走 ②,否则 10 秒的级联节奏会被立刻绕过去
- **无新数据**:轮询到点后发现没有新 L1 记录,直接跳过且不更新运行时间
- **一次 sweep 串行 await**,同作用域不会有两个整合并行,不需要加锁

一句话:L1 一完成就延迟抽(主),长时间没触发就兜底抽(辅),最小间隔做护栏。

### 1.3 正常会话与 L2 的关系

会话走**主路**,L2 走**支路**——两者**互不阻塞,但严格依赖,最终闭环**。

```
正常会话(主路):  会话进来 → 消息落库 L0 → L1 抽取原子记忆 → 会话继续正常进行

记忆抽取(支路):  L1 完成后级联触发 L2 → 按游标读新 L1 记录 → 聚合进场景
```

为什么不是"互不相干",有三个耦合点:

1. **数据上游**:L2 吃的就是 L1 抽出的记忆——没有 L1,就没有 L2 可聚合
2. **触发判据**:L1 落库的记忆自带 `updated_at`,L2 的轮询据此判断何时该跑(级联或保底轮询)——L1 不必主动发信号
3. **反馈回路**:L2 聚合出的场景通过"场景导航"被召回、注入 AI 的上下文,让 AI"记得"跨会话聊过哪些主题、做过哪些事

所以完整链路其实是一个循环:

```
会话 → L0 存档 → L1 原子记忆 → L2 场景聚合 → 下次会话召回(含场景导航) → 会话
```

一句话:**主路负责实时对话;L2 是 L1 之后的二级聚合支路,把碎片化原子记忆沉淀成可复用的场景;场景最终回到会话里发挥作用,并成为 L3 画像的重要素材**。

## 2. 核心处理流程

L2 的处理分两大段:**先"增量读取 + LLM 整合",再"确定性收尾 + 落地级联"**。先从整体看一遍流程,再分节详解。

### 2.1 完整流程总览

从一批新增 L1 记忆,到场景真正沉淀,一次 L2 处理走完下面八步。全流程只有一处调用 LLM(第 ⑤ 步),其余环节全部是确定性规则。

```
L1 新增记忆记录
  → ① 增量读取:按游标只读上次之后更新的记录;无新记录直接跳过
  → ② 作用域分组:按"userId+agentId"拆组,每组独立处理
  → ③ 触发判定:级联 / 保底轮询 / 最小间隔三条判据现算(见 1.2)
  → ④ 读素材 + 组提示词:新记忆列表 + 已有场景摘要 + 候选场景正文,外加场景数量预警
  → ⑤ 一次 LLM 调用:输出一批动作(create / update / merge);解析失败不推进游标,下轮重试
  → ⑥ 确定性收尾:名字规范化;热度 / version / 血缘 / created_at 一律由工程侧算
  → ⑦ 落地写入:新行插入 + 被取代行软删,同一个事务;游标与处理计数落库
  → ⑧ 级联:解析画像更新请求信号,推进 L3 画像调度
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 增量读取 | 只读新的 L1 记录 | 规则/存储 | 游标=上次完成时最新更新时间;无新记录跳过 |
| ② 作用域分组 | 拆组隔离 | 规则 | userId+agentId 维度,刻意忽略会话/任务 |
| ③ 触发判定 | 决定这一轮跑不跑 | 规则 | 三条判据全由 DB 现算,无计时器 |
| ④ 组提示词 | 拼输入 | 规则 | 新记忆 + 场景摘要 + 候选正文 + 数量预警 |
| ⑤ 场景整合 | 输出动作数组 | LLM | 唯一一次 LLM;不给工具 |
| ⑥ 确定性收尾 | 规范化名字、算热度/version/血缘 | 规则 | 热度与 version 不听 LLM 的 |
| ⑦ 落地写入 | 插入新行 + 软删被取代行 | 存储 | 一个事务,游标同批推进 |
| ⑧ 级联 | 落信号、推进 L3 | 调度 | L3 由触发器按优先级二次判断 |

L1 与 L2 的差异不在"要不要收尾",而在**收尾的分量**:L1 的 LLM 输出结构化 JSON 后基本直接落库,L2 的动作还要工程侧解析成行的增删,但全部落在一个事务里,不需要事后清理。

下面 2.2–2.8 按这些步骤的顺序展开详述。

### 2.2 增量读取与输入构造

L1 已按游标持续产出记忆,L2 **不处理全量历史**——每次只读"上次游标之后新增的那批记录",按作用域分组后送给整合器。

传给 LLM 的记忆**只保留文本内容**,不携带类型、优先级等 L1 结构字段——因为 L2 要让 LLM 自由整合,而不是按类型机械搬运。

一次 L2 处理的输入由三部分组成:

| 输入 | 内容 | 作用 |
|------|------|------|
| **新记忆列表** | 本次新增的 L1 记忆文本 | 唯一整合来源 |
| **已有场景摘要** | 当前所有场景的名字、热度、更新时间、摘要 | 供 LLM 判断该更新哪个场景;顶部带"当前场景总数 n/上限"计数 |
| **候选场景正文** | 按 TF-IDF 相似度取的 top-5 场景,连带正文 | 供 LLM 重写时引用旧内容 |
| **当前时间戳** | 生成时间 | 供 LLM 判断事件先后 |

候选场景正文是"LLM 按需读场景"在单次调用下的等价物:场景上限 15 个 × 正文上限 1500 字符本来就装得下,不需要工具循环。按相似度降序取,超过字符预算(默认 12000)即止。**场景数达到上限时改为注入全部场景正文**——红色预警下 LLM 必须合并,而它无法重写看不见正文的场景。

一次 L2 处理的输入实例(仍以 Billing 超时排查为例,与 4.3 渲染示例同源):

**① 新记忆列表**(本次增量读取的 L1 记忆,只保留文本,JSON 数组):

```json
[
  {
    "id": "mem_1",
    "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
    "created_at": "2026-08-18T02:10:00.000Z"
  },
  {
    "id": "mem_2",
    "content": "用户(王小明)决定将 api-gateway 的超时告警阈值调整为 2 秒",
    "created_at": "2026-08-18T02:15:00.000Z"
  }
]
```

**② 已有场景摘要**(顶部带"当前场景总数 n/上限",下面按场景列出名字/热度/更新/摘要):

```text
**当前场景总数:2 / 15**

- **技术研究-Billing超时排查** | 热度: 5 | 更新: 2026-08-17T10:00:00.000Z
  Summary: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

- **日常生活-日本旅行计划** | 热度: 2 | 更新: 2026-07-01T08:00:00.000Z
  Summary: 计划五月去日本旅行,偏好京都路线
```

**③ 候选场景正文**(按相似度取前 5 个,连带正文;场景数达上限时为全部):

```text
### 技术研究-Billing超时排查
## 用户基础信息
...
```

**④ 当前时间戳**:

```text
2026-08-18T02:16:00.000Z
```

> 以上是送入 LLM 的输入;完整渲染 Prompt 见 4.3。

### 2.3 场景数量上限与分级预警

L2 对场景总数有**硬性上限(默认 15 个)**,通过提示词里的**三级预警**约束 LLM:

| 预警级别 | 触发条件 | 强制要求 |
|----------|----------|----------|
| 红色 | 场景数 ≥ 上限 | **必须先 MERGE**:把最相似的 2-4 个场景合并为 1 个并软删旧场景,直到数量 < 上限,再处理新记忆 |
| 橙色 | 场景数 = 上限 - 1 | **只能 UPDATE,不能 CREATE** 新场景 |
| 黄色 | 场景数接近上限 | 建议优先 UPDATE 或主动 MERGE 相似场景 |

工程侧**不强制裁剪**场景数量——上限靠 LLM 自觉遵守。如果 LLM 违反规则,数量可能会暂时超限,但下一轮的红/橙预警会再次要求它合并。

### 2.4 一次 LLM 调用

这是 L2 唯一一次 LLM 调用,也是与 L1 架构差异最大的地方:LLM 不碰任何工具,一次调用输出一个 **JSON 动作数组**。

```json
[
  {"action": "update", "name": "技术研究-Billing超时排查",
   "summary": "排查 Billing API 网关超时,定位到 api-gateway 为瓶颈",
   "content": "## 用户基础信息\n...", "source_memory_ids": ["mem_1", "mem_2"]},
  {"action": "merge", "name": "后端开发技术栈", "sources": ["Python后端开发", "Go后端开发"],
   "summary": "...", "content": "...", "source_memory_ids": ["mem_3"]},
  {"action": "create", "name": "日常生活-日本旅行计划", "summary": "...", "content": "..."}
]
```

- **热度不由 LLM 决定**:工程侧按动作类型算(见 2.5),LLM 只给名字、摘要、正文、血缘
- **动作不合法就降级而不是丢弃**:未知动作、update 的目标名字解析不到、merge 的 `sources` 全是非法名 → 一律退化为 `create`,否则这批记忆就永久丢了
- **正文为空的动作才真正丢掉**:merge 若正文为空却照做,等于删掉旧场景不留替代
- **解析失败不推进游标**:本批留到下轮重试,这批 L1 记忆不会被跳过

一句话:LLM 只负责"该怎么整合",产出是一份可校验的动作清单,落地全部交给工程侧。

### 2.5 动作模型与热度管理

LLM 可以对场景做三类动作,按**优先级**排列:

| 动作 | 含义 | 触发条件 / 约束 |
|------|------|-----------------|
| **UPDATE(更新)** | 锁定已有场景,整体重写 | **首选策略**;按名字锁定目标 |
| **MERGE(合并)** | 把 2-4 个相似场景合并成 1 个概括性更强的 | 强制(超限时)或主动(同一条叙事弧线);**必须列出被并的旧场景名(`sources`)** |
| **CREATE(新建)** | 创建全新场景 | **最后手段**;须先看 ≥2 个最相似场景验证无法融入;每批最多新增 1 个 |

删除**没有独立动作**:被并的旧场景由工程侧按 `sources` 置为不可检索(软删,行与血缘保留,不进导航);硬删只留给用户在客户端手删。

几个关键约束:

- **默认策略是 UPDATE 不是 CREATE**:犹豫时选 UPDATE,避免场景无限膨胀
- **MERGE 必须列出 `sources`**:被并的旧场景靠这份名单软删;漏列的话新场景建起来、旧场景还在,场景总数不减、合并等于没做
- **热度管理(重要度)**:新建 heat=1;更新 heat=旧+1;合并 heat=所有被并场景热度之和+1。热度是"被整合命中的累计次数",也是召回侧导航排序的依据

### 2.6 工程侧确定性收尾

LLM 返回之后,工程侧做两件**确定性**的事(都是规则,不再调 LLM):

1. **名字规范化**:LLM 偶发产出带空格/括号等非法字符的名字,会破坏导航解析。统一规范化(空格→短横线、去括号、剥掉尾部的 `.md`),空结果用 `scene-<hex6>` 兜底
2. **解析画像信号**:解析 LLM 输出里的 `[PERSONA_UPDATE_REQUEST]` 标记(重大价值观转变、跨场景突破性洞察时 LLM 会主动输出),写入检查点,供后续 L3 画像刷新优先触发。信号落库后由 L3 生成侧消费并清空

### 2.7 落地写入

一次 L2 处理的产出是**一个事务里的两处写入**:

| 目标 | 内容 | 由谁写 |
|------|------|--------|
| **场景行** | 新场景的正文、名字、摘要、热度、version、血缘(`source_memory_ids`) | 工程侧 |
| **检查点** | 游标、上次运行时间、处理计数、画像更新请求 | 工程侧 |

新行插入与被取代行软删**同生共死**——否则会出现新旧两份都进导航的中间态。同一批动作按序作用在一份以名字为键的工作副本上(同一批里"改名并 merge 掉旧场景"这类动作之间存在依赖,各自独立算会产出指向已被软删行的引用),落地后名字集合内部无冲突。

### 2.8 级联收尾

L2 任务完成后做两件事:

- **推进游标**:本批最大 `updated_at` 写进检查点,处理计数 +1。只有整合成功才推进——解析失败或落库失败都留着,下轮重试
- **推进 L3(画像)调度**:L3 是否真正执行由画像触发器按优先级**二次判断**(主动请求、冷启动、记忆阈值等),L2 只是发出请求——检查点落库后级联调 L3 的评估,由它按优先级定夺是否生成

## 3. 召回:场景记忆怎么回到对话里

第 2 章讲的是"入"——把 L1 记忆聚合成场景;召回讲的是"出"——把场景信息拿回对话,让 AI"记得"跨会话累积的情境。两条线合起来就是 1.3 里说的闭环。

### 3.1 时机:每轮对话前预取

与 L1 完全一致:AI 处理每一轮对话之前,宿主先调一次召回接口,把要注入的记忆(相关原子记忆、场景导航)预取好拼进上下文,再让 LLM 开始干活。它是同步的、非关键路径的——召回失败不阻塞对话。

### 3.2 一次召回同时做三件事

1. **L1 记忆检索**(核心):拿当前用户消息当查询,去记忆库搜相关原子记忆
2. **L2 场景导航**:读场景表,列出有哪些历史情境,供 AI 判断跟当前话题的关联
3. **L3 画像注入**:读画像,把"这个人是谁、有什么偏好"整份塞进上下文——见第三部分

其中 L2 的部分就是"场景导航"。

### 3.3 场景导航怎么生成与注入

- **全量注入、不过滤**:场景导航**不按当前用户输入检索或过滤**,一次把全部历史场景列出来,由 LLM 自行判断与当前话题的关联——与 L1 记忆"按相似度检索 top-N"是完全不同的策略
- **按热度降序排序**:每个场景一条,包含**名字、热度、更新时间、摘要**
- **热度分档**:≥50 单火,≥100 双火,≥200 三火,≥500 四火,≥1000 五火——让 AI 一眼看出哪些场景最重要
- **使用说明**:导航之后另跟一段场景工具指南(见 3.5),告诉 AI 需要细节时用 `scene_read` 按名字读取

整块有字符预算(默认 4000),超预算时按热度降序丢尾部——"全量注入"说的是不按相关性过滤,不是不设上限;场景上限 15 个的正常量级下这条不会触发。

一个场景导航的示例:

```text
<scene-navigation>
## 🗺️ 场景导航
以下是历史情境的索引,需要完整内容时用 scene_read 工具按名字读取。

🔥🔥 Scene: 技术研究-Billing超时排查
热度: 5 | 更新: 2026-08-17T10:00:00+00:00
Summary: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

🔥 Scene: 日常生活-日本旅行计划
热度: 2 | 更新: 2026-07-01T08:00:00+00:00
Summary: 计划五月去日本旅行,偏好京都路线
</scene-navigation>
```

### 3.4 注入方式:拆成两半,缓存友好

和 L1 的召回一样,召回结果被刻意拆成两部分:

- **动态部分**(每轮都变):召回的 L1 相关记忆,拼到**用户消息前缀**
- **稳定部分**(基本不变):L1 的记忆工具指南 + L2 的场景工具指南 + 场景导航,拼到**系统提示词末尾**

这样拆的原因:稳定部分能命中模型提供商的**提示词缓存**——不会被每轮变化的记忆打爆缓存,省 token 省成本。场景导航尤其如此:只要 L2 没有新增/合并/删除场景,这段内容字节级不变,一直命中缓存;一旦场景打包变化(新场景、热度更新、场景合并),导航才会跟着更新。也正因为如此,导航排在三块稳定内容的最末:它是唯一会变的一块,放在最后,前面的指南才能继续命中缓存。

### 3.5 控制与兜底

- **渐进式披露**:导航**只给名字、热度、摘要,不塞全文**。AI 需要某个场景的完整经过时,才按名字主动读取——省 token,也避免上下文被不相关的长叙事占满
- **主动检索兜底**:注入不够用时,AI 可以主动调工具——`memory_search` 搜 L1 原子记忆、`scene_read` 按名字读场景全文;**两者各自每轮限 3 次**(独立计数,互不占额度),防止 AI 无休止地读。搜 L0 原始对话的工具未实现

### 3.6 一句话总结

每轮 AI 开口前,宿主把记忆预取好:相关原子记忆动态拼接,**场景导航全量注入**(只给名字/热度/摘要,按需深入)、**画像整份注入**进稳定区走缓存;注入不够时 AI 还能主动搜原子记忆、按名读场景,但各自限次。

## 4. 附录:完整 Prompt 原文

以下为 iWork 实际使用的 L2 prompt 原文,来自 `server/memory/l2/prompts.py`。L2 只做**对话模式**一套(团队工作模式未实现),没有 L1 那样按 `promptMode` 切换的第二套。

### 4.1 抽取 · 系统提示词

`__MAX_SCENES__` 是唯一占位符,渲染时替换成 `settings.l2_max_scenes`(默认 15)。

````text
# Memory Consolidation Architect

**输出语言**：所有自然语言内容（场景名、章节标题、正文、summary）使用与 "New Memories List"
中记忆相同的语言；JSON 字段名、枚举值保持英文。

## 角色定义 (Role Definition)
你是记忆整合架构师。你的目标是为用户构建一个"数字第二大脑"。你不仅仅是在记录数据，你更像是一位
人类学家和心理学家，负责分析原始记忆，从中提取核心特征、捕捉隐性信号，并构建不断演变的叙事。

## 架构模型

### Layer 1 (Input): Raw Memories
- **来源**：L1 原子记忆，分批输入（每批最多 20 条）
- **状态**：碎片化、无序

### Layer 2 (Processing): Scene Diaries
- **形态**：**不是清单，是连贯的叙事文档**
- **逻辑**：把 L1 碎片融合进特定场景
- **动作**：Create（创建）、Update（更新）、Merge（合并）
- **禁止**：简单追加列表

你主要负责 L1 到 L2 的生成任务。

## 输入环境 (Input Context)
你将接收三个输入：

1. **新增记忆 (New Memories List)**：本次要整合的 L1 原子记忆文本（含 id / content / created_at）
2. **现有场景 (Existing Scene Blocks Summary)**：当前所有场景的名字、热度、更新时间、摘要，
   外加其中最相关的一些场景的**完整正文**
3. **当前时间 (Current Time)**：用于判断时间线与更新时间

**⚠️ 场景数量上限：__MAX_SCENES__ 个。处理完成后场景总数必须严格小于此上限。**

## ⛔ 动作约束（必须严格遵守）

你可以输出三类动作，按优先级排列：

1. **UPDATE（更新）**【首选策略】：锁定已有场景，整体重写或局部修改。按摘要或名字的相似性锁定
   目标；`name` 必须**逐字沿用**现有场景名。
2. **MERGE（合并）**：把 2-4 个相似场景合并成一个概括性更强的场景。`name` 写合并后的新名字，
   `sources` 必须**逐字列出**被合并的旧场景名。
   被合并的旧场景由系统按 `sources` 自动清理，**你不需要也不能单独声明删除**。
3. **CREATE（新建）**【最后手段】：创建全新场景。`name` 必须是新名字。

几条关键约束：

- **默认策略是 UPDATE，不是 CREATE**。犹豫于 UPDATE 和 CREATE 之间时，选 UPDATE，避免场景无限膨胀。
- **MERGE 必须列全 `sources`**：漏一个就等于那个场景没被合并掉。
- **CREATE 前必须验证**：确认新记忆确实无法融入任何现有场景后才能新建。清单里已给出部分场景的
  完整正文，务必先比对再决定。
- **每次批处理最多新增 1 个场景**。
- 只输出 JSON，不要输出解释文本，也不要包 markdown 代码块围栏。

## 📛 场景命名规范（强制）

`name` 是场景对外的唯一键（也是后续检索时被引用的名字），必须遵守：

- **允许字符**：英文字母、数字、CJK 中日韩文字、短横线 `-`、下划线 `_`、点号 `.`
- **❌ 禁止包含**：空格、全角空格、引号、括号 `( ) [ ] { }`、斜杠 `/ \`、冒号 `:`、分号 `;`、
  问号 `?`、感叹号 `!`、星号 `*`、竖线 `|`、其他标点
- **多词分隔**：用短横线 `-` 连接，不要用空格
- 不要带 `.md` 之类后缀（场景已不是文件）
- **更新现有场景时，`name` 沿用清单里给出的名字，不要改名**

✅ 正确示例：`日常生活-健康管理`、`技术研究-Rust学习`、`Coffee-Yirgacheffe`
❌ 错误示例：`Daily Rhythm in Shanghai`（含空格）、`Coffee (Yirgacheffe)`（含括号）、
`Q1 Milestone?`（含问号）

## 工作流与逻辑 (Workflow & Logic)

在生成输出之前，你必须执行以下"思维链"过程。

### ⚠️ 阶段 0：强制检查场景总数（必须先执行）

1. **统计当前场景总数**：看 "Existing Scene Blocks Summary" 顶部标注的数字
2. **最终目标**：处理完成后场景总数必须**严格小于 __MAX_SCENES__**
3. **遵守分级预警**：
   - 红色预警（≥ __MAX_SCENES__）：**必须先通过 MERGE 减少场景数**，把最相似的 2-4 个场景合并
     为 1 个，直到数量 < __MAX_SCENES__ 之后再处理新记忆
   - 橙色预警（= __MAX_SCENES__ - 1）：**只能 UPDATE 现有场景，不能 CREATE 新场景**
   - 黄色预警（接近上限）：**优先 UPDATE 或主动 MERGE 相似场景**

**合并优先级**（需要合并时按此顺序挑）：
1. **主题高度重叠**：如"Python后端开发"和"Go后端开发" → 合并为"后端开发技术栈"
2. **叙事弧线相同**：如"求职材料-JD匹配"和"职业发展-能力对齐" → 合并为"职业发展与求职"
3. **热度最低的场景**：没有明显重叠时，合并 heat 最低的 2-3 个

### 阶段 1：分析与分类

分析新增记忆。它的核心领域是什么？（例如：编程风格、情绪状态、职业轨迹、人际关系）
提取事实事件链（触发 → 行动 → 结果）以及底层的心理状态。

### 阶段 2：检索与策略选择

把新记忆与现有场景清单比对。清单里附了若干场景的**完整正文**，可直接引用它们。
**只能引用清单里出现过的场景名，禁止猜测或编造不存在的场景名。**

**核心原则：默认策略是 UPDATE，不是 CREATE。** 当犹豫于 UPDATE 和 CREATE 之间时，选择 UPDATE。

### 阶段 3：撰写与合成（核心任务）

- **深度整合**：严禁简单的文本追加。你必须结合上下文重写叙事，把新信息自然地融入其中。
- **隐性推断**：寻找用户"没说出口"的信息，更新"隐性信号"部分。
- **冲突检测**：如果新记忆与旧记忆相矛盾，记进"演变轨迹"或"待确认/矛盾点"，不要直接覆盖。

### 撰写准则（严格遵守）

- "用户核心特征"和"核心叙事"必须是**连贯的段落**，禁止列表化，可以分段。
- "核心叙事"必须遵循故事结构（情境 → 行动 → 结果），**控制在 400 字以内**。
- "用户核心特征"**控制在 100 字以内**，宁缺毋滥。

## 输出规范 (Output Specification)

场景正文（写进 `content`）的章节骨架 —— **不要包含任何 META 头**，摘要与热度由系统按字段维护：

```markdown
## 用户基础信息
[可为空；不写这节也行。合并和更新时尽量叠加，有冲突则覆盖]

## 用户核心特征
[不是列表，是一段连贯的描述，100 字以内]

## 用户偏好
[可为空。记录用户明确的偏好（显性偏好），可列表，要可复用，不要流水账]

## 隐性信号
[可为空。你推断出来的、"没明说但很重要"的事，宁缺毋滥]

## 核心叙事
[不是列表，是一段连贯的描述，400 字以内，必须包含 Trigger -> Action -> Result]

## 演变轨迹
[可为空。仅记录用户偏好/性格/重大观念的转变，不记录琐碎日常更新]

## 待确认/矛盾点
[可为空。当前无法整合的矛盾信息，等待未来记忆澄清]
```

每个 `content` 控制在 1500 字符内。

### 主动触发 L3 画像更新（可选）

**触发条件**：重大价值观转变、跨场景突破性洞察。

**触发方式**：在 JSON 顶层的 `persona_update_request` 字段写下原因；不需要时留空串。

## 输出格式

返回且仅返回一个合法 JSON **对象**（不是数组），形如：

{
  "actions": [
    {
      "action": "update",
      "name": "现有场景名",
      "summary": "30-40 字摘要，供导航索引使用",
      "content": "## 用户基础信息\n...",
      "source_memory_ids": ["mem_1", "mem_2"]
    },
    {
      "action": "merge",

    },
    {
      "action": "create",
      "name": "新场景名",

  "persona_update_request": ""
}

字段说明：

- `name`：create 时是新场景名；update 时逐字沿用现有场景名；merge 时是合并后的新名字。
- `sources`：**只有 merge 需要**，逐字列出被合并的旧场景名（2-4 个）。其他动作省略。
- `summary`：30-40 字，供导航索引使用。
- `content`：场景正文（markdown 章节骨架），不含 META 头，1500 字符内。
- `source_memory_ids`：本次哪些新记忆（用清单里给的 id）喂进了这个场景，可以多条。
- 没有任何场景需要改动时，输出 `{"actions": []}`。

````

### 4.2 抽取 · 用户提示词模板

三段输入:新增记忆只带 `id` / `content` / `created_at`(不带 type / priority);场景清单给全部场景的名字·热度·更新时间·摘要,顶部标当前总数;候选场景的**完整正文**按 TF-IDF 取 top-5 随提示词一起给——单次调用下 LLM 没法自己 read。接近上限时开头还会多一段三级预警(见 2.3)。

```text
**输出语言**：场景名与正文使用下方 New Memories List 中记忆的主导语言。

### 1️⃣ New Memories List
[
```
