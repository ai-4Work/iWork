## L1-1. 概述

L1 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L0 按轮次增量记录的对话消息(用户与 AI 的每一轮)
- **输出**:结构化的记忆记录,**双写**到两条通道
  - 按天追加的产出文档(L1 记忆记录)——只追加不修改,是事实源,用于备份/恢复
  - 向量库—— 检索主引擎(本地向量库或腾讯云向量库)

### L1-1.1 L1 的数据来源

L1 的输入就是 L0 里存的历史对话,而且是**增量、按游标**读取的,不是每次把整个历史重新抽一遍。

**L0 里的对话存在两处**
- 一份按天追加的原始文档(L0 对话存档),是事实源,永久保留**清洗后的完整对话文本**(处理流程见下)
- 一份同步镜像到检索库里的 L0 表,带元数据,供后续检索用;自动捕获消息时两者会一起写入

**L0 里存什么、不存什么**

L0 是"故意全量记录"的,但这个"全量"有一个重要前提——**只有 user 和 assistant 的文本消息会进 L0**,非对话文本由捕获侧直接挡在门外。

而且落库的不是 hook 进来的逐字消息——消息在**写入 L0 之前**会依次过四道处理:

1. **角色/类型过滤**:只收 user / assistant;数组 content 只取 `type="text"` 片段(工具返回、thinking、图片等非 text 块丢弃)
2. **文本清洗**:剥注入的记忆标签、框架元数据、行首时间戳、媒体标记(`[media attached: ...]`)、`System: [timestamp] Exec completed` 行、base64 图片、null 字符
3. **代码块剥离**:assistant 回复里的围栏代码块整体删除(仅 assistant 角色),只留自然语言说明
4. **结构过滤**:空/纯空白、框架噪音、斜杠命令 → 丢弃

这四道都是**结构性清洗,不是语义压缩**——不截断、不摘要、无长度上限,幸存下来的 user/assistant 纯文本**基本逐字完整**保留。

- **包含**:
  - user / assistant 两种角色的消息;content 为数组时只取 `type="text"` 的文本片段
  - 经清理后的纯净文本:注入的记忆标签、框架元数据、行首时间戳、媒体标记(`[media attached: ...]`)、`System: [timestamp] Exec completed` 等框架行都会被剥掉
  - assistant 剥离代码块后的自然语言说明(``` 围栏代码块整体删除,避免大段代码污染)
  - 内嵌 base64 图片替换为 `[image]` 占位(保留"这里有一张图"的位置信息,丢弃原始数据)
- **不包含**:
  - `role="tool"` 的工具调用返回、`role="system"` 的系统消息——**整体丢弃**,所以大段工具结果根本进不了 L1
  - 非文本片段:`tool_result`、`tool_use`、`image_url`、`thinking` / `redacted_thinking`(模型内部推理块)、原始图片数据
  - assistant 回复中的代码块内容
  - 框架噪音:会话引导、会话重置(/new、/reset)、NO_REPLY、pre-compaction 内存冲刷提示等
  - 斜杠命令、空 / 纯空白消息

一句话:L0 的"全量"是对**人机对话文本**全量——工具返回、图片、代码块这类非对话文本不进 L0,既省存储,也天然让 L1 远离大段工具内容。

**为什么丢得对:记忆存结论,不存过程**

被挡在门外的内容大多是**过程性数据**——工具执行原文、模型内部推理、代码正文、图片像素,价值集中在"当下这个任务",任务结束就失效;而记忆要的是**可复用的结论**("超时集中在 api-gateway"、"用户喜欢日本料理"),这类结论会在下个会话继续生效。

取舍标准只有两条:
- **复用价值**:对未来的会话还有没有用?过程性、一次性的信息,提取进记忆只会污染记忆库
- **提取成本**:被丢的恰好是 token 最重的部分(几百 KB 文件、长推理、大代码块),挡在门外等于把 L1 重跑 LLM 的最大开销挡在门外

而"丢"不等于"消失"——这是**分层存储**,每类信息各有去处,只是不在记忆里:
- 工具原文 → offload 管线:截断送摘要 + 全文落 COS ref,按需读取
- 对话逐字 → L0 存档:永久保留、可检索
- 代码 → 代码仓库本身
- 模型内部推理 → 唯一真正不保留的,因为它对谁都无复用价值

一句话:记忆是"提炼结论",不是"备份过程";原始数据的备份职责由 offload 与 L0 存档承担。

**L1 是怎么读的**
- 优先从检索库按游标增量拉取,游标只返回上次之后新产生的消息;检索库不可用时,降级去读原始文档
- 游标记录"上次抽到哪一行",保存在检查点里,保证每条消息只被抽一次、某一轮失败也不丢断点
- 每次会**多捞一批**消息,只处理最早的一批,多捞的部分作为"存量积压"的信号,用来判断是否要继续抽(见 1.2)

**读出来之后**:先过一道质量门(规则预筛,滤结构噪音、纯符号),再切成"新消息(真正提取对象)"和"背景消息(仅供理解上下文)"两部分,才送进模型抽取;闲聊、无意义内容由 LLM 抽取时按"宁缺毋滥"规则滤掉。

### L1-1.2 抽取时机

L1 抽取**不是固定定时任务**,而是"**对话轮次驱动 + 空闲兜底 + 级联排空 + 会话冲刷**"四种时机,最终都汇入同一个 L1 任务队列。

| # | 时机 | 触发方式 | 说明 |
|---|------|----------|------|
| ① | 阈值触发(主) | 每轮对话后累计计数,达到设定阈值立即触发 | 每轮对话结束、消息落库后,给当前会话累计一轮;达到阈值(默认每 N 轮,预热开启则首轮就触发)时,立即入队抽取 |
| ② | 空闲兜底 | 空闲计时器到期 | 一直没凑够阈值时,给会话挂一个空闲计时器(默认 10 分钟);用户停聊后计时器到期,把当前累积的消息抽一次。同时对"计时器触发但该会话其实已抽完"的情况会直接跳过,避免重复抽取 |
| ③ | 存量级联 | 抽取完成后发现还有存量 | 一次抽完如果发现原始消息还积压很多,就立即再排一次抽取;只剩少量尾巴,则重新挂个空闲计时器稍后兜底;同时推进下一层(L2)的调度 |
| ④ | 会话冲刷 | 会话结束 | 会话明确结束时入队冲刷任务,把最后没抽的消息一次性收尾 |

**为什么会有大存量**:你可能会问——有阈值触发在前面,怎么还会积压一大片?关键在于,**阈值触发和游标推进是两套不同的口径**:阈值按"对话回合数"计数(每轮对话记一次,触发后清零),游标按 L0 里真实的消息行数推进。只要 L0 里堆了大量不是按"每轮一条"节奏进来的消息,游标就会大幅落后,第一次抽取一捞就是满页,于是级联连续抽。典型场景:

- **批量灌入历史数据**:导入、迁移恢复、初始化。这些消息一次性写入 L0,根本不经过逐轮计数,阈值一直不触发,但游标后面已经堆了几百上千条
- **抽取长时间没跑**:worker 重启、宕机、锁被占,期间对话还在继续,消息持续落 L0;恢复后第一次抽就发现积压一大片
- **一轮对话产生的消息特别多**:阈值按"轮"触发,但每次抽取只送最多 10 条新消息给模型;工具调用密集、多人群聊、长对话时,消息进库速度超过抽取速度,游标后面越堆越多

换句话说:**正常聊天节奏下最多留个尾巴,由空闲计时器兜底;只有当 L0 出现大批非节奏性数据时,才会走到级联立即续抽**。

**非服务模式的等价逻辑**:同样靠"轮次达到阈值 → 立即抽;没到阈值 → 挂空闲计时器;计时器到期 → 兜底抽"。触发原因就三种:达到阈值、空闲超时、会话冲刷。

一句话:聊得够多立刻抽(主),不聊了过一会儿兜底抽(辅),存量多连续抽(补),会话结束全抽(收)。

### L1-1.3 正常会话与记忆抽取的关系

会话走**主路**,记忆抽取走**支路**——两者**互不阻塞,但严格依赖,最终闭环**。

```
正常会话(主路):  会话进来 → 消息落库 L0 → 会话继续正常进行
                (L0 就是对话存档区,主路自己也在用)

记忆抽取(支路):  L1 不碰正在进行的会话,按游标读 L0 里新存的消息
                → 抽取 → 去重 → 写入记忆库
```

为什么不是"互不相干",有三个耦合点:

1. **数据上游**:L1 吃的就是 L0 存的对话——没有 L0,就没有 L1 可抽
2. **启动通知**:每轮会话落库后,主路会给调度器"记一笔",据此决定支路何时跑(凑够轮数就抽,没凑够就挂计时器);即便主路不通知(比如批量导入了历史数据),L1 照样能靠游标把新数据抽掉
3. **反馈回路**:L1 抽出的记忆写进向量库,下次会话时被召回、注入 AI 的上下文,让 AI"记得"之前聊过的东西

所以完整链路其实是一个循环:

```
会话 → L0 存档 → L1 抽取 → 记忆库 → 下次会话召回 → 会话
```

一句话:**主路负责实时对话,只把消息存进 L0;L1 是独立按游标从 L0 抽数据的支线,互不阻塞;但支线的产出最终会回到主会话里发挥作用**。

### L1-1.4 各层的作用:为什么不能只靠 L1

L1 之上还有 L2(场景)、L3(画像)两层,加上最底层的 L0,四层各有分工。可以用"各自回答什么问题"来理解:

| 层 | 内容 | 回答的问题 | 注入方式 |
|----|------|-----------|----------|
| **L0 对话记录** | 原始对话逐字存档(事实源) | "当时原话是什么" | 不直接注入,靠"对话搜索"工具按需查原文 |
| **L1 原子记忆** | 单条事实碎片(结构化) | "和这条对话直接相关的具体事实是什么" | 按查询检索 top-N,拼到用户消息前缀(动态) |
| **L2 场景记忆** | 跨会话拼成的连贯叙事(情景) | "有哪些进行中的情境、每个情境的全貌是什么" | 全量注入"场景导航"(路径/热度/摘要),放系统提示词末尾(稳定) |
| **L3 画像** | 凝练的稳定身份(语义) | "这个人是谁、喜欢什么、该怎么服务" | 整份注入,放系统提示词末尾(稳定) |

为什么不能只靠 L1(哪怕 L1 已经会抽 persona 类型的记忆):

1. **L1 是碎片,没有"故事线"**。连续两周排查 Billing 超时会产生几十条 L1 碎片,但每条都是孤立的一句话。只召回碎片,AI 看到的是"一堆事实",看不到"这是个持续的项目、进展到哪、中间有哪些决策和转折"。L2 把碎片整合成连贯叙事(起因→行动→结果、演变轨迹、矛盾点),AI 才真正理解当前任务上下文。

2. **L1 命中依赖查询措辞**。召回拿"当前用户消息"当查询做检索,只返回最相似的前几条;措辞一变就可能召回不到。而 L2 场景导航是**全量注入、不过滤**的,画像也是**整份注入**——这两个是"兜底保证",不依赖当轮检索。

3. **L1 攒不下跨会话的全貌**。L1 抽取偏会话级;L2/L3 刻意忽略用户/会话/任务维度,按"团队+agent"**跨会话累积**。横跨几十个会话的长期项目,只有 L2 能攒成一份完整场景。

4. **token 效率与渐进式披露**。L1 碎片无限累积,永远塞不进上下文,只能检索 top-N。L2 场景导航一行一个场景,几十个场景只是一小段;L3 画像是份凝练文档。L2 只给"目录",AI 需要细节时用工具按路径读全文——不相关场景的正文根本不进上下文。

5. **画像不是事实点,是综合判断**。L1 的 persona 记忆是"用户喜欢日本料理"这类原子事实,会无限累积、可能互相矛盾;L3 画像基于 L2 场景综合分析,推断出"这个人整体是谁"(核心特征、隐性信号、价值观),是一份稳定、自洽、有界的身份文档。前者动态召回、按需给;后者稳定注入、永远在场。

## L1-2. 核心处理流程

L1 的处理分两个阶段:**先"场景切分 + 记忆抽取",再"召回 + 冲突判断"**。先从整体看一遍九步流程,再分节详解。

### L1-2.1 完整流程总览

从一批 L0 新增消息,到记忆真正落库,一次 L1 处理走完下面九步。全流程只有两处调用 LLM(第 ③、⑥ 步),其余都是规则、算法或存储操作——这是控制成本的关键设计。

```
L0 新增消息
  → ① 质量门(规则预筛):滤结构噪音、纯符号;闲聊由 LLM 抽取时按"宁缺毋滥"滤
  → ② 切分:新消息(≤10)+ 背景消息(≤5)
  → ③ 一次 LLM 调用:场景切分 + 记忆抽取(结构化输出)
  → ④ 上限截断(≤10 条/会话)+ 分配临时记忆编号
  → ⑤ 候选召回:向量余弦 / 关键词检索(算法,非 LLM;无能力则跳过 ⑥)
  → ⑥ 一次批量 LLM 调用:对每条新记忆输出 store/update/merge/skip 决策
  → ⑦ 落地写入:产出文档追加(事实源)+ 向量库写入(检索),
       update/merge 时删目标记忆 + 版本号递增
  → ⑧ 写记忆生成血缘日志
  → ⑨ 级联:重置计数 → 推进 L2 调度
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 质量门 | 规则预筛 | 规则 | 滤结构噪音、纯符号,不给 LLM 加负担;滤不掉语义上的闲聊 |
| ② 切分 | 拆输入 | 规则 | 新消息(≤10)是**唯一**提取来源;背景(≤5)仅供理解上下文 |
| ③ 场景切分 + 抽取 | 一次 LLM 调用 | LLM | 输出结构化 JSON:情境 + 该情境下的记忆;严禁从背景提取 |
| ④ 截断 + 编号 | 控制量、打标 | 规则 | 每会话 ≤10 条,超出截断;分配临时编号供下一步定位 |
| ⑤ 候选召回 | 找相似记忆 | 算法 | 向量余弦(首选)→ 关键词(降级);滤同批、取前 5;不跨租户;无能力直接跳过 |
| ⑥ 冲突判断 | 逐条决策 | LLM | 一次批量调用,输出 store / update / merge / skip |
| ⑦ 落地写入 | 双写 | 存储 | 产出文档追加(事实源)+ 向量库(检索);update/merge 删目标、版本号递增 |
| ⑧ 血缘日志 | 记录来源 | 存储 | 记下每条记忆从哪批消息来,供后续追溯 |
| ⑨ 级联 | 收尾 | 调度 | 重置会话计数;推进 L2 场景聚合 |

按阶段读这张表:

- **① → ④ 提炼**:把 L0 消息准备好,提炼成候选记忆(质量门 → 切分 → 抽取 → 截断编号)
- **⑤ → ⑥ 去重**:算法先找相似记忆,LLM 再逐条定动作,避免库里出现重复/冲突
- **⑦ → ⑨ 落库收尾**:双写存档 + 记血缘,最后触发下一层聚合

其中 LLM 只出现在 ③(抽取)和 ⑥(去重)两处,其余环节全部确定性执行,不做无谓的模型调用。

下面 2.2–2.7 按这九步的顺序展开详述。

### L1-2.2 质量门:规则预筛

从 L0 读出来的消息,在送进 LLM 之前先过一道质量门。它是**规则预筛**,机械剔除明显不值得进模型的消息:

- **结构噪音**:空 / 纯空白消息、框架内部噪音(引导语、会话重置、占位回复)、斜杠命令(如 /new、/reset)
- **纯符号**:完全由符号组成、或纯问号的短消息

设计上 L0 是**故意全量记录**的——只做宽松的结构过滤,把严格过滤推迟到 L1 消费消息的那一刻。目前质量门生效的就是"结构噪音 + 纯符号"这两类;长度、注入特征这类规则在代码里有,但当前未启用。

质量门**滤不掉语义上的"闲聊"**:闲聊、无意义内容要等 LLM 抽取阶段,按 prompt 里"宁缺毋滥"的规则判断。质量门的价值是把明显没营养的消息挡在模型调用**之前**,既省 token,也防止脏数据进入记忆。

### L1-2.3 增量读取与输入构造

L0 已按轮次持续记录对话,L1 **不处理全量历史**——每次只读"上次游标之后新增的那批消息",再切分成两部分送给 LLM:

| 部分 | 数量 | 作用 |
|------|------|------|
| **新消息** | ≤ 10 条 | **唯一**提取记忆的来源 |
| **背景消息** | ≤ 5 条 | 仅帮助 LLM 理解上下文/指代/时间,**严禁从中提取记忆** |

读出来的消息先过一道**质量门**(见 2.2)再做切分。抽取结果另带每会话上限(默认 10 条),超出的截断。

### L1-2.4 场景切分与记忆抽取

一次 LLM 调用完成两件事:对历史对话做**场景切分**(判断情境切换),同时得到每个场景下的每条原子记忆(结构化输出)。

### L1-2.5 候选召回

"找相似记忆"这一步由**算法**完成,不是 LLM:

| 环节 | 完成方式 | 是否 LLM |
|------|----------|----------|
| 召回候选(找相似记忆) | 向量余弦检索(首选)→ 关键词检索(降级)→ 跳过去重(无能力时) | ❌ 否 |
| 冲突判断(store/update/merge/skip) | 一次批量 LLM 调用 | ✅ 是 |

三级降级方案:
1. **向量召回**:批量对新记忆算向量,余弦检索,过滤同批后取相似度最高的前 5 条
2. **关键词召回**:无向量计算服务时,改用关键词检索
3. **跳过去重**:向量库为空且无检索能力时,所有记忆直接作为新增存储

两条边界:
- **租户隔离**:候选召回永不跨租户,只在当前团队的隔离范围内检索
- **排除同批**:召回时滤掉本次同批新记忆自己,避免"自己和自己冲突"

### L1-2.6 冲突判断

一次批量 LLM 调用,对每条新记忆从四种动作里选一个:

- **store** = 新增
- **update** = 同一事实/事件,新记忆更优(更具体/更晚/纠错),以新记忆为主覆盖旧记忆,可保留旧记忆仍正确的细节
- **merge** = 同一事实或演化过程,新旧记忆互补且不矛盾,合并成一条更完整记忆(可**跨类型**、可**多对多**)
- **skip** = 已有记忆更好,新记忆无增量或更模糊,忽略

没有独立的"删除"动作:删除是 update/merge 的**副作用**——被指定为目标 ID 的旧记忆会从**向量库实时删除**,产出文档里的旧行靠定期对账清理。

### L1-2.7 落地写入

四条动作的落地语义:

- **store**:产出文档追加 + 向量库写入
- **update/merge**:查目标记忆的版本,新记录版本号为目标版本最大值加 1;从向量库删除目标记录,产出文档追加新记录(旧行保留待清理)
- **skip**:什么都不做

**双写容错**:
- 产出文档写失败不阻塞向量库写,反之亦然
- 向量计算失败时只写元数据与检索字段,不写向量
- 向量写失败不影响产出文档主流程

### L1-2.8 级联收尾

L1 任务完成后做两件事:
- 重置该会话的计数(供计时器去重判断)
- **推进下一层(L2)的调度**,触发 L2 场景聚合

## L1-3. 召回:记忆怎么回到对话里

第 2 章讲的是"入"——把对话抽成记忆写进库;召回讲的是"出"——把库里已有的记忆拿回对话,让 AI"记得"之前聊过什么。两条线合起来就是 1.3 里说的闭环:会话 → 抽取入库 → 下次召回 → 再进会话。

### L1-3.1 时机:每轮对话前预取

AI 处理每一轮对话之前,宿主会先调一次召回接口,带上**当前用户消息 + 会话标识**;拿到结果后把它拼进给 LLM 的上下文,再让 LLM 开始干活。

- 它是**同步**的——LLM 等着这份记忆到位
- 但它属于**非关键路径**——召回失败或超时不会阻塞对话,只在响应里带一个错误码,对话照常进行

**"每轮对话"的准确定义**:指用户**每发一条新的用户消息**就构成一轮。预取不是只在会话开头做一次,也不是每个会话只做一次,而是**每条新用户消息触发一次**——AI 处理该条消息之前,用这条消息本身当查询去召回。

- **跳过的情形**:取不到当前用户消息、或查询清洗后过短(不足 2 个字符)时,本轮不召回
- **"轮"的口径**:是**用户输入**维度。一次用户消息 = 一轮;AI 在同一轮内部的多次模型调用(如工具调用循环)不重复触发召回
- **对应到实现**:召回挂在 `user.before` 注入点,语义就是"在最新一条用户消息之前";检索词取自当前这条用户消息

### L1-3.2 一次召回同时做三件事

召回不是只查 L1,而是三层一起:

1. **L1 记忆检索**(核心):拿当前用户消息当查询,去记忆库搜相关记忆
2. **L2 场景导航**:读场景索引,列出有哪些历史情境,供 AI 判断跟当前话题的关联
3. **L3 画像注入**:读用户画像文件,把"这个人是谁、有什么偏好"塞进上下文


三件事在一次召回里并行完成,一起注入。

### L1-3.3 L1 记忆检索怎么做

- **查询先清洗**:剥掉网关注入的元数据、图片 base64 等,只留纯意图;查询太短(不足 2 个字符)直接跳过,不搜
- **三种策略**:
  - 关键词检索(FTS5 全文检索)
  - 向量检索(余弦相似度)
  - 混合(默认):两者并行跑,再用融合排序合并——两边都命中的排得更靠前
- **口径**:默认取 5 条、相似度阈值 0.3、整体超时 5 秒
- 配了向量检索但向量服务不可用时**直接失败报错**,而不是悄悄降级——让上层明确知道发生了什么

### L1-3.4 注入方式:拆成两半,缓存友好

召回结果被刻意拆成两部分,放进不同位置:

- **动态部分**(每轮都变):召回的 L1 相关记忆,拼到**用户消息前缀**,包在"相关记忆"标签里,并注明"仅作参考,不代表当前任务"
- **稳定部分**(基本不变):画像 + 场景导航 + 一份"记忆工具使用指南",拼到**系统提示词末尾**

这样拆的原因:稳定部分能命中模型提供商的**提示词缓存**——不会被每轮变化的记忆打爆缓存,省 token 省成本。

**一个具体例子**(场景:用户王小明是后端工程师,正和 AI 排查 Billing API 超时;画像里有"喜欢日本料理",还规划了五月去日本旅行。跨两轮看注入差异):

第 1 轮,用户问"看看今天的超时日志":

```
[System 提示词末尾 —— 稳定部分]
<user-persona>
用户叫王小明,30岁,后端工程师,偏好简洁中文回复。
</user-persona>
<scene-navigation>
- 我（AI）在帮用户排查 Billing API 超时
- 我（AI）在和用户规划五月日本旅行
</scene-navigation>
<memory-tools-guide>
（记忆工具使用指南:tdai_memory_search / tdai_conversation_search / read_file,每轮合计限 3 次）
</memory-tools-guide>

[User 消息前缀 —— 动态部分]
<relevant-memories>
以下与当前对话相关,仅作参考,不代表当前任务进程:
- [episodic|超时排查] 用户上周定位到超时集中在 api-gateway (活动时间: 2026-08-12)
- [work_fact] Billing API 网关超时阈值当前为 3 秒
</relevant-memories>
用户: 看看今天的超时日志
```

第 2 轮,用户切话题问"五一去日本有什么好路线?":

```
[System 提示词末尾 —— 稳定部分]
（与上一轮完全相同 → 命中提示词缓存,这一段 token 不再重复计算）

[User 消息前缀 —— 动态部分]
<relevant-memories>
以下与当前对话相关,仅作参考:
- [persona] 用户喜欢日本料理,去过三次京都
- [episodic|旅行计划] 用户计划五月去日本旅行 (活动时间: 2026-05-01 ~ 2026-05-10)
</relevant-memories>
用户: 五一去日本有什么好路线?
```

两轮之间,**稳定部分字节级不变**,原样拼在系统提示词末尾,命中缓存省成本;**动态部分随用户问题每轮换**,所以被刻意放到用户消息前缀,避免把系统提示词那段缓存打爆。

另外注意一点:稳定部分里的**画像(L3)**和**场景导航(L2)**是**整份读取/生成**的——不按当前用户输入做检索或过滤,每次召回都原样带上。所谓"基本不变"是相对的:当 L2 新增场景、L3 沉淀新的画像事实时,这段内容才会跟着更新;更新之前则保持字节级一致以命中缓存。场景导航尤其如此——一次注入全部历史情境,不做按输入的预筛选,由 LLM 自行判断与当前话题的关联;注入不够用时再看 3.5 的"读场景文件"工具主动深入。

例子里稳定部分那一块的 `<memory-tools-guide>`(**记忆工具使用指南**)是一段静态说明文本,完整内容如下:

```xml
<memory-tools-guide>
## 记忆工具调用指南

当上方注入的记忆片段不足以回答用户问题时,可主动调用以下工具获取更多信息:

- **tdai_memory_search**:搜索结构化记忆(L1),适用于回忆用户偏好、历史事件节点、规则等关键信息。
- **tdai_conversation_search**:搜索原始对话(L0),适用于查找具体消息原文、时间线、上下文细节;也可用于补充或校验 memory_search 的结果。
- **read_file**(Scene Navigation 中的路径):当已定位到相关情境,且需要该场景的完整画像、事件经过或阶段结论时使用。

### ⚠️ 调用次数限制
每轮对话中,tdai_memory_search 和 tdai_conversation_search **合计最多调用 3 次**。
- 首次搜索无结果时,可换关键词或换工具重试,但总调用次数不要超过 3 次。
- 若 3 次搜索后仍无结果,说明该信息不在记忆中,请直接根据已有信息回复用户,不要继续搜索。
</memory-tools-guide>
```

### L1-3.5 控制与兜底

- **预算控制**:单条记忆的字符上限、召回总字符上限;超长的截断(带"…已截断"后缀,提示可用工具查详情),超预算的丢弃
- **主动检索兜底**:注入的记忆不够用时,AI 可以主动调工具——"记忆搜索"搜 L1、"对话搜索"搜 L0 原文、"读场景文件"进具体情境;其中两个搜索工具**每轮合计限 3 次**,防止 AI 无休止地搜

### L1-3.6 一句话总结

每轮 AI 开口前,宿主用当前这句话当"问题",先把三层记忆(相关记忆、画像、场景导航)预取好拼进上下文;稳定部分走缓存、动态部分每轮换;注入不够时 AI 还能主动再搜,但限次。

## L1-4. 附录:完整 Prompt 原文

以下为 L1 抽取与去重的完整 prompt,按"对话 / 团队工作"两种场景,各两套系统提示词 + 各一个用户提示词模板。

### L1-两套提示词的来源与选择

L1 的 prompt 分两套,对应两种记忆口径:

- **对话模式(chat)**:persona / episodic / instruction,面向个人对话,让 AI 记住"这个用户"
- **团队工作模式(code)**:work_fact / work_task / work_method / work_artifact,面向团队协作,沉淀可共享的工作记忆

用哪套由一个配置项 `promptMode` 决定,只认 `chat` / `code` 两个值,**默认 `chat`**,配置写成其它值一律回退 `chat`。设置位置:顶层 `promptMode` 或 `prompts.mode` 定全局;`extraction` 组可单独覆盖 L1 抽取/去重,`persona` 组可单独覆盖 L2/L3,不设则继承全局。

它是**纯静态配置**:不按团队、agent 或会话自动切换;团队版面板也只支持按 agent/team 绑定自定义提示词文本,不提供 chat/code 模式设置。运行时,同一个开关会同时传给场景切分、抽取、去重三处——配置是 `code` 就整套用团队版,是 `chat` 就整套用对话版,不会混搭。

### L1-4.1 抽取 · 对话模式系统提示词

```text
你是专业的"情境切分与记忆提取专家"。
你的任务是分析用户的对话，判断情境切换，并从中提取结构化的核心记忆（仅限 persona, episodic, instruction 三类）。

**输出语言**：所有自由文本字段（`scene_name`、memory `content`）使用与用户消息相同的语言；JSON 字段名、枚举值、ISO 时间戳保持英文。

### 任务一：情境切分（Scene Segmentation）
分析【待提取的新消息】，结合【上一个情境】，判断并输出当前对话的情境。
- 继承：无明显切换，沿用上一个情境。
- 切换条件：用户发出明确指令（如"换话题"）、意图转变、或提出独立新目标。
- 一段对话可能只有一个情境，也可能有多个情境（话题多次切换时）。
- 命名规则："我（AI）在和xxx（用户身份）做xxx（目标活动）"（**使用上述输出语言**，约 30-50 个字符或等价长度，单句，全局唯一）。

---

### 任务二：核心记忆提取（Memory Extraction）
结合背景和当前情境，仅从【待提取的新消息】中提取核心信息。

【通用提取原则】
1. 宁缺毋滥：过滤琐碎闲聊、临时性指令和一次性操作（如"这次、本单"）；剔除不可靠的边缘信息。
2. 独立完整：记忆必须"跳出当前对话依然成立"，无上下文也能看懂。提取主体必须以"用户（姓名）"或"AI"为核心。
3. 归纳合并：强关联或因果关系的多条消息，必须合并为一条完整记忆，不可碎片化。

【支持提取的三大类型】（必须严格遵守类型规则）
> 下面给出的"提取句式"和"触发词"仅作为中文骨架参考；**实际 `content` 必须按上述输出语言书写**（例如英文用户 → "The user (Maya) is a senior product manager based in Berlin"）。

1. 个性化记忆 (type: "persona")
   - 定义：用户的稳定属性、偏好、技能、价值观、习惯（如住所、职业、饮食禁忌）。
   - 提取句式："用户（[姓名]）喜欢/是/擅长..."
   - 打分 (priority)：80-100（健康/禁忌/核心特质）；50-70（一般喜好/技能）；<50（模糊次要，可丢弃）。
   - 触发词：喜欢、习惯、经常、我这个人...

2. 客观事件记忆 (type: "episodic")
   - 定义：客观发生的动作、决定、计划或达成结果。绝不包含纯主观感受。
   - 提取句式："用户（[姓名]）在 [最好是精确绝对时间] 于 [地点] [做了某事（可以包含起因、经过、结果）]"。
   - 时间约束：尽量基于消息的 timestamp 推算绝对时间，如能确定则在 metadata 中输出 activity_start_time 和 activity_end_time（ISO 8601格式）。无法确定时可省略。
   - 打分 (priority)：80-100（重要事件/计划）；60-70（一般完整活动）；<60（琐碎事项，直接丢弃）。

3. 全局指令记忆 (type: "instruction")
   - 定义：用户对 AI 提出的长期行为规则、格式偏好、语气控制。
   - 提取句式："用户要求/希望 AI 以后回答时..."
   - 触发词：以后都、从现在开始、记住、必须。
   - 打分 (priority)：-1（极其严格的全局死命令）；90-100（核心行为规则）；70-80（重要要求）；<70（临时要求，直接丢弃）。

---

### 不应该提取的内容
- 琐碎闲聊、问候；临时性的纯工具性请求（如"这次帮我翻译一下"）
- 一次性操作指令（如"这次、本单"相关）
- 重复的内容；AI助手自身的行为或输出
- 不属于以上3类的信息
- 纯主观感受（不带客观事件的情绪表达）

### L1-4.4 去重 · 对话模式系统提示词

```text
你是记忆冲突检测器。批量比较多条【新记忆】与【统一候选记忆池】中的已有记忆，逐条决定如何处理。

**输出语言**：`merged_content` 使用与候选池中已有记忆相同的语言；JSON 字段名、枚举值、record_id、ISO 时间戳保持英文。

## 核心规则

- **跨 type 合并**：不同 type（persona / episodic / instruction / work_fact / work_task / work_method / work_artifact）的记忆如果语义上描述同一事实/事件，**可以合并**。
- **多对多合并**：一条新记忆可以同时替换/合并候选池中的**多条**已有记忆（通过 target_ids 数组指定）。
- 合并后你必须判断新记忆的最佳 type（merged_type）。

## 判断逻辑

1. **分辨记忆性质**：
   - **状态类**（persona/instruction）：偏好、特质、长期设定、相对稳定的事实、行为规则
   - **事件类**（episodic）：一次性经历、带时间点的客观记录，建议合并同一件事的前因后果

2. **判断是否同一事实/事件**：主体相同、主题一致、时间接近、scene_name 相似

3. **选择动作**：
   - "store"：视为新信息，新增当前记忆。
   - "skip"：已有记忆更好，新记忆无增量或更模糊，忽略当前记忆。
   - "update"：同一事实/事件，新记忆在内容或时间上更优（更具体、更晚或纠错），以新记忆为主覆盖旧记忆，可保留旧记忆中仍正确的细节。
   - "merge"：同一事实或同一演化过程，多条记忆信息互补且不矛盾，合并成一条更完整记忆，信息尽量不冗余。

4. **策略倾向**：
   - 状态类：多条描述同一偏好/特质 → 倾向 merge；无增量 → skip；明确更新 → update
   - 事件类：同一事件的前因后果、不同阶段 → 倾向 merge 为一条完整叙述；完全相同 → skip
   - 跨类型示例：一条 episodic "用户在 2018 年开始做播客" + 一条 persona "用户有播客制作经验" → 可 merge 为一条 persona 或 episodic（取决于信息侧重）

5. **timestamp 处理**：
   - merge / update 时，merged_timestamps 应包含**所有相关记忆的时间戳并集**（去重排序）
   - 这样可以保留事件发生的完整时间线

## 输出格式

严格输出 JSON 数组，每个元素对应一条新记忆的决策。不输出任何其他内容：

[
  {
    "record_id": "新记忆的 record_id",
    "action": "store|update|skip|merge",
    "target_ids": ["要删除的候选记忆 record_id 1", "record_id 2"],
    "merged_content": "合并/更新后的记忆内容（merge/update 时必填）",
    "merged_type": "合并后的最佳 type：persona|episodic|instruction|work_fact|work_task|work_method|work_artifact（merge/update 时必填）",
    "merged_priority": 85,
    "merged_timestamps": ["合并后的时间戳数组，包含所有新旧记忆时间戳的并集（merge/update 时必填）"]
  }
]

字段说明：
- target_ids：要删除替换的旧记忆 ID **数组**（可以 1 条或多条）。store/skip 时省略或为空。
- merged_content：merge/update 时的最终记忆文本。store/skip 时省略。
- merged_type：merge/update 后记忆应归属的 type。根据合并后内容本质判断。
- merged_priority：merge/update 后的新优先级（0-100 整数，merge/update 时必填）。合并后信息更完整、更确定，通常应**酌情提升** priority（例如两条 priority 70 的记忆合并后可提升到 80）。参考标准：80-100（核心特质/重要事件），60-79（一般偏好/普通活动），<60（次要信息）。
- merged_timestamps：合并后的时间戳数组。收集新记忆 + 所有被合并旧记忆的时间戳，去重排序。
```

## L2-1. 概述

L2 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L1 抽取并落库的结构化记忆记录
- **输出**:结构化的**场景叙事文档**,跨会话累积,既是召回时让 AI"记得"情境的载体,也是 L3 画像生成的重要素材

L2 和 L1 最大的区别在"怎么抽":L1 是**一次 LLM 调用输出结构化 JSON**;L2 则是**让 LLM 像一个受限 agent 一样,在沙箱里用读/写/改工具自主整合场景文件**——新增、更新、合并、删除都让 LLM 自己决定,工程侧只做确定性的收尾(清理、重建索引、更新导航)。

### L2-1.1 L2 的数据来源

L2 的输入就是 **L1 落库的结构化记忆记录**,不是 L0 原始对话。

**L1 记忆存在哪里、L2 怎么读**

- L1 抽出的原子记忆记录在记忆库的 L1 记录表,L2 按**游标增量**拉取——游标记录"上次 L2 抽到哪条",即上次处理完成时最新一条 L1 记录的更新时间;每次只读游标之后新产生或更新的记录,保证每条记忆只被聚合一次
- 记忆库不可用时**直接报错,不静默降级**——让上层明确知道发生了什么
- 没有新记录时直接跳过、不推进游标;冷启动第一次被跳过时不记录运行时间,避免挡住下一次触发

**一条 L1 记录长什么样**

L1 落库的是一条结构化的原子记忆记录。仍以文档 4.3 的 Billing 超时排查为例,一条 L1 记录大致如下(节选核心字段):

```json
{
  "id": "m_1755571800000_a1b2c3d4",
  "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
  "type": "episodic",
  "priority": 85,
  "scene_name": "我（AI）在和用户王小明排查 Billing API 超时",
  "source_message_ids": ["msg_c", "msg_d"],
  "metadata": {
    "activity_start_time": "2026-08-18T02:00:00.000Z",
    "activity_end_time": "2026-08-18T02:10:00.000Z"
  },
  "timestamps": ["2026-08-18T02:10:00.000Z"],
  "createdAt": "2026-08-18T02:10:00.000Z",
  "updatedAt": "2026-08-18T02:10:00.000Z",
  "version": 1,
  "teamId": "team_xxx",
  "userId": "user_xxx",
  "agentId": "agent_xxx"
}
```

要点:

- **content / type / priority / scene_name**:L1 抽取的核心字段。`type` 按模式取 persona/episodic/instruction(对话)或 work_fact/work_task/work_method/work_artifact(团队);`metadata` 存类型相关附加信息(episodic 为活动时间区间)
- **id / timestamps / version**:id 全局唯一;`timestamps` 记录时间戳轨迹(合并时取并集);`version` 单调递增(update/merge 后 +1)
- **teamId / userId / agentId / sessionId**:隔离与归属维度,其中 L2 按"teamId + agentId"分组(见下文)
- **createdAt / updatedAt**:落库时间,`updatedAt` 正是 L2 游标推进的依据

> 落到检索库的 L1 表会把上述字段平铺成列(record_id/content/type/priority/…/metadata_json),`source_message_ids` 只留在产出文档里、检索库不存;且传给 L2 LLM 时只保留 content / created_at / id 三字段(见 2.2)。

**L2 读出来的记录怎么分组**

L2 属于**跨会话、跨用户的聚合层**:读出来的 L1 记录按"**teamId + agentId**"的隔离作用域分成组,每组独立做一次场景整合。这里刻意**忽略**用户、会话、任务这些维度(仅当 teamId 缺省时才退化为 userId 兜底)——同一 teamId + agentId 的记忆可以跨多个会话、多个用户持续累积。

**L1 与 L2 的游标关系**

L2 的游标落在 L1 记录上,但 L2 处理的是"teamId + agentId"聚合后的记录集合,和 L1 的"按会话"是两套维度。只要 L1 持续产出新记忆,L2 的游标就会持续推进。

### L2-1.2 抽取时机

L2 抽取**不是固定定时任务**,由"L1 完成后级联 + 保底轮询 + 频率限制"三部分共同决定。

| # | 时机 | 触发方式 | 说明 |
|---|------|----------|------|
| ① | L1 完成后级联(主) | L1 抽取成功 → 为该作用域调度一个延迟计时器 | 默认延迟 10 秒;同一作用域的计时器"只提前不推迟",保证尽快聚合新记忆 |
| ② | 保底轮询(辅) | 上一次 L2 完成后,挂一个最大间隔计时器 | 默认 3600 秒兜底,保证一直有新记忆但没被级联到的场景也能被聚合 |
| ③ | 最小间隔保护(约束) | L2 触发时间的下限 | 同一作用域两次 L2 至少间隔默认 900 秒,防止连续 L1 把 L2 触发打爆 |

边界情况:

- **冷会话**:超过 24 小时未活跃的会话,保底轮询会跳过,不再空转
- **downward-only 定时器**:计时器只允许提前、不允许推迟——新消息来了尽快抽,但也不违背最小间隔
- **无新数据**:轮询到点后发现没有新 L1 记录,直接跳过且不更新运行时间

**两种部署模式的等价逻辑**:单进程内嵌模式与多副本服务模式的调度器实现不同,但语义一致——L1 完成后通过计时器级联 L2,外加最大间隔保底轮询;服务模式由中心化的任务扫描器消费到期计时器,并用分布式锁保证多副本不会重复执行同一个 L2 任务。

一句话:L1 一完成就延迟抽(主),长时间没触发就兜底抽(辅),最小间隔和冷会话做护栏。

### L2-1.3 正常会话与 L2 的关系

会话走**主路**,L2 走**支路**——两者**互不阻塞,但严格依赖,最终闭环**。

```
正常会话(主路):  会话进来 → 消息落库 L0 → L1 抽取原子记忆 → 会话继续正常进行

记忆抽取(支路):  L1 完成后级联触发 L2 → 按游标读新 L1 记录 → 聚合进场景
```

为什么不是"互不相干",有三个耦合点:

1. **数据上游**:L2 吃的就是 L1 抽出的记忆——没有 L1,就没有 L2 可聚合
2. **启动通知**:L1 每完成一批抽取,都会给调度器记一笔,据此安排 L2 何时跑(延迟触发或保底轮询)
3. **反馈回路**:L2 聚合出的场景通过"场景导航"被召回、注入 AI 的上下文,让 AI"记得"跨会话聊过哪些主题、做过哪些事

所以完整链路其实是一个循环:

```
会话 → L0 存档 → L1 原子记忆 → L2 场景聚合 → 下次会话召回(含场景导航) → 会话
```

一句话:**主路负责实时对话;L2 是 L1 之后的二级聚合支路,把碎片化原子记忆沉淀成可复用的场景;场景最终回到会话里发挥作用,并成为 L3 画像的重要素材**。

## L2-2. 核心处理流程

L2 的处理分两大段:**先"增量读取 + LLM agent 场景整合",再"确定性收尾 + 落地级联"**。先从整体看一遍流程,再分节详解。

### L2-2.1 完整流程总览

从一批新增 L1 记忆,到场景真正沉淀,一次 L2 处理走完下面九步。全流程只有一处调用 LLM(第 ⑤ 步),而且是"agent 式"调用——LLM 通过读/写/改工具在沙箱里自主完成场景文件的增改合并。

```
L1 新增记忆记录
  → ① 增量读取:按游标只读上次之后更新的记录;无新记录直接跳过
  → ② 作用域分组:按"teamId+agentId"拆组,每组独立处理
  → ③ 备份:本地模式把整个场景目录快照备份(服务模式交给存储后端)
  → ④ 读索引 + 组提示词:新记忆列表 + 已有场景摘要 + 当前时间,外加场景数量预警
  → ⑤ 一次 LLM agent 执行:沙箱内用读/写/改工具自主新增/更新/合并场景文件(失败从备份还原)
  → ⑥ 确定性收尾:清理软删/空/残留文件 → 规范化文件名 → 全量重建场景索引
  → ⑦ 更新导航:把场景导航追加到画像文件末尾;解析 LLM 的画像更新请求信号
  → ⑧ 落地收尾:单调修复处理计数 → 变化场景以画像形态同步进记忆库 → 写生成血缘日志
  → ⑨ 级联:推进 L3 画像调度
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 增量读取 | 只读新的 L1 记录 | 规则/存储 | 游标=上次完成时最新更新时间;无新记录跳过 |
| ② 作用域分组 | 拆组隔离 | 规则 | teamId+agentId 维度,刻意忽略用户/会话/任务 |
| ③ 备份 | 场景目录快照 | 存储 | 仅本地模式;服务模式由存储后端负责 |
| ④ 组提示词 | 拼输入 | 规则 | 三输入 + 数量预警 + 可读文件清单 |
| ⑤ 场景整合 | 增改合并场景文件 | LLM agent | 唯一一次 LLM;沙箱;自主决策 |
| ⑥ 确定性收尾 | 清理/规范化/重建索引 | 规则 | 索引只由工程侧写,LLM 不可见 |
| ⑦ 导航更新 | 画像追加导航 + 解析信号 | 规则 | 画像不存在/只剩导航时跳过 |
| ⑧ 落地 | 计数修复/同步/血缘 | 存储 | 计数单调取大,不整体覆盖 |
| ⑨ 级联 | 推进 L3 | 调度 | L3 由触发器按优先级二次判断 |

其中 LLM 只出现在第 ⑤ 步,其余环节全部确定性执行。工程侧在 LLM 之后做四件"收拾残局"的事(⑥⑦ 里),这是 L2 与 L1 的显著差异——L1 的 LLM 输出结构化 JSON 后基本直接落库,而 L2 的 LLM 在文件系统里自由操作,必须有一层规则来清理、校验、重建。

下面 2.2–2.8 按这九步的顺序展开详述。

### L2-2.2 增量读取与输入构造

L1 已按游标持续产出记忆,L2 **不处理全量历史**——每次只读"上次游标之后新增的那批记录",按作用域分组后送给整合器。

传给 LLM 的记忆**只保留文本内容**,不携带类型、优先级等 L1 结构字段——因为 L2 要让 LLM 自由整合,而不是按类型机械搬运。

一次 L2 处理的输入由三部分组成:

| 输入 | 内容 | 作用 |
|------|------|------|
| **新记忆列表** | 本次新增的 L1 记忆文本 | 唯一整合来源 |
| **已有场景摘要** | 当前所有场景文件的文件名、热度、摘要 | 供 LLM 判断该更新哪个场景;顶部带"当前场景总数 n/上限"计数 |
| **当前时间戳** | 生成时间 | 供 LLM 填写场景文件头里的创建/更新时间 |

另外还附一份"**已有场景文件清单**"——LLM 只能读取清单里的文件,不能猜测或编造不存在的文件名。

一次 L2 处理的输入实例(仍以 Billing 超时排查为例,与 4.3 渲染示例同源):

**① 新记忆列表**(本次增量读取的 L1 记忆,只保留文本,JSON 数组):

```json
[
  {
    "id": "mem_1",
    "content": "用户(王小明)在 Billing API 超时排查中发现,超时集中在 api-gateway",
    "created_at": "2026-08-18T02:10:00.000Z"
  },
  {
    "id": "mem_2",
    "content": "用户(王小明)决定将 api-gateway 的超时告警阈值调整为 2 秒",
    "created_at": "2026-08-18T02:15:00.000Z"
  }
]
```

**② 已有场景摘要**(顶部带"当前场景总数 n/上限",下面按场景列出文件名/热度/更新/摘要):

```text
**当前场景总数:2 / 15**

### 技术研究-Billing超时排查.md
**热度**: 5 | **更新**: 2026-08-17T10:00:00.000Z
**summary**: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

### 日常生活-日本旅行计划.md
**热度**: 2 | **更新**: 2026-07-01T08:00:00.000Z
**summary**: 计划五月去日本旅行,偏好京都路线
```

**③ 当前时间戳**:

```text
2026-08-18T02:16:00.000Z
```

**附:已有场景文件清单**(LLM 只能 read 清单里的文件,不能猜测或编造别的文件名):

```text
- `技术研究-Billing超时排查.md`
- `日常生活-日本旅行计划.md`
```

> 以上是送入 LLM 的输入;完整渲染 Prompt 见 4.3。

### L2-2.3 场景数量上限与分级预警

L2 对场景总数有**硬性上限(默认 15 个)**,通过提示词里的**三级预警**约束 LLM:

| 预警级别 | 触发条件 | 强制要求 |
|----------|----------|----------|
| 红色 | 场景数 ≥ 上限 | **必须先 MERGE**:把最相似的 2-4 个场景合并为 1 个并删除旧文件,直到数量 < 上限,再处理新记忆 |
| 橙色 | 场景数 = 上限 - 1 | **只能 UPDATE,不能 CREATE** 新场景 |
| 黄色 | 场景数接近上限 | 建议优先 UPDATE 或主动 MERGE 相似场景 |

工程侧**不强制裁剪**文件数量——上限靠 LLM 自觉遵守,工程侧只负责事后清理 LLM 留下的脏文件(见 2.6)。如果 LLM 违反规则,数量可能会暂时超限,但下一轮的红/橙预警会再次要求它合并。

### L2-2.4 LLM agent 执行

这是 L2 唯一一次 LLM 调用,也是与 L1 架构差异最大的地方。LLM 不是"输出一段 JSON 就结束",而是被当作一个**受限的文件操作 agent**:

- **沙箱隔离**:LLM 的工作目录被钉在场景文件目录,索引、检查点、画像等系统文件对 LLM **物理不可见**,它改不了自己看不见的东西
- **工具白名单**:只开放**读、写、改**三个文件工具,没有命令执行等越权能力
- **删除的唯一方式**:把文件内容写成 `[DELETED]` 标记(写空字符串会被工具拒绝),由工程侧随后真正清理
- **服务模式**:LLM 的文件工具走对象存储,而不是本地文件系统
- **失败恢复**:LLM 执行异常时,本地模式从备份把整个场景目录**整体还原**,防止 LLM 半途写入或清空沙箱泄漏到下一轮召回;恢复失败只记日志,绝不掩盖原始错误

一句话:给 LLM 一个"只装了三个文件工具的沙箱工作台",让它自己决定怎么整合场景。

### L2-2.5 动作模型与热度管理

LLM 在沙箱里对场景文件可以做四类动作,按**优先级**排列:

| 动作 | 含义 | 触发条件 / 约束 |
|------|------|-----------------|
| **UPDATE(更新)** | 锁定已有场景,整体重写或局部修改 | **首选策略**;按摘要/文件名相似性锁定目标 |
| **MERGE(合并)** | 把 2-4 个相似场景合并成 1 个概括性更强的 | 强制(超限时)或主动(同一条叙事弧线);**合并后必须删除旧文件** |
| **CREATE(新建)** | 创建全新场景文件 | **最后手段**;须先读 ≥2 个最相似场景验证无法融入;每批最多新增 1 个 |
| **删除(软删)** | 标记文件待清理 | 唯一方式:把文件内容写成 `[DELETED]` 标记 |

几个关键约束:

- **默认策略是 UPDATE 不是 CREATE**:犹豫时选 UPDATE,避免场景无限膨胀
- **MERGE 必须删旧文件**:被合并的旧文件必须写 `[DELETED]` 标记,否则文件总数不减、合并无效(打 `[ARCHIVE]` 之类的标记不算删除)
- **热度管理(重要度)**:新建 heat=1;更新 heat=旧+1;合并 heat=所有相关场景热度之和+1。热度是"被记忆命中的累计次数",也是召回侧导航排序的依据

### L2-2.6 工程侧确定性收尾

LLM 执行完之后,工程侧做四件**确定性**的事(都是规则,不再调 LLM):

1. **软删清理**:扫描场景目录,把内容为 `[DELETED]` 标记、空白,以及"只有文件头没有正文"的残留文件真正删除。后者是 LLM 合并时没删干净旧文件的产物
2. **文件名规范化**:LLM 偶发产出带空格/括号等非法字符的文件名,会破坏下游解析。在重建索引前统一重命名(空格→短横线、去括号等),保证后续所有读取方只见规范名
3. **全量重建索引**:重扫剩余场景文件,从每个文件的文件头解析出摘要/热度/时间,重建场景索引。索引**只由工程侧维护**,LLM 在沙箱外看不到
4. **更新导航 + 画像信号**:
   - 读最新索引生成"场景导航",剥离画像里旧的导航后追加重写;如果画像文件还不存在、或画像只剩导航没有正文,则跳过,等画像生成
   - 解析 LLM 文本输出里的 `[PERSONA_UPDATE_REQUEST]` 标记(重大价值观转变、跨场景突破性洞察时 LLM 会主动输出),写入检查点,供后续 L3 画像刷新优先触发

### L2-2.7 落地写入

一次 L2 处理的产出会写到多个目标,各目标**独立容错,失败互不阻塞**:

| 目标 | 内容 | 由谁写 |
|------|------|--------|
| **场景文件** | 场景叙事正文 + 文件头(创建/更新时间、摘要、热度) | LLM 工具 |
| **场景索引** | 所有场景的文件名/摘要/热度/时间的清单 | 工程侧 |
| **画像文件** | 画像正文 + 追加的场景导航 | 工程侧 |
| **检查点** | 处理计数、画像更新请求 | 工程侧 |
| **记忆库镜像** | 变化的场景以"画像"形态同步进记忆库(只做镜像,不建向量检索) | 工程侧 |
| **血缘日志** | 本次场景产出由哪批 L1 记忆生成 | 工程侧 |

其中"记忆库镜像"要说明一点:L2 场景**本体不直接进向量检索**——记忆库里的 L1 记录承担检索职责,L2/L3 的画像只是以"内容镜像"的形式同步过去,用于多副本共享与恢复。

### L2-2.8 级联收尾

L2 任务完成后做两件事:

- **单调修复计数**:在并发临界区内重读检查点,只对"处理计数"做取大,绝不整体覆盖——否则会抹掉并发节点推进的 L1 游标,导致重复抽取
- **推进 L3(画像)调度**:触发下一层画像生成。但 L3 是否真正执行由画像触发器按优先级**二次判断**(主动请求、冷启动、记忆阈值等),L2 只是发出请求

## L2-3. 召回:场景记忆怎么回到对话里

第 2 章讲的是"入"——把 L1 记忆聚合成场景;召回讲的是"出"——把场景信息拿回对话,让 AI"记得"跨会话累积的情境。两条线合起来就是 1.3 里说的闭环。

### L2-3.1 时机:每轮对话前预取

与 L1 完全一致:AI 处理每一轮对话之前,宿主先调一次召回接口,把三层记忆(相关记忆、场景导航、画像)预取好拼进上下文,再让 LLM 开始干活。它是同步的、非关键路径的——召回失败不阻塞对话。

### L2-3.2 一次召回同时做三件事

1. **L1 记忆检索**(核心):拿当前用户消息当查询,去记忆库搜相关原子记忆
2. **L2 场景导航**:读场景索引,列出有哪些历史情境,供 AI 判断跟当前话题的关联
3. **L3 画像注入**:读画像文件,把"这个人是谁、有什么偏好"塞进上下文

其中 L2 的部分就是"场景导航"。

### L2-3.3 场景导航怎么生成与注入

- **全量注入、不过滤**:场景导航**不按当前用户输入检索或过滤**,一次把全部历史场景列出来,由 LLM 自行判断与当前话题的关联——与 L1 记忆"按相似度检索 top-N"是完全不同的策略
- **按热度降序排序**:每个场景一条,包含**路径、热度、摘要**
- **热度分档**:≥50 单火,≥100 双火,≥200 三火,≥500 四火,≥1000 五火——让 AI 一眼看出哪些场景最重要
- **使用说明**:导航底部附带提示,告诉 AI 需要细节时用什么工具按路径读完整场景

一个场景导航的片段示例(画像文件末尾追加的稳定内容):

```text
---
## 🗺️ Scene Navigation (Scene Index)
*以下是当前场景记忆的索引,可根据需要 read 读取详细内容。*

### Path: {数据目录}/scene_blocks/技术研究-Billing超时排查.md
**热度**: 5 | **更新**: 2026-08-17T10:00:00.000Z
Summary: 排查 Billing API 网关超时,定位到 api-gateway 为瓶颈

### Path: {数据目录}/scene_blocks/日常生活-日本旅行计划.md
**热度**: 2 | **更新**: 2026-07-01T08:00:00.000Z
Summary: 计划五月去日本旅行,偏好京都路线

📌 使用说明:
- Path 是场景块的路径,可直接使用 read 工具读取完整内容
- 热度:该场景被记忆命中的累计次数,越高越重要
- Summary:场景的核心要点摘要
```

### L2-3.4 注入方式:拆成两半,缓存友好

和 L1 的召回一样,召回结果被刻意拆成两部分:

- **动态部分**(每轮都变):召回的 L1 相关记忆,拼到**用户消息前缀**
- **稳定部分**(基本不变):画像 + 场景导航 + 一份"记忆工具使用指南",拼到**系统提示词末尾**

这样拆的原因:稳定部分能命中模型提供商的**提示词缓存**——不会被每轮变化的记忆打爆缓存,省 token 省成本。场景导航尤其如此:只要 L2 没有新增/合并/删除场景,这段内容字节级不变,一直命中缓存;一旦场景索引变化(新场景、热度更新、场景合并),导航才会跟着更新。

### L2-3.5 控制与兜底

- **渐进式披露**:导航**只给路径、热度、摘要,不塞全文**。AI 需要某个场景的完整画像、事件经过或阶段结论时,才按路径主动读取完整场景文件——省 token,也避免上下文被不相关的长叙事占满
- **主动检索兜底**:注入不够用时,AI 可以主动调工具——"记忆搜索"搜 L1、"对话搜索"搜 L0 原文、"读场景文件"进具体情境;其中两个搜索工具**每轮合计限 3 次**,防止 AI 无休止地搜

### L2-3.6 一句话总结

每轮 AI 开口前,宿主把三层记忆预取好:相关原子记忆动态拼接,**场景导航全量注入**(只给路径/热度/摘要,按需深入),画像进稳定区走缓存;注入不够时 AI 还能主动读场景文件,但搜索限次。

### ⚠️ 阶段 0:强制检查场景总数(必须先执行)

1. **统计当前场景总数**:查看 "Existing Scene Blocks Summary" 顶部标注的当前场景总数

**合并优先级**(当需要合并时,按以下顺序选择):
1. **主题高度重叠**:如"Python后端开发"和"Go后端开发" → 合并为"后端开发技术栈"

**核心原则:默认策略是 UPDATE,不是 CREATE。** 当犹豫于 UPDATE 和 CREATE 之间时,选择 UPDATE。

1. **UPDATE(更新)**【首选策略】: 如果存在相关的 Block(基于摘要或文件名的相似性),先用 **read** 读取文件内的具体信息,再锁定该 Block 进行更新(**write** 整体重写 或 **edit** 局部替换)
2. **MERGE(合并)**:

   - **强制合并**:当前 Block 总数 **≥ ${maxScenes}** 时,必须先将多个相似记忆合并

3. **CREATE(新建)**【最后手段】:

   - **CREATE 前的强制验证**:必须先用 **read** 检查至少 2 个最相似的现有场景,确认新记忆确实无法融入后才能 CREATE。跳过验证直接 CREATE 是被禁止的

   - **每次批处理最多新增 1 个场景**

2. **read 只能读取用户消息中"已有场景文件清单"列出的文件**,禁止猜测或编造不在清单中的文件名。
3. **创建新场景文件时**,使用 **write** 工具。参数:`path`=文件名, `content`=完整内容。
4. **局部更新场景文件**:使用 **edit** 工具。参数:`path`=文件名, `edits`=[{`oldText`: 旧内容, `newText`: 新内容}]。对于大范围重写或结构性变更,建议使用 **read** + **write** 整体重写。
5. **场景索引和系统配置由工程系统自动维护**,你只需专注于操作 `.md` 场景文件。
6. **删除文件的唯一方式**:使用 **write** 工具将文件内容写为 `[DELETED]` 标记(`path`=文件名, `content`=`[DELETED]`)。系统会自动清理带有此标记的文件。**禁止**写入空字符串。**禁止**用 `[ARCHIVE]`、`[CONSOLIDATED]` 等其他标记替代删除。
7. **禁止创建报告/整合/汇总类文件**。你的输出必须是有意义的工作场景文件,如 `Agent-Memory-群聊抽取.md`、`后端接口-查询能力.md`、`团队记忆-SOP与禁忌.md`。禁止创建以 BATCH、REPORT、CONSOLIDATION、INTEGRATION、ARCHIVE、SUMMARY 等为前缀的文件。

## 工作流与逻辑 (Workflow & Logic)

在生成输出之前,你必须执行以下过程:

### ⚠️ 阶段 0:强制检查场景总数(必须先执行)

**在处理任何记忆之前,你必须:**

1. **统计当前场景总数**:查看 "Existing Scene Blocks Summary" 顶部标注的当前场景总数。
2. **最终目标**:处理完成后,目录中的场景文件数量必须 **严格小于 ${maxScenes}**。
3. **遵守分级预警**:
   - 红色预警(≥ ${maxScenes}):**必须先通过 MERGE 减少文件数量**,将最相似的 2-4 个场景合并为 1 个,**并删除被合并的旧文件**,直到文件数 < ${maxScenes} 后,再处理新记忆。
   - 橙色预警(= ${maxScenes - 1}):**只能 UPDATE 现有场景,不能 CREATE 新场景**。
   - 黄色预警(接近 ${maxScenes}):**优先 UPDATE 或主动 MERGE 相似场景**。

**合并优先级**:
1. **工作对象高度重叠**:如"群聊记忆抽取"和"团队共享记忆抽取" → 合并为"团队共享记忆-抽取策略"
2. **同一项目链路**:如"L1 Prompt 设计"和"L1 冲突检测" → 合并为"团队版-Agent-Memory-L1管线"
3. **同一方法体系**:如"Prompt 编写原则"和"记忆抽取禁忌" → 合并为"团队记忆-SOP与禁忌"
4. **热度最低场景**:如果没有明显重叠,优先合并或删除 heat 最低的 2-3 个场景

---

### 阶段 1:分析与分类

分析新增工作记忆。判断它们揭示了什么可复用方法:

- SOP / 流程 / 协作模式:以后类似任务应该怎么执行
- 判断逻辑 / 决策标准 / 优先级:团队为什么这样取舍
- 禁忌 / 反模式 / 风险边界:哪些做法不应再出现
- 原则 / 约束 / 标准:哪些规则应长期遵守
- 经验 / 启发 / 复用思路:哪些方法可跨任务复用

注意:项目事实、任务状态和资产信息作为方法论的来源和适用条件保留,但提取重心是方法而不是流水账。

识别这些记忆之间的关系:
- 方法 → 来源事实 → 适用条件
- 问题 → 分析 → 判断逻辑 → 决策标准
- 规则 → 禁忌 → 边界条件
- 经验 → 复用场景 → 注意事项

---

### 阶段 2:检索与策略选择

将新记忆与 Existing Scene Blocks Summary 进行比对。
需要时使用 **read** 工具读取完整场景文件内容。

**只能读取用户消息中"已有场景文件清单"列出的文件,禁止猜测其他文件路径。**

**核心原则:默认策略是 UPDATE,不是 CREATE。** 当犹豫于 UPDATE 和 CREATE 之间时,选择 UPDATE。

策略选择(按优先级排序):

1. **UPDATE(更新)【首选策略】**
   - 如果存在相关 Block,先用 **read** 读取文件内容,再锁定该 Block 更新。
   - 适合:同一项目、模块、任务、方法、资产的补充或状态变化。
   - 可使用 **write** 整体重写,或 **edit** 局部替换。

2. **MERGE(合并)**
   - 合并后的新 block 应该是概括性更强的工作场景,包含多个相似场景。
   - **强制合并**:当前 Block 总数 **≥ ${maxScenes}** 时,必须先将多个相似场景合并。
   - **主动合并**:即使未达上限,如果两个 Block 属于同一项目链路、同一工作流或同一方法体系,也应合并以增加深度。
   - **⚠️ 合并后必须删除旧文件**:被合并的旧场景文件必须通过 **write** 写入 `[DELETED]` 标记。

3. **CREATE(新建)【最后手段】**
   - **前提条件**:当前场景总数 < ${maxScenes}
   - **CREATE 前的强制验证**:必须先用 **read** 检查至少 2 个最相似的现有场景,确认新记忆确实无法融入后才能 CREATE。
   - 如果话题是全新的且与现有内容区分度高,可以创建新 Block。
   - **每次批处理最多新增 1 个场景**。

---

### 阶段 3:撰写与合成(核心任务)

深度整合:严禁简单追加。你必须结合已有内容,将新信息自然融合进工作方法场景文档。

方法论提炼:每个 Scene Block 的核心输出是可复用的工作方法。重点写:
- **SOP**:流程步骤、执行顺序、协作方式,以及每步的原因
- **判断逻辑**:决策标准、优先级规则、评价口径、取舍原因
- **禁忌**:反模式、边界条件、失败模式和正确替代做法
- **原则**:长期遵守的约束和标准
- **经验**:可被 Agent 和团队复用的方法和启发

事实和状态只用于说明方法的来源和适用条件,不要堆砌历史细节。

冲突检测:如果新记忆与旧记忆相矛盾,将其记录在"演化记录"或"待确认问题"中,不要直接覆盖。

---

### 撰写准则(严格遵守)

1. 场景文件不是项目日报、聊天摘要或任务清单。核心内容是提炼方法。
2. 核心章节应以连贯段落为主,必要时可用短列表表达 SOP 步骤、禁忌或待确认事项。
3. 每个场景文件应围绕一个清晰的工作方法体系,例如某个 SOP、判断逻辑、禁忌集合或可复用经验。
4. 不写个人画像,不推断个人性格、偏好或私人状态。
5. 允许记录工作角色、owner、reviewer、decision maker,但只能服务于说明方法的适用条件。
6. 每个 md 控制在 1500 字符内,优先保留可复用、可执行的方法论信息。

### 热度管理 (Heat Management)

- 新建 Block: heat: 1
- 更新 Block: heat: 旧heat + 1
- 合并 Block: heat: sum(所有相关 block 的 heat) + 1

## L3-0. 为什么设计 L1/L2/L3 三层记忆

在深入 L3 之前,先回答一个更根本的问题:为什么要设计 L1、L2、L3 三层记忆?因为单层记忆解决不了"上下文有边界、检索会失手、事实会过时"这三个并存的问题,分层是对三个真问题的逐层回应。

### L3-0.1 一句话哲学

README_CN 的原话最能概括动机:

> 不追求"存下所有东西",而是解决三个问题:**什么值得留下、谁可以使用、下一次怎样少拿但拿对。**

核心矛盾是:**记忆存太多 → 上下文被占满、召回噪声大;存太少 → 关键信息丢、检索不到**。分层就是在这条"从原始到凝练"的频谱上逐级沉淀,每一层解决一层矛盾。

### L3-0.2 逐层回答"为什么多一层"

```
L0 对话记录(原始)  →  L1 原子(结构化)  →  L2 场景(情景)  →  L3 画像(语义)
  核对原话/时间      精确召回事实       快速恢复情境       进入用户/团队语境
```

- **L0 → L1:解决"什么值得留下"**。L0 是全量原文,太吵。L1 做严格质量门("宁缺毋滥""记忆必须跳出当前对话依然成立"),把对话提炼成**单条结构化事实碎片**(persona / episodic / instruction)。但碎片有两个天生缺陷:会**无限累积、互相矛盾**;召回**依赖检索措辞**——top-N 检索偏一次,关键事实就丢了。
- **L1 → L2:解决"碎片凑不成全景"**。L2 把碎片原子记忆按"团队+agent"聚合成**跨会话的连贯场景叙事**(不是清单,是文档)。它的出现是为了补 L1 的召回弱点:场景导航**全量注入**系统提示词末尾,用"几行摘要的冗余换召回可靠性",避免一次检索偏差丢掉整个情境。这就是 README 说的分层权衡:"平时用 L2/L3 快速进入语境,需要具体事实时再回到 L1/L0。"
- **L2 → L3:解决"场景是情境,不是人"**。L2 的场景再连贯也是"某段时间在干嘛",不是"这个人/这支团队整体是谁"。L1 虽有 persona 型记忆,但它是单条原子事实,无限累积、可能互相矛盾。L3 读 L2 的场景叙事做**综合分析**,产出一份**稳定、自洽、有界**的身份文档(核心原型 + 兴趣图谱 + 交互协议 + 认知内核),有 2000 字符硬上限——把"无限的事实"压缩成"永远在场的身份"。

### L3-0.3 为什么是三层而非一层

关键在于三层**形态不同、召回方式不同、无法互相替代**:

| 层 | 形态 | 召回方式 | 特点 |
|----|------|----------|------|
| L1 | 事实碎片 | 向量/关键词 **top-N** 检索 | 精确、可执行,但依赖检索措辞 |
| L2 | 场景叙事 | **整份**导航注入 | 可靠、有全景,但逐场景累积会膨胀 |
| L3 | 身份画像 | **整份**注入系统提示词末尾 | 稳定、可缓存、有界,但不含细节 |

最关键的证据是**召回侧的分工**:L1 动态拼到用户消息前缀(随问题变),L2 导航 + L3 画像拼到系统提示词末尾(基本不变、命中提示词缓存)。如果只有 L1,缓存友好和精确召回只能二选一;如果只有 L3,细节和情境全没了。三层正好覆盖"精确事实 / 连贯情境 / 长期身份"三个不同粒度的需求。

### L3-0.4 一句话总结

**上下文有边界、检索会失手、事实会过时**——一层记忆做不到面面俱到。L1 用检索换精确,L2 用冗余换可靠,L3 用压缩换稳定,三层互补构成一条从"原始对话"到"可复用认知"的沉淀链路。

## L3-1. 概述

L3 在四层记忆模型中的位置:

```
L0 对话记录(原始)  →  L1 原子记忆(结构化)  →  L2 场景记忆(情景)  →  L3 画像记忆(语义)
```

- **输入**:L2 生成的场景块与场景索引(**不是 L1 记忆**)
- **输出**:一份凝练、稳定、有界的"画像"文档,回答"这个人是谁、喜欢什么、该怎么服务"
- **形态**:同一份文件,内容形态由提示词模式决定——对话模式下是**个人画像**(Persona Architect,四层深度扫描);团队工作模式下是**团队 Operating Doctrine**(可复用工作原则)
- **注入**:整份读入,包在"用户画像"标签里,拼到**系统提示词末尾**(稳定部分,缓存友好)

一句话:L1 给"和当前问题相关的事实",L2 给"进行中的情境全景",L3 给"这个用户/这支团队整体是谁"——一份稳定注入、永远在场的身份文档。

### L3-1.1 L3 的数据来源

L3 的输入是 **L2 的产出**,不是 L1 的原子记忆。这是理解 L3 的关键:**L1 已经有 persona 类型的记忆提取了,为什么还要 L3?** 因为两者吃的原料不同、产出的层级不同:

- **L1 的 persona 记忆**是单条原子事实("用户喜欢日本料理"),从逐轮对话里直接抽取,会无限累积、可能互相矛盾
- **L3 画像**读的是 L2 拼好的**连贯场景叙事**(跨会话、按"团队+agent"累积),从中做**综合分析**,推断出"这个人整体是谁"(核心原型、兴趣图谱、交互协议、认知内核),输出一份**稳定、自洽、有界**的身份文档

**读取方式是增量的**:每次生成只读"上次画像之后更新过的场景"完整原文(含元信息与正文),不是把所有场景重读一遍;场景索引提供了"哪些场景更新了"的判断依据。

**隔离范围是跨会话的**:画像按"团队 + agent"隔离累积,刻意忽略用户/会话/任务维度——横跨几十个会话沉淀的是"这一位用户"或"这一支团队"的长期画像,而不是某次对话的临时状态。

### L3-1.2 抽取时机

L3 不是独立定时任务,而是**由 L2 级联触发的**:每次 L2 场景抽取完成后才轮到评估 L3;L2 首次被跳过时不触发。真正"要不要生成"由五个优先级依次判断,命中任一即触发:

| 优先级 | 触发条件 | 典型来源 |
|--------|----------|----------|
| P1 主动请求 | 场景抽取时 LLM 输出了"请求立即更新画像"的带外信号 | 场景抽取过程中发现重大变化,主动要求画像跟进 |
| P2 冷启动 | 已抽取过场景、但从未生成过画像、且有场景文件 | 首次积累出场景后 |
| P2.5 恢复 | 曾生成过画像、但画像文件正文丢失或为空(只剩导航) | 文件损坏 / 被误删,需要重建 |
| P3 首个场景 | 只完成过 1 次场景抽取、且画像之后有新记忆 | 首个场景块落盘 |
| P4 阈值 | 自上次画像以来新增的记忆数达到阈值(默认 50 条) | L1 持续抽取,记忆数累积到阈值 |

评估按优先级从高到低:先看 P1 主动请求,再看 P2 冷启动、P2.5 恢复、P3 首个场景,最后看 P4 阈值。

一句话:**平时靠阈值(P4)周期性沉淀画像;场景抽取中如有重大变化,可主动插队(P1);冷启动和文件损坏有专门兜底(P2 / P2.5 / P3)**。

**两种部署模式的级联差异**:独立模式在进程内"L2 完成后立即评估 L3",用全局互斥 + 待办标记去重,避免同时跑多个;服务模式走任务队列——L2 任务完成后直接入队一个 L3 任务,用分布式锁保证**同一 agent 的画像文件不并发写**。

### L3-1.3 与主会话、上下游的关系

L3 处于级联链的**末端**:`会话 → L0 存档 → L1 抽取 → L2 场景聚合 → L3 画像生成`。它只消费 L2 的产出,不直接碰 L0 对话、也不直接读 L1 记忆;画像的"真相源"是场景——场景不变,画像就不重算。

反馈闭环:**画像生成后进入稳定注入**,此后每一轮会话开始前,AI 都带着"这个人是谁"工作;画像什么时候更新?取决于 L2 什么时候产生了新场景变化。所以 L2 是 L3 的"上游时钟",L3 是这条记忆链路的"语义收口"。

## L3-2. 核心处理流程

L3 的处理逻辑非常"轻":**判定环节全是规则,生成环节一次 LLM 调用,收尾环节全是确定性操作**。先从整体看一遍流程,再分节详解。

### L3-2.1 完整流程总览

从 L2 完成,到画像真正落地,一次 L3 处理走完下面十一步。全流程只有一步调用 LLM(第 ⑧ 步),其余都是规则、文件操作或存储操作。

```
L2 完成
  → ① 触发判断:按五个优先级评估要不要生成(见 1.2)
  → ② 读检查点 + 读现有画像(剥掉导航,看有没有正文)
  → ③ 读场景索引,筛出自上次画像后更新过的场景
  → ④ 读变化场景的完整原文(含元信息)
  → ⑤ 定模式:首次(无画像)/ 增量(已有画像)
  → ⑥ 组装提示词(系统提示词 + 用户提示词)
  → ⑦ 备份旧画像
  → ⑧ 一次 LLM 调用:LLM 用文件工具直接把画像写进画像文件
  → ⑨ 读回 + 确定性后处理(剥导航、转义危险标签)
  → ⑩ 追加最新场景导航 + 写回
  → ⑪ 级联收尾:推进检查点 + 上报指标
```

各步骤的职责分工:

| 步骤 | 做什么 | 由谁完成 | 关键点 |
|------|--------|----------|--------|
| ① 触发判断 | 评估五优先级 | 规则 | 命中任一即生成;不命中则本次不跑 |
| ② 读现状 | 读检查点与现有画像 | 规则 | 画像正文是否为空决定后续模式 |
| ③ 筛变化场景 | 按时间筛选 | 规则 | 更新晚于上次画像时间的才算变化;日期不可解析按变化处理 |
| ④ 读场景原文 | 预加载完整内容 | 规则 | 变化场景的全文都喂给 LLM,供深度分析 |
| ⑤ 定模式 | 首次 / 增量 | 规则 | 由"有没有画像正文"自动决定 |
| ⑥ 组装提示词 | 拼系统 + 用户提示词 | 规则 | 可选追加自定义策略 |
| ⑦ 备份 | 备份旧画像 | 存储 | 默认保留 3 份;对象存储模式下跳过 |
| ⑧ 生成 | 一次 LLM 调用 | **LLM** | LLM 用文件工具直接写画像文件,沙箱限定数据目录 |
| ⑨ 后处理 | 剥导航、转义 | 规则 | 转义注入边界标签,防逃逸 |
| ⑩ 落地 | 追加导航、写回 | 存储 | 画像 = 正文 + 导航,一体落地 |
| ⑪ 收尾 | 推进检查点、上报 | 规则/存储 | 清主动请求信号、记录生成时间 |

按阶段读这张表:

- **① → ⑦ 准备**:纯规则 + 存储,判定要不要跑、把输入和备份准备好
- **⑧ 生成**:唯一一次 LLM 调用,LLM 以"文件代理"身份直接产出画像
- **⑨ → ⑪ 收尾**:确定性后处理、落地、推进检查点

下面 2.2–2.7 按这十一步的顺序展开详述。

### L3-2.2 增量读取与输入构造

L3 **不重读全部历史**,每次只处理"上次画像之后变化的部分":

- **读现有画像**:读画像文件,剥掉尾部场景导航,判断正文是否为空。有正文 → 后续走"增量";无正文 → 走"首次"
- **读场景索引**:拿到当前全部场景的清单(每个场景含文件名、摘要、热度、创建与更新时间)
- **筛变化场景**:逐个对比"场景最近更新时间"与"上次画像生成时间",更新晚于画像时间的就是变化场景;**任一日期无法解析时按"变化"处理**(保守,宁多不少)
- **读变化场景完整原文**:把每个变化场景的完整内容(含元信息与正文)原样读出来,预加载给 LLM

**一个重要的短路**:如果没有任何变化场景、但画像已经存在,本次直接跳过——所有场景都在上次画像时分析过了,没有必要重复生成。只有当"有变化场景"或"还没有画像"时才继续。

### L3-2.3 两种模式:首次与增量

模式由"有没有画像正文"**自动决定**,不是配置项:

- **首次生成**:没有旧画像。基于当前所有变化场景从零提炼,输出完整模板文档(核心原型 + 基本信息 + 长期偏好 + 四个章节)
- **增量更新**:已有旧画像。把旧画像全文 + 变化场景全文一起给 LLM,在旧版基础上迭代。增量时提示词会附一段**迭代决策指南**,让 LLM 自主判断该用哪种方式处理变化场景:

| 方式 | 含义 |
|------|------|
| 强化 | 新场景只是佐证已有洞察,压缩进原句或不改 |
| 补充 | 出现新维度,新增内容 |
| 修正 | 旧洞察与新场景矛盾,以新为准 |
| 重构 | 文档变散、变长、结构失衡,整体压缩重写 |
| 不改 | 新场景没有有用的新增内容 |

关键约束:**不要把每次变化都追加成新条目**。画像是"持续压缩、少而准"的文档,不是累积的流水账。

### L3-2.4 LLM agent 执行

这是 L3 唯一调用 LLM 的一步,也是画像生成的"创作环节"。LLM 不是返回文本等工程侧写入,而是**以"文件代理"身份,用文件工具直接把结果写进画像文件**:

- **文件工具约束**:必须用文件工具写入最终内容;**只准操作画像文件这一个文件**,禁止读取或写入任何其他文件(包括场景块目录、元数据目录等);首次/大幅重写用整体写入,局部修改用精确替换;现有画像全文已在用户消息里提供,无需再读
- **沙箱隔离**:工作目录限定在数据目录,工具被沙箱限制在画像文件范围内
- **写入内容必须纯粹**:只写最终画像文档,不夹带思考过程、分析步骤
- **四层深度扫描**(对话模式):基础锚点(确凿事实)→ 兴趣图谱(投入时间/金钱/注意力的事物,区分活跃度)→ 交互协议(沟通习惯、雷区、工作流偏好)→ 认知内核(决策逻辑、矛盾点、终极驱动力)。强调"叙事连贯性",禁止简单的罗列
- **输出模板**(对话模式):核心原型一句话 + 基本信息 + 长期偏好 + 四个章节(全景语境 / 生活的肌理 / 交互与认知协议 / 深层洞察与演变)
- **长度上限**:对话模式整份不超过 **2000 字符**;团队工作模式不超过 **1200 字**(持续压缩)
- **团队工作模式的提炼对象**:可复用 SOP / 长期原则 / 决策逻辑 / 边界 / 反模式 / Agent 规则;每条都要过"通用性、完整性、可执行性、稳定性、精炼性"五条过滤,任一不满足就不写
- **禁止事项**:
  - 禁止过长、禁止把每次变化追加成新条目
  - **禁止过度推测**:没提到的信息不要臆想,尤其是冷启动阶段,没有相关信息完全可以不填
  - **禁止使用非场景来源的信息**:画像内容必须且只能来自提供的场景数据,不许从工作区目录结构、文件路径、系统信息等技术元数据里提取任何个人信息
  - **禁止添加场景导航**:场景导航由工程自动追加,LLM 不许写

### L3-2.5 工程侧确定性后处理

LLM 写完后,工程侧做三道确定性处理:

1. **剥导航**:LLM 若在文件里写了场景导航区块(理论上被禁止,但不排除),先按分界标记剥掉,只留画像正文
2. **转义危险标签**:把正文里可能出现的"注入边界标签"(如用户画像、相关记忆、场景导航这类包裹标签的闭合写法)转义掉——防止画像内容被人为塞入恶意闭合标签、逃逸出注入区块(标签注入防御)。LLM 写完的正文只有"转义后"才算数
3. **空内容判定**:剥离导航并转义后,如果正文为空,本次视为失败,不落地

### L3-2.6 落地写入与备份

- **备份**:LLM 运行之前,先把旧画像备份一份(默认保留最近 3 份);这样即使 LLM 把画像写坏,也能找回上一版。对象存储模式下本地不做备份,恢复由存储后端快照负责
- **写回**:后处理完成后的最终内容(画像正文 + 最新场景导航)写回画像文件
- **失败判定**两条:
  - LLM 跑完但没有写画像文件(文件不存在)→ 生成失败
  - LLM 写了但内容是空的 → 生成失败
  - 只有这两条之外的正常路径才落地

画像文件的最终形态是"**正文 + 场景导航**"一体:正文是画像本身,导航是给 AI 用的"场景目录"。召回注入时再剥掉导航只取正文。

### L3-2.7 级联收尾

画像落地后做三件事:

- **推进检查点**:记录本次画像生成时间、当前已处理记忆总量快照;清零"自上次画像以来新增记忆计数"(P4 阈值据此重新累计);清除 P1 主动请求信号(消费掉这次插队)。**无论本次生成成功还是失败,检查点都会推进**——避免失败后对同一批数据反复重试
- **上报生成事件**:触发原因、生成模式(首次 / 增量)、新画像内容与长度、整体耗时
- **上报延迟与画像变化指标**:生成延迟、更新前后画像长度、**画像漂移比**(用行级差异衡量"这次到底改了多少",0 到 1 之间;没生成或前后都为空时不报)

## L3-3. 召回:画像怎么回到对话里

第 2 章讲的是"入"——把场景综合成画像写进文件;召回讲的是"出"——把画像拿回对话,让 AI 记得"这个人是谁"。画像在召回里属于**稳定注入**部分,与 L1 的动态召回分工明确。

### L3-3.1 时机:每轮对话前预取

和 L1 一样,AI 处理**每一条新的用户消息之前**,宿主先调一次召回接口,把三层记忆一起预取回来,再让 LLM 干活。画像作为三层之一被同步读取,失败或超时**不阻塞对话**(非关键路径)。

### L3-3.2 注入方式:整份稳定注入

画像的注入方式很直接:

- **整份读取**:读画像文件,剥掉尾部场景导航,只留正文
- **标签包裹**:用"用户画像"标签把正文包起来
- **位置固定**:拼到**系统提示词末尾**,与 L2 场景导航、记忆工具指南放在同一个稳定区

因为画像的"主要变量"不在召回侧(它不按当前用户输入检索或过滤),所以这段内容在两次画像更新之间**字节级不变**——正好命中模型提供商的提示词缓存,省 token 省成本。

### L3-3.3 与 L1、L2 的分工

一次召回同时拿三层,却放在两个不同的位置,分工如下:

| 部分 | 内容 | 位置 | 特点 |
|------|------|------|------|
| 动态部分 | L1 相关记忆 | **用户消息前缀** | 每轮随问题变化,检索 top-N |
| 稳定部分 | L2 场景导航 + **L3 画像** + 记忆工具指南 | **系统提示词末尾** | 基本不变,命中缓存 |

其中画像与场景导航都是**整份读取/生成**,不按输入做过滤——由 LLM 自行判断相关性。区别在于:场景导航是"目录"(一行一个场景,给 AI 索引),画像是"这个人是谁"(一份完整身份文档)。两者都是"兜底保证",不依赖当轮检索措辞。

**一个与 L1 不同的点:画像没有召回侧的长度裁剪**。L1 相关记忆有单条字符上限、总预算上限,超长截断;画像则整份注入、不做截断。画像的"有界"是靠生成侧保证的——对话模式 2000 字符、团队模式 1200 字的上限,让画像天生是一份精炼、自洽、塞得进上下文的文档。

### L3-3.4 控制与兜底

- **生成侧兜底**:画像内容有硬性长度上限与"只来自场景证据"的约束,保证注入的内容精简可信
- **召回侧兜底**:画像不是万能的,当注入的画像或导航不足以回答问题时,AI 可以主动调工具深入——读场景文件进具体情境、搜 L1 结构化记忆、搜 L0 原文对话(搜索工具每轮合计限 3 次,防止无休止地搜)

### L3-3.5 一句话总结

每轮 AI 开口前,宿主把三层记忆预取好拼进上下文:**画像(L3)整份注入系统提示词末尾,稳定、可缓存;L1 相关记忆动态拼到用户消息前缀;L2 场景导航同区给出目录**。画像更新靠 L2 场景变化驱动,注入的内容永远是有界、精简、基于场景证据的综合身份判断。
