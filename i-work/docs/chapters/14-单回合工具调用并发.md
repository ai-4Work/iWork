# 单回合工具调用并发（优化后）

> 本文是《单回合工具调用并发》第 9 节优化方案的**独立整理版**，聚焦优化落地后的设计：**分段调度**。优化前的现状机制（per-采样轮读写锁闸门、FuturesOrdered 并发队列、`parallel_execution` 等）见原文档第 1–8 节，本文不重复，只讲"优化后"。
>
> 叙事顺序：**先分析有哪些工具、这些工具的特点（第 1 节）；再讲整体逻辑（第 2 节）**。
>
> 本文讲两个层面：**§1–§2 是单个 agent 一个 turn 内**的工具调度（分段调度）；**§3 是多个 agent 并发**时跨 agent 的读写互斥。两层正交，各自解决各自的问题。
>
> **落地情况**：§1–§2 **已落地**（服务端 `server/tools/scheduling.py` + `query_loop._run_segments`；读 / 写名单落在 `server/scheduling.yaml`，改名单不用动代码；客户端按 `request_id` 各建一张卡、确认/跳过按钮认准自己那张）。§3 跨 agent 读写互斥**未实现**。

## 1. 工具有哪些：清单与特点

### 1.1 工具清单

| 工具 | 类型 | 角色 |
|---|---|---|
| `glob` | 内置 | 文件模式匹配，只读探索 |
| `grep` | 内置 | 内容搜索，只读 |
| `read_file` | 内置 | 读文件，只读 |
| `write_file` | 内置 | 写文件 |
| `edit_file` | 内置 | 编辑文件 |
| `bash` | 内置 | 执行兜底，读和写都靠它 |
| `skill` | 扩展 | 加载 skill 指令集 |
| `task` | 服务端（团队 lead 注入）| 委派子任务给专家子 agent |
| MCP 工具 | MCP | 按需接入外部服务器工具（如百度搜索 MCP）|
| skill 脚本 | 非工具（本质 `bash`）| 由模型经 `bash` 执行，不自动跑 |

### 1.2 工具的特点（读 / 写判定）

调度依赖对每个工具"读 / 写"的判定。按工具特点分类：

**① 只读内置 → 判"读"（可并行）**：`glob`/`grep`/`read_file`，语义就是读，直接进读段。`skill`（加载 SKILL.md 指令集）同为只读，一并进读段。

**② `write_file` / `edit_file` → 判"写"**：结构化写文件通道，参数自带 `path`——**自我声明**，所以能解析出文件路径。判"写"，且在写段内能靠文件路径做同文件排队、异文件并行。

**③ `bash` → 黑盒，靠读白名单**：路径运行时才定、读写分不清，解析不出文件路径，是**黑盒**。方案不解析命令拿路径，改用读白名单 `command_is_read_only` 判定。

一条命令判纯读 = **"程序在名单里" + "命令串没有写构造"**。

**名单落在 `server/scheduling.yaml`**（与 `permissions.yaml` 同套加载形状，`SchedulingPolicy` 编译成 frozen 集合）：`read_tools` / `command_tools` / `read_only_commands` / `write_flags` / `read_only_git_subcommands` / `git_query_flags` / `write_file_tools`。代码里只留机制——护栏字符与命令解析，不存名单副本。加一条只读命令 = 编辑 YAML + 重启。文件缺失即引擎启动报错；单个键缺失则该类别保守退化为"全判写"（不报错、只慢）。名单的等价性由 `tests/test_tool_scheduling.py` 卡住。

**核心名单（无条件安全）**：

| 类别 | 命令 |
|---|---|
| 文件内容 | `cat` `head` `tail` `more` `less` `wc` `od` `xxd` `hexdump` `strings` `file` |
| 搜索过滤 | `grep` `egrep` `fgrep` `rg` |
| 目录/信息 | `ls` `tree` `du` `df` `stat` `which` `type` `lsof` |
| 环境/系统 | `env` `printenv` `pwd` `echo` `date` `uname` `hostname` `id` `whoami` `ps` |
| git 只读 | `git status` `git diff` `git log` `git show` `git branch` `git rev-parse` `git describe` `git blame` `git remote` |

**可扩展（自身基本只读，需额外排除写 flag）**：

- `sed`：排除 `-i` / `--in-place`；
- `awk`：排除程序体内重定向（`>`）；
- `curl`：排除 `-o`/`--output`、`-d`/`--data`、`-X POST`；
- `cut`/`sort`/`uniq`/`tr`：本身只读，直接进；
- `find`：排除 `-exec`/`-delete`。

**护栏（对整个命令串生效，不满足 → 判非只读 → 写段）**：

- 不含 `>` `>>` `2>` `<`；
- 不含管道 `|`、`&&`/`;` 链、`$(...)`、反引号、heredoc `<<`；
- 整体必须是**单命令**——出现任何链/替换/重定向，直接 fail 到写段，不猜。

**说破的两点**：

1. **代价**：真实 turn 里纯读只占一部分，`build`/`test`/`install`/脚本/`git checkout` 会退回写段串行。这是拿并发换安全。（这类"不可解析的写"在跨 agent 层默认锁整个工作区，靠**衍生目录表**收窄到子树，见 §3.3。）
2. **"读"是置信度测试，不是解析**：`git status` 其实会 touch `.git/index`（刷新 stat 缓存，无害）。白名单不需要精确，只要"有把握不乱动用户文件"；没把握就串行。

**落地**：`SchedulingPolicy.command_is_read_only(cmd)`（名单从 `server/scheduling.yaml` 读），在着色阶段决定 bash 进读段还是写段。

**④ MCP 工具 → 数据驱动**：判定式是"配置开关 `supports_parallel_tool_calls`（服务器级）|| 服务器指定 `readOnlyHint`（工具级）"——**二选一为真 → 判读（可并行）；两者都无 → 判写（串行，默认）**。

- `knowledge` 服务器：`search` 工具在 `tools/list` 返回 `annotations.readOnlyHint = true` → 判 **读**，可并行，能跟 `glob` / `read_file` 同时跑；
- `git-ops` 服务器：`create_branch` / `commit` 等工具未标 `readOnlyHint`，配置里也没开 `supports_parallel_tool_calls` → 判 **写**，串行，同轮其他工具排队等它。

**⑤ skill 脚本 → 非工具（跟随 `bash`）**：skill 脚本本质是 `bash`，不自动跑、由模型经 `bash` 执行 → 跟随 `bash` 的判定。

**⑥ `task` → 判"写"**：委派子 agent 会创建子会话、产生副作用 → 判"写"，段内串行，同轮其他工具排队等它。**这是 agent 内的段内判定**；跨 agent 的全局互斥下 `task` **不持锁**（它阻塞等子 agent，而子 agent 要用锁，父持锁就会父子死锁），见 §3.3。

**判定总表**：

| 工具 | 归类 |
|---|---|
| 只读内置（`glob`/`grep`/`read_file`）| 读段 |
| `skill` | 读段（加载 SKILL.md 指令集，只读）|
| `write_file` / `edit_file` | 写段（参数抽 `path`，同文件排队、异文件并行）|
| `bash` | 纯读 → 读段（并行）；非纯读 → 写段（串行）|
| MCP 工具 | 配置开关 `supports_parallel_tool_calls`（服务器级）\| \| 服务器指定 `readOnlyHint`（工具级），二选一为真 → 读段；都无 → 写段 |
| `task` | 写段（串行）；跨 agent 不持锁（防父子死锁，见 §3.3）|
| skill 脚本 | 非工具（本质 `bash`），跟随 `bash` 的判定 |

### 1.3 工具集定位

**定位**：编码助手 + 联网（经 MCP）+ 团队 lead 可委派子 agent。据此**明确不需要**：`write_knowledge`（知识只读够了）。

**结论**：对上述定位，**现有工具集已够用**，配比干净——读段并行、`write_file` / `edit_file` 写段（同文件排队/异文件并行）、非纯读 `bash` 写段（串行）、`task` 串行。上面这套是**agent 内**的读 / 写配比；落到跨 agent 层，每个工具还要再映射成"路径域 + 模式"（§3.3），非纯读 `bash` 靠衍生目录表把锁域从根收窄到子树。

## 2. 整体逻辑

### 2.1 完整 turn 流程

一个 turn 里多工具调用的完整执行链（对照原文档第 1–8 节的骨架，变的只是调度）：

1. **模型流式返回** → 每个 tool call 转成 `ToolCall`，先**攒在 `pending` 里不执行**（客户端工具的 delta 本来就憋在流尾一次性吐出，攒着不增加等待）。
2. **流结束、assistant 文本写回历史之后**，把 `pending` 一次性交给分段调度。位置不能挪：工具行先于 assistant 文本落库，会破坏"`reasoning_content` 与 `tool_calls` 同一条消息"（DeepSeek 要求）。
3. **着色**：每个调用按第 1.2 节判定为"读 / 写"。
4. **分段执行**：按发出顺序扫描成连续段，段间严格按模型顺序串行。**读段**：整段的 `client.tool_request` 先一股脑推给客户端，再并发等所有回投。**写段**：一条一条来（当前实现写段纯串行；设计上"相邻异文件 `write_file`/`edit_file` 并行"尚未开启）。
5. **按序收口**：段内并发的调用只产出结果，收口（写历史 / `tool.after` 钩子 / 事件 / 计数）**串行且按模型发出顺序**做。
6. **下一采样轮**：新上下文、重新着色分段。
7. **某轮无 tool call → turn 结束**。

### 2.2 分段调度（核心）

**核心：不拿锁，把工具按"读 / 写"着色，扫描成连续段——连续读成读段、连续写成写段；读段并行、写段排队，段间严格按模型发出顺序执行。** 取代原方案的"动态读写锁"机制（原 9.3 / 9.4 的 per-file 锁 + 白名单锁）。

**分段规则**（模型一次返回 N 个工具，按发出顺序扫描着色）：

- 连续的读 → 一个**读段**：段内全并行；
- 连续的写 → 一个**写段**：段内按模型顺序执行，仅"相邻且异文件的 `write_file` / `edit_file`"可并行；
- 段间严格按模型发出顺序串行（读段 / 写段交替），**任何段不跳过、不重排**。

例：`读1、读2 | 写1 | 读3、读4 | 写5、写6` → 读1、读2 并行 → 写1 → 读3、读4 并行（能看到写1 的副作用）→ 写5、写6（同文件排队、异文件并行）。

**写段内部规则**（保持模型顺序，不重排）：

| 相邻写组合 | 处理 |
|---|---|
| 相邻且异文件 `write_file` / `edit_file` | 并行（**当前实现尚未开启**，写段一律串行）|
| 相邻且同文件 `write_file` / `edit_file` | 排队 |
| 其余（非白名单 `bash`、写工具与 `bash` 相邻、`task`）| 按模型顺序串行，不并发 |

**解决的原问题**：

- 读段与写段永不同段 → 写工具不再阻塞只读工具，且不存在"写入途中被读半截"；
- 写段内受控（同文件排队、异文件 `write_file` / `edit_file` 例外并行、其余含 `bash` / `task` 串行）→ 写写不真并发；
- 相对"两阶段（读全先、写全后）"的改进：**保留模型发出顺序**——`[写 a.rs, 读 a.rs]` 仍是写先读后（读到改后）；`[读 a.rs, 写 a.rs]` 仍是读先写后（读到改前）。

### 2.3 顺序语义与边界

**顺序语义**：

- **段间完整保留模型发出顺序**（读段 / 写段交替，不重排）——这是分段调度相对"两阶段（读全先、写全后）"的改进；
- 常见依赖场景天然成立：`[写 a.rs, 读 a.rs]` → 写先读后、读到改后 ✓；`[读 a.rs, 写 a.rs]` → 读先写后、读到改前 ✓；`[write_file, cargo build]` → 改完再编译 ✓；
- 代价：读和写被段边界隔开，`[读1, 写1, 读2]` 里读2 必须等写1（不能和读1 并行）——这是"保留顺序 + 读写不并行"的必然取舍；
- 已知边界：段间完全串行，段与段之间的并行度比"两阶段"低（块交替时无法并跑）。

### 2.4 实现提示与模型配合

**实现提示**：

- **不做增量派发、不做并发队列**：工具调用本来就在流尾一次性吐出，提前启动读没有墙钟收益，所以"攒在 `pending` → 流尾单遍分段"就够了，不需要 `FuturesOrdered` 之类的有状态调度器。分段写成**模块级纯函数**（`segment_tool_calls`），可以直接单测。
- **执行与收口分离，用"并发执行、按序收口"代替加锁**：历史拼接是读-改-写（`MAX(sequence)+1` 分配序号、把 `tool_call` 块 merge 进上一条 assistant 行的 `tool_calls` 数组），并发写会丢块、产生孤儿 `tool` 行、序号重号。做法是段内并发**只产出结果、不写历史**，段结束后**按模型发出顺序串行**收口 → 竞态自然消失，无需锁，且 `tool_calls` 数组顺序 = 模型发出顺序。
- **段内执行顺序 = 模型发出顺序**，先到先排；读段被最慢的那个拖住（一期接受）。
- **名单进配置、机制留代码**：读 / 写名单（工具名、命令白名单、写 flag、git 子命令与查询 flag、写类工具名）在 `server/scheduling.yaml`，代码里只留护栏字符与命令解析——护栏是安全底线（判错不可逆），放进配置等于给"把重定向当只读"开口子。配置在引擎 `__init__` 里加载（`SchedulingPolicy()`），缺文件即启动报错，不留代码兜底副本。
- **跨 agent** 才需要真的锁表（§3）。

**模型配合（提示词引导）**：

分段调度已保留模型发出顺序，因此"改完立刻读验证"这类**副作用依赖**不再需要提示词兜底。提示词引导降级为**建议**：仍建议模型**尽量**不让同一轮的工具调用依赖彼此的结果**参数**（那种必须多轮等结果再生成的），以降低不必要的串行等待。

- 现状已有 API 级开关 `parallel_tool_calls`（`client_common.rs:28`、`client.rs:947`），管"模型能否一次发多个调用"；
- 定位：副作用依赖由分段调度天然满足；参数级依赖仍需模型拆成多轮——提示词引导只针对后者。

## 3. 多 agent 下的读写互斥

> §1–§2 讲的是**单个 agent、单个 turn 内**的调度：模型发出的多个工具调用，按顺序扫成读段 / 写段，读段并行、写段串行。这一节讲**多个 agent 并发**时怎么办。
>
> 两者是**两层不同的东西**，不冲突也不重复：§1–§2 保的是**一个 agent 内的因果序**；本节保的是**跨 agent 的不撞车**。

### 3.1 两层结构

| | 保什么 | 谁定顺序 | 范围 |
|---|---|---|---|
| 层1 · agent 内（§1–§2）| 因果序：段间不重排、段内读并行写串行 | 模型 | 每个 agent 自己的 turn |
| 层2 · 跨 agent（本节）| 不撞车：同一时刻只有一个写碰某路径 | 到达先后（FIFO）| 进程级共享的路径锁表 |

**为什么不能合并成一件事**：段是 **per-agent** 的——每个 agent 有自己的模型输出、自己的发出顺序，两条调用流不能合并扫描；跨 agent 也没有共享的因果序可保（A 的"读 x"和 B 的"写 x"之间，模型没表达过任何先后）。所以层2 只做**互斥**，不做**排序**。

> 多 agent 是同一进程里的多个 `QueryLoopEngine` 协程（`server/engine/query_loop.py:221-244`，`get_or_create` 里 `asyncio.create_task(engine.run())`），共享同一工作目录与同一客户端。跑 `task` 委派时就是这种形态：lead 的引擎阻塞等子引擎跑完（`server/engine/task_handler.py:79-139`）。

### 3.2 核心模型：路径域 + 模式

**每个工具调用 = 一个"路径域" + 一个"模式"**。冲突判定 = **域相交 且 模式不兼容**。

模式只有两种，且**刻意不对称**——理由是后果不对称：

| 模式 | 谁 | 解析不出域时 |
|---|---|---|
| **X**（排他）| 所有写 | **危险** → 退最粗：对根拿 X |
| **S**（共享）| 能解析出具体域的读 | **无害** → 不取锁 |

一条只读被判成写，代价是多一次串行（慢，但安全）；一条写被判成读，代价是两个写同时改一个文件（丢数据）。所以拿不准时**一律偏向写**。

### 3.3 工具 → 域 / 模式

| 工具 | 路径域 | 模式 |
|---|---|---|
| `read_file x` | `x` | S |
| `glob` / `grep` 带路径 | 该子树 | S |
| `glob` / `grep` 不带路径 | — | 不取锁（无具体域）|
| `skill`（加载 SKILL.md 指令集）| — | 不取锁（只读、无路径）|
| `write_file` / `edit_file x` | `x` | X |
| 非纯读 `bash` | 根；能被衍生目录表 / 沙箱 `allowWrite` 收窄 → 子树 | X |
| 纯读 `bash`（读白名单通过）| — | 不取锁 |
| skill 脚本 | 跟随 `bash` | 跟随 `bash` |
| MCP 读工具（`readOnlyHint`）| — | 不取锁 |
| MCP 写工具 | 根 | X |
| `task` | — | **不取锁（唯一例外）**（理由见下）|

**和 §1.2 的关系**：§1.2 判的是"进读段还是写段"（agent 内），本表判的是"要不要拿跨 agent 锁"（层2）。进读段的工具 → 按本表取 S 或不取锁；进写段的工具 → 拿 X。**唯一的错位是 `task`**：它在 §1.2 里判"写段"（段内串行、同轮其他工具等它，这是对的），但在层2 **不持锁**——它阻塞等子 agent，子 agent 要用锁，父若持锁就死锁。

**`task` 不持锁是实现约束，不只是设计选择**：`task` 在写段循环内逐条执行（`query_loop.py:2386-2391` 的 else 分支，`_execute_tool` 把 `task` 派给 `task_handler`，再 `await` 子 agent 跑完），而**同一段里的锁会包住这次 `await`**。父持锁 → 子拿不到锁（父子同工作区、共用同一把锁）→ 父子死锁。所以任何加在写段上的锁都必须**按调用**获取、并显式跳过 `task`；把锁包在整个写段循环外面会直接死锁。

**`bash` 的域从哪来**：`write_file` / `edit_file` 的路径来自参数（`server/tools/permission.py:409` 的 `tool_input["path"]`），**自我声明**；而 `bash` 路径运行时才定、读写分不清（§1.2③），解析不出，所以默认对整个工作区拿 X。**衍生目录表**（`target/`、`node_modules/`、`__pycache__/`、`.git/` 等）把这类写的域从"根"收窄到"子树"——`cargo build` 只锁 `target/`，不再锁全工作区。

### 3.4 落地：意向锁

借数据库的**层次锁**思路：把工作目录当"表"、路径当"行"，避免"锁整张表"和"锁某一行"互相看不见而漏判。

- 写 → `IX`(根) + `X`(子)：先声明"我要在根下面某处写"，再锁具体路径；
- 不可解析的写 → 直接 `X`(根)；
- 精确读 → `IS`(根) + `S`(子)；
- 宽读（无具体域）→ 不进锁表。

兼容规则：**X 与一切互斥；IS / IX / S 互相兼容**。

例：A 写 `a.rs`、B 写 `b.rs` → 两者各拿 `IX`(根) 互相兼容，再各拿自己的 `X`，路径不同 → 并行。C 若要 `X`(根)（不可解析的写），则与 A、B 的 `IX`(根) 互斥 → 等它们做完。

### 3.5 顺序

跨 agent 只有**两处**真实存在的顺序，其余不需要排序：

1. **agent 内因果序**：就是 §1–§2 的分段调度，模型自己定的；
2. **父子顺序**：`task` 阻塞等子 agent 跑完（`server/engine/task_handler.py:79-139`），已天然成立。

除此之外，跨 agent 的工具调用之间没有"谁先谁后"的语义，只有"能不能同时"——所以层2 是**锁表**，不是**队列**。

### 3.6 四条纪律

1. **每个工具调用只持一把锁**（或按路径排序后依次持多把），不嵌套 → 无交叉死锁。
2. **持有范围 = 从决定执行到客户端结果收口**，含首段超时后的 reconcile 宽限窗（`server/engine/query_loop.py:362` 的 `_tool_reconcile_timeout`、收口逻辑 `query_loop.py:572`）——宽限期内锁不能松，否则别的写会挤进来。
3. **超时 / 断连 / forbidden 都要释放**，不能因为客户端没回就永久占锁。
4. **FIFO** → 公平，不饿死。

### 3.7 挡不住的边界

1. **锁罩不到模型思考时段**：A "写完 → 思考 → 读验证"跨 agent 敞开——A 思考时锁已放，B 可能在这中间改了同一文件。
2. **锁防撞车不防语义冲突**：两个 agent 都改同一文件，谁后到谁覆盖，结果取决于到达顺序、不看内容。语义上仍需**文件所有权**（文档 9 §9 的 ownership 分配）来隔离。
3. **`write_file` 挡不住丢失更新**：它的内容来自会话级旧读（几轮之前读的），锁只管写回那一刻，管不了内容已过期。**`edit_file` 不同**：它的读在**工具执行内部**、和写回在同一把锁里，所以文档 9 §9 的"时序 3 静默覆盖"在 `edit_file` 上被消除。
4. **宽读可能读到半截**：不进锁表的读（如无路径的 `grep`、纯读 `bash`）不受保护。
5. **"根 X"会 stop-the-world**：不可解析的写锁整个工作区，而精确读要取 S，于是它同时停住读和写。这是**明知代价**，靠衍生目录表把域从根收窄到子树来压——收窄后波及面从全工作区降到子树。

### 3.8 例子

A 的 turn：`读x → 写y → 读y`；B 的 turn：`读y → 读x → 写y`。两条流并发跑：

| 时刻 | A | B | y 的锁 | 说明 |
|---|---|---|---|---|
| t1 | 读x ✅ | 读y ✅ | 空闲 | 两个读同时跑（都拿 S）|
| t2 | 写y ▶ | 读x ✅ | A 独占 (X) | B 的读x 不等 A 的写y（不同路径）|
| t3 | 读y ⏳ | 写y ⏳ | A 独占 (X) | 只有这一格在排队 |
| t4 | 读y ✅ | 写y ⏳ | 空闲 | A 读到刚写的那版 |
| t5 | — | 写y ▶ | B 独占 (X) | B 最后写 |

要点：**冲突只在"同一路径、一读一写或两写"时发生**（t3 的 y）；不同路径的读写不互相等（t2 的 A 写 y 与 B 读 x 并行）。

## 4. 验证

- 着色：`cat a` → 读段；`cat a > b`、`sed -i`、`cargo build` → 写段；`task` → 写段。
- 段内：两个相邻 `write_file` / `edit_file` 异文件 → 并行；同文件 → 排队（按模型发出顺序）。
- 段间：`读1、读2 | 写1 | 读3、读4` → 读1、读2 并行；写1 等它们跑完；读3、读4 等写1 跑完再并行。
- 隔离：任意读与任意写永不同段（无"途中被读"）；非白名单 `bash` 不与其他写并发。

## 5. 远期（记录不实现）

- **沙箱联动（订正）**：原设想的"沙箱做 ACL 决策时其实知道命令实际访问的路径，回传给调度器就能做真 per-file 判断"**不成立**——landstrip 只在**越界被拒**时产生 trap JSON（`13.1-权限控制.md:285`），工作区内的写是**静默放行**、不产生任何访问记录；底层 Landlock / AppContainer 是"允许目录写"模型，本就无访问日志；Windows 上还只是**目录级** DACL，连 glob `denyWrite` 都不强制（`13.1-权限控制.md:278-283`）。要拿到真实访问路径需 fanotify / 审计子系统级别的改动，成本远超收益，**搁置**。
