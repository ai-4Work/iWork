# 权限控制技术方案

> 本文是权限控制的**技术方案**，明确服务端/客户端职责、判定流程、策略配置与实现细节。设计参考 OpenAI Codex CLI 的权限体系（详见《权限控制-codex.md》），结合 iWork Client-Server 架构落地。
>
> 核心定位一句话：**服务端定规则、判三态、生成策略；客户端执行、代理域名审批、沙箱兜底；判定与确认全程走现有 NDJSON chunk 通道**。

## 0. 现状与目标

### 0.1 现状

| 现状 | 缺口 |
|---|---|
| `server/tools/permission.py` 的 `PermissionChecker` 仅做路径前缀黑名单 | `query_loop.py:287` 实例化时未传 `blocked_paths`，黑名单为空 → **实际空转、从不拒绝** |
| `server/hooks/deny-rm.sh` + `hooks.json` 拦截危险 shell（`rm -rf /` 等） | 手写脚本，非结构化、不可查询、不可审计 |
| 可观测性已接线：`TOOL_PERMISSION_DENIED` 事件（observability/events.py:31）、指标（metrics.py:56）、审计（audit.py:70）、错误码（error_codes.py:53） | 无策略评估记录（哪条规则命中、为何判定） |
| Build 模式已有 `confirm/skip/abort` 确认流（query_loop.py:1559-1589） | 仅 Build 模式，服务端不消费 `requires_approval` 做拦截 |

### 0.2 目标

1. **服务端是权限判定唯一权威**：每次工具调用前判出三态 `Skip / NeedsApproval / Forbidden`，并生成策略包下发。（网络域名判定除外：allow/deny 与"要不要问"由客户端代理 CONNECT 判定，见 §4.4。）
2. **客户端是执行与强制层**：执行工具、本地代理域名审批、landstrip 沙箱兜底。
3. **判定与确认经 chunk 传递**：不引入新传输层，复用 `client.tool_request` / `/tool-result` 通道。
4. **Windows 为主**：利用 landstrip 的跨平台能力，Windows 上按能力降级（见 §4.6）。

## 1. 架构总览

```
┌─────────────────────────── 服务端（判定权威）──────────────────────────┐
│  策略配置 permissions.yaml ──► 三态判定引擎（permission.py）            │
│       基础画像 ⊕ 临时叠加 = 本次有效权限                                 │
│       决策一：Skip / NeedsApproval / Forbidden                        │
│       决策二：要不要建沙箱                                              │
│              │                                                       │
│              ▼ 策略包（policy JSON）+ 三态                             │
└──────────────┬────────────────────────────────────────────────────────┘
               │ chunk: client.tool_request { tool_name, input, policy, requires_approval }
               ▼
┌─────────────────────────── 客户端（执行 + 强制）──────────────────────┐
│  ① 本地代理：注入 HTTPS_PROXY，提取 host → 本地白名单判定             │
│  ② landstrip 沙箱：landstrip run -p policy.json -- <cmd>              │
│  ③ 审批 UI：needs_approval 弹确认（确认/跳过/终止）                     │
│  ④ 结果 + trap 审计 ──► /tool-result ──► 服务端注入上下文 + 审计       │
└──────────────────────────────────────────────────────────────────────┘
```

**三层拦截，职责分明**：

| 层 | 做什么 | 粒度 | 管什么 |
|---|---|---|---|
| 服务端静态判定 | 工具调用前，基于 LLM 参数 + 策略判三态 | 工具级 | 要不要问、能不能自动跑 |
| 客户端代理 | 提取域名，本地白名单判定 | 域名/连接级 | 域名规则的强制执行 |
| 沙箱兜底 | landstrip 运行时物理拦截 | 目录/进程级 | 漏判也拦得住 |

## 2. 权限模型（三个维度）

参考 codex，权限体系拆成三个维度，可自由组合：

| # | 维度 | 管什么 | 配置入口 |
|---|---|---|---|
| 1 | 文件系统读写权限 | 能读、写、删哪些文件 | `permissions.<名>.filesystem` |
| 2 | 网络访问权限 | 能不能联网、连哪些域名 | `permissions.<名>.network` |
| 3 | 工具审批策略 | 要不要问（分全局/工具两层） | 顶层 `approval_policy` + `tool_rules` |

前两个维度拼成一条**权限画像**，整场会话默认共用；第三个维度独立。运行时可通过 `request_permissions` / `require_escalated` **临时叠加**放宽（只加不减）。

**本次有效权限 = 基础画像 ⊕ 本次临时叠加**

### 2.1 内置画像

| 画像 ID | 文件系统 | 网络 | 说明 |
|---|---|---|---|
| `:read-only` | 全盘只读 | 受限（只能回环） | 最保守，Windows 无沙箱时的兜底默认 |
| `:workspace` | 工作区可写、`/tmp` 可写、其余只读；`.git`/`.env` 强制 deny | 受限 | 日常开发默认 |
| `:full`（danger-full-access） | 不限 | 不限 | 关掉整套权限体系，不建沙箱 |

### 2.2 三态判定

| 判定 | 含义 | 后续 |
|---|---|---|
| `Skip` | 够格，直接执行 | 进执行（可 `bypass_sandbox`） |
| `NeedsApproval` | 要问人 | 客户端弹确认（确认/跳过/终止） |
| `Forbidden` | 硬停，连问都不问 | 拒绝 + 注入上下文返回模型 |

## 3. 按工具分类的判定

判定不是通用的"解析参数 ↔ 比对配置"引擎，而是**按工具分类**各有一套逻辑。这是本方案最关键的取舍：**安全边界不能靠解析参数守**（参数会被硬链接 / TOCTOU / 路径拼接骗），精细拦截靠服务端静态判定 + 沙箱，服务端审批层只负责"要不要问"。

| 工具类别 | 服务端判定做什么 | 解析路径吗 | 拦截靠谁 | 对应 codex |
|---|---|---|---|---|
| **内置文件类**（write / edit / apply_patch） | 解析 `path`（patch 则逐路径）比对 filesystem 策略 → allow/needs_approval/forbidden | ✅ | 沙箱兜底 | `assess_patch_safety` |
| **命令类**（bash / exec_command） | 只查命令规则（`rule("rm","-rf","forbidden")` 前缀匹配）+ 危险命令启发式 | ❌ | 沙箱运行时硬拦 | exec policy |
| **网络类**（web_fetch 等） | 不做域名静态判定，服务端一律放行 | ❌ | 客户端代理 CONNECT 提取 host → 本地比对白名单判定；未命中按 `approval_policy` 总闸 + `unknown_domain` 细化（见 §4.4） | `network_rule(...)` |
| **其它**（自定义/MCP） | 默认兜底：文件系统受限才问 | ❌ | 沙箱 | `default_exec_approval_requirement` |

> 命令类**完全不解析路径**——`echo x > /etc/passwd` 里的 `/etc/passwd` 服务端不看，由沙箱运行时硬拦。未命中 `tool_rules` 与危险启发式的命令默认放行（allow → skip，不弹窗）。因此**沙箱兜底是命令类工具的硬前提**；Windows 上 landstrip 为目录级粗粒度，命令类的路径约束即目录级（详见 §4.6）。

### 3.1 六项配置的关系

六项配置按归属维度、作用工具、判定方（服务端静态 / 客户端代理）、匹配方式划分：

| 配置 | 归属维度 | 作用对象 | 判定方 | 匹配方式 |
|---|---|---|---|---|
| `filesystem` | 维度1（画像内） | 文件类（write/edit/apply_patch） | 服务端 | 逐路径比对可写根 / deny |
| `network.domains` | 维度2（画像内） | 网络类 | 客户端代理 | 域名通配 allow/deny（deny > allow） |
| `network_rules` | 维度3 工具层 | 网络类 | 客户端代理 | host + protocol 精确（不认通配） |
| `tool_rules` | 维度3 工具层 | 命令类（bash/exec_command） | 服务端 | 命令 token 前缀（按会话 `shell_env` 语法适配：PowerShell→Windows 分词+大小写不敏感、bash/zsh→POSIX+大小写敏感；规则可 `shell:` 归属，缺省 all） |
| `dangerous_patterns` | 维度3 工具层 | 命令类 | 服务端 | 命令子串匹配（yaml 全量为准、对所有 shell 生效；未配置按会话 shell 自动选默认集：POSIX / +PowerShell 盘符破坏性操作） |
| `approval_policy` | 维度3 全局层 | 全部（服务端三态翻译 + 客户端网络总闸） | 服务端 + 客户端代理 | — |

**两条判定链互不交叉**：

- **文件/命令类（服务端静态）**：文件类走 `filesystem` 逐路径判定；命令类走 `tool_rules` 前缀匹配，未命中再查 `dangerous_patterns` 子串，都没命中兜底 allow。两者产出的 allow / prompt / forbidden 基调再由 `approval_policy` 翻成三态。
- **网络类（客户端代理，服务端恒 allow 不下域名判定）**：CONNECT 提取 host+protocol → 先比 `network_rules`（精确）→ 未中再比 `network.domains`（通配，deny > allow）→ 仍未中过 `approval_policy` **总闸** + 画像 `unknown_domain` 细化（详见 §4.4）。

**`approval_policy` 的双重角色**：

- **服务端**：把 prompt 基调翻成 needs_approval（on-request）或 forbidden（never / granular 关闭时）；allow → skip、forbidden → forbidden 一票定音，不受它影响。
- **客户端代理**：当网络未命中白名单时的全局总闸（never → 直接拒；granular 且 `network:false` → 拒；放行后按 `unknown_domain` 细化）。

**优先级与覆盖**：精确 rule（`network_rules`）先于通配白名单（`network.domains`）；域名内 deny > allow。网络三件套（`network_rules` / `network.domains` / `approval_policy` 的网络角色）全部发生在客户端代理，对服务端网络判定无影响。

### 3.2 MCP / 外部工具与权限（现状 + 目标设计）

> 分类（file/command/network/other）与执行位置（CLIENT/SERVER）是**两把正交的尺**。本节把会读写的 MCP / skill 工具在权限体系里的真实位置讲清，再给收编方向（第 3 项 M1/M2 已落地，执行通道分派与落点边界见 `权限控制-运行逻辑.md` §5）。

**1. 分类与执行（现状）**

- 引擎 `classify_tool`（`permission.py`）只把**内置白名单**归 file/command/network：command（bash/exec_command）、network（web_fetch/web_search）、file（write/edit/apply_patch + read/glob/grep）。任何 **MCP 工具**（服务端 `github_create_issue`、客户端上报的 MCP 名）与 **skill** 都不在集合 → 落 `other` → `_evaluate_other` **恒 allow** → skip：**不判路径、不进沙箱、不弹窗**，哪怕它们底层读写文件 / 联网 / 碰库。
- 执行位置是另一把尺（`dispatcher.classify`）：客户端上报的 MCP 归 `CLIENT`（走 `client.tool_request`，随包带 policy，query_loop CLIENT 分支）、服务端 MCP 归 `SERVER`（走 MCP 运行时 dispatch）、记忆/task 直接服务端。**位置只决定"在哪跑"，不改变"other 恒 allow"这条判定。**
- ⚠️ 与 §3 表格"其它（自定义/MCP）→ 默认兜底：文件系统受限才问"的差异：那是**设计意图**（受限才问人）；**阶段0 实现为恒 allow**（`_evaluate_other` 注释"先不误伤服务端/记忆工具"，见 §7.1）。别把表格意图当现状。

**2. 执行位置 ≠ 沙箱（现状）**

- `policy.sandbox.required` 随每个 CLIENT 工具的 `client.tool_request` 下发，但客户端**只有 bash 的执行路径（`file:exec`）消费它**并调 `runSandboxed`（agent-client `sandbox.ts`，WRITE_RESTRICTED 受限令牌）。
- 客户端 MCP 走 `mcp:call-tool` → `main/mcpManager.ts` → MCP SDK `client.callTool`，**转发给 MCP server 进程**，与 `runSandboxed` 零交集；skill 客户端裸读 SKILL.md。
- 网络同理（§8.6.2）：已给 **bash 与 MCP stdio 子进程**注入 HTTPS_PROXY（`mcpManager` buildProcessEnv）。**sse / streamable-http 的请求由 Electron 主进程发出、不经本地代理**——已落地（M2）：`mcpManager` 给两 transport 注入 `walledFetch`（undici ProxyAgent → 本地代理，目标一律走 CONNECT 判域名），http/sse MCP 联网现在过代理网络墙。

**3. MCP 执行层收编：写墙（stdio）+ 网络墙（http/sse）——M1/M2 已落地（剩余收口见 M3）**

"和 bash 放一块"要放对地方——**执行层同类、审批层不同判据**。bash 与 stdio MCP 都有"客户端 spawn 本地子进程"这半边，同一把受限令牌写墙与同一个代理 env 都能罩住（同类在**执行层**）；差别只在审批判据：bash 有命令文本 → 服务端能按 tool_rules / 危险启发式做命令级判定；MCP 只有 (server, tool, args)、**无命令文本 → 命令级弹窗整条不做**（不同类在**审批层**）。于是 MCP 受控面收敛为两道墙、无第三道（命令级弹窗）：

- **写墙（进程级，只 stdio）— M1 已落地**：`main/mcpManager.ts` 把 SDK `StdioClientTransport` 的 `command` 换成沙箱 runner 入口（`console-shim → runner --workspace/--temp/--mode workspace-write -- <真实命令>`，WRITE_RESTRICTED 受限令牌）。生命周期按**会话级惰性执行实例**走：发现（`connect` 早连读 `tools/list` schema）与执行分离，执行实例在首个受控 `callTool` 时按"当前策略 `sandbox.required` + 该 workspace"判定——命中且沙箱探活通过则**关旧建新受限实例**、同 workspace 复用；`tools/list` 只出 schema、无模型输入，发现实例裸连即可（不保留裸连进程给执行）。`:full`（`sandbox.required:false`）/ 无 workspace / 沙箱不可用 → **直连回退并告警**（fail-open 仅限这三类例外场景）。策略或 workspace 变化即关旧重建；**并发多 workspace 与跨会话空闲回收 = M3（未做）**。
- **网络墙（域名级）— M2 已落地**：http / sse MCP 无本地进程可包、套不上写墙，只能落**网络层**。`mcpManager` 给 sse / streamable-http transport 注入 `walledFetch`（undici `ProxyAgent` dispatcher → 本地代理），目标域一律经本地代理 CONNECT → 走 §8.6.2 判定链（白名单 / network_rules / approval_policy / unknown_domain），allow 直通、ask 弹窗、deny 拒；stdio MCP 进程内连接靠注入的代理 env 自然走代理。
- **无命令级弹窗 → 准入退到接入级信任**：服务端对 MCP 维持 other 恒 allow → skip，不引入 tool_rules / 启发式 / 按参数问（§1 ⑥，**设计如此、非缺口**）。MCP 的"人肉闸"落在**用户配 config 允许接这个 server**——接入级明示信任，之后墙内读写全自动、不逐调用打断；`api.ts` 执行前校验该 server 已 connected（未连接即拒）。

**与 bash 沙箱同源的三处缺口**（墙只管到边界，别高估）：
1. **写墙只限写、不拦读**——墙内 filesystem MCP 仍可读全盘（令牌层无单文件 deny、只认写白名单）；
2. **写墙是范围墙、不是动作墙**——墙内删 / 覆盖 / 破坏性 fs 全放行，MCP 又缺 bash 的 forbid 启发式兜底；
3. **写墙只罩 stdio、罩不到 http/sse**——http/sse MCP 无本地进程，进程级写墙对其不适用（只能靠网络墙兜出网侧；其对本地文件系统的读写不受本墙约束）。

> M1/M2 的具体客户端接线与 M3 收口方向见 `权限控制-运行逻辑.md` §5（执行通道分派、生命周期、别高估墙）。

## 4. 后端实现细节

### 4.1 三态判定引擎（`server/tools/permission.py`）

将 `PermissionChecker` 改造为判定引擎：

```python
@dataclass
class Verdict:
    verdict: Literal["skip", "needs_approval", "forbidden"]
    reason: str | None = None
    matched_rule: str | None = None      # 命中哪条规则（可观测/审计）
    policy: PolicyPacket | None = None   # 阶段1起下发，见 §4.4

class PermissionEngine:
    def __init__(self, config_path: str): ...
    def evaluate(self, tool_name: str, tool_input: dict, ctx: EvalContext) -> Verdict:
        # ctx = 基础画像(编译后) + approval_policy + 本次临时叠加 + 会话级覆盖
        ...
```

判定流程（对标 codex 决策一）：

```
工具调用
  │
  ├─ ① 按工具分类（dispatcher.classify 扩展）
  │     ├─ 文件类：解析 path/patch 逐路径 vs filesystem 策略
  │     ├─ 命令类：命令前缀 vs tool_rules + 危险命令启发式
  │     ├─ 网络类：不下域名判定（客户端代理 CONNECT 判定）
  │     └─ 其它：默认兜底（文件系统受限才问）
  │
  ├─ ② 出判定基调 allow / prompt / forbidden / 无命中
  │
  ├─ ③ approval_policy 翻译成最终三态：
  │     allow → Skip；forbidden → Forbidden（一票定音）
  │     prompt → on-request 下 NeedsApproval；never 下 Forbidden
  │     无命中 → 各工具兜底
```

`EvalContext` 来源：启动时读取 `server/permissions.yaml`，`compile_permission_profile_selection` 编译成 `(FileSystemPolicy, NetworkPolicy)`；`approval_policy` 编译成枚举；`:workspace_roots` 等符号路径按会话 workspace 解析成真实路径（会话创建时注入，见 `POST /sessions` 的 `workspace` 字段）。

### 4.2 引擎接线（`server/engine/query_loop.py`）

`_check_tool_permission`（query_loop.py:1402）从"抛异常即拒绝"升级为"消费 Verdict 三态"：

```python
async def _check_tool_permission(self, msg, tool_name, tool_input, tool_call_id, turn) -> str | None:
    """返回 'skip' | 'needs_approval' | 'forbidden' | None(不通过)"""
    ctx = self._build_eval_context(msg.session)          # 基础画像 + approval_policy + 临时叠加
    verdict = self.permission.evaluate(tool_name, tool_input, ctx)
    if verdict.verdict == "forbidden":
        # 拒绝：记录审计 + 指标 + TOOL_PERMISSION_DENIED 事件 + 错误注入上下文
        tool_permission_denied_total.add(1, attributes={"tool_name": tool_name})
        await self._emit(AgentEventType.TOOL_PERMISSION_DENIED, {...})
        await self.context_mgr.append_tool_result(..., {"success": False, "error": verdict.reason})
        return "forbidden"
    if verdict.verdict == "needs_approval":
        # 确认流：现有 Build confirm/skip/abort 机制（query_loop.py:1559-1589），泛化到所有模式
        return "needs_approval"
    return "skip"
```

调用点（query_loop.py:1186 Build 模式、1202 自动模式）改为 `result = await _check_tool_permission(...)` 后按三态分支：

- `skip` → `_execute_tool_chunk(...)` 直接执行
- `needs_approval` → 走 `client.tool_request` 确认流（带 `requires_approval=true` + `policy`），等待 `/tool-result` 返回确认/跳过/终止
- `forbidden` → `continue` 注入错误结果，不让 LLM 卡死（复用现有"被拒不是死路"行为）

### 4.3 策略包下发（`server/models/events.py`）

`ClientToolRequest`（models/events.py:31-43）新增 `policy` 字段。策略包字段对标 codex `FileSystemSandboxPolicy` + `NetworkSandboxPolicy`：

```json
{
  "filesystem": {
    "profile": "workspace",
    "allow_write": ["{workspace}", "/tmp"],
    "deny_write": ["{workspace}/.git/**", "**/.env"],
    "deny_read": ["**/.ssh/**", "{workspace}/.env"]
  },
  "network": {
    "enabled": false,
    "allow_domains": ["registry.npmjs.org"],
    "deny_domains": ["*.internal"],
    "unknown_domain": "ask",
    "approval_policy": "on-request",
    "network_rules": [{"host": "registry.npmjs.org", "protocol": "https", "decision": "allow"}]
  },
  "sandbox": { "required": true }
}
```

服务端在判定通过后，由 `PermissionEngine.build_policy` 构建策略包，随 `client.tool_request` 下发（query_loop.py:1576-1594 构造处）。客户端据此执行工具、建沙箱。`network.http_proxy_port` 不在此包内——代理端口由**客户端自选自决**，不上报服务端。

### 4.4 域名级审批（客户端代理本地判定）

- **职责划分**：服务端不做域名静态判定（网络类工具在服务端一律放行）；域名的 allow/deny 判定在**客户端代理**，未命中白名单时"要不要问"由服务端下发的 `network.approval_policy` **总闸**（`never` / `granular` 且 `network:false` → 拒）+ 画像 `unknown_domain` 细化把关，判定执行在客户端。
- **判定流程**：客户端起本地 HTTP 代理，spawn 工具子进程时注入 `HTTPS_PROXY/HTTP_PROXY → http://127.0.0.1:<客户端自选空闲端口>`；防火墙/沙箱只放行该端口（对标 codex win.rs:642）。代理从 CONNECT 行提取目标 host（对标 codex http_proxy.rs:178），比对**服务端下发的** `allow_domains` / `deny_domains`（**deny > allow**）：
  - 命中 allow → 转发；命中 deny → 拒绝；
  - 未命中 → 先过**全局 `approval_policy` 总闸**（从策略包 `network.approval_policy` 读取）：`never` → 直接拒；`granular` 且 `network:false` → 直接拒。总闸放行后再按画像 `unknown_domain` 细化：`ask` → 客户端弹确认（同意 → 转发并写入**会话级缓存**，后续同 host 不再问，对标 codex"批准后写回规则"；拒绝 → 拦）；`deny` → 直接拦。**覆盖只存客户端本地、会话内有效**——跨会话重新问，服务端不存覆盖、无持久化端点。
- **服务端只负责配置下发与审计回传**：阶段1 经 policy 包带 `network` 策略（`permissions.yaml` 仍是唯一配置源）；客户端判定结果（`network_approvals` 数组）随 `/tool-result` 回传，服务端逐条落审计 `tool.network_approval`（observability/audit.py），**不参与判定决策**。

### 4.5 升级重试 + 临时叠加

- **升级重试**（对标 codex orchestrator.rs:401）：沙箱内失败（EACCES / 网络受限）→ 客户端把失败原因随 `/tool-result` 回传 → 服务端带 `retry_reason` 重新走审批 → 批准后下发宽松策略重试。`/tool-result` 回传体增加可选字段 `retry_reason`。
- **临时叠加**：新增 `request_permissions` 工具（模型主动申请）与命令级 `require_escalated`（单条命令自带的附加权限声明）。服务端审批通过后在**本次有效权限**上并集放宽（只加不减，对标 codex `merge_permission_profiles`）。

### 4.6 landstrip 沙箱 + Windows 降级

- **客户端**用 landstrip 创建沙箱执行工具进程：`landstrip run -p policy.json -- <cmd>`，policy.json 由服务端策略包转换（ASR 格式：`filesystem.allowWrite/denyWrite/denyRead/allowRead` + `network.httpProxyPort`）。Linux 底层为 Landlock + seccomp；Windows 为 AppContainer。
- **Windows 能力边界（粗粒度）**：

  | 能力 | Linux | Windows（AppContainer） |
  |---|---|---|
  | 文件规则粒度 | 路径/glob 级，访问时评估（含新建文件） | 目录级（AppContainer SID 的 DACL） |
  | glob `denyWrite` | 强制 | **不强制** |
  | 动态审批（运行时 query） | 支持 | **不支持** |
  | 读 | 默认放开 | 需显式 read allowlist |

  因此 Windows 上 landstrip 只做**进程级目录兜底**；文件级精细 deny（`**/.env` 等）由服务端静态判定承担（deny → forbidden，直接注入错误、不达客户端），不依赖 landstrip。
- **无沙箱降级**：客户端上报 landstrip `doctor` 结果（沙箱是否可用，可经 `/sessions` 或心跳）。Windows 无沙箱时，服务端强制默认画像降为 `:read-only`（对标 codex config_toml.rs:762——无沙箱兜底时"工作区可写"等于全盘可写，太危险）。
- **trap 审计**：landstrip 拒绝输出结构化 JSON（`{"Filesystem":["write","/repo/out","seccomp"]}`）随 `/tool-result` 回传，喂给现有 `TOOL_PERMISSION_DENIED` 事件 / audit（observability/audit.py）。

## 5. 前端（客户端）改动

客户端（Electron）是执行与强制层，新增以下能力（对应 codex 的客户端/沙箱机制）：

### 5.1 本地 HTTP 代理（域名审批）
- Electron 主进程内嵌 Node HTTP 代理（监听 `127.0.0.1:<客户端自选空闲端口>`——端口**客户端自决**，不上报服务端，不进入策略包）。

> 文件类工具的路径强制由**服务端判定**承担（`_evaluate_file`：deny → forbidden 不达客户端，越界 → needs_approval，根内 → skip），客户端不再做应用层路径预检（§8.3 取消说明）。

### 5.2 landstrip 沙箱
- 接入 landstrip：`landstrip run -p <policy.json> -- <cmd>` 执行命令类工具；policy.json 由服务端策略包转换（ASR 格式）。
- 启动时跑 `landstrip doctor` 检查平台沙箱可用性，上报服务端（决定是否降级画像）。
- 拦截结果（trap JSON）随 `/tool-result` 回传。

### 5.3 审批 UI（确认/跳过/终止）
- 复用现有 Build 模式确认 UI（mockup/index.html:3234-3239 的 confirm/skip/stop 按钮），泛化到所有模式。
- 新增：`client.permission_request` 统一弹窗（对标协议文档 L9884），展示工具名、输入预览、`matched_rule`、`reason`、`effect: confirm`；用户可"记住选择"（写入会话级覆盖，回传服务端）。

### 5.4 会话级覆盖与缓存
- 用户确认/跳过/批准域名后，客户端保存会话级覆盖（`{tool_prefix → allow/deny}`、`{host → allow}`），随 `/tool-result` 回传服务端持久化，后续判定优先。
- 断线续传：`/tool-result` 幂等（按 `request_id`），客户端重连后补报未回传的结果。

> 客户端的分阶段实现计划见 **§8**：P1 契约同步+requires_approval 消费 → P2 本地 HTTP 代理+域名审批 → P3 landstrip 沙箱+Windows 降级（曾规划的独立"应用层路径预检"已取消，见 §8.3）。

### 7.1 阶段0：服务端三态判定引擎（已落地）

阶段0 的三个交付物均已落地：`permission.py` 改造为 `PermissionEngine`、新增 `server/permissions.yaml`、`query_loop.py` 完成接线，配套 `tests/test_permission.py` 三态单测。以下按真实代码说明实现逻辑。

#### 1. 判定引擎 `server/tools/permission.py`

- **引擎构造**：`PermissionEngine.__init__` 读取 `permissions.yaml`，编译出 `approval_policy` / `default_profile` / `tool_rules` / `danger_heuristics` / `dangerous_patterns` / `file_path_check` / `profiles` 七份状态；画像编译时内置三档 `:read-only` / `:workspace` / `:full`（不可被覆盖），自定义画像 `extends` 继承父画像的 filesystem（`_compile_custom_profile` 先深拷贝父项再叠加自身）。
- **判定入口** `evaluate(tool_name, tool_input, ctx) -> Verdict`：权限引擎唯一的对外入口，query_loop.py 每次工具调用前都调它。

  | 入参 | 类型 | 说明 |
  |---|---|---|
  | `tool_name` | `str` | 要调的工具名，如 `write_file` / `bash` / `web_fetch` |
  | `tool_input` | `dict` | LLM 传给工具的参数，如 `{"path": "/a.txt"}`、`{"command": "git status"}` |
  | `ctx` | `dict \| None` | 判定上下文，目前只带 `workspace`（会话工作区绝对路径），用于把配置里的 `@WORKSPACE@` / `@TMPDIR@` 占位符解析成真实路径 |

  返回值 `Verdict`：`verdict` 三态之一；`reason` 给用户看的判定理由；`matched_rule` 命中的规则名（审计用）。

  函数体五步：
  1. 从 `ctx` 取 `workspace`
  2. 按 `default_permissions` 选当前画像
  3. 画像 `disabled`（`:full`）→ 直接 `skip`
  4. `classify_tool` 分四类：file → `_evaluate_file`、command → `_evaluate_command`、network 与其它 → `_evaluate_other`（网络不做域名静态判定），产出决策基调 allow / prompt / forbidden
  5. `_translate` 结合 `approval_policy` 把基调翻成最终三态

  示例：

  ```
  evaluate("bash", {"command": "rm -rf /"}, {"workspace": "/home/me/proj"})
    → classify_tool 得 command
    → _evaluate_command 分词命中 "rm -rf /" 禁止规则
    → _translate 得 Verdict("forbidden", matched_rule="tool:bash rm -rf /")
  ```
- **按类判定（allow / prompt / forbidden）**：
  - **file**（`_evaluate_file`）：`path` 命中 deny（`_is_denied`，含 workspace 相对 deny 规则与 glob）→ forbidden；写工具（write_file / edit_file / apply_patch）路径不在可写根（`_resolve_roots` 解析 `@WORKSPACE@` / `@TMPDIR@` / 绝对路径）→ prompt；读工具仅 deny 拦截。
  - **command**（`_evaluate_command`）：三步判定，**未命中任何规则的命令默认放行（allow-by-default）**，分词与大小写按会话 `shell_env` 语法适配：
    1. 分词 → `tool_rules` 前缀匹配（`_match_command_rule`，命中 rule 的 decision 即 allow/prompt/forbidden），命中即定音。`shell_env=powershell`（Windows 客户端）用 Windows 分词（`shlex posix=False`，保留 `C:\` 反斜杠）且大小写不敏感；bash/zsh/空走 POSIX 分词 + 大小写敏感（向后兼容）。每条规则可选 `shell: powershell | posix | all`（缺省 `all`，对所有会话生效），会话 shell 归属与规则不符则跳过该条（语法隔离，见下）；
    2. 未命中 → 查危险命令启发式（子串匹配；PowerShell 会话大小写不敏感），默认集按会话 shell 选：未配置 `dangerous_patterns` 时，bash/zsh 用内置 POSIX 集，`powershell` 在 POSIX 基础上并集盘符级破坏性操作（`Clear-Disk` / `Remove-Partition` / `Format-Volume` / `format c:` 等）；yaml 配置了 `dangerous_patterns` 则全量替换内置（对所有 shell 生效）。命中 → prompt；
    3. 两步都没命中 → 兜底 `return "allow"` → `skip` 免确认执行（如 `cd "G:/论文2" && ls -la` 这类只读命令）。
    **完全不解析路径**，路径级拦截靠后续阶段的沙箱；对比 Codex 对未匹配 shell 默认 prompt，iWork 命令类默认放行。
    > **规则词法 = 客户端实际 shell 语法**：Windows 客户端命令执行壳被迫为 PowerShell（写沙箱与 MSYS/bash 实测不兼容，见 agent-client `sandbox.ts`），因此 `tool_rules` 里的规则要按 PowerShell 词法写（`Remove-Item -Recurse -Force`），Linux/mac 才按 bash/zsh（`rm -rf`）。外部程序命令（`git`/`npm`/`node`…）三端词法一致，无需区分。精确 token 前缀 + 语法不同天然互不命中，同文件可并存多套词法规则而互不串扰；`shell:` 字段用于显式归属。
  - **network**：服务端不做域名静态判定，一律 `allow`（→ `skip`）——域名 allow/deny 由客户端代理在 CONNECT 时提取真实 host、比对本地持有的白名单判定（见 §4.4）。`web_search`（参数 `query`）等无 URL 入参的工具同样放行，交给代理。网络"要不要问"的判定**不在服务端**，而是把全局 `approval_policy` 编进策略包下发给客户端代理执行：
    - **服务端静态判定**：恒 `allow`→`skip`，不产 prompt，因此不走上面 `_translate` 的三态翻译表——`approval_policy` 对网络工具的服务端结果**无影响**。
    - **网络 Ask 的去向**（客户端代理消费，未命中白名单时）：`approval_policy` 当**全局总闸**——`never` → 直接拒；`granular` 且 `network:false` → 拒；否则再按画像 `unknown_domain` **细化**（`ask` → 客户端弹确认 / `deny` → 画像级禁问）。
    - **下发载体**：`build_policy` 的 `network.approval_policy` 字段（on-request / never / granular dict），随 `client.tool_request` 下发给客户端（见 §7.2 字段表）。
  - **other**：阶段0 一律 `allow`（避免误伤服务端/记忆工具）。
- **三态翻译** `_translate`：把各分类产出的决策基调（allow / prompt / forbidden）翻成最终三态，`prompt` 的去向由 `approval_policy` 决定：

  | 决策基调 | `approval_policy` | 最终三态 | 说明 |
  |---|---|---|---|
  | `allow` | — | `skip` | 直接执行 |
  | `forbidden` | — | `forbidden` | 一票定音，连问都不问 |
  | `prompt` | `on-request`（默认） | `needs_approval` | 逐次判定，够格自动放行 |
  | `prompt` | `never` | `forbidden` | 从不问，需要问的一律拒绝 |
  | `prompt` | `granular`（对应开关开） | `needs_approval` | 按工具类别逐类放行 |
  | `prompt` | `granular`（对应开关关） | `forbidden` | 该类审批被关闭 |

  > `granular` 按工具类别映射开关 key：command→`shell`、network→`network`、file/other→`rules`；开关未配置时默认开（True）。

  > ⚠️ 网络恒 `allow` 不经过本表（服务端不判域名，见上文 network 段）；`network` 这个 granular key 虽在 `_translate` 里预留，但服务端网络判定永远走不到 prompt 分支。网络 Ask 的审批在**客户端代理**，由下发的 `network.approval_policy` 总闸 + 画像 `unknown_domain` 把关（见 §7.2 字段表）。

#### 1. `network_rules` 编译下发

`network_rules` 是顶层全局配置（host + protocol 精确规则，不认通配，维度同 `tool_rules` 的"精确优先"思路），阶段0 引擎完全没解析。本次新增编译：

#### 2. 审计接收 `tool.network_approval`

客户端把一次工具执行内的多次域名判定打包成 `network_approvals` 数组，随 `/tool-result` body 回传；服务端逐条落审计。

  ```python
  else:
      result = result_val if isinstance(result_val, dict) else {"success": False}
      for appr in (result.get("network_approvals") or []):
          if not isinstance(appr, dict):
              continue
          await self._emit(AgentEventType.NETWORK_APPROVAL, {
              "host": appr.get("host"),
              "protocol": appr.get("protocol"),
              "decision": appr.get("decision"),

              "request_id": request_id,
          })
  ```

#### 3. 设计决策

- **端口客户端自决**：代理监听端口由客户端自选空闲端口，**不上报服务端、不进策略包**——`network.http_proxy_port` 已废弃（§6 字段表标注），服务端 `policy.network` 为 `enabled / allow_domains / deny_domains / unknown_domain / approval_policy / network_rules`（`approval_policy` 为网络总闸，随包下发）。
- **会话级覆盖持久化不做**：用户批准域名后的覆盖只存客户端本地、会话内有效，跨会话重新问；服务端不存覆盖，无新增表 / 端点。

| 工作区路径 | **不做应用层路径预检**（旧 `guardPath`/`resolveWorkspacePath` 守卫已移除），路径三态判定由服务端 `_evaluate_file` 承担（deny→forbidden / 越界→needs_approval / 根内→skip），主进程仅 `resolve` 归一化 | 与权限判定一致 |
| 结果回传 | `submitToolResult`（`services/api.ts:572-594`）POST `/tool-result/{requestId}`，body 仅 `{status, output?, error?, exit_code?, duration_ms}` | 无 `skipped` / `network_approvals` / `sandbox_traps` |
| 域名审批 / 沙箱 | **无**：无本地代理、无 `HTTPS_PROXY` 注入、无域名白名单、无 landstrip | 空白 |
| 权限弹窗 | `client.permission_request` 不存在 | 空白 |
| 多智能体 | `multiAgentStore.ts:472-486` 有平行 `client.tool_request` 处理 | 需同步改 |
| `fullAccess` | `types/index.ts:73` 定义且有默认值，但**从未被任何逻辑消费** | 悬空字段 |

#### 8.1.2 权限空白清单（客户端侧缺口）

1. `ClientToolRequest` 类型缺 `requires_approval / policy / tool_call_id / step / reasoning`（`types/index.ts:444-452`）
2. `requires_approval` 未消费 → 自动模式该放行的工具（`skip`）也会弹确认
3. `policy` 未消费 → 无 `network` 白名单可注入代理、无 `sandbox.required` 可配沙箱（P2/P3 无从下手）
4. 无本地 HTTP 代理 → 域名 allow/deny 无处执行（服务端不判域名）
5. 无 landstrip 沙箱 → 命令类无进程级兜底
6. `skipTool` 提交的是 `{status:'error'}`，**服务端 `append_skip_feedback` 死路径从未触发**（见 §8.8）
7. 无 `network_approvals` / `sandbox_traps` 回传 → 域名判定与沙箱拦截不进审计

#### 8.1.3 目标

1. **该问的问、够格的自动跑**：消费 `requires_approval` 二分 auto-execute / 确认
2. **域名审批在客户端代理落地**：CONNECT 提取 host，白名单 + 总闸 + unknown_domain 判定，结果回传审计
3. **landstrip 沙箱进程级兜底**：命令类硬拦，Windows 按能力降级
4. **回传闭环**：`skipped` / `network_approvals` / `sandbox_traps` / `retry_reason` 随 `/tool-result` 上报

### 8.2 客户端权限三层架构

```
┌────────────────────────── 客户端（Electron）──────────────────────────┐
│  协议层  NDJSON 流消费 client.tool_request → 读 requires_approval/policy │
│              │  skip: 自动执行（auto-execute，按 request_id 幂等）       │
│              ▼  needs_approval: 确认 UI（确认/跳过/终止）               │
│  代理层  本地 HTTP 代理（127.0.0.1:自选端口）← spawn 注入 HTTPS_PROXY   │
│              │  CONNECT 提取 host → 白名单 → 总闸 → unknown_domain      │
│              ▼                                                       │
│  沙箱层  landstrip run -p policy.json -- <cmd>（命令类进程级兜底）      │
│              │                                                       │
│              ▼  /tool-result { skipped, network_approvals, sandbox_traps, ... }
└──────────────────────────────────────────────────────────────────────┘
```

| 层 | 做什么 | 粒度 | 消费的契约字段 |
|---|---|---|---|
| 协议层 | 决定"问不问"，分发执行/确认 | 工具级 | `requires_approval` |
| 代理层 | 域名 allow/deny + 要不要问 | 域名/连接级 | `policy.network.*` |
| 沙箱层 | 命令类运行时物理拦截 | 目录/进程级 | `policy.sandbox.required` |

> 与服务端"三层拦截"对照：协议层对应服务端静态判定（服务端定三态，客户端按 `requires_approval` 落地）；代理层与沙箱层是服务端规划里"归客户端"的两块。文件工具的路径判定由服务端 `_evaluate_file` 完成（deny → forbidden 不达客户端、越界 → needs_approval），客户端不做重复预检（§8.3 取消说明）。

### 8.3 阶段划分总览

| 阶段 | 一句话目标 | 依赖 | 服务端是否已具备 |
|---|---|---|---|
| **P1** 契约同步 + requires_approval 消费 | 客户端"该问的问、够格的自动跑"，policy 接到工具上 | 无 | 是（chunk 已带两字段） |
| **P2** 本地 HTTP 代理 + 域名审批 | CONNECT 提取 host，白名单+总闸+unknown_domain 判定，回传 network_approvals | P1 | 是（`network_approvals` 审计已接） |
| **P3** landstrip 沙箱 + Windows 降级 | 命令类进程级兜底，无沙箱 fail-closed | P1（代理端口给 P2） | 部分（`sandbox.required` 已下发；trap 审计服务端可选） |

> **曾规划的独立"应用层路径预检"已取消**：服务端 `_evaluate_file`（permission.py:322-342）已对文件工具做完整路径三态判定——命中 deny → forbidden 直接注入错误、不达客户端；越界写 → prompt → needs_approval 弹确认；根内 → skip。客户端**不再做应用层路径预检**：旧 `resolveWorkspacePath` / `guardPath` 兜底守卫已移除，主进程仅保留 `resolve` 归一化，越界写经确认后由客户端直接执行（write_file 真实写出；bash 仍受 P3 沙箱目录级约束）。命令类的路径无法可靠解析（bash 语法多样），兜底靠 P3 沙箱 + 危险命令启发式。故不设独立应用层路径预检阶段。

**为什么这个顺序**：

1. **P1 必须排第一**：类型缺 `requires_approval/policy`，一切无从谈起。`requires_approval` 是"要不要问"的唯一真源，不消费则自动模式每次都要手点、且 skip 工具会静默裸跑。纯渲染层改动，行为只会从"全问"收敛到"该问的问"，零安全回归。顺手把 `skipTool` 的 `skipped:true` 补上（修复服务端死路径）。
2. **P2 其次**：依赖 P1 的 policy 送达（renderer→main）与确认泛化；同时是 P3 `policy.json` 里 `network.httpProxyPort` 的前置。
3. **P3 最后**：依赖代理端口 + 外部二进制 landstrip，且 Windows 能力边界决定它只能做目录级兜底，文件级精细 deny 由服务端判定承担（§4）；升级重试依赖服务端阶段3，客户端只留字段。

### 8.4 P1 契约同步 + requires_approval 消费（纯渲染层）

#### 8.4.1 类型同步（`renderer/src/types/index.ts`）

**chunk 是什么**：服务端在 CLIENT 工具分支推一条 NDJSON 行，`type` 为 `client.tool_request`（`query_loop.py:1584-1594`）。客户端 `ndjson.ts` 逐行解析成对象，其类型定义在 `renderer/src/types/index.ts:444-452`——但当前**只声明了 `type/seq/request_id/tool_name/input/message_id/agent_id`**，服务端已下发的字段缺 `requires_approval/policy/tool_call_id/step`（`reasoning` 模型预留但未推）。

服务端实际推送的 chunk（JSON 形态）：

```json
{
  "type": "client.tool_request",
  "seq": 42,
  "request_id": "8f3b9c2e-...",
  "tool_name": "write_file",
  "input": { "path": "src/a.txt", "content": "hi" },
  "message_id": "5d91f0aa-...",
  "tool_call_id": "toolu_01h...",
  "step": 3,
  "requires_approval": false,
  "reasoning": null,
  "policy": { "filesystem": { "profile": ":workspace", "allow_write": ["G:/ws", "/tmp"], "deny_write": ["G:/ws/.git/**"], "deny_read": ["G:/ws/.git/**"] }, "network": { "enabled": false }, "sandbox": { "required": true } }
}
```

字段全表（对应 `server/models/events.py:31-44` `ClientToolRequest`）：

| 字段 | 类型 | 服务端是否推送 | 客户端现状 | 说明 |
|---|---|---|---|---|
| `type` | `"client.tool_request"` | ✅ | 已有 | chunk 类型标识，NDJSON 行分发靠它 |
| `seq` | `number` | ✅（流层填充） | 已有 | NDJSON 序号，断线重连 `since_seq` 用 |
| `request_id` | `string` | ✅ | 已有 | 本次工具请求唯一 ID：确认流 bind、`/tool-result/{request_id}` 回传、断线幂等都靠它 |
| `tool_name` | `string` | ✅ | 已有 | 工具名（`read_file`/`write_file`/`bash`/...） |
| `input` | `object` | ✅ | 已有 | LLM 传给工具的参数字典 |
| `message_id` | `string` | ✅ | 已有 | 所属助手消息 ID |
| `agent_id` | `string?` | 多智能体会话才有 | 已有 | 所属 agent 标识 |
| `tool_call_id` | `string?` | ✅ | **缺，需补** | LLM 工具调用的 `tool_call_id`（Build 模式用） |
| `step` | `number?` | ✅ | **缺，需补** | Build 模式步骤号 |
| `requires_approval` | `boolean` | ✅ | **缺，需补** | 是否要问：`false`=auto-execute；`true`=弹确认（Build / 普通 / 自动均 = `verdict==needs_approval`；forbidden 不达客户端） |
| `reasoning` | `string?` | ❌（模型预留，当前未填充） | **缺，需补** | 判定理由，服务端暂未 push，先接受备用 |
| `policy` | `PolicyPacket \| null` | ✅ | **缺，需补** | 策略包（`build_policy` 产出，字段见 §7.2），客户端执行/建沙箱依据；`:full` 画像为精简包 |

> 客户端补齐上述字段后，同时给 `ToolCall` 加 `approvalRequired?: boolean` 与 `policy?: PolicyPacket | null`（`chatStore.ts:276` 构造处透传）。

#### 8.4.2 auto-execute（`stores/chatStore.ts:263-285`）

收到 `client.tool_request` 时按 `requires_approval` 二分：

- **`false` → auto-execute**：不落 `pending`，直接置 `running` 并 `executeClientTool` + `submitToolResult`（复用 `confirmTool` 的执行逻辑，抽成一个 `runClientTool(requestId, toolName, input)` 辅助）。**按 `request_id` 幂等**——断线重连重放 chunk 时不二次执行。
- **`true` / 缺省（向后兼容）** → 走现有 pending 确认流。

> ⚠️ **只作用于 `client.tool_request` 分支**。Build 模式的 `build.step_pending` 走的是另一条 `buildApi.confirm` 路径（`chatStore.ts:751-755`），不要在 client 工具分支误判 Build 步骤（见 §8.10 R3）。

#### 8.4.3 确认 UI 按需显示（`components/chat/SegmentsView.tsx:168-175`）

按钮显示条件从 `tool.status === 'pending'` 收紧为 `pending && approvalRequired !== false`。auto-execute 的工具根本不落 pending，按钮自然不显示——状态机少一条分支，比"pending 但隐藏按钮"干净。

#### 8.4.4 多智能体平行同步（`stores/multiAgentStore.ts:472-486`）

平行实现同款：补 `approvalRequired/policy`、支持 auto-execute。否则平行 agent 继续"一律问"。

#### 8.4.5 skipTool 修正（`chatStore.ts:758-785`）

`skipTool` 当前提交 `{status:'error', error:'User skipped the tool'}`。服务端只认顶层 `skipped` 标志（`query_loop.py:1606` → `append_skip_feedback`），所以 **`skipped:true` 从未触发**。改为提交 `{status:'error', skipped: true, error:'User skipped the tool'}`，让 skip 反馈真正进上下文（详见 §8.8）。

- 自动模式 `git status` 免确认直接跑
- 越界写（`needs_approval`）仍弹确认
- Build 模式消费 skip：`git status`（skip）免确认直接执行；越界写（needs_approval）仍弹确认；forbidden 拦截

### 8.6 P2 本地 HTTP 代理 + 域名审批

> 服务端已具备：`policy.network` 全部字段随策略包下发、`network_approvals` 审计接收（阶段2）。客户端代理留待本阶段实现。

#### 8.6.1 主进程新增 `main/proxyServer.ts`（单例）

- `http.createServer` 处理 `CONNECT`（`req.url` = `host:port`，host 提取统一用 `new URL('http://' + req.url).hostname`，兼容 IPv6 `[::1]:443` 括号与绝对形式 URL）与绝对形式 HTTP；命中转发用 `net.connect` 双向 pipe，拒绝回 403
- `listen(0)` 自选空闲端口，`address().port` 供 getter
- 持状态：`currentNetworkPolicy`、会话级 host 缓存、单次执行的 `networkApprovals` 缓冲
- **先起代理再 spawn**（`listen` 完成拿到端口后才注入子进程 env），顺序天然成立

#### 8.6.2 spawn 注入代理（`main/fileOps.ts:216-222`、`main/mcpManager.ts:66-73`）

`file:exec`（bash）与 MCP stdio 子进程的 env 追加：

```
HTTPS_PROXY=http://127.0.0.1:<port>
HTTP_PROXY=http://127.0.0.1:<port>
ALL_PROXY=http://127.0.0.1:<port>
NO_PROXY=localhost,127.0.0.1
```

> ⚠️ 边界一（子进程 env）：**只对"被注入 env 的子进程"生效**——bash 与 MCP stdio 子进程，主进程 fetch 不读 HTTPS_PROXY。
>
> ⚠️ 边界二（主进程 http/sse MCP）→ 已由 M2 收口：`mcpManager` 给 sse / streamable-http transport 注入 `walledFetch`（undici `ProxyAgent` dispatcher → 本地代理，`src/main/mcpManager.ts`），目标域一律经本地代理 CONNECT → 命中本判定链（allow 直通 / ask 弹窗 / deny 拒）。代理未就绪时回退直连并告警（启动竞态例外，见 §3.2）。

#### 8.6.3 判定流程（CONNECT 时，deny > allow）

```
提取 host（new URL('http://'+req.url).hostname，CONNECT 默认端口 443）
  │
  ├─ ① 会话缓存（先前已批准）→ 转发
  ├─ ② network_rules（精确 host+protocol，forbidden > prompt > allow）→ 命中即定
  ├─ ③ deny_domains（glob）→ 拒
  ├─ ④ allow_domains（glob）→ 转发
  ├─ ⑤ 未知 → approval_policy 总闸：
  │     never → 拒；granular 且 network:false → 拒
  │     放行 → unknown_domain：
  │       deny → 拒
  │       ask → 客户端弹确认（NetworkConfirmDialog）→ 同意：转发 + 写会话缓存；拒绝：拒
  └─ 每次判定记 networkApprovals（host/protocol/decision/approved）
```

> 域名匹配：无 glob 时后缀匹配（`host === pattern || host.endsWith('.' + pattern)`，apex 含子域）；有 glob（`*`/`?`）时 glob 匹配；**deny > allow**；host 先小写。协议识别：CONNECT → https，绝对形式行 → http。

#### 8.6.4 审批 UI：`NetworkConfirmDialog`（顶层 Modal）

- **复用不了工具卡确认**：工具确认 bind 一个工具的 `request_id`，网络 ask bind 一个 socket——一个确认对应多个连接。必须新建顶层 Modal。
- main 经 `webContents.send('proxy:network-ask', {host, protocol})` 推送，renderer 显示弹窗，用户同意/拒绝经 `resolve-network` IPC 回解。
- **30s 超时默认拒**（显著小于服务端 `sync_waiter.wait` 的 120s，见 §8.9）。

#### 8.6.5 会话缓存与回传

- 会话缓存：main 进程 `Map<host, {approved, ts}>`，会话切换清空，**不持久化**（对标服务端决策"跨会话重新问"）。
- IPC 新增：`proxy:set-policy` / `proxy:get-port` / `proxy:take-network-approvals` / `proxy:resolve-network`（`main/index.ts` + `preload/index.ts` + `renderer/src/services/ipcClient.ts` 补 stub）。
- renderer `submitToolResult` 前调 `take-network-approvals`，把本工具执行期的 `networkApprovals` 并入 body（见 §8.8）。

#### 8.6.6 验收

- `git clone https://evil.example.com/...` 命中 deny_domains → 403
- allow 域名正常放行
- 未知 host + `unknown_domain: ask` → 弹窗批准后同命令再次运行不再问（会话缓存）；拒绝 → 拦
- 服务端收到 `NETWORK_APPROVAL` 审计事件

### 8.7 P3 landstrip 沙箱 + Windows 降级

> 服务端只提供 `policy.sandbox.required`（阶段1已落地），其余全部是客户端职责（§7.4 决策1：服务端不碰沙箱可用性）。

#### 8.7.1 主进程新增 `main/sandbox.ts`

| 方法 | 职责 |
|---|---|
| `doctor()` | `landstrip doctor` 探活，缓存结果；每次需要沙箱时先探（按次降级，不降级会话） |
| `buildLandstripPolicy(policy, proxyPort)` | 把服务端策略包转 ASR 格式：`filesystem.allowWrite/denyWrite/denyRead` + `network.httpProxyPort`（用 §8.6 端口） |
| `runSandboxed(cmd, policyJson)` | `landstrip run -p policy.json -- <cmd>` 执行命令类工具 |
| `takeTraps()` | 解析 landstrip 拦截输出的结构化 JSON（`{"Filesystem":["write","/repo/out","seccomp"]}`）缓冲 |

#### 8.7.2 接入 `fileOps.ts` `file:exec`

- `policy.sandbox.required && doctor ok` → `landstrip run -p policy.json -- <cmd>`
- `required` 且不可用 → **命令类 fail-closed**（返回 error），读工具裸跑（按次降级，读不影响）
- trap JSON 并入 `submitToolResult.sandbox_traps`

#### 8.7.3 Windows 能力边界

landstrip 在 Windows 为 AppContainer，目录级粗粒度：glob `denyWrite` 不强制、动态审批不支持、读需显式 allow。所以 Windows 上沙箱只做**进程级目录兜底**；文件级精细 deny（`**/.env` 等）由服务端判定承担（deny → forbidden，不达客户端，§4）。前置条件：安装 landstrip 二进制。策略构建（`buildLandstripPolicy`）实测两条硬约束：**读必须是显式 allowlist**（`denyRead: ["**"]` + `allowRead: [cwd, "."]`，否则 `POLICY_UNRESTRICTED_READ`）；`allowLocalBinding` 在 Windows 不支持（`POLICY_TCP_BIND_UNSUPPORTED`），本地代理走 `windows.allowLoopback` 放行。

#### 8.7.4 无沙箱降级

`required && doctor 不可用` → 命令类 fail-closed、读工具裸跑，**每次调用重新探活**，不因一次失败降级会话（对齐 §7.4 决策1）。服务端不追踪 `sandbox_available`，客户端自决。

#### 8.7.5 `retry_reason` 只留字段

`ToolResult`/`submitToolResult` 加 `retry_reason?: string`，**但暂不填充**：升级重试需要服务端用宽松策略重新 push（overlay 合并 + query_loop 重试逻辑均未实现，服务端阶段3#4），现在发会被忽略且无重试。详见 §8.10。

#### 8.7.6 验收

- 有 landstrip 时 `rm -rf` → 沙箱出 trap，随结果回传
- 无 landstrip 时 bash 返回 error、read_file 仍可用

### 8.8 回传扩展与审计

`submitToolResult`（`services/api.ts:572-594`）body 扩展为可选字段：

| 字段 | 类型 | 来源阶段 | 服务端消费 |
|---|---|---|---|
| `skipped` | `boolean` | P1 | 顶层 `skipped` → `append_skip_feedback`（`query_loop.py:1606`） |
| `network_approvals` | `{host, protocol, decision, approved}[]` | P2 | 逐条 emit `NETWORK_APPROVAL`（`query_loop.py:1613-1623`）→ 审计 `tool.network_approval` |

## 9. 客户端代理（网络策略执行层）

> 本章是权限控制里**客户端代理与网络策略**的专项说明，从 HTTP 代理基础知识讲起，到 iWork 本地代理的实现、判定链、`network.enabled` 语义澄清、弹窗链路、策略下发与排障。承接 §4.4（域名级审批）、§5.1（本地 HTTP 代理）、§8.6（P2 本地 HTTP 代理 + 域名审批），把分散在各章的网络判定知识收拢成一章。
>
> 一句话定位：**网络策略的执行主体在客户端代理——服务端只下发 `policy.network`，代理在 CONNECT 时提取真实 host、按判定链决定放行/拦截/弹窗，结果回传服务端审计**。

### 9.1 基础知识：HTTP 代理是什么

代理（Proxy）是客户端应用与目标服务器之间的中间人。**尊重代理环境变量的应用**（curl / git / npm / pip 及绝大多数 CLI 网络工具）会把 HTTP/HTTPS 流量交给代理转发，而不是自己直连。

**两类流量形态**：

| 形态 | 触发场景 | 代理能看到什么 | 处理方式 |
|---|---|---|---|
| `CONNECT` | HTTPS（TLS） | 只看到目标 **host + 端口**（CONNECT 行），**看不到 payload** | 建 TCP 隧道对通，两端跑 TLS（不解密、不做 MITM） |
| absolute-form | 明文 HTTP | host + 端口 + **path** | 代理转发请求 |

**环境变量**（应用找代理的口令）：

```
HTTPS_PROXY=http://127.0.0.1:<port>   # HTTPS 走这个代理
HTTP_PROXY=http://127.0.0.1:<port>    # HTTP 走这个代理
ALL_PROXY=http://127.0.0.1:<port>     # 兜底，两者都没覆盖的走这个
NO_PROXY=localhost,127.0.0.1          # 这些 host 直连、不走代理
```

- **注入而非系统代理**：只把 env 传给**工具自己的子进程**，不影响系统代理设置、不劫持其它应用。
- **只能按 host 拦，不能看内容**：HTTPS 隧道不解密，所以网络策略的粒度是「域名/连接级」，不是「内容级」——这是设计边界（隐私 + 简单，零依赖）。

### 9.2 iWork 本地代理设计（`main/proxy.ts`）

- **实现**：Node 内置 `http` 模块，零依赖（`agent-client/src/main/proxy.ts`）。
- **监听**：`127.0.0.1:<自选空闲端口>`（`server.listen(0)`），端口客户端自决、不上报服务端。
- **注入**：bash（`file:exec`）与 MCP stdio 子进程 spawn 时注入 `HTTPS_PROXY / HTTP_PROXY / ALL_PROXY = http://127.0.0.1:<port>`、`NO_PROXY = localhost,127.0.0.1`（`getProxyEnv`，proxy.ts:285-294）。
- **两类请求**：
  - `CONNECT`（HTTPS）：`req.url = "host:port"`，`new URL('http://' + raw).hostname` 提取 host（兼容 IPv6 `[::1]:443` 括号）。判定后 `200 Connection Established` → `net.connect` 双向 pipe（TCP 隧道）；拒 → `403`。
  - absolute-form（HTTP）：`new URL(req.url)` 提取 host + path，判定后经 `httpRequest` / `httpsRequest` 转发；拒 → `403`。
- **只判 host，不做 MITM/TLS 解密**。
- **故障处理**：`server.on('error')` 只吞掉不拖垮应用；端口未就绪时 `getProxyEnv` 返回 `{}` → 子进程直连（fail-open 的兜底）。

### 9.3 判定链 `decideHost`（proxy.ts:73-98）

按优先级依次判定，命中即返回（`allow` = 放行转发 / `deny` = 403 拦截 / `ask` = 弹窗）：

```
① currentPolicy 为空 或 network.enabled 为 false → allow（直通，不判域名、不记审计）
② 会话缓存命中（本会话先前已批准该 host）→ allow
③ network_rules（精确 host+protocol）：
     forbidden → deny；prompt → ask；allow → allow
④ deny_domains（glob/后缀匹配）→ deny
⑤ allow_domains → allow
⑥ approval_policy 总闸：'never' → deny；granular 且 network:false → deny
⑦ unknown_domain === 'deny' → deny；否则 → ask（弹窗确认）
```

**域名匹配**（`matchDomain`，proxy.ts:58-70）：无 glob → 后缀匹配（`host === p || host.endsWith('.' + p)`，apex 含子域）；有 glob（`*` / `?`）→ glob 匹配；host 先转小写。deny > allow 由调用顺序保证。

> ①② 的顺序：会话缓存（「已批准 → 放行」记忆）**先于**白名单判定——同 host 批准一次后本会话不再问，即使它写在 deny 里也放行（对标「批准后写回规则」语义，§4.4）。

### 9.4 关键语义：`network.enabled: false` = 放行，不是禁网

这是最容易误解的一点，也是网络相关排障的根。

| 值 | 客户端行为 | 含义 |
|---|---|---|
| `enabled: false`（默认） | `decideHost` 第 ① 步直接 `return 'allow'` | **网络策略整个关掉，fail-open**——所有连接放行，不判定、不拦截、不弹窗 |
| `enabled: true` | 才走 ③-⑦ 判定链 | 命中白名单自动放行；未命中才可能弹窗（ask）或拦截（deny） |

所以「`enabled: false` = 不能访问外网」是**反的**。要开启网络管控（域名白名单 + 未命中确认），必须 `enabled: true`。

对应 YAML：内置 `workspace` / `read-only` 的 `network.enabled`（`server/permissions.yaml:47`）。

### 9.5 网络确认弹窗链路

```
main proxy.ts askAndWait（30s 超时默认拒）
  → windowGetter().webContents.send('proxy:network-ask', { host, protocol })
  → preload 转发（onNetworkAsk 回调）
  → renderer NetworkConfirmDialog（顶层 Modal）展示 host
  → 用户同意/拒绝 → ipcClient.proxy.resolveNetwork(host, protocol, approved)
  → main proxy:resolve-network IPC → pendingResolvers 解出 → 弹窗 Promise resolve
  → 同意：转发 + 写会话缓存（本会话同 host 不再问）；拒绝：403
```

- **同一 host 复用同一个弹窗**（`inFlightAsks`），避免 git clone 多连接刷屏。
- **30s 超时默认拒**，显著小于服务端 `sync_waiter` 的 120s（§8.9 R6）。
- **会话缓存不持久化**：`sessionHostCache` 随 `proxy:reset-session`（切换会话）清空，跨会话重新问。
- **为什么复用不了工具卡确认**：工具确认 bind 一个 `request_id`，网络 ask bind 一个 socket——一个确认对应多个连接，必须新建顶层 Modal（§8.6.4）。

### 9.6 策略下发链路（服务端 → 客户端）

```
服务端 PermissionEngine.build_policy（permission.py:323-359，读 server/permissions.yaml 编译）
  → query_loop.py CLIENT 工具分支 push client.tool_request（含 policy 字段，query_loop.py:1576-1596）
  → renderer chatStore 收到 → ipcClient.proxy.setPolicy(policy)
  → main proxy:set-policy IPC → currentPolicy（proxy.ts:242-244）
  → 代理判定时读 currentPolicy.network
```

关键点：

- **`permissions.yaml` 是唯一配置源**：服务端把编译后的网络策略随 policy 包下发，客户端只消费、不自行定规则。
- **每次 CLIENT 工具请求都会重新 build_policy 下发**：每个会话的 `PermissionEngine` 实例启动时重新加载 YAML，所以改 YAML 后**新会话/新一次工具请求**即生效。
- **内置画像的 network 从 YAML 读取**（`permission.py._compile_profiles`，2026-09 修复）：此前内置 `:read-only` / `:workspace` 被硬编码为「不可覆盖」且不传 network，Profile.network 恒为 `enabled=false`，YAML 里改 `enabled:true` 无效（见 §9.8 案例1）。

### 9.7 判定结果回传审计

- 每次判定记入 `networkApprovals` 缓冲（按 host+protocol+decision+approved 去重，proxy.ts:100-112）。
- 工具执行结束，renderer 在 `submitToolResult` 前调 `proxy:take-network-approvals` 取出，随 `/tool-result` body 的 `network_approvals` 回传（§8.8）。
- 服务端 `query_loop.py` 逐条 emit `NETWORK_APPROVAL` 事件 → 审计 `tool.network_approval`（资源记目标 host，§7.3 之2）。

### 9.8 排障案例

**案例1：改了内置 workspace 的 `network.enabled: true` 却不生效**

- 现象：客户端访问外网仍不弹窗、全放行。
- 排查链：
  1. 先确认 `enabled` 语义——默认 `false` = fail-open 全放行（§9.4），所以**现象本身符合默认值**，问题在「改 true 没生效」。
  2. 确认 `policy.network.enabled` 是否真的下发成 true——`build_policy` 从 `profile.network` 读，而内置 `:workspace` 画像在 `_compile_profiles` 里被 `continue` 硬跳过，YAML 的 network 段被丢弃 → Profile.network 恒为 `NetworkPolicy(enabled=False)` → 下发的包恒 `enabled:false` → 客户端 `decideHost` 第 ① 步直接 allow。
- 根因：**服务端内置画像 network 被代码写死，配置文件被忽略**（不是客户端问题）。
- 修复：`permission.py._compile_profiles` 让内置 `read-only` / `workspace` 的 network 段按 YAML 读取（复用 `_build_network`，filesystem 保持内置，`:full` 保持 disabled）。回归安全：YAML 不写 network 时回落默认 `enabled=false`，行为不变。配套 `tests/test_permission.py` 新增 `test_builtin_workspace_network_from_yaml`。
- 验证：YAML 内置 workspace `network.enabled: true` → 新建会话 → bash `curl https://未命中白名单域名` → 应弹网络确认框；未命中 + `unknown_domain: ask` 批准后同 host 本会话不再问。
