# iWork Agent 测试理念

## 核心思想：信任递增金字塔

测试体系按照**信任递增**的方式组织，每一层建立在前一层的基础上，逐层扩大验证半径。这不是一个"测试套件"，而是一个**测试体系**——有分层、有阶段、有演进路径。

```
        ┌──────────┐
        │  第4层    │  CI/CD 可持续回归
       ┌┤  自动化    ├┐
       │└──────────┘│
      ┌┤  第3层       ├┐
      ││  韧性/鲁棒性   ││
     ┌┤  第2层          ├┐
     ││  轨迹/端到端      ││
    ┌┤  第1层             ├┐
    ││  组件测试            ││
    └────────────────────────┘
```

## 四层结构

### 第1层：组件测试

**目标**：验证每个零件本身是对的。

针对性地测试每个模块的功能，粒度到函数/类级别。这一层必须扎实——如果组件测试有遗漏，上层测试查出的问题就分不清是零件坏了还是协作坏了。

- 每模块独立，mock 外部依赖
- 通过标准：所有单模块测试 green，关键路径覆盖率达标

以下清单基于 `agent-client-serve-merry-meerkat.md` 技术详细设计文档，列出每个组件需要覆盖的测试功能点。


### 第2层：轨迹测试 + 端到端测试


#### 从"过程"和"结果"两条判据出发

轨迹测试和端到端测试不是同一件事，必须分开立判据：

- **端到端看结果**：任务最终的产物或状态对不对。
- **轨迹看过程**：中间每一步合不合规矩——该并发的并发了吗、该串行的串行了吗、被拒绝的工具有没有真的不发出客户端往返、报错后有没有换路。

两者不可互相顶替。只看结果，轨迹可以错得很离谱而任务照样完成：读操作和写操作并发下发了、工具报错后原地重试同一入参、skill 的脚本在加载 skill 之前就跑了、出错时没把会话停掉。这类问题在"最后交付物对不对"这个判据下全部隐形。

#### 任务从业务功能入手

语料面就是 agent 手上的工具与技能，共三层：

- **6 个内置客户端工具**：`bash`、`read_file`、`write_file`、`edit_file`、`glob`、`grep`
- **14 个 Hub skill**（见 `server/skill-hub.json`）


#### 三档复杂度

| 档位 | 判定 | 附加要求 |
|---|---|---|
| 简单 | 单一工具，或 skill 的单一功能 | 1 次工具往返 |
| 中度 | 3–5 次工具调用组成 | 跨 ≥2 个工具面，且命中 ≥1 项协作特征 |
| 复杂 | 10–20 次工具调用组成 | 或命中重特征（上下文压缩 / 子 agent / recall 召回 / 超时对账） |



#### 通过标准的落地

本节开头写的"所有预定义的协作轨迹全部通过"，其"预定义协作轨迹"指的就是按上述口径产出的用例集，按档位分簿组织：`简单任务-内置工具+Skill测试用例.xlsx`（15 个 sheet：`内置工具` + 14 个 skill，共 140 条）、`中度任务-内置工具+Skill测试用例.xlsx`（1 个 sheet：`中度任务`，50 条）与 `复杂任务-内置工具+Skill测试用例.xlsx`（1 个 sheet：`复杂任务`，10 条），三者共同构成第2层的用例基线。

用例只承载**期望**，不写断言：结果期望落在「期望行为」列，过程期望落在「参考轨迹」列。两条判据各自的期望都要陈述得足够具体——"期望行为"写清最终该产出什么、"参考轨迹"写清过程中必须成立的不变量，避免"轨迹合理""顺序正确"这类无法判定的措辞。评判由评估 agent（或人工）对照这两列期望进行，判据是"期望中陈述的要点是否成立"，而不是跑一段代码去断言（文件内容类产物尤其如此）。相应地，任务选型倾向**最终产物可判**的类型（生成的文件、写入的记忆、创建的对象、会话状态）；"写得好不好"这类主观判断另立 `manual` 标注并控制数量。

### 第3层：韧性 / 鲁棒性测试

**目标**：验证系统在异常发生时能扛住，并按照预定策略恢复。

这里的**鲁棒性**更多指的是 **LLM 能自觉处理回灌给它的异常**——系统不崩、不死锁只是底线，真正的韧性体现在错误交回 LLM 之后，它能不能自己走出来。

#### 题眼：交回去，再收得回来

传统软件的韧性是"不让错误逃出去"——拦截、兜底、返回错误码。Agent 系统的韧性是"把错误交回去，再收得回来"：异常不是终点，而是下一轮推理的输入。异常处理的第一现场因此从代码层上移到了 LLM 层——大部分错误不以 exception 形态出现，而是表现为 LLM 拿到一个"失败"的观测之后该怎么走。

#### 分界轴：故障卡没卡在某个 LLM 指令的应答上

LLM 是一个"下指令 → 等应答 → 看结果 → 再下指令"的循环。**凡是卡在某个 LLM 指令的应答上的故障，都必须把异常信息回灌进上下文**——不回灌，LLM 要么僵在原地等，要么拿到一个假的"成功"继续往下走。凡是循环之外的故障（进程级、连接级、用户级），回灌没有信息增量，由代码消化，该提示的提示。


这条轴把异常切成两类，**两类不是互斥的抽屉，而是同一条链的两段**：重试/重连类先由固定逻辑处理，耗尽了才转成回灌（对照 12.2："固定逻辑决定'怎么做'，不决定'下一步做什么'"）。

| | A 类：不走 LLM | B 类：回灌给 LLM 自决 |
|---|---|---|
| 判定 | 不由 LLM 自行消化 | 卡在 LLM 指令的应答上，且错误信息可判 |
| 形态 | 拦截/兜底/返回错误码终止 / 重试 / 静默 | 错误文本注入上下文，LLM 换方案 |
| 被测对象 | **代码**（查表式决策路径） | **模型**（自调能力） |
| 判据性质 | 确定性、可断言 | 非确定性、看轨迹 |


> 口径说明：本节原先按"四级策略（重试 → 降级 → 暂停 → 终止）"组织。12.2 已把 1.8.2 的四级扩展为六级谱系，本层的异常覆盖以六级为准——四级是三级的骨架，不是全集（Skill 加载失败、权限拒绝都在四级之外）。

#### 常见异常举例

**B 类**——卡在某个 LLM 指令的应答上，回灌。按大类列：

| 大类 | 具体异常 | 回灌什么 |
|---|---|---|
| 工具不存在 | LLM 捏造了 tool name；调用了未加载 / 已下线的 skill 工具 | "工具 'xxx' 不存在"，并列出可用工具 |
| 参数非法 / 格式异常 | `tool_use` 的 input 不是合法 JSON、schema 不符、缺必填字段（1.8.1 #12） | 解析错误 + 期望结构，让它重出 |
| 内置工具执行失败 | `bash` 非零退出、`read_file` 目标不存在 / 不可读、`glob` / `grep` 入参非法 | 含 stderr 的失败原因 + 可用替代路径 |
| 编辑类失败 | `edit_file` 匹配不到唯一目标、多处匹配、与文件实际内容不符 | "未匹配 / 目标不唯一"这个事实 + 候选位置，让它重读后重写 |
| 权限 / 护栏拦截 | 权限检查禁止、工作区越界、Hook STOP、需审批被拒（1.8.1 #15 / 1.8.3） | "该操作被拒"这个**事实**，让它换合法方案（拦截本身不可推翻） |
| MCP 工具异常 | `tools/call` JSON-RPC error、调用超时、服务断连重连耗尽（1.8.1 #17） | 可读化后的 MCP 错误（2.7.4 G4），形如"MCP 工具 'x' 执行失败: \<error\>" |
| Skill 脚本失败 | skill 脚本非零退出、依赖缺失、入参与脚本期望不符 | 含 stderr 的错误 + 该 skill 的用法提示 |
| 服务端直执行工具失败 | `recall` 召回失败、记忆读写异常 | 失败原因。注意边界：记忆写冷却（返回 skipped）与 Skill 加载失败属 A 类，静默容忍 |
| `@文件` 引用异常 | 文件被删 / 不存在、超 8000 字被截断（1.8.1 #5） | 警告文本替代内容，由它决定换源还是继续 |
| 网络超时（重试耗尽） | 共 3 次尝试（首次 + 2 次重试），退避 1s、2s；第 3 次失败即终止（1.8.1 #7） | 合成"上次调用失败"，让它换路径——重试是第一段，回灌是第二段 |
| Client 回传异常 | 回传超时 120s（#18）、`request_id` 不匹配（篡改，#20）、对账窗判不出（C-2/C-3） | 超时**当场不回灌**（操作可能还在跑，回灌会致重复副作用），恢复时必须回灌；不匹配 → "回传对不上号"；判不出 → 只读/可重放标"可安全重试"，写类标"需确认" |
| 子 agent 委派失败 | `task` 派发抛异常、子会话 `success=false`（9.11.8） | 子任务的失败原因，让它决定重派 / 换成员 / 自己干 |
| 死循环提醒 | 连续 3 次同工具同输入（1.8.1 #13） | "你已连续 3 次调用同一工具，请换方案"。**插在终止之前一级**，不替代终止。当前实现是直接强制终止，回灌这一级标 `known-gap` |
| 内容安全拦截 | `content_filter`，输出被安全策略拦下（1.8.1 #14） | **模糊**回灌"输出被安全策略拦截，请重新生成"，不给触发细节——说清是什么触发的等于教模型绕过滤器；1~2 次未过即终止。当前实现是直接中止，标 `known-gap` |
| 输出被截断 | 达到 `max_tokens` | 注入续写提示，让它接着写，而不是把半截输出当成品 |

三点补充：

- **注入接缝只有两条**。内置工具（含 skill 脚本）与 MCP 工具全部在客户端执行，错误以回投 body 的形式回到服务端；另一条是 LLM 连接层重试耗尽后**合成**的观测（#7），由框架写进下一轮。其余大类都归这两条之一。
- 接缝的另一头有分界：**LLM 服务级失败**（Rate Limit、认证失败）重试耗尽后没有可交回的对象——连不上就没人能决策，落 A 类终止（见 R3 用例）；只有框架还能继续组装下一轮时，合成观测才有回灌的余地。
- 表中 `known-gap` 两行（#13 / #14）的"回灌"是**目标行为**：`1-Query Loop 引擎.md` 的 1.8.1 现写的是强制终止与中止。测试文档不能描述系统不具备的行为，用例按目标行为设计并标缺口。

**A 类**——没卡上，分两种情形。

（一）LLM 根本不在场——故障发生在它进来之前或之外：

- 队列满 / 重复入队 / 会话已归档（入队阶段，HTTP 429 / 幂等 / 410 直接返回）
- 认证失败 401/403、Rate Limit 退避耗尽（连接建不起来）
- DB 查询超时、并发抢锁失败（框架在查库、抢锁，LLM 不知情）
- Token 超限强制压缩（上下文组装的框架行为）
- 客户端连接断开 / buffer 回放、用户 Plan/Build 无响应 300s（客户端与用户侧）
- Skill 加载失败（静默容忍，只影响该 Skill 可见性）、记忆写冷却（返回 skipped）

（二）那条指令已有结局、系统正在收尾——卡不卡已经无所谓：

- 轮次耗尽（≥25）、单消息超时（300s）
- 死循环检测：**检测**在这一层（可断言），检测到之后先回灌提醒属 B 类，只有"回灌没救回来"才走到这里的终止
- 内容安全拦截的**终止**端点在这层，但拦截事实要先回灌（B 类表），回灌到次数上限仍未通过才落这里
- MCP 服务级终止（整个服务没了，不是单次调用失败）

（三）易漏的一类——卡在应答上，但错误信息**判不出来**：工具执行"成功"但读到的是错误数据、测试通过但其实是假象。形态像 B 类，可回灌了 LLM 也看不出错，只能靠外部验证层或 HITL（12.6 缺口 1）。

**一条快速判法**：问"LLM 此刻是不是在等这个结果？"——是，就回灌；不是（它还没开始等，或者已经不用等了），就归代码。

#### A 类：LLM 没路可走的错（代码处理，确定性回归）

判据承接分界轴：**这个故障有没有卡在某个 LLM 指令的应答上？** 卡上了——LLM 有一条指令在等结果，而结果没来、或是坏消息——就把异常信息回灌进上下文，交给它自决（B 类）。没卡上，才归 A 类，两种情形：LLM 根本不在场（队列满、认证失败、Token 超限发生在它进来之前或之外），或者那条指令已经有了结局、系统正在收尾（轮次耗尽、执行超时、用户无响应、必须终止的兜底）。LLM 缺的常常不是办法，而是**信息**——它不知道自己在重复、不知道自己被拦了、不知道回传对不上号；把信息交给它，路就出来了。所以判据不是"错是谁引起的"。

测的是代码路径有没有按设计生效。这是 Agent 系统里少数**确定性可测试**的部分（12.5.4），因此可以进 CI 做阻断式门禁——失败即真 bug。

三类断言：

1. **策略生效与上限**：LLM 重试共 3 次尝试（退避 1s、2s；第 3 次失败即终止）、MCP 重连 ≤3、轮次 ≤25、单消息 ≤300s。到顶必须收住，而不是继续自旋。注意分界：连续 3 次 `(tool, md5(input))` 相同的**检测**在这一层（可断言），但检测到之后先回灌提醒 LLM 那一步属 B 类；A 类只管"回灌没救回来时必须终止"这道兜底。
2. **状态一致性**：终止后状态机回 IDLE/归档、`current_message_id` 清空、stream buffer 冲刷或丢弃有确定行为、内存态（`plan_confirmed` / `build_step`）重置、子任务级联取消。中途终止的收尾规则当前定义不全（6.4），对应用例标 `known-gap`。
3. **可见性（永不静默）**：任何影响结果的异常都要有用户可见反馈，A 类的提示语义是**通知并要求介入**——`message.error(fatal=true)` 或进入 SUSPENDED。对照 1.8.2 的"不推送 system.status 的场景"清单逐一复核。

一个易漏项：**证据不足的异常也归 A 类**。工具执行"成功"但读到的是错误数据——系统一切正常，LLM 拿着这个结果也看不出错。它形态上像 B 类（卡在工具应答上），实质判不出来，只能靠外部验证层（编译 / 测试 / schema 校验）或 HITL。这是当前最大空白（12.6 缺口 1），用例先标 `known-gap` 而不是 pass。

#### B 类：回灌给 LLM 自决的异常（采样评估）

这一类的成败不在模型单方面，而在一条三段链上——**韧性是链的联合属性，不是模型的属性**：

| 段 | 职责 | 断了的表现 |
|---|---|---|
| ① 工具产出**可判的**错误 | stderr / 退出码 / MCP 错误可读化 / 补足失败上下文（2.7.4 G4/G5） | 错误文本糊成一团，模型无从下手 |
| ② 框架把它**注入**下一轮上下文 | 1.8.2 第 2 级，形如"工具 'xxx' 执行失败: <原因>。请尝试其他方法。" | 错误被吞、被摘要掉、并发回填顺序错位 |
| ③ 模型据此**换方案** | 改入参 / 换工具 / 换路径 | 原样重试、礼貌地空转 |

**最常断的是第①段**。12.4.4 明写"错误注入的质量直接决定 LLM 能否正确修正"。用例判负时先按三段定位，再决定是改错误文本、改注入逻辑，还是记模型波动——归因错了，修的地方就全错。

判据分下界和上界，**两半都在才算这一层**：

- **下界（不能少）**
  - B1（代码层，可断言）：错误文本确实出现在下一轮的上下文里。
  - B2（轨迹层，可判）：LLM 下一轮的动作与产生错误的那次**存在差异**——工具名 / 入参 / 路径至少一处不同。这是"换方案"的机械判据，用来替代"轨迹合理"这类无法判定的措辞。
  - B3（轨迹层，可判）：错误文本含足以支撑判断的证据（失败原因、关键参数、可用的替代路径）。
- **上界（不能多）**——"由 LLM 自决"是无界的，无界的自决就是空转（12.4.3 自认："LLM 会礼貌地无限重试、可能越修越错"）：
  - 同一 `(tool, input)` 连续 3 次 → 已有（1.8.4）。
  - 同一错误**类型**累计 N 次但输入微变 → 当前只有缺口（12.4.5 自愈边界 / 12.6 缺口 6），标 `known-gap`。
  - 自愈消耗的轮次 / token 超阈值 → 与 11.6 成本预算联动。

可见性（永不静默）对 B 类同样生效，只是语义不同：B 类是**通知但不打断**——流程继续，用户在 system.status 里能看到异常发生过。这一条正是"B 类不是静默自愈"的依据。



#### 怎么测

B 类正常跑永远不会触发，**必须靠注入**。注入点选在**工具 / MCP / LLM 连接边界**——替身顶替真工具、stub 顶替真端点，不往引擎里打补丁。边界上有两条路：

- **造环境，让工具真失败**（推荐）：扰动 workspace、运行环境与外部端点，把条件摆成必然失败的形状——文件真的不存在、依赖真的没装、权限真的不够、端点真的连不上。控制的是**条件**，不是**结果**。
- **造假结果**：用替身工具顶替真工具，把应答换成事先写好的失败（`bash` 返回退出码 1 + stderr、`read_file` 返回"文件不存在"、MCP 返回 JSON-RPC error）。省事，但①段是编的——测的是"我写的那段话能不能流下去"，不是"工具真的会这么报错吗"。

选前者，因为①段（错误文本是否可判）正是三段链**最常断**的一段；拿一段编出来的文本去测它，等于自问自答。两条路都控制第①段、观察②③段，三段才分得开。

| 类别 | 怎么造 | 判什么 | 性质 |
|---|---|---|---|
| A 类 | 确定性故障注入：重试打满 3 次、轮次推到 25、request_id 改错 | 断言式：重试次数、终止状态、状态机回 IDLE、有无 `message.error` | 确定性，可进 CI 硬门禁 |
| B 类 | 注入一条**可判**的异常（工具失败 / 端点断开） | 轨迹式：错误是否进上下文、下一轮动作有没有变 | 非确定性，只能采样 |
| 未知异常 | 随机断依赖、随机杀协程 | 属性式：不崩、不死锁、能回合法态 | 注入确定、判定看性质 |

**B 类要抓三个检查点**，缺一个就没法定位：

1. 注入的**原始**错误文本（你造的那条）
2. 进入下一轮上下文的文本（是否被截断、被摘要掉、并发回填顺序错位）
3. 下一轮的动作（工具名 / 入参 / LLM 调用，与出错那次对比）

三段连起来看，判负时才知道该改哪里：①错误文本本身不可判（最常见）、②注入没到位、③模型没换方案。只记第三样，就会把①的锅记到模型头上。

**注入粒度**也要设计：一次性失败（测它换不换路）、持续失败（测上界——会不会一直试到停不下来）、第 N 次才失败（测死循环提醒那一类）。持续失败那组尤其值得做：自愈边界规则现在是缺口（12.4.5 / 12.6 缺口 6），持续注入正好能把"无界空转"暴露出来。

**制造真实异常：六族手法。** 造环境不是随口造，动手方式归结为六族。测试人员按族找把手，不必每条用例重新发明：

| 族 | 拉哪个把手 | 典型异常 |
|---|---|---|
| 缺 / 坏依赖 | 不装或人为卸载包；改 PATH、换解释器版本 | skill 脚本 `ModuleNotFoundError`、命令找不到 |
| 缺 / 坏文件 | 不创建目标文件、删掉它、造超大字文件、写入不可解析的内容 | 目标文件不存在、`@文件` 超限、脚本输入格式错 |
| 收紧权限 | 改 `permissions.yaml` 加 forbid、画像切 `:read-only`、改文件 ACL | 权限拒绝、护栏拦截 |
| 换外部端点 | `base_url` 指向本地 stub、`mcp-hub.json` 的启动命令改坏、只 accept 不响应 | 网络超时、Rate Limit、MCP 连接失败 |
| 改时序 | 延迟回投、丢一次回投、回错 `request_id`、乱序回填 | Client 回传超时 / 不匹配、对账判不出 |
| 制造不一致 | 让模型读过之后从外部改掉文件（race） | `edit_file` 匹配不到、写入冲突 |

**首批三条统一用「换外部端点」这一族**（本地 stub 断开 / 429）——故障落在 LLM 连接本身，任何用例都天然依赖它，不用编排 workspace，也就不会出现"注入的东西和 prompt 对不上"；其余五族留待后续用例。

**每条用例在表里怎么写。** 这一列的读者是**测试人员**，写法固定为「打法 / 步骤 / 预期」三段，「复原」按需（有落盘现场才写），且"步骤"要能照着敲：

```text
打法：缺依赖族 —— 人为卸载依赖
步骤：1) pip uninstall -y pandas
      2) 让 agent 跑 smart-charts 的脚本（它 import pandas）
预期：脚本非零退出，stderr 含 "ModuleNotFoundError: No module named 'pandas'"；
      该片段应原样进入下一轮上下文，且下一轮动作与出错那次不同
复原：pip install pandas，或整轮跑在可回滚的 venv 里
注意：模型可能自己 pip install 装回来而自愈
```

现状备忘：环境里当下就缺 `pandas` / `python-docx` / `pdf2image`，`smart-charts`、`docx`、`pdf` 的脚本现在跑就真挂——这几条不用造，直接可用。

**真跑的两个代价。**

1. **文本不稳**：真 stderr 含解释器全路径、盘符、平台转义，随机器变。所以"期望行为"里断言**可判的证据片段**（`[Errno 2]`、`ModuleNotFoundError`），不锁死原文——这反而更贴 B3"证据充分"。
2. **可自愈 ⇒ 不可重复**：模型可能真的把依赖装回去、把文件补出来，第二次跑就不再失败。用例必须**环境可回滚**（可丢弃的 venv、一次性 workspace），否则进不了 CI。这是真跑方案的成败点。

**FakeLLM 只能测到第②段**——错误有没有被正确注入，那是代码，可断言、可进 CI；第③段（模型据不据此换方案）必须真实 LLM 采样，同一注入跑多次看分布，红一次不代表代码有 bug。这是 B 类不该进阻断式门禁的原因。

### 第4层：自动化可持续测试

**目标**：保证测试体系不会腐烂。

将前三层的测试全部接入 CI/CD 流水线，每次 PR / merge 自动执行。不是一次性建完，而是与前三层同步演进——每写好一层测试，就接入 CI，做到可持续回归。

- 每次 PR / merge 自动跑全量测试
- 覆盖率报告
- 失败自动通知，阻断合并
- `fast`（FakeLLM）和 `slow`（真实 LLM 采样）通过 markers 区分调度频率
