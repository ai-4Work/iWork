# iWork Agent 测试理念

## 核心思想：信任递增金字塔

测试体系按照**信任递增**的方式组织，每一层建立在前一层的基础上，逐层扩大验证半径。这不是一个"测试套件"，而是一个**测试体系**——有分层、有阶段、有演进路径。

```
        ┌──────────┐
        │  第4层    │  CI/CD 可持续回归
       ┌┤  自动化    ├┐
       │└──────────┘│
      ┌┤  第3层       ├┐
      ││  韧性/鲁棒性   ││
     ┌┤  第2层          ├┐
     ││  轨迹/端到端      ││
    ┌┤  第1层             ├┐
    ││  组件测试            ││
    └────────────────────────┘
```

## 四层结构

### 第1层：组件测试

**目标**：验证每个零件本身是对的。

针对性地测试每个模块的功能，粒度到函数/类级别。这一层必须扎实——如果组件测试有遗漏，上层测试查出的问题就分不清是零件坏了还是协作坏了。

- 每模块独立，mock 外部依赖
- 通过标准：所有单模块测试 green，关键路径覆盖率达标

以下清单基于 `agent-client-serve-merry-meerkat.md` 技术详细设计文档，列出每个组件需要覆盖的测试功能点。


### 第2层：轨迹测试 + 端到端测试

**目标**：验证组件之间的协作是否正确。

"轨迹"指的是一个完整交互流程中组件之间的调用链——引擎收到 LLM 的 tool_use 后是否正确调用了 ToolDispatcher → ToolDispatcher 是否把结果正确注入回 ContextManager → SyncWaiter 是否正确暂停/恢复 → StreamBuffer 是否正确缓冲和推送。端到端测试则覆盖从 HTTP 请求进入到 NDJSON 流式输出的完整链路。

- 覆盖范围：Ask / Plan / Build 三种模式的完整协作流程、多 Agent 协作编排、Skill prompt 注入 → LLM 调用 → 工具执行的链路、消息排队与出队流程
- 通过标准：所有预定义的协作轨迹全部通过

### 第3层：韧性 / 鲁棒性测试

**目标**：验证系统在异常发生时能扛住，并按照预定策略恢复。

分为两类：

- **已知异常测试（confirmatory）**：针对设计文档中定义的 25 种异常场景和四级处理策略（重试 → 降级 → 暂停 → 终止），逐一验证恢复策略是否有效。覆盖所有组件——LLM 层、工具执行层、引擎层、用户交互层、数据层。
- **未知异常测试（exploratory）**：以模糊/混沌方式随机注入故障（随机断开依赖、随机协程超时），验证系统不会崩溃、不会死锁、最终能回到合法状态。目的是发现"没想到的崩溃路径"。

### 第4层：自动化可持续测试

**目标**：保证测试体系不会腐烂。

将前三层的测试全部接入 CI/CD 流水线，每次 PR / merge 自动执行。不是一次性建完，而是与前三层同步演进——每写好一层测试，就接入 CI，做到可持续回归。

- 每次 PR / merge 自动跑全量测试
- 覆盖率报告
- 失败自动通知，阻断合并
- `fast`（FakeLLM）和 `slow`（真实 LLM 采样）通过 markers 区分调度频率
