# 权限控制 · 运行逻辑（决策链 + 场景速查）

> 姊妹篇：字段与实现细节见 [docs/chapters/权限控制.md](./权限控制.md)。本文不重复字段表，只讲**一条工具请求从服务端判定到客户端落地，先后走了什么、遇到什么情况落在哪一档**。
> 默认前提（除另行标注外）：会话为 Windows 客户端 → `shell_env=powershell`；画像 `:workspace`；`approval_policy: on-request`；配置以当前 `server/permissions.yaml` 为准。

## 0. 三层防线 + 两把尺子（先建立心智模型）

把权限体系拆成三层，各有各的活：

| 层 | 在哪 | 干什么 | 对应物 |
|---|---|---|---|
| ① 审批层 | 服务端 `evaluate()` | 判一条请求 **要不要问人**（自动 / 弹窗 / 直接禁） | verdict 三态 |
| ② 策略包 | 服务端 `build_policy()` | 随每次 `client.tool_request` 下发本会话的 filesystem/network/sandbox | policy 包 |
| ③ 执行层 | 客户端 Electron | **真跑**：命令与 stdio MCP 套受限令牌沙箱（写墙）/ 文件工具裸写 / http·sse MCP 与联网命令走本地代理按域名判 | 执行与拦截 |

**两把尺子互不相干，这是理解全篇的钥匙：**

- 尺子 A = 服务端 verdict（`skip` / `needs_approval` / `forbidden`）→ 只管"要不要问人、要不要硬拒"，**不决定是否沙箱**。
- 尺子 B = 画像 → 决定策略包里的 `sandbox.required`。除 `:full` 画像外**恒为 `true`**——即命令类工具几乎总是要进沙箱。

推论（后面会反复出现）：
- **allow 只免审批，不代表免沙箱**。`git status` 配 allow 会跳过弹窗自动跑，但**仍套受限令牌**。
- **needs_approval 批准后，命令仍进沙箱**。弹窗过的是"问人"这关，执行层的令牌还在。
- 反过来，被沙箱拒 ≠ 一定弹过窗；命令写工作区外是**无弹窗直接被令牌拒**（见 §3）。

一句话：**服务端管"判"，客户端管"执行与拦截"，沙箱是命令类工具的执行墙，弹窗只是审批闸。**

## 1. 判定顺序总览（先判什么、再判什么）

先给一张**从判定到落地的全链路总图**（含沙箱怎么用），把整体顺序钉在脑里，再往下分节拆细节：

```
一条工具请求（工具名 + 参数 + 会话 shell_env）
   │
   ▼
① 选画像 default_permissions
   ├─ 命中 :full（disabled）→ 短路：一律 skip + 不建沙箱（命令也裸机）
   └─ 其它（:workspace / :read-only / 自定义）→ 继续
   │
   ▼
② 按工具分类 classify_tool ── 决定“怎么判”
   ├─ file    → 判【路径】deny / 可写根 / 越界         （§2）
   ├─ command → 判【命令】tool_rules / 危险子串        （§3）
   ├─ network → 服务端不判：恒 allow；域名判在客户端代理（§4）
   └─ other（记忆 / MCP / skill）→ 服务端不判：恒 allow → skip；落地分道见 ⑥（§5）
   │
   ▼
③ 判定结果 → 内部决策  allow | prompt | forbidden
   │
   ▼
④ approval_policy 收尾（只处理 prompt）
   ├─ never / granular 键关 → forbidden
   └─ 默认                 → needs_approval
   （allow 不变 → skip；forbidden 不变）
   │
   ▼
⑤ 按 verdict 派发 ── 是否弹窗 ──
   ├─ forbidden      → 不派发：错误“权限禁止”回模型（无卡片）
   ├─ needs_approval → 弹窗审批：批准→执行；拒绝→错误（卡片 pending）
   └─ skip           → 不弹窗：自动执行（卡片 running）
   │
   ▼
⑥ 客户端执行层 ── 这条操作【进不进沙箱】
   ├─ file（write/edit/read/glob/grep）
   │    → 逻辑定死：不走沙箱、只弹窗
   │      主进程 node fs 裸读写；越界/敏感只靠弹窗闸：deny→拒 / 越界→弹窗 / 通过→裸写（§2）
   ├─ command（bash）
   │    → 进沙箱：sandbox.required=true（非 :full）→ 受限令牌（§3）
   │      写工作区内 → 成功；写工作区外 → OS access denied（命令失败）
   │      （:full → sandbox.required=false → 裸机执行）
   ├─ network（web 联网）
   │    → 服务端已 skip；客户端【本地代理】在 CONNECT 判域名：
   │      白名单未命中 → 按 approval_policy + unknown_domain 弹网络确认 / 拒（§4）
   └─ other（记忆 / MCP / skill）→ 服务端恒 allow → skip（无命令级弹窗，§5）
        ├─ 记忆 → 服务端 DB 直连；skill → 纯上下文注入进上下文
        │    （两者都不 spawn 本地进程、不套墙，仍"信任默认"）
        └─ MCP 工具：客户端按名带 {server_id}_ 前缀认 server（api.ts）
             ├─ stdio 通道（本地子进程）
             │    └─ policy.sandbox.required?
             │         true（非 :full）→ 写墙：dsh runner 受限令牌，
             │            写 workspace+会话 temp 内→成功；写外→OS access denied
             │         false（:full / 无 workspace / 沙箱不可用）→ 直连回退（告警）
             └─ http / sse 通道（出网、无本地进程可包）
                  └─ 注入 walledFetch → 本地代理【网络墙】CONNECT 判域名：
                      白名单 allow / 未知域名弹网络确认 / deny 拒（§5）
```

上面的 ①–④ 是**服务端判定**（`server/tools/permission.py` `evaluate()`，固定顺序），⑤–⑥ 是**客户端落地**（agent-client）。四类工具里**只有 file / command 真进判定**；network / other 服务端恒 allow：网络那类的域名判定挪到客户端代理，other 整类落到客户端执行层按底层通道收编（§5）。执行层的墙分**进程级**与**域名级**两档——进程级（受限令牌沙箱）罩 bash 与 stdio MCP 这类会 spawn 本地子进程的通道；域名级（本地代理）罩联网命令与 http/sse MCP 的出网。file 靠路径判定+弹窗、不套令牌；记忆走服务端 DB、skill 无进程无出网，两者不套墙。

> skill 与 MCP 工具在服务端都归 **other**（不在 file/command 集合）→ 恒 allow → skip：**引擎不判路径、不做命令级弹窗**（MCP 只有 (server, tool, args)、没有命令文本，命令级弹窗整条不做）。但"服务端不判" ≠ "客户端不防"：执行层按**底层通道**收编——stdio MCP 与 bash 同归子进程通道、套同一把受限令牌写墙；http/sse MCP 客户端出网、走本地代理网络墙（都在客户端，见 §5）。记忆走服务端 DB、skill 是纯上下文注入（无本地进程），只有这两类仍属"信任默认"——别把 other 当铁板一块。

两个词容易混，先分清：

- 内部决策 `allow | prompt | forbidden`：分支判出的"原始结论"（①②③产出）。
- 对外三态 `skip | needs_approval | forbidden`：`prompt` 经 `approval_policy` 转换后**用户最终看到的行为**（④产出）。

### verdict 三态 → 用户看到什么

| verdict | requires_approval | 用户看到 | 说明 |
|---|---|---|---|
| `skip` | `false` | 无弹窗，直接执行 | 命中 allow 规则 / 没踩任何东西 |
| `needs_approval` | `true` | 工具卡片挂起，弹确认（批准/拒绝） | 命中 prompt 规则 / 危险启发式 / 越界写等 |
| `forbidden` | 不派发 | 模型收到错误"权限禁止"，无卡片 | 命中 forbidden 规则 / deny 路径 / 全局 never |

## 2. 文件类工具分支（write / edit / read / glob / grep）

**服务端判定**（`_evaluate_file`）——逐路径比对，**是唯一会解析路径的分支**：

```
文件工具，拿到 path
  │
  ├─ file_tools.path_check=false         → allow（关掉路径预检）
  ├─ 无 path 参数                         → allow（交给执行侧兜底）
  ├─ 命中 deny 规则（.git/**, .env …）   → forbidden（不弹窗，服务端直接拒，读同受拦）
  ├─ 写工具(write/edit)：
  │     ├─ 在可写根内(workspace / tmpdir / 自定义) → allow → skip（自动写）
  │     └─ 越界（在可写根外）                   → prompt → 弹窗
  └─ 读工具(read/glob/grep)：只受 deny 拦，不判可写根 → 无 deny 即 allow
```

⚠️ **执行真相（重要）**：write/edit/read 在客户端是**裸 node `fs` 读写**（agent-client `fileOps.ts` 的 `file:write`/`file:edit`），**不经过沙箱、不套受限令牌**。`policy.sandbox.required` 对文件工具**不起执行作用**——只在工具卡片上预置个"沙箱运行"角标（见 §7 不对称点）。

> 因此对文件工具而言：**工作区内写 = 信任（skip 裸写）；工作区外写 = 弹窗是唯一闸门，批准即裸写**。.git/.env 走 forbid，连弹窗都没有。

## 3. 命令类工具分支（bash）

**服务端判定**（`_evaluate_command`）——**不解析路径**，只按会话 shell 语法做词法匹配：

```
一条命令
  │
  ├─ ① tool_rules 精确 token 前缀匹配（按会话 shell 分词）
  │     分词：powershell → Windows 分词(保留 C:\ 反斜杠) + 大小写不敏感
  │           bash/zsh    → POSIX 分词 + 大小写敏感
  │     规则可按 shell 归属过滤：powershell | posix | all（缺省 all）
  │     命中即返回 allow | prompt | forbidden（一条顶格，不继续往后扫）
  ├─ ② 危险命令启发式 dangerous_patterns（子串 contains）
  │     配置了 → 全量替换内置默认（对所有 shell）
  │     没配置  → 按会话 shell 自动选：POSIX 集（rm -rf /、mkfs.、chmod 777 …）
  │                + PowerShell 会话并集盘符级操作（Clear-Disk / Remove-Partition /
  │                  Format-Volume / format c: …）
  │     命中 → prompt（问人）
  └─ ③ 都没命中 → allow → skip（自动执行）
```

**执行真相（重要）**：命令走客户端 `file:exec`（agent-client `fileOps.ts`），**沙箱在此生效**：

- `policy.sandbox.required === true`（除 `:full` 外都这样）→ `runSandboxed`：WRITE_RESTRICTED 受限令牌，写白名单 = **命令工作目录（默认即 workspace 根）+ 会话临时目录**；白名单外的写（别的盘符 / 目录）OS 层 `access denied`。fail-closed：`doctor()` 探测沙箱不可用就直接报"沙箱执行失败"，**绝不静默降级裸机**。
- `policy.sandbox.required === false`（只有 `:full`）→ 裸机执行，无令牌。

于是出现和文件工具**正好互补**的现象：

| | 文件工具（write/edit） | 命令工具（bash） |
|---|---|---|
| 工作区外写入 | 有弹窗（needs_approval），批准后**裸写** | 通常**无弹窗**（skip），但被沙箱**令牌拒** |
| 谁真正挡 | 弹窗是唯一闸门 | 沙箱 OS 层是执行墙 |
| .git/.env deny | 服务端 forbid | 沙箱白名单是整根，拦不住（见 §7） |

> **组合命令为什么靠沙箱兜**：前缀匹配只看开头 token。`git status && Remove-Item -Recurse -Force C:\x` 命中 `git status` 的 allow 规则即整体 skip 自动跑——真正拦住强删的，是它作为命令进了沙箱、对 `C:\x` 的写被令牌拒掉。

## 4. 网络类分支（web_fetch / web_search / 联网命令）

- **服务端不判域名**：网络类工具一律 `allow` → `skip`（服务端也拦不住 HTTPS 明文外的域名，见源码 docstring）。"要不要放行某个域名"被**整体下放到客户端本地代理**，在 **CONNECT 时**判定。
- **客户端代理判定链**（只在画像 `network.enabled=true` 时启用；`:workspace` 默认 `enabled=false`）：
  1. 顶层 `network_rules`（host + protocol 精确）先比 → allow / prompt / forbidden；
  2. 未命中 → 比画像 `domains` 白名单（deny 优先于 allow；`*.x` 只子域、`**.x` 含主域、`*` 全匹配）；
  3. 仍未命中（未知域名）→ 受**全局 `approval_policy` 总闸**约束：`never` → 一律拒；`granular` 且 `network:false` → 拒；否则再按 `unknown_domain`：`ask` → 客户端弹网络确认，`deny` → 画像级禁问直接拒。
- ⚠️ **`network.enabled: false` = 放行不拦，不是禁网**。`server/permissions.yaml` 里 `:workspace` 默认 `enabled:false`，含义是代理**不判定、不拦截、不弹窗，所有连接直接放行**。真要启用域名管控，得像示例里的 `dev` 画像那样开 `network.enabled: true` 配 `domains`。

`approval_policy` 这条**总闸会随 policy 包下发到客户端**（`network.approval_policy` 字段），所以它在网络这里管的是客户端代理的 Ask；而它在服务端管的是命令/文件类 prompt（见 §6）。

## 5. 外部工具分支（other：记忆 / MCP / skill）——审批恒 allow，执行层按底层通道收编

服务端 `classify_tool` 只认内置白名单，任何**记忆 / MCP / skill 工具都归 other**（`_evaluate_other`）：恒 allow → skip，不判路径、不做命令级弹窗。整类"其它"在客户端执行层按**底层通道**区分防护：

| 落点 | 底层通道 | 客户端执行层 |
|---|---|---|
| 记忆（load_memory / write_memory） | 服务端 DB 直连 | 无本地进程可套；信任默认 |
| skill（SKILL.md / skillDir） | 纯上下文注入（客户端裸读进上下文） | 不 spawn 进程、不套墙；要跑脚本靠模型发 bash（那套走沙箱） |
| MCP 工具（`{server_id}_` 前缀） | stdio → 客户端 spawn 本地子进程；http/sse → 客户端出网 | **收编：两道墙**（见下） |

MCP 的收编与 bash 同源，但要说清"同在哪、不同在哪"：bash 与 stdio MCP 都有"客户端 spawn 本地子进程"这半边——同一把受限令牌写墙、同一个代理 env 都能罩住（同类在**执行层**）；差别只在**审批判据**：bash 有命令文本，能走 tool_rules / 危险启发式那套命令级判定；MCP 只有 (server, tool, args)、没有命令文本，**命令级弹窗整条不做**（不同类在**审批层**）。所以 MCP 受控面 = **两道墙，无第三道（命令级弹窗）**：

- **写墙（进程级，只 stdio）— M1 已落地**：`mcpManager` createTransport 的 stdio 分支在 restricted 模式用 `buildSandboxedSpawnParams`（agent-client `sandbox.ts`）把 SDK `StdioClientTransport` 的 spawn 参数换成 runner 入口——`{command: electron(RUN_AS_NODE), args:[console-shim, --workspace <ws>, --temp <会话temp>, --mode workspace-write, --, <server命令>…], env(+DSH_*/ELECTRON_RUN_AS_NODE), cwd: <ws>}`，server 从 spawn 起被 WRITE_RESTRICTED 令牌限在**该 workspace + 会话 temp**。console-shim 隐藏黑窗；runner 的 Kill-On-Close Job Object → 关 runner 级联杀 server（长驻 MCP 孤儿回收由包内兜底）。写墙根跟该次执行的 workspace 走，切换 workspace → 关旧建新。fail-open 回退（直连 + 告警）仅限三类例外：`:full` / 画像 disabled（`sandbox.required=false`）、无 workspace、沙箱 doctor 探活失败。
- **网络墙（域名级）— M2 已落地**：http / sse MCP 无本地进程可包、套不上写墙，只能落网络层——`mcpManager` 给 sse / streamable-http transport 注入 `walledFetch`（undici `ProxyAgent` dispatcher → 本地代理地址），目标域一律经本地代理 CONNECT → 走 §8.6 `decideHost` 判定链（白名单 / network_rules / approval_policy / unknown_domain），allow 直通、ask 弹窗、deny 拒。stdio MCP 进程内连接靠注入的 `HTTPS_PROXY` env 自然走代理。代理未就绪（启动竞态）时 walledFetch 回退直连并告警。
- **无命令级弹窗 → 准入靠接入级信任**：服务端对 MCP 维持 other 恒 allow → skip（§1 ⑥，设计如此）；客户端 `api.ts` 前缀命中后校验该 server **已 connected**（未连接即拒）。墙内读写全自动、不逐调用打断。

**生命周期（会话级惰性执行实例）**：发现与执行分离。发现（`connect`）早连一次读 `tools/list` schema 并上报（listTools 是固定服务端代码、无模型输入，发现实例不保留给执行）；首个受控 `mcp:call-tool` 按"当前 `policy.sandbox.required` + 该 workspace"惰性判定，与现有实例不符则**关旧建新受限实例**，同 (workspace, restricted) 复用，策略 / workspace 变化即重建（重建串行化，避免并发双换）。**「未做 M3」**：并发多 workspace 同 server、跨会话空闲受限实例正确关停与无泄漏、发现层裸连窗口的进一步收口。

**客户端判断逻辑怎么走**（执行通道分派，非服务端类别）：

```
tool_request 到达（带 verdict + policy 包）
  ├─ 本地文件通道（write/edit/read/glob/grep）→ 裸 fs；路径判定/弹窗服务端已过，不套墙
  ├─ 子进程通道（bash / exec_command / stdio MCP）
  │    └─ policy.sandbox.required?
  │         true（非 :full）→ 受限令牌沙箱
  │             bash      → 每次调用 spawn 一个新沙箱进程
  │             stdio MCP → 首个受控调用惰性建受限实例、(workspace, restricted) 复用，切换即重建
  │         false（:full / 无 workspace / 沙箱不可用）→ 裸机 spawn（直连回退，仅这三类例外）
  │    env 一律注入 HTTPS_PROXY → 联网走代理域名墙
  └─ 主进程网络通道（web_fetch / sse + http MCP）→ 无本地进程可套墙 → 注入 walledFetch（undici
       ProxyAgent dispatcher）→ 本地代理 CONNECT 判域名
```

**别高估墙（与 bash 沙箱同源 + MCP 特有）**：
1. **写墙只限写、不拦读**——墙内 filesystem MCP 仍可读全盘（令牌层无单文件 deny、只认写白名单）；
2. **写墙是范围墙、不是动作墙**——墙内删 / 覆盖 / 破坏性 fs 全放行，且 MCP 无 forbid 启发式兜底；
3. **写墙只罩 stdio、罩不到 http/sse**——http/sse MCP 无本地进程，进程级写墙不适用，靠网络墙兜出网侧；其对本地文件系统的读写不受本墙约束；
4. **网络墙 ask 的 UX 与 bash 联网一致**（NetworkConfirmDialog，30s 超时默认拒）——MCP 不做命令级弹窗，但**域名级确认弹窗照常**。

一句话：**MCP 与 bash 在执行层同归子进程通道、受同一把写墙约束；差别只在 MCP 无命令文本 → 不做命令级弹窗，只留"写墙 + 网络墙"，准入靠"用户接入 server"的接入级信任。** http 类够不着写墙，只能落网络墙（M2）；并发多 workspace / 空闲回收等收口 = M3（未做）。

## 6. 全局开关 approval_policy：同一把闸、两处生效

`approval_policy` 是"要不要问人"的总闸，取值与作用：

| 取值 | 服务端（命令/文件类的 prompt） | 客户端代理（网络未命中白名单） |
|---|---|---|
| `on-request`（默认） | prompt → needs_approval（弹窗） | 按 `unknown_domain` 再细化（ask→弹窗 / deny→拒） |
| `never` | 所有 prompt → forbidden（连弹窗都没有） | 一律拒 |
| `granular` | 按类别键开关，关着 → forbidden | `network:false` → 拒；`true` → 按 `unknown_domain` |

granular 的键与判定类别的对应（服务端 `_translate`）：

| granular 键 | 管辖 |
|---|---|
| `shell` | 命令类工具的 prompt（tool_rules 命中 / 危险启发式） |
| `rules` | 文件类工具的 prompt（越界写等，路径规则） |
| `network` | 网络未命中白名单时的 Ask（客户端代理执行） |

## 7. 已知不对称 / 别踩坑（当前实现诚实版）

这些是**代码现状**，读本文档时最容易产生"应该不是这样吧"的地方，先摆出来：

1. **"沙箱运行"角标对文件工具是预置的、不代表真套令牌**。卡片 `sandboxed = policy.sandbox?.required === true`（agent-client `chatStore.ts`），对 write/edit/read 一律照 policy 画成 true，但它们的执行是裸 fs 写、没套令牌。真实沙箱值只在 bash（`file:exec`）回填。→ 文件工具卡片标注偏乐观。
2. **命令改工作区内 `.env` / `.git` 拦不住**。沙箱写白名单是**整个 workspace 根**（粗粒度），deny 单文件（`.env`、`.git/**`）不在令牌层生效；命令分支服务端又不解析路径。所以 `Set-Content .env …` 这类命令若没命中 tool_rules / 危险模式，会 skip 且沙箱放行（因为就在根内）。**文件级 deny / 只读约束目前只对文件工具生效。**
3. **`sandbox.required` 只对命令类工具生效**，且除 `:full` 恒 true。它不反映"这条命令危不危险"，只反映"画像档位"。
4. **服务端网络类一律放行**：域名的 allow/deny/ask 全在客户端代理，服务端日志看不到域名拦截结论（要看去客户端代理侧）。
5. **MCP 与 skill 的防护不对称**：MCP 已被客户端执行层收编到两道墙（stdio → 受限令牌写墙；http/sse → 本地代理网络墙），见 §5；skill 仍是"信任默认"的**纯上下文注入**（只读 SKILL.md / skillDir 进上下文、不 spawn 沙箱进程；要跑脚本靠模型发 bash，那套走沙箱）。别把服务端"都归 other 恒 allow"当成"客户端都不套墙"——审批层同档，执行层按底层通道分（§5）。
6. **「16-内置工具集成」按执行位置把工具分三类、说"MCP 也由客户端执行"，别据此推"都在沙箱执行"**。执行位置只决定"在哪跑"；防不防护按**通道**分（本地文件 / 子进程 / 出网），不是按执行位置、也不等于服务端类别——记忆 / skill / MCP 都归 other，只有 MCP（子进程 / 出网那两半）被收编（§5）。位置与防护是两把正交的尺（见 §0）。

## 9. 快速自测 / 调试引导

碰到"为什么没弹窗 / 为什么被拒 / 为什么命令写不出去"时，按这个顺序定位：

1. 这条**工具属于 file / command / network / other 哪类**？→ 决定走哪个分支（§2/§3/§4/§5）。
2. 服务端 verdict 是 skip / needs_approval / forbidden？→ 看 `evaluate()` 三态（§1）。forbidden 会以"权限禁止"错误回给模型，弹窗不会出现。
3. verdict=skip 的命令却写不出去？→ 去看**执行层**：是不是沙箱令牌拒的（access denied）——skip ≠ 免沙箱（§0）。
4. 文件工具批准了却担心越界？→ 记住文件工具是**裸写**、弹窗是唯一闸门（§2/§7.1）。
5. 网络连不通 / 该弹没弹？→ 画像 `network.enabled` 是否 true（`:workspace` 默认 false=全放行），域名是否命中白名单，`approval_policy` 总闸（§4/§6）。

> 判定结论（服务端）看引擎 `evaluate` 路径；域名拦截结论在客户端代理侧（proxy decideHost），两端日志各自查。

## 10. 网络墙的执行通道覆盖与缺口：谁真被拦、谁只是“配合”、边界在哪

把 §4 的“域名墙在客户端”落到执行细节，就是这一节：**“联网会被代理拦”这句话，对不同执行通道可靠度完全不同**。墙本质是**域名级、协作式**的本地代理——只拦“愿意或被迫走 `127.0.0.1:<port>` 的流量”，没有 OS 级出口封禁。可靠度分层追到根上就是一句——**流量走不走代理由谁决定**：应用主动读配置、决定改道，还是网络层被动强制、应用不知情。先把送流量进门的几种通用方式摊开（10.0），再落本工程的三手段（10.3）。

### 10.0 送流量进墙的通用方式：谁决定走不走代理（主动 vs 被动）

先钉一个事实：**任何拦截点（代理服务）都不会自己抢流量**——想拦，得先把流量“送”到它面前。通用方式就三类，主线只有一条：**走不走代理服务由谁决定——是应用主动去读配置、决定改道，还是网络层被动强制、应用根本不知情。**

| 方式 | 谁决定 | 主动 / 被动 | 覆盖 | 可靠性 | 应用举例 |
|---|---|---|---|---|---|
| 环境变量代理（`HTTP(S)_PROXY` / `ALL_PROXY`） | 应用的网络库读 env 后决定改道 | **主动**（协作） | 读到该 env 的进程（及子进程）里、且库认 env 的请求，通常只 http/https | 对方乐意读才进 | 命令行里认 env 的库：curl / wget、python（requests / httpx）、rust reqwest——`export HTTPS_PROXY=…` 后自动改道（本工程手段三） |
| 系统代理设置（OS 代理偏好） | 应用 / 库选择“使用系统代理”才走 | **主动**（协作，但多数浏览器 / 桌面 App 默认读） | 愿意读系统代理的应用 | 应用不用就没用 | 浏览器 / Electron / 多数桌面 App：Windows“代理”设置、macOS 网络偏好填好即默认跟随（如 Clash 开“系统代理”后 Chrome 就走） |
| TUN / 透明代理 / 网关 | 网络层改路由、流量被强制劫走 | **被动**（强制） | 进入该网卡 / 网关的全部 IP 包：任意 TCP / UDP、任意协议 | 唯一“全经过” | 游戏加速器、全局 VPN / TUN 模式（Clash TUN、Surge）、公司 / 路由器网关——连 SSH、游戏、UDP 等非 HTTP 流量也能接管 |

区分就一句：**主动 = 应用逻辑里真有“读配置 → 决定改道”这一步**（env、系统代理都算）→ 范围受“谁愿意读、读不读得懂”限制、天然会漏（不读 env 的应用、非 http 协议的流量都不进，10.2 展开协作式上限）；**被动 = 应用不读也不知情、被网络层强制** → 只有 TUN 那一档，代价是它在网络层、见不到“域名”这种应用层语义，想按内容细判得上 TLS 卸载 / MITM（本工程没用这档，见 10.6.7）。

不管哪种方式把流量送到，拦截点干的事都一样三件：**收连接 → 按目标判放不放行（allow / ask / deny）→ 放行则转发（明文 http 绝对式）或开隧道（CONNECT，https）**。env / 系统代理送到的是**应用层代理**（判定只到 host，见 10.1）；TUN 送到的是**网络层**，没有“代理解析请求”这一步。本工程的“三手段”是把 env 那类主动档落到具体客户端的办法（代码显式指定 walledFetch、进程内钩子 shim，见 10.3）；可靠度排序见 10.7。

### 10.1 TCP CONNECT 代理：原理与流程

这一节把 TCP CONNECT 代理讲透——它是什么、两种工作模式怎么选、一次 https 请求到底怎么走、代理能看见什么、为什么看不见内容。不依赖代码也能读懂，末尾落到 agent-client `proxy.ts` 的实现（判定链细节见 §4）。

**墙不是“转发抓包代理”，是开隧道的 CONNECT 代理**

本章说的“墙”，是一个跑在 `127.0.0.1:<随机端口>` 的 **HTTP CONNECT 代理**（agent-client `proxy.ts`，零依赖 node http）。它和“帮你抓网页 / 转发请求”的代理不是一回事：**不替客户端发起请求、不读请求内容**，只做一件事——在“要联网的工具进程”与目标服务器之间**开一条 TCP 隧道**，并在开隧道前对目标域名做一次 allow / deny / ask 判定。为什么是“隧道”而不是“转发”？看下面两种模式的差别。

**HTTP 代理的两种工作模式：转发 vs 隧道**

- **转发（absolute-form 绝对式请求，仅明文 http）**：客户端不直连目标，而是把整条请求“写”给代理——请求行是绝对式的 `GET http://host:port/path HTTP/1.1`。代理**看得见 URL 里的路径**，由它替客户端连上游、把响应转回；相当于一封“拆开看过再投递”的信，内容对它透明，它还能缓存 / 改写。
- **隧道（CONNECT）**：代理**不拆信、只接管子**。客户端先请代理去连目标，代理连上后回一句“通了”，再把两端 socket 对接；此后客户端与目标之间直接互丢字节，代理原样搬运、一个字不看。

一句口诀：**转发代理“看得见内容、替你去取”；CONNECT 代理“看不见内容、只替你搭路”。** https 走不了转发、只能走隧道，原因见下。

**落到真实客户端，就是一句对应：http 走转发、https 走隧道。** 这层选择不由代理决定——本地墙是同一个进程、同一个 `127.0.0.1:<port>`，只是开了两个入口：收到 absolute-form 请求走转发（`proxy.ts` `server.on('request')`），收到 CONNECT 走隧道（`server.on('connect')`）；走哪条由**客户端 HTTP 库按协议自己挑**。为什么这样分？http 内容是明文，客户端能把完整 URL 亮给代理、让代理“代取”最省事；https 内容是端到端加密，客户端亮不出明文（除非 MITM，而本墙不做），只能先请代理“开条隧道”再自己握手。两条入口的 allow / deny / ask 判定都收口到同一个 `decideHost`、只判 host，拦不拦与走哪条无关。

**CONNECT 是 HTTP/1.1 里的一个普通方法**

`CONNECT` 不是某代理软件的私有协议，它就是 HTTP/1.1 定义的一个方法，平时不用于“取网页”。客户端向代理发一行：

```
CONNECT www.baidu.com:443 HTTP/1.1
Host: www.baidu.com:443
```

语义是：“请你替我与 `www.baidu.com:443` 建立一条 TCP 连接；连上之后这条连接不再走 HTTP 那套，我们把它当裸管道，直接往里丢字节。”客户端**不用改一行代码**——HTTP 客户端库普遍约定读环境变量 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`，一旦有值就把“直连目标”改成“先连到代理、由代理转连目标”。本地墙正是靠把这个变量注入子进程 env，让遵守约定的客户端自己“送上门”（进代理的方式见 10.3）。

**为什么 https 非隧道不可**

TLS 握手是客户端与目标服务器**端到端**的密钥协商：只有目标持有自己的私钥、只有通信双方能完成握手。代理既没有目标的私钥、也插不进密钥交换，**“替客户端握手”行不通**——因此 https 流量代理唯一能做的，就是把路搭好、让双方自己握。反过来说，能被绝对式转发的只有明文 http。而今天绝大多数出网是 https，所以“看到 CONNECT 请求”几乎就等于“墙在起作用”。

**一次 https 请求走本地墙的完整流程**（与 `proxy.ts` 处理一致）：

```
CONNECT 不是客户端"真正要发"的请求，而是那条真实 https 请求被改道后的"先开隧道"动作。
真正起点在工具代码里的一行联网调用：

工具进程里真正要联网的是这行业务代码：
   fetch("https://www.baidu.com/s?wd=天气")    # 普通 https GET，本应直连 www.baidu.com:443
      │  但进程 env 被注了 HTTPS_PROXY=127.0.0.1:<port>（墙的地址）
      ▼
客户端 HTTP 库把这行请求"改道"：不直连 baidu，先连本地代理——于是它
对代理发的已不是 GET，而是一行"替我开条隧道"的元请求：
   ① CONNECT www.baidu.com:443 HTTP/1.1        # 不是业务请求，是改道后的前置动作
      │
      ▼
本地代理 server.on('connect') 收到这行 CONNECT
   │ 解析请求行 → 目标 host:443（只取这行里的域名，不解正文）
   ▼
decideHost(www.baidu.com) → 三种结论
   ├─ deny → 直接回 403，隧道不开（工具表现=连不上）             [终]
   ├─ ask  → 弹网络确认窗（同一 host 复用一次弹窗；30s 超时默认拒）
   │         ├─ 批准 → 该 host 记入会话缓存（同会话后续直通）→ 放行
   │         └─ 拒绝 / 超时 → 回 403，隧道不开                   [终]
   └─ allow（ask 批准也并入这条）→ 放行
      ▼
放行执行：代理主动 netConnect 去连 www.baidu.com:443
   ├─ 连上 → 回 200 Connection Established；把客户端抢跑的 head
   │         连同之后双向字节 pipe 给对端 → 隧道打通（下格 ②）
   └─ 连不上 → 回 502，隧道不开                                  [终]
      ▼
② 原客户端 ↔ 目标服务器之间建立裸 TCP 隧道
   之后 TLS 握手成功，那条真正的 GET（fetch 的那条）才作为
   第一条业务请求原样流过隧道；代理全程只转发、不解密
```

上图把「真实请求 → 改道 → 代理判定 → 放行连上游 → 隧道」串在了一起，`deny` / `ask` / `allow` 的分支只画到主干。下面用文字按 `proxy.ts` 的真实顺序再拆一遍（第 1、2 步发生在**工具进程侧**，第 3 步起才是代理收到 CONNECT 后的处理），把图里压掉的判定链顺序、`head`、`502` 等细节补全：

1. **发现代理地址**：进程读 env 的 `HTTPS_PROXY`（本地墙注入），把“连目标”改为“先连 `127.0.0.1:<port>`”。
2. **发 CONNECT**：客户端向代理发 `CONNECT www.baidu.com:443 HTTP/1.1`。TLS 客户端常“抢跑”——同一连接上可能已跟着发出最早的几个 TLS 握手字节（称为 `head`）。
3. **解析目标**：代理 `server.on('connect')` 收到，从请求行解析出目标 host（+端口）；实现是 `new URL('http://' + req.url)` 取 `hostname`。
4. **判定**：`decideHost(host, 'https')` 出三态——`deny` → 回 `403`、隧道不开（工具表现为“连不上”）；`ask` → 弹网络确认，30s 超时默认拒；`allow` → 进入下一步。（判定链顺序：策略启用 → 会话缓存 → 精确规则 → `deny_domains` → `allow_domains` → `approval_policy` 总闸 → `unknown_domain` → 默认 ask，细则见 §4。）
5. **连上游、回 200**：放行后代理 `netConnect` 主动去连目标 443；连上先回 `200 Connection Established`，再把抢跑的 `head` 字节与之后的双向流 `pipe` 起来 → 隧道成立。
6. **隧道内走业务**：客户端与目标做正常 TLS 握手 + 请求 / 响应；代理只转发字节、从不解密。
7. **拆隧道**：任一端断开即拆——客户端异常则销毁上游；上游连不上则回 `502`。

**代理究竟能看到什么：只有 host**

回看流程，代理只在第 3 步从 CONNECT 请求行拿到 `host:port`，其余一切都不可见：隧道里是端到端 TLS，路径 / 请求头 / 正文对代理全是不透明字节。判定粒度因此只能是“域名放不放行”，拦不了站点内某个路径 / 某类内容——这正是“网络判定只到 host”那句话的出处。

（精确一点、不夸大：隧道字节对代理是“流经但不过问”，本实现是纯 `pipe`、从不解析。技术上若想再挖一点，也只能去读 TLS 握手 ClientHello 里的明文 SNI 字段——它同样够不到“URL 路径 / 内容”这一层，且 ECH / DoH 还能再把它藏起来。结论不变：按内容拦在本设计里不存在。）

**明文 http：绝对式能看路径，放行仍只按 host 判**

明文 http 走另一个入口：客户端以绝对式请求打到代理，触发 `server.on('request')`。此时 URL 是完整的，代理技术上看得见路径，但放行与否仍只取 `URL.hostname` 进同一个 `decideHost`——只看“这个域放不放行”，不细看路径；放行后由代理替客户端向上游转发（改写 host 头）。

**想看内容只有 MITM 一条路 —— 本设计不做**

“代理看不见 https 内容”不是能力缺陷，是 CONNECT 的设计使然；要按内容拦只剩一条路：**MITM**——代理向客户端假扮目标（出示自己签发的证书），先把这段 TLS 解了、看清内容，再以自己的身份与目标另开一段。代价很高：

- 每个要联网的客户端进程都得**信任代理的 CA**（系统 / 进程级装根证书）；
- 证书固定（certificate pinning）的客户端会**直接握手失败**；
- 代理成为透明中间人，所有 https 都被它解密——性能与隐私代价都重。

本墙选 CONNECT + 只判 host，换来“**任何客户端不用改造、不用信任我的证书，只要愿意走 env 指的路，就能被我按域名拦**”。要更细的管控，宁可限制整类工具 / 服务端控（见 10.6 缺口 3），也不上 MITM。

### 10.2 先破一个直觉：起了代理 ≠ 本机外网流量全走它（通用机制）

下面是纯通用知识，不针对任何具体实现——回答一个常见疑问：“我在本机起了个代理，是不是本机所有对外网络连接都会经过它？”

**代理不会自动拦截流量**

“起了个代理”和“流量经过它”是两码事。代理本质只是一个监听在某个 `地址:端口` 上的服务，它不会主动去抢任何连接；只有被“主动送进来”的连接才会从它过。所以判断“会不会全经过”，真正要问的是“怎么把流量送进来的”——也就是配置方式。

**三种配置档位，决定覆盖范围（从小到大）**

- **环境变量式**：在某进程的环境里设 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`。只影响“读到该变量的那个进程（及其子进程）”，且要求对方的网络库**认这个变量**；出了这个进程，谁都管不着。
- **系统代理设置**：在 OS 的代理设置（Windows 设置 / macOS 网络偏好 / Linux 桌面环境）里填代理。系统把它“广播”给**愿意读系统代理的应用**（浏览器、多数桌面 App、不少网络库）。但有两条限制：① 仍是协作式——应用不读就没用；② 基本只管 **TCP 的 http/https**。
- **透明代理 / 网关 / TUN**：部署在网络出口（路由器 / 防火墙旁路）或用 TUN 虚拟网卡把流量“劫走”。程序不用配、甚至不知道自己在被代理，网络层直接接管。这是唯一接近“全经过”的档位——但它的本质是**改网络路径**，不是“装个本地代理软件”能实现的。

**即便配置到位，也不是“所有”连接**

无论哪一档，都有天然绕过的流量类型：

- **非 http/https 的 TCP**（SSH、各种私有协议）：多数应用不走 HTTP 代理，除非服务端特别支持 SOCKS / CONNECT 隧道。
- **UDP 类**（QUIC / HTTP/3、音视频、游戏）：HTTP 代理一般是 TCP 的，管不到 UDP。
- **加密 DNS**（DoH / DoT）与**直连 IP** 的流量：常常绕过。
- 监听地址也决定范围：只监听 `127.0.0.1` 就仅本机可连；监听 `0.0.0.0` 才可能被局域网使用（但一般不应把本机代理暴露成开放代理）。

**一句话分清术语**

- **HTTP 转发 / CONNECT 代理**：需要客户端**主动设置 / 认变量**才生效，是“协作式”。绝大多数本地代理属于此类。
- **透明代理**：网络层强制，客户端**不需要配合**，这才是“流量自动全过”的那种。

所以通用结论是：**本地起一个普通 HTTP 代理，不等于全局网关**——只有“被配置到、又愿意遵守”的进程才走它；想让某台机器“所有对外连接都经过”，需要系统代理接管或透明网关那一套。

### 10.3 本工程进代理的方式

本地代理是被动等连接的“协作式”服务（10.2）——谁都不配它、谁都不进，就谁都不拦。所以本墙真正的功夫在**怎么把各类客户端“送”进代理**：同一把墙，手段按目标客户端分三种。

切分三手段的轴有两条：**对方网络库认不认 `HTTP(S)_PROXY` env**、**有没有 spawn 时点可塞 env**。

认 env 的——curl / wget、python（urllib / requests / httpx）、rust reqwest——默认把“读 env”当改道行为，**手段三**只注 env 就送上门。

**Node 系默认不认**：undici 内置 fetch 故意不读 env；node-fetch / axios / 原生 http(s) 走 `http(s).globalAgent`，同样不读。这类里的主进程（**手段一**）**早已在跑**、连 spawn 前塞 env 的时点都没有，运行时改 `process.env` 也没用 → 只能绕开 env，把 `ProxyAgent` dispatcher 显式钉到每次请求。

stdio 子进程（**手段二**）则**有** spawn 时点、env 也注得进去，但塞了没人读 → 于是 shim 让 `EnvHttpProxyAgent` 去读、再全局接上。env 在这条路**不是没用**——是 shim 在消费它。

**手段一：主进程代发（http / sse / streamable-http MCP）**

这类连接本就是从主进程发出的，只要把主进程的出网 fetch 换成“直指本地代理”的 dispatcher 就能必进 CONNECT 层——不用对方读任何变量、也不改对方代码。覆盖表里“主进程代发 → 100% 命中”说的就是它。

**为什么这层不能靠“注 env 让它自己来”？** 因为它用的“现成网络库”正是主进程内置 `fetch`（undici 实现），而 undici 的 fetch **故意不读 `HTTP(S)_PROXY`**（和 curl / python requests 相反，后者读 env 是默认行为）；再加上主进程早已在跑，不存在“spawn 它之前往 env 塞代理地址”的环节。所以手段一不走 env，而是把代理**直接指定到每次请求上**。这里几个词容易绕，拆开：

- **`fetch`**：Web 标准那一层 API，底层并不自己连网——真正把请求发出去的是 **dispatcher**（undici 概念，默认一个直连型 `Agent`，DNS 后直接 TCP/TLS 连目标）。
- **dispatcher**：可替换的“发送器”。想改路由有两条路：全局 `setGlobalDispatcher(X)`，或这一次调用 `fetch(url, { dispatcher: X })`。手段一用后者。
- **`ProxyAgent`**：undici 自带的一种 dispatcher，让请求不改发目标地址、而是统一发给一个代理服务器。它和 `proxy.ts` 是**一对**——`proxy.ts` 是代理**服务器**（墙本体，监听 `127.0.0.1:<port>`、做 CONNECT / absolute-form 判定）；`ProxyAgent` 是代理**客户端**（把流量送进这堵墙的入口）。
- **`walledFetch`**：给原生 `fetch` 换 dispatcher 的薄壳（agent-client `mcpManager.ts`）——自己不发起连接，只把 `dispatcher: new ProxyAgent(proxyUrl)` 塞进每次调用的 `init` 再调原生 fetch；返回照旧是标准 `Response`。SDK 的 `SSEClientTransport` / `StreamableHTTPClientTransport` 都接受自定义 `fetch` 选项，把 `walledFetch` 传进去即接管其全部出网。

**不选“`setGlobalDispatcher` 全局一换”的原因**：主进程还有自己的 `fetch`（连 i-work server、检查更新等），不该被拖进 MCP 墙去走域名弹窗——按次传 `dispatcher` 只罩住这两个 MCP transport，作用域干净。

**手段二：Node stdio MCP —— env 只算引子，真正靠 shim 强制**

Node 系客户端的问题在于**只注 env 没用**：Node 内置全局 fetch / undici 默认不读 `HTTP(S)_PROXY`；node-fetch v3 / axios 走 node 核心 `http(s)`，同样不读 env。于是纯注 env 对 Node 系 stdio MCP = 漏（实测 baidu-search-mcp 即此：搜索请求直连外网、代理连 CONNECT 都看不到）。补法（agent-client `nodeProxyShim.ts`）：主进程在 spawn stdio MCP 前，往子进程 env **追加** `NODE_OPTIONS=--require=<%TEMP%\agent-desktop-net-shim.cjs>`（不覆盖已有 NODE_OPTIONS）；Node 启动即执行该 shim，做两件事强制改道：

1. `undici.setGlobalDispatcher(new EnvHttpProxyAgent())` → 内置 fetch / undici 改走代理（多份 undici 副本共享全局 dispatcher 槽位；`EnvHttpProxyAgent` 尊重 `NO_PROXY`）；
2. `http.globalAgent` / `https.globalAgent` 换成 `http(s)-proxy-agent`（CONNECT 隧道）→ node-fetch / axios / 原生 http(s) 改走代理。

边界与兜底：

- 只对 **stdio** 注入；http/sse 走主进程 `walledFetch`、天然可靠。
- shim 路径放 `tmpdir`（无空格，规避 Windows `NODE_OPTIONS` 解析）。
- 全程 `try/catch`、**fail-open**：注入失败子进程照旧直连，绝不让 MCP 起不来；`NODE_NO_WARNINGS` 压掉 undici 实验告警。
- 适用面：只罩 **Node** 运行时（npx / node 起的 MCP）；python / go / rust / java 不经 Node、读不到这 shim。
- **bash 通道暂不注入**（见 10.6 缺口 1）。

**两手段的“同与不同”（walledFetch vs Node shim，别当成同一件事）**

目的同、机制反：都进的是**同一把本地墙**、代理没就绪也都 fail-open，但“改在哪儿、罩哪段流量”是两回事，别混：

- **拦截点相反**：手段一是**替换调用点**——把自写 `walledFetch` 作为 `fetch` 选项传给 SDK transport，只对这两个 transport 的请求显式塞 `dispatcher: ProxyAgent`（主进程还有自己的 fetch 连 i-work server 等，按次传不连坐）；手段二是**替换进程全局默认**——子进程启动先跑 shim，`setGlobalDispatcher(EnvHttpProxyAgent)` + 换 `http(s).globalAgent`，进程内任何 Node HTTP 客户端**隐式继承**、无需传参——代价是没法像手段一那样“只罩某几条连接”。
- **代理地址来源不同**：手段一由主进程现算 `getProxyUrl()` 显式 `new ProxyAgent(url)`；shim 是落在子进程 `<TEMP>` 里的静态 `.cjs`，够不到主进程的 `ProxyAgent` 实例 / `getProxyUrl()`，只能靠 spawn 时注入的 `HTTP(S)_PROXY` env、用子进程自带 undici 的 `EnvHttpProxyAgent` 在**运行时自己读**——这就是手段二必须“注 env + shim”双管齐下的根因：env 是喂给 shim 里的 `EnvHttpProxyAgent` 的，不是喂给 undici 原生 fetch（它本就不读 env）。
- **罩住的流量对象不同**：http/sse MCP 的**协议本身就走 HTTP**，walledFetch 罩的是 SDK transport 发往远程 MCP server 的那段 MCP 报文；stdio MCP 的 MCP 报文走 stdio、根本不涉网，shim 罩的是子进程里 server **自己发起的业务外呼**（它去调天气 / 别的 API 等）以及一切 Node 出网——别把“给 MCP 报文开墙”和“给 server 的业务开墙”混成一件事。

**手段三：读 env 的库 —— 纯注 env 就够（bash 里的大多数）**

curl / wget、python（urllib / requests / httpx）、rust reqwest 把“读 `HTTP(S)_PROXY` 并改道”当默认行为。只要 spawn 子进程时把代理 env 并进去（`fileOps.ts` `getProxyEnv()`、`mcpManager.ts` `buildProcessEnv`），它们就会自己送上门。这也到“协作式”的上限：**对方默认读 → 会进；既不读 env 又非 Node 的原生进程（go 无 `ProxyFromEnvironment` / java 等）→ 无运行时注入手段，只能原生直连**（见 10.6 缺口 3）。

### 10.4 覆盖表：谁真被拦、谁只是“配合”

> 这张“谁出现在 CONNECT 层、谁只是路过”的图，就是下表“发起方/可靠度”那栏的由来：主进程代发的 http/sse MCP 100% 出现在 CONNECT 层；读 env 的客户端会自己送上门；既不读 env 又非 Node 的原生进程根本不经过这个代理，自然“看不见、拦不到”。

| 执行通道 | 进墙? | 拦截机制 | 发起方 / 可靠度 |
|---|---|---|---|
| http / sse / streamable-http MCP | ✅ 必进 | 主进程 `walledFetch`（agent-client `mcpManager.ts`）：undici `ProxyAgent` dispatcher 直指本地代理，CONNECT 判域名 | 主进程代发 → **100%** 命中 decideHost |
| stdio MCP（Node：内置 fetch / undici / node-fetch / axios / 原生 http(s)） | ✅ 进 | env `HTTPS_PROXY` **+ `NODE_OPTIONS=--require` shim 强制改道**（见 10.3 手段二） | Node 运行时内 → 高 |
| stdio MCP / bash（curl·wget / python urllib·requests·httpx / rust-reqwest） | ⚠️ 配合 | 只注 env `HTTPS_PROXY`（读 env 是这些库的默认行为） | 对方默认读 → 中 |
| stdio MCP / bash 里跑 go（无 `ProxyFromEnvironment`）/ java 等 | ❌ 绕过 | 无 env 可读、无运行时注入手段 | 原生直连 |
| bash 里的 **node / npx 脚本**（内置 fetch） | ❌ 绕过 | bash env **只注 env proxy、没注入 shim** | Node fetch 默认不读 env → 直连 |
| 服务端自执行的联网（模型在远端 search / build 后回传文本） | ❌ 本地看不到 | 流量不出现在本机 | 只能服务端控 |

### 10.5 两个先摆出来的执行事实（与“沙箱 = 网络受控”的直觉相反）

- **写墙只管写、不管网络**（`sandbox.ts` 顶部注释明说）。WRITE_RESTRICTED 令牌只限写；**“沙箱运行”≠“联网受控”**——沙箱里的 bash / stdio MCP 照样能出网，出网只受下面这把域名代理墙约束。
- **网络判定只到 host**（`proxy.ts` `decideHost`），不做 MITM / TLS 解密 → 按内容 / 路径拦不了；HTTP/3（QUIC/UDP）、DoH 这类不走 CONNECT 的协议天然绕过。IP 直连的 host 匹配不上域名表 → 落到 `unknown_domain` 兜底（ask / deny），还算有兜。

### 10.6 缺口 / 待完善（当前实现诚实版）

1. **bash 通道的 Node 仍裸奔**：`file:exec` env 只并了 `getProxyEnv()`（`fileOps.ts`），没像 stdio MCP 那样加 shim → bash 里跑 `node` / `npx` 脚本的 fetch 仍直连。补法：同一 shim 也并入 bash env（非 node 进程自动忽略；`NO_PROXY=localhost` 保住回环）。
2. **shim 的 globalAgent 层没做 NO_PROXY**：内置 fetch 层有 `EnvHttpProxyAgent` 尊重 `NO_PROXY`，但 node-fetch / axios 那层是直接换 globalAgent → 连本地回环也会被导进代理。补法：给代理 Agent 加“回环直连”的 override。
3. **非 Node 原生子进程（go / java…）** 没有运行时注入手段：要么靠对方读 env，要么 OS 级隔离（Windows AppContainer 只能“全禁 / 全放”、不能按域名）→ **架构边界**。这类要真拦，只能“限制整类工具”或回到服务端控。
4. **连接期无策略直连**：MCP 在 app 启动时 connect、彼时 `currentPolicy = null` → 即便合作式流量也 passthrough、不记审计（一般只是拉一次包）；进会话、首个 `client.tool_request` 把 policy 经 `proxy:set-policy` 下发后才真正按域名判。
5. **策略与放行缓存是全局单份**：`currentPolicy` 与 `sessionHostCache` 都是模块级单例 → 多会话 / 多智能体同时跑时，后到策略会顶掉先到者的判定口径，无 per-session 隔离（与 §5 的 M3“并发多 workspace”同属未收口项）。
6. **服务端对网络类恒 allow → skip**：域名 ask 只发生在客户端代理侧，服务端日志看不到域名拦截结论（要看去客户端侧，见 §7.4）。

7. **环境变量只是“路标”，真拦的是那台本地 HTTP 代理——协议上限 HTTP(S)（架构边界，与 3 同类）**：注入 `HTTP(S)_PROXY` env 本身不拦任何流量，它只把“读这个 env 的 HTTP 客户端”**指**向 `127.0.0.1:<随机端口>`；进不进墙取决于对方读不读 env（手段三）、有没有 shim 强制（手段二），且进来了也只是“走 HTTP 代理语义”的那部分。本地墙正是一台 HTTP 代理，只开两个口：

   - 明文 http → 绝对式请求（代理看得见路径，判定仍只取 host）；
   - https（及任何被 CONNECT 隧穿的 TCP）→ CONNECT，只见 host。

   所以即便“人人送进门”，覆盖也只是 **HTTP(S) 协议本身**，其余天然绕过：
   - **SSH / FTP / SMTP / IMAP**：各有自己的代理约定（SOCKS / `-o ProxyCommand` / 直连 25·587·465 找中继），默认不读 `HTTP_PROXY` → 不进墙；
   - **DNS**：标准解析走 UDP / TCP :53，与 HTTP 代理无关（DoH 若用认 env 的 http client 实现，会以 https 到某 host 进代理、能按域名拦——粒度仍只到 host）；
   - **QUIC / HTTP3**：UDP，HTTP 代理是 TCP 的 → 天然绕过（承 10.5）；
   - **不读 env 又无 shim 罩的原生进程**（go / java）与 bash 里的 node / npx → 协作式彻底失效（见 1、3）。

   一个反直觉点：CONNECT 语义上能隧穿**任意 TCP**，一个“特意去用代理”的 SSH / FTP 客户端也能被拖进来；但现实中这些协议默认不这么做 → 实测效果就是“只罩 HTTP(S)”。想连这些协议一起管住，只能上 10.2 的 TUN / 透明代理 / 网关档（改网络路径、客户端无需配合），本地 HTTP 代理做不到。

8. **“上限 HTTP(S)”说的是送达约定、不是隧道能力——CONNECT 隧道本身能驼任意 TCP，但能不能被拦，取决于客户端肯不肯把自己送进门（给 7 补个根因澄清，与 3、7 同类）**：隧道只管“搭路 + 原样搬运”，字节对代理透明、它不挑协议——若真有客户端对墙发 `CONNECT smtp.server:587` / `host:22`，`server.on('connect')` 照接、`decideHost` 照判 host、隧道照开，SMTP / IMAP / SSH / FTP / DNS-over-TCP 它都能隧穿。但这只是“handle 得了”，不等于“会被拦到”：墙拦截成立的前提是流量**被主动送进门**（10.2 主动轴），而非 HTTP 协议客户端恰恰普遍没有“读 `HTTP(S)_PROXY` 就改道”的约定，默认不送 → 墙看不见 → 拦不到。逐协议看：

   - **SMTP / IMAP**：邮件客户端几乎不读 env、也没有标准 HTTP CONNECT 代理配置位（顶多有 SOCKS）→ 默认直连，不进墙；
   - **SSH**：不读 env，要过代理得手动 `ProxyCommand`（如 netcat `-X connect`）或 `ProxyJump` → 默认直连，不进墙；
   - **FTP**：经 HTTP 代理的经典做法是转发代理的 absolute-form `GET ftp://…`（不是 CONNECT）；个别客户端（FileZilla）支持 HTTP CONNECT 但要手动开 → 默认不走；
   - **DNS**：本地解析走 UDP/TCP:53，与 HTTP 代理无关；DoT:853 也不读 env → 不进墙。

   一句话：隧道对协议无歧视，真正拦路的是“送不送进门”——10.1“看到 CONNECT ≈ 墙在起作用”能成立，正是靠 https 客户端（浏览器 / fetch）**志愿读 env 来送**；哪天真有 SMTP 客户端配了 CONNECT，墙照样按 host 判它（粒度仍只到域，见 10.5）。想连不肯上门的协议一起强制管住，只能上 10.2 的 TUN / 透明代理档（改网络路径、客户端无需配合）。

   落到**实现 skill / MCP 里的网络客户端**，这句“送不送进门”要再操作化一层：**拦截前提 = 出站网络栈会先对墙说 CONNECT；而认不认代理是库自己的事——平台注入的 env 只对“认 env 的库”生效**。会认 env / 自带 proxy 的库（python requests / httpx、curl、rust reqwest，以及 JS 里的 **nodemailer**——读 `HTTP(S)_PROXY`、也带内置 `proxy` 选项）脚本一继承 bash 注入的代理 env 就自动进墙，作者零成本；不认 env 的库（python **smtplib / imaplib**、undici 内置 fetch / node-fetch / axios 等）env 等于白注——JS 那批平台另有 shim 兜底，裸 socket 的 smtplib 只能作者手写 CONNECT 把流量送进门（顺带修正 10.3“Node 系默认不认 env”的说法：那是 undici fetch 那批，nodemailer 这类认 env）。

   于是结论再拧半圈：**“某类协议能不能被拦”不在墙、也不在协议，而在“客户端用了哪个库、它认不认代理”**——skill / MCP 作者挑会认 env / 带 proxy 的库（发邮件用 nodemailer 或 HTTP 邮件 API，别用裸 smtplib），拦截几乎免费；挑裸 socket 库就得自写 CONNECT，否则 host 配置再全也拦不到（流量不进墙）。

9. **别把“判据只到 host”当成“只留 CONNECT 就够了”——absolute-form 转发那支是“让明文 http 也能进墙被拦”的通道，保留两入口比砍掉更稳（对应客户端代理 `proxy.ts`）**：本地墙对放行的判定确实**只取 host**——CONNECT 走 `server.on('connect')`、absolute-form 走 `server.on('request')`，两个入口都只 `extractTarget` / `new URL(...)` 取 `hostname`、进同一把 `decideHost(host, protocol)`（`proxy.ts:73`），不拿路径做策略、更不做 MITM / 解密（见 10.1）。但“判据是 host-only”不等于“可以把 http 转发那支删了只留 CONNECT”：

   - **两个入口是 HTTP(S) 代理的两种客户端习语，不是一强一弱**：https → CONNECT 隧道；明文 http → absolute-form 转发。absolute-form 那支（`proxy.ts:185`）不是“多看了路径”的增强，它的存在意义是**让明文 http 流量也被送进门、按 host 拦**——没有它，curl / python requests 这类对 `http://` 出站时发 absolute-form 的库，请求连代理的处理都收不到（无 `request` 监听器 → 连接挂起 / 不通），是“直接失败”，不是“被拦或放行”。
   - **CONNECT 机制上确实能覆盖 http**（CONNECT 能隧穿任意 TCP，undici 的 `ProxyAgent` 连 http 目标也走 CONNECT 隧道，`walledFetch` 那条路基本用不上 absolute-form），但前提是“客户端肯 CONNECT”；认 env 的 curl / requests 对明文 http 仍发 absolute-form、不会自己改走隧道——两入口并不互相覆盖。
   - 想砍 absolute-form，前提是接受“本墙不罩明文 http、它一律失败”——可不少内网 / 自建 / 测试端点是明文 `http://`（且 `network_rules` 里 `protocol:'http'` 那条分支只在 absolute-form 入口会命中），砍了会误伤它们。
   - 结论：**判据 host-only 是设计，保留两入口是实现**——absolute-form 是“把明文 http 客户端也送进门”的那条协作式通道，与 CONNECT 共享同一把 host 尺；除非产品明确接受明文 http 出站一律失败，否则保留两入口比只留 CONNECT 更稳。

### 10.7 收束：可靠度排序与补强顺序

**“联网被拦”的可信度排序 = 主进程代发（http / sse MCP）> Node stdio MCP（env + shim 强制）> 读 env 的各类库（python / curl / rust）> 既不读 env 又非 Node 的原生进程（基本裸奔）。** 补强顺序建议：bash 也注入 shim（堵 1）→ shim 层补 NO_PROXY（堵 2）→ 其余为架构边界 / 未收口项（3–7）。
