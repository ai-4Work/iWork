## 1. 概述

**线程即 Agent。** 每个 agent 就是一个 `thread`（逻辑会话单元），多 agent 本质上是一棵"线程树"。所有状态、通信、并发控制都围绕这棵树展开。

**核心思想：分散式 / 树形层级多 agent 架构。**

- 任务分解交给 LLM 自发用工具 spawn 子线程，**没有集中调度器**；
- 通过 `AgentPath` 树寻址 + 异步邮箱通信；
- 靠"总数 / 执行中 / 常驻 LRU"三层原子计数控制并发；
- 每个线程独立持有 Session 状态并持久化到 rollout 文件；
- 冲突规避依赖角色系统（worker 所有权）与共享文件系统的显式提示。

**设计维度框架（怎么读这份文档）**：设计一个多 agent 系统，核心就 4 个维度，各自回答一个问题，每个维度对应文档一节：

- **任务分解与协调**（第 4 节）——大任务怎么拆、分给谁、谁控制谁？→ Codex：LLM 自发 `spawn` 线程树，**无集中调度器**
- **多 agent 通信**（第 6 节）——拆开后 agent 之间怎么交换信息？→ `AgentPath` 树寻址 + 异步邮箱 + `FINAL_ANSWER` 自动回传
- **资源竞争**（第 5 节）——并发跑时共享资源（CPU/内存/文件/LLM API）怎么争、怎么限？→ 总数 / 执行中 / 常驻 LRU 三层原子计数
- **状态一致性**（第 9 节）——多 agent 共享的世界怎么保持一致、防冲突？→ 文件层不检测靠模型自律、内存层分层原语、持久化串行写

这 4 维有内在顺序：**分解**是起点（怎么拆决定协作模式、资源分配、状态边界）→ **通信**是通道（拆完要协作，协作靠消息）→ 协作必然**并发**、并发必然**争资源** → 多 agent 共享世界必须**一致**，否则协作产出不可信。一句话收尾：**分解决定怎么协作，协作引入竞争，竞争需要一致兜底。**

**每个维度为什么存在（服务什么目标）**：这 4 维本质是在系统设计的目标轴之间权衡——

| 维度 | 服务的目标 |
|---|---|
| 资源竞争 | **性能**（快）+ **可用性**（活） |
| 状态一致性 | **正确性**（对）+ 可恢复（丢不了） |
| 任务分解与协调 | **可扩展性**（能做单 agent 做不到的大任务） |
| 多 agent 通信 | **协作**（信息能到达） |

## 2. 整体架构

| 组件 | 职责 |
|---|---|
| `Session` | 单个 agent 的运行状态（对话记录、输入邮箱、当前回合） |
| `CodexThread` | 包装 Session，对外提供提交操作、启动 / 转向回合 |
| `ThreadManagerState` | 全局线程注册表，线程派生的入口 |
| `AgentControl` | **控制平面**，每个根会话创建一次，所有子 agent 共享 |

`AgentControl` 是核心，持有四个共享组件：

- `AgentRegistry` —— 总数限制 + agent 树
- `V2Residency` —— LRU 常驻管理
- `AgentExecutionLimiter` —— 执行并发限制
- `RolloutBudget` —— 预算控制

## 3. Agent 与角色

系统内置三种角色：`default` / `explorer` / `worker`：

| 角色 | 用途 | 关键规则（写入提示词） |
|---|---|---|
| `default` | 默认 agent | — |
| `explorer` | 只读代码库搜索 | 鼓励并行派生多个 explorer 查独立问题；避免重复覆盖同一问题；可信赖结果 |
| `worker` | 执行与生产工作 | 显式分配**文件所有权**；告知"你不是一个人在代码库"，不要回滚他人修改 |

**角色只降能力、不超父权限**。用户可自定义角色。

## 4. 任务分解与协调

### 无集中调度器

没有中央 scheduler 分配任务。每个 agent 的主循环都是：取上下文 → 请求模型 → 执行工具 → 循环。"下一步做什么"由各 agent 的 LLM 自行决定。

### 工具层（模型如何"分解任务"）

协作工具统一注册：

- `spawn_agent` — 派生新 agent
- `followup_task` — 给已有 agent 新任务并**触发**回合
- `send_message` — 发消息**不触发**回合
- `wait_agent` — 阻塞等待邮箱活动
- `interrupt_agent` / `list_agents` — 中断 / 列举

### 协调寻址：AgentPath 树

线程注册表维护一张"路径 → agent 元数据"的映射，路径分层如 `/root`、`/root/explorer_1`。消息寻址、解析目标都靠路径。

### 上下文继承（fork）

`spawn_agent` 的 `fork_turns` 参数控制上下文继承：

| 值 | 含义 |
|---|---|
| `none` | 全新上下文，只带初始 prompt |
| `all`（默认） | 完整历史 fork |
| `N`（正整数） | 只 fork 最近 N 轮 |

fork 时清洗历史：只保留 system/developer/user 消息与最终答案，丢弃工具调用细节，并换成子自己的 developer 指令。

**通俗解读（上下文是怎么传的）**：上下文传递就两种机制，父子、子子用法不同——

- **出生继承（fork）**：只在子 agent 被 spawn 那一刻发生，一次性、单向（父→子）。三档：`all`（完整历史）、`N`（最近 N 轮）、`none`（全新，只带初始 prompt）。而且不是原封不动抄——**先清洗**：只留 system/developer/user 消息和最终答案、丢掉工具调用细节、再换成子自己的 developer 指令。所以子是"带着父的清洗版记忆出生"。
- **消息注入**：运行时的通信靠邮箱消息，消息在接收方下一回合构建上下文时被渲染成片段注入，模型像读对话一样读到。注意：发件人**不会把整个上下文推过去**，传过去的只是那一封信的内容。

分方向看：

- **父子**：出生时靠 fork（父把清洗后的记忆给子）；运行中靠消息一来一回（父派活/追加、子汇报/自动回传结果）。子还带着父/根的回合标识，随时知道"从哪来、根是谁"。
- **子子（兄弟）**：**没有出生继承**——兄弟各自独立 fork 自同一个父，出生后各长各的，彼此**不分享各自新增的历史**；"共同的底子"来自父，不是兄弟互相传。运行中技术上能消息互发（会注入对方上下文），但设计上软约束压回树形、不鼓励横向；真要想交换中间产物，靠共享文件系统（A 写、B 读）。

一句话：**父子靠"出生继承 + 消息来回"，兄弟靠"各自继承父 + 消息/文件"，兄弟之间不共享各自的新记忆。**

### 门控：multi_agent_mode

多 agent 模式开关控制模型能否"自发"用多 agent 工具：

- `ExplicitRequestOnly`（默认）— 模型只在用户显式要求时使用
- `Proactive` — `reasoning_effort=ultra` 时默认；模型可主动拆任务
- `Custom` — 配置/模型目录自定义策略

### 通俗解读：root 在"分解与协调"里到底管什么

**你的直觉对的部分（典型主流程）**：root 是任务入口——它通过工具层 spawn 子 agent 干活；子 agent 干完结果自动回传；root 在下一回合读到结果、自己判断下一步怎么走（继续派活 / 追加任务 / 改方向 / 收尾）。这正是第 8 节走查画的那条主线，也是设计上想要的形状。

**关键纠偏：没有集中调度器，root 不是"中央大脑"**：

- 分解不是 root 一个人做的——每个 agent（含子 agent）都自己跑回合循环、自己的模型决定"下一步做什么"；子 agent 内部怎么干活，root 不干预、也不知道细节；
- 谁都能 spawn——子 agent 也能再派生孙 agent，任务分解是一棵可以任意往下长的树，不止 root 一层；
- root 的"协调者"身份靠**软约束 + 提示词**引导（层级协作、只跟直系上下级说话），不是硬性集中调度——兄弟真要去直连，系统也不拦。

**那 root 到底管什么**：

- **发起**：把大任务拆成子任务、决定 spawn 谁、派什么活（拆到哪一层由各 agent 自行决定）；
- **汇总**：收子 agent 的结果，把各条线的产出拼起来；
- **定大方向**：根据结果判断下一步怎么走；
- **不管过程**：子 agent 怎么执行、内部怎么组织，root 不微观管理。

**一句话收尾**：root 是"**发起者 + 汇总者 + 决策者**"，不是"中央调度器"——分解靠各 agent 自发 spawn，协调靠消息往来，树的每一层都能继续派生。**这是"分散式树形"，不是"根做主的中央集权"。**

## 5. 资源竞争：并发时争什么、怎么解决

### 并发时争什么：6 类资源竞争

多 agent 并发跑 turn 时，6 类资源会产生竞争。先给结论：**代码内的瓶颈不在 LLM 调用层**——采样路径没有客户端并发信号量/队列，客户端不节流，真正的 rate limit 瓶颈在服务端；代码内真正会卡的是**持久化**（SQLite 单写者 + 会话索引全局锁）和**内存**（常驻上下文、驱逐串行化、邮箱洪峰无背压）。

| 资源域 | 竞争形态 | 现有控制 | 性能影响 | 可用性影响 |
|---|---|---|---|---|
| LLM/模型调用 | 多 agent 并发采样，共享 HTTP 连接池，无客户端并发信号量/队列 | agent 层 `max_concurrent_threads_per_session` | 代码内无瓶颈；真正瓶颈在服务端 rate limit | 服务端限流触发时子 turn 失败/退避 |
| 执行并发（CPU） | 多 turn 并发跑 | `AgentExecutionLimiter`，超限 `AgentLimitReached` | 子 agent 并发度被掐在 effective 值 | 超限是"拒绝"而非"排队" |
| 内存常驻 | 每 agent 持有完整对话/模型上下文 | `V2Residency` LRU 驱逐 | 驱逐同步阻塞、上下文重建贵 | 上下文暴涨有 OOM 风险 |
| SQLite 单写者 | 并发 spawn 的元数据/spawn 边/投影挤同一 state.db | WAL + busy_timeout 5s + 池 5 | 并发写排队 | 5s 超时报错 |
| 文件系统 | 共享 cwd 无文件锁 → 覆盖冲突 | 模型自律 + 乐观校验（见第 9 节） | — | 逻辑覆盖丢失 |
| exec 沙箱 + 日志 | Windows 沙箱全局态、stderr 日志锁 | 全局 Mutex | 并发 shell/日志互锁 | — |

怎么解决？——**三层并发控制**（下面第一/二/三层）管 spawn 总数、执行并发、常驻内存；**文件系统竞争**靠提示词自律 + 乐观校验；其余竞争域（LLM 调用 / SQLite / exec 沙箱与日志）靠连接池、WAL 与全局锁。下面逐块展开。

**为什么是"三层"而不是"六类各配一层"**：6 类是**问题清单**（争什么），三层是**解法家族**（怎么限），不是一个层面的东西。6 类里"并发类"的三个——线程总数、同时执行、常驻内存——病根是同一个"超上限会失控"，所以用同一套思路（设上限、超限拒绝/驱逐）打包成三层；这三层恰好是同一个线程一生的三道闸（出生 / 开工 / 完工后留不留），共享"原子计数 + 拒绝驱逐 + 无死锁"这套技术。其余 4 类（LLM 调用 / SQLite / 文件系统 / exec 沙箱与日志）病根不是并发超限，各有专属解法，不进三层。一句话：**6 类竞争 = 并发类（归三层限）+ 非并发类（各自单独解）**，"三层"不是和"6 类"并列的分法，而是对并发类的统一解法。

### 第一层：总数限制（spawn 槽）

线程注册表用**原子计数 + CAS（比较并交换）**预留 spawn 名额：每次派生先读当前值，达到上限即返回"已达上限"拒绝；否则用 CAS 试着把计数加一，**失败说明有人抢先，拿新值重试**——两个并发 spawn 只有一个能赢，绝不超发。配 RAII 占位（派生结束无论成功失败都自动归还），防泄漏。

### 第二层：执行中限制（活跃 turn）

用计数器限制**同一时刻正在执行的子 agent 数**：回合开始前先查名额，有名额则占位加一，返回一个守卫；守卫在回合结束（含异常）时**自动减一**归还——计数必然归还、不会漏。并发阈值由配置控制（`max_concurrent_threads_per_session`）。

### 第三层：常驻 LRU 驱逐（V2Residency）

**先看常驻内存占的是什么**：每个 agent 常驻时揣着一份**完整对话 + 模型上下文**——对话历史、渲染好的上下文、邮箱里攒着的信，都在内存里。关键是线程**干完活不自动释放**：线程跑完了、结果也回传了，那份上下文还留在内存里占地方，因为哪天消息再来还要靠它接着干。N 个 agent 就有 N 份这样的上下文，**内存峰值 ≈ 全部常驻线程的对话之和**——所以常驻必须设上限，超了就得"请出去"，否则上下文越堆越多，迟早撑爆 OOM。

**再看怎么解决（LRU 驱逐）**：给常驻线程设容量上限，超容量时把"最久没用到的"那个请出内存：

1. 从 LRU 队列弹出最久未用的 agent
2. 检查是否可卸载（已完成/出错/中断 且 无活跃 turn 且 邮箱无待处理项）
3. 关停并等待 → 保存环境选择 → 移除线程、卸出内存
4. 消息再来时，从落盘的记录**懒加载**恢复该 agent——重新读回那段上下文，代价是重建贵

另有**深度限制**：限制线程嵌套深度，防无限递归。

### 文件系统竞争

所有 agent **共享同一工作目录与容器文件系统**（系统明确告知模型这一点）。文件访问经执行策略（allow/deny 规则）与沙箱控制，**没有文件级锁**——冲突靠角色提示词（worker 所有权、不要回滚他人修改）+ 模型自律规避。

### 深潜：逐类看 6 个竞争域的实现细节

> （执行并发 / 内存 / 文件系统的机制见上文"第二层 / 第三层 / 文件系统竞争"，这里补实现深潜。）

逐类看：

- **LLM/模型调用**：调用链走模型客户端流式采样。采样路径**无信号量、无请求队列**（事件通道只回传、不限制）；多 agent 并发采样的共享点只有 HTTP 连接池；重试每回合独立、指数退避；服务端返回限流只记录、不客户端节流。**结论：代码内没有竞争点，真正瓶颈是服务端 rate limit。**
- **执行并发（CPU）**：计数器记录当前活跃子 agent 数，回合开始前查名额，超限报"已达上限"；只对子 agent 生效。阈值取 **effective = 配置值 − 1**（留 1 给 root；默认 4 → effective ≈ 3 个并发子 agent）。**超限是"拒绝"不是"排队"**——子回合直接不启动。
- **内存常驻**：用互斥保护的 LRU 队列管理常驻 agent，容量满时**同步**关停驱逐最久未用者——多 agent 并发触发驱逐会**串行化**；可卸载要求已完成/出错 + 无活跃回合 + 邮箱空。被驱逐的 agent 靠懒加载恢复，代价是**整段历史重读 + 反序列化重建上下文**。邮箱洪峰时取信直接并入待处理项、**无背压** → 上下文暴涨，内存峰值 = 全部常驻线程的对话。
- **SQLite 单写者**：连接池开 WAL + 写同步 + 忙等待超时 **5 秒** + 连接池容量 **5**；所有 agent 共享同一个数据库池。多 agent 并发派生时，元数据写入、派生边、历史投影全挤同一个库——并发写排队、写锁被占最多等 5 秒。**最大瓶颈是会话索引上的全局锁**：改名全进程串行、删除还要整文件重写。

**通俗解读（"单写者"是什么意思 / 库里存什么）**：

- **"单写者"是 SQLite 的写规则**：同一时刻只有一个连接能持写锁、真正往库里写；写是**串行**的，多个写请求来了排队一个个来，不可能两个写同时成功。读宽松得多——尤其在 WAL 模式下，有人写的时候别人照样能读，写、读互不堵。
- **为什么它是竞争点**：所有 agent 共享同一个 state.db，并发派生线程时元数据、派生边、投影全往这一个库里挤 → 写请求排队；写锁被占超过 5 秒就超时报错。
- **库里到底存什么**：线程 / 会话元数据（登记信息）、派生边（谁 spawn 谁，即"族谱"）、rollout 投影（从流水账提炼的关系索引）、会话索引（支持改名 / 删除）。**对话正文不在库里**——在每线程独立的 rollout 文件里，详见第 9 节。
- **怎么缓解（但改不了"单写"本性）**：WAL（读写不互堵）+ 忙等待超时 5 秒（先等再报错）+ 连接池 5（多连接排队）。写仍然串行，只能让它排得顺畅。
- **为什么不能多写**：写本质是"改同一份共享文件"，两个写者同时改，结果无法确定——必须排个先后，即串行化。号称支持"并发写"的数据库，底层同一时刻也只有一个事务真正提交落盘，其余排队或冲突重试——"多写"只是把排队藏进更复杂的机制，本质仍是一个一个来；真并行还得做冲突检测（CAS / 版本号 / 合并），复杂、且每次写都付代价。
- **原子 + 持久逼着单写**：写的时候别人不能看到"写到一半"（原子性）、最后必须真落盘（持久性），单写者让"一次只提交一个事务"天然成立。SQLite 定位嵌入式、免运维，用单写者换"简单可靠"；WAL 只放宽了读、写者之间照样互斥——是刻意取舍，不是技术缺陷。
- **文件系统**：共享工作目录、无文件锁 → 覆盖冲突（详见第 9 节）。历史文件每线程独立 + 每线程一把锁 + 跨进程加锁文件被占即返回冲突、不阻塞——这条其实不卡。
- **exec 沙箱 + 日志**：Windows 沙箱有全局互斥锁和工具缓存互斥锁；权限审批走专用阻塞线程池、会挤占池容量；日志写 stderr 用全局锁，多 agent 日志互锁。

### 收尾：性能瓶颈排序 / 可用性风险 / 无死锁

**两个维度的收尾**：

- **性能瓶颈排序**（影响吞吐）：**持久化**（SQLite 单写 + 会话索引全局锁）> **内存**（驱逐串行化 + 上下文重建）> 日志/沙箱。LLM 调用在代码内反而是最"松"的。
- **可用性风险点**：服务端 rate limit（LLM 层）、上下文暴涨 OOM（内存层）、SQLite 5s 超时报错、`AgentLimitReached` 拒绝子 turn。
- **无死锁**：所有锁都是短临界区、无嵌套交叉；邮箱竞争仅发生在目标 agent 的单队列上。三层限制（总数 / 执行中 / LRU）都是"拒绝或驱逐"，不是互等，所以不会死锁，代价是可能"饿"——子 turn 被拒或常驻被逐。

### 通俗解读：并发不是越多越好

多 agent 并发是好事，但不是"并发越多越好"——并发必然带来资源竞争、资源有限，所以要给并发设上限。第 5 章整个思路可以收成四点：

- **限什么——分资源域限，不是一刀切"少并发"**：三层上限各防一类失控——限 spawn **总数**（防线程无限膨胀）、限**同时执行**（防 CPU 打满）、限**常驻内存**（防上下文撑爆 OOM）；
- **怎么限——拒绝 / 驱逐，不是排队等**：超了直接拒（子 turn 不启动）或驱逐最久未用者。用"拒绝"换"无死锁"——没有 agent 互相等，代价是可能"饿"（子 turn 被拒、常驻被逐）；
- **真正瓶颈在哪——不在并发本身，在持久化和内存**：性能瓶颈排序是持久化（落盘单写 + 全局锁）> 内存（驱逐串行化 + 上下文重建）> 日志/沙箱；LLM 调用反而是最"松"的。所以限制并发只是"兜底不失控"，真正卡吞吐的是"把状态落盘"和"把上下文留在内存"这两件事；
- **竞争不只有并发一种**：SQLite 写串行、文件系统覆盖冲突、exec 全局互斥——都是并发引发的副作用，解法不全是"限并发"，而是 WAL / 提示词自律 / 全局锁。

**一句话收尾**：并发要"限"，但限不是目的而是**兜底**——用三层上限防失控、用"拒绝/驱逐"换无死锁；真正决定性能天花板的是持久化和内存。

## 6. 通信机制

### 消息载体

agent 间通信统一用一个消息结构承载：`author`、`recipient`、`other_recipients`、`content`、`encrypted_content`、`trigger_turn`。

**通俗解读（消息载体在讲什么）**：这一节说的是"一封信长什么样"。不管消息是派活、汇报还是自动回传的结果，所有 agent 间消息都以同一个结构为载体，就像统一的信封——系统只需处理一种形状的信，靠信里的**类型**（派活 / 发消息 / 追加任务 / 结果）和**属性**（敲不敲门）区分用途。信封上有六个信息：

- **发件人**：这封信是谁写的——收件人由此知道消息从哪来、来自谁；
- **主收件人**：这封信主要是给谁的——**寻址就靠它**，运行时把名字翻译成精确工号，信只投给这一个人；
- **其他收件人**：顺带抄送的人（类似"抄送"），一封信可以不止一个收件人；
- **内容**：信的主体文字，真正"说的话"；
- **加密内容**：可选的加密正文，敏感信息可以不走明文；
- **敲不敲门**：投递后要不要唤醒收件人立刻开回合——催活型敲、知会型不敲。

一句话：**消息载体 = 统一的"信封模板"（发件人 + 收件人 + 抄送 + 正文 + 加密正文 + 敲不敲门），所有 agent 间通信都被装进这个信封走邮箱。**

拿两个实际例子看它长什么样（`type` 即通信类型 Spawn / Message / Followup / Result）：

**例 1：父给子追加任务**（催活，要敲门）：

```json
{
  "type": "Followup",
  "author": "/root",
  "recipient": "/root/auth_worker",
  "other_recipients": [],
  "content": "登录模块的测试补全后再验证一次",
  "encrypted_content": null,
  "trigger_turn": true
}
```

**例 2：子干完活的自动回传**（知会，不敲门）：

```json
{
  "type": "Result",
  "author": "/root/auth_worker",
  "recipient": "/root",
  "other_recipients": [],
  "content": "登录模块已实现并补全测试",
  "encrypted_content": null,
  "trigger_turn": false
}
```

同一套信封、两种用法：例 1 是父催活（`Followup`、`trigger_turn: true`、发件人是父）；例 2 是子自动回传结果（`Result`、`trigger_turn: false`、发件人是子）——只改几个字段，用途就不同。

**补充说明（author / recipient 是字符串，运行时做键查找）**：这两个字段就是**字符串**，投递时拿它做一次**精确的键查找**——用整个字符串去注册表里比对，命中即得目标工号，然后投信；**没有按 `/` 分段逐级下钻的树遍历**。它"长得像路径"是三个原因：一是**保证唯一**（`/root/auth_worker` 这种命名天然不重名，键必须唯一）；二是**出生时真用父路径拼接**——派生子 agent 时，子地址 = 父地址字符串 + "/" + 子名字，所以字符串确实编码了辈分（**生成地址时用，不是查找时用**）；三是**人好看懂**（调试、列清单时比随机 ID 可读得多）。另外，消息路由里判断"谁是谁的父"也不靠解析这个字符串，而是靠**显式记录的血缘字段**（取信时汇总的父子回合标识）。一句话：**author / recipient 是字符串，运行时做键查找、不爬树；"路径"是命名规则（唯一 + 可读 + 出生时继承辈分），不是查找算法。**

### 投递链路

1. 发送方工具处理 → 调起发送入口
2. 若 `trigger_turn`，先检查执行并发额度
3. 投递到接收方**邮箱**
4. 接收方收到 → 信进邮箱 → 空闲则唤醒开始新回合

通信类型：`Spawn / Message / Followup / Result`。

**通俗解读（这一节在讲什么）**：所有 agent 间通信——父派活、子汇报、兄弟互发、子干完活的结果自动回传——物理上都是"往对方邮箱投一封信"，没有别的通道。但**投进邮箱 ≠ 收到**：信真正算"送达"，是收件人开新回合时把信取出来、并进自己的对话记忆那一刻，之后才永久保存。至于信投给谁，**寻址是程序干的**——模型只需要写"发给谁"，运行时把那个名字翻译成目标 agent 的精确工号，信就只送到这一个人手上，一对一、没有广播，也不会投错人。这套地址是**树形**的：地址的长短代表血缘深浅，它既是每个 agent 的唯一身份，也是它的"族谱"——谁派生了我、根是谁，都记在地址里。

### 主 → 子（三种工具，区别在 trigger_turn）

| 工具 | trigger_turn | 效果 |
|---|---|---|
| `spawn_agent` | true | 派生新 agent，首条消息即初始任务（NEW_TASK） |
| `followup_task` | true | 投递并立即唤醒目标开新回合（NEW_TASK） |
| `send_message` | false | 只入邮箱，不打断目标当前回合（MESSAGE） |

限制：`followup_task` **不能指定 root 为目标**。

**通俗解读（trigger_turn 在讲什么）**：这封信带不带"敲门"属性，决定了投递后要不要催对方立刻开工。**催活型**（派新活）：投进邮箱的同时敲醒对方，催他马上开一个新回合来干活；**知会型**（顺口说一声）：只把信放进邮箱、不敲门，对方该忙啥忙啥，绝不打断手头的活。配套有个"攒着再送"的优化：如果邮箱里只有不敲门的消息，就延迟到下一回合一起取——犯不着为了一句闲话专门唤醒对方、白费一次思考。

### 子 → 主：自动 FINAL_ANSWER 回传

子 agent 回合进入终态时，运行时自动投递结果给直接父 agent——**不是子 agent 调用 send_message**：

子回合终态被运行时拦截，把最终答案包成 `Result` 类型、`trigger_turn=false` 的消息，投进直接父的邮箱。

> V1 是另一套：派一个独立 watcher 订阅子状态，终态注入通知。

**通俗解读（结果怎么自动送回来）**：子 agent 干完活，结果不用它自己记得"写信给爸爸"——**运行时兜底自动回传**。子 agent 只要正常把回合收尾（给出最终答案），系统在它收尾那一刻，自动把最终答案打包成一封信，投进**直接父 agent** 的邮箱；子 agent 自己零操作，甚至不知道有这个机制。

这封信有四个讲究：

- **只回给直接父**：靠血缘（谁派生了我）判断，不往上广播给祖辈、也不发给兄弟；
- **不敲门**：父 agent 正在忙就绝不打扰，它忙完、下回合整理思绪时自然读到这封信，像读对话一样读到子 agent 的最终答案；
- **两条路都通**：父 agent 主动等待 = 守在信箱旁听铃，信一到、铃一响，立刻从阻塞中恢复；不等待 = 下回合自然收到。两种方式不冲突；
- **与主动发消息并存**：自动回传负责"干完的结果"（零操作兜底），主动发消息是子 agent 手里的可选工具，负责"干到一半的汇报、提问"。两者机制不同、各管各的，可以同时用——子 agent 中途主动汇报，到点再由系统自动把最终结果送回去。

### 兄弟之间

**技术上允许直连**：共享注册表 + 路径寻址无"只能发祖先/后代"硬校验，`list_agents` 可列出所有存活 agent，兄弟路径可解析、可投递。设计上压成层级模型靠**软约束**：完成通知只自动生成子→父方向；提示词引导树形协作。

**通俗解读**：技术上兄弟之间完全可以互发消息（大家的地址都能查到、都能投递），但设计上有意**不鼓励横向协作**：完成通知只自动生成"子→父"方向，协作被引导成"只跟直系上下级说话"，把整个消息流压回一棵清晰的树，而不是一张乱网。

### 消息如何进入模型上下文

邮箱消息在接收 agent 回合中被渲染成上下文片段：

```
Message Type: MESSAGE | NEW_TASK | FINAL_ANSWER
Task name: <recipient>
Sender: <author>
Payload:
<payload text>
```

统一以"助手"角色的用户片段注入，模型像读对话一样读到其他 agent 的内容。

### 邮箱（InputQueue）的具体实现

每个线程的邮箱归 Session 持有，核心是**两个成员**：

- **邮件队列**：互斥锁保护的 FIFO 内存队列，线程安全
- **活动通知通道**：每次投递就广播"有动静"，`wait_agent` 的阻塞就靠订阅它

生命周期四步：

1. **入队**：压入队尾，然后广播"有动静"
2. **订阅**：拿到通知接收端，`wait_agent` 订阅后带超时阻塞；活动类型分"有邮件" / "用户输入打断"
3. **消费**：回合构建上下文时**整批出队**，转成回合输入，并汇总父/根回合标识（血缘）
4. **唤醒**：只有 `trigger_turn==true` 的邮件才唤醒空闲线程；`send_message` / FINAL_ANSWER 只入队不敲门

投递时机优化：回合里只有不敲门邮件时延迟到下一回合投递，**避免为了非关键消息额外采样一次**。

**纯内存存储**：邮件队列不落盘，进程/线程销毁即丢失。两道保护：(a) LRU 驱逐前要求邮箱为空，避免卸出时丢消息；(b) 一旦邮件被消费进回合上下文，会随对话历史写入持久化记录。

**通俗解读（一个邮箱长什么样）**：一个 agent 的邮箱就两样东西——**一个能排队的信件架**（FIFO，先来先处理；因为可能多个 agent 同时往里投信，这个架子必须线程安全，同时塞也不乱、不丢）和**一个"来信号"铃铛**（每次有信投进来就广播"信箱有动静了"，主动等待的人就守在铃旁）。三个动作对应三个环节：**投信** = 放到架子上 + 摇一下铃；**取信** = 收件人开新回合、整理思考材料时，把攒下的信**一锅端出来**全带进回合，一次取空；**唤醒** = 只有"敲门型"的信才会去叫醒空闲的收件人，"知会型"的悄悄躺着。两个性质：**邮箱是纯内存的**，信只存在内存里，进程一结束就全没，所以"可靠"的边界就是"信被取出来并进了记忆"；也正因如此，把某个 agent 请出内存（临时卸载）之前，会先确认他邮箱已经空了，防止把信弄丢。

**通俗解读（一个 agent 就一个邮箱）**：邮箱本质是"**收件箱**"，归**收件人**所有，不是发件人的东西。每个 agent 恰好挂一个自己的收件箱，任何想跟他说的话——父派活、子汇报、兄弟互发、自动回传——都投进这**同一个**箱子里排队。发件人没有"公用的发件箱"：他要写信，就是把信直接投到**对方**的收件箱，动作落在对方邮箱上。也不会混信：信是点对点投的，只有那个 agent 的精确地址能收到，他的邮箱里只会出现"写给他的"信；每封信还带着发件人和消息类型，收信人取信时能认出"谁寄来的、是派活还是汇报还是结果"。一句话：**邮箱 = 每个 agent 独享的收件箱；通信 = 往收件人的唯一收件箱投信。**

### 子 agent 如何区分自己的消息

三层机制保证子 agent 只收到并认领"给自己的"消息：

1. **点对点投递**（程序路由）：`send_message` / `followup_task` 的目标经寻址解析成**精确线程标识**，消息只投进该线程邮箱——没有广播共享队列，无需自己筛选。
2. **fork 清洗**（历史干净）：继承父上下文时，agent 间通信条目被过滤，子 agent 不会带着发给别人的旧消息启动。
3. **模型认领**（语义层）：每封消息带任务名（接收方）/ 发件人；子 agent 从首条 NEW_TASK 得知自己的规范任务名，提示词明确"`to=/root/...` 即你的身份"，据此用收件人路径匹配自己身份。

**通俗解读（为什么不会收到别人的信）**：三层机制层层设防——**点对点投递**靠寻址，名字被翻译成精确工号、信只投一人，别人的信根本不会进你的邮箱；**继承清洗**在你"出生"（继承父的记忆）时把"发给别人的旧信"滤掉，你不会带着不相干的信息启动；**认领规则**靠信封——每封信都写着收件人名字，你用路径认出"这封是给我的"，然后才读。

### 邮箱之外的其他通信方式

以上讲的都是"agent 之间说出来的话"——这类内容走邮箱，是唯一通道。但广义的"信息怎么到达"还有几条旁路，分工不同、互不冲突：

| 途径 | 性质 | 通俗说明 |
|---|---|---|
| **共享文件系统** | 间接、持久 | 所有 agent 共用同一个工作目录（详见第 9 节）。agent A 把中间产物写成文件，agent B 读到继续干——不经过邮箱。比邮箱重（要落盘）但更持久（跨回合、跨进程）；无文件锁，靠"所有权 + 模型自律"防冲突 |
| **上下文继承** | 一次性、单向 | 派生子 agent 时把父的对话历史传给子（详见第 4 节）。子"一出生就带着父的记忆"，不用发消息去问 |
| **状态广播** | 实时、不带内容 | 各 agent 的状态（空闲/忙/完成/出错）实时广播（详见第 9 节），父扫一眼就能看出子干完没有，不必等消息 |
| **共享持久化** | 系统层面 | 对话历史落盘、派生关系入库（详见第 5 节）。被请出内存的 agent 靠重读自己落盘的记录恢复记忆 |
| **用户中转** | 人参与 | 用户直接给根 agent 输入，等于一条"人→系统"的信息通道，间接影响所有 agent |

一句话收尾：**说"话"走邮箱，干"活"靠文件，出生"带"记忆靠上下文继承，看"状态"靠广播。**

## 7. 工具清单

协作工具统一注册，分 V1 / V2 两套。**去重后共 9 个不同工具函数**，当前默认（V2）启用 6 个。

| 工具函数 | V1 | V2 | 作用 |
|---|---|---|---|
| `spawn_agent` | ✅ | ✅ | 派生新 agent（建线程 + 派初始任务） |
| `send_input` | ✅ | — | V1 版发消息（可 `interrupt`） |
| `close_agent` | ✅ | — | V1 关闭 agent 及其子孙，释放额度 |
| `resume_agent` | ✅ | — | V1 恢复已关闭的 agent |
| `send_message` | — | ✅ | 发消息，不触发回合 |

- 整套受启用开关门控；启用名称空间时可挂到协作命名空间，且不可从执行类工具内部调用

## 8. 完整生命周期走查

场景：root 实现登录模块。时序如下。

```
/root (回合中)                    auth_worker (新线程)             explore_tests (新线程)
    │ ① spawn_agent                   │                                │
    │──► spawn handler 建线程─────► 启动, 回合循环                     │
    │◄── {task_name} 立刻返回        │ (并发执行)                        │
    │ ② 本地不重叠工作                │                                │
    │                                 │ ③ send_message(主动)           │
    │◄────────────────────────────────│                                │
    │ ④ wait_agent(阻塞本回合)        │                                │
    │                                 │ ⑤ 回合终态 → 运行时自动         │
    │◄──────────────── FINAL_ANSWER ──┘                                │
    │ "Wait completed."                                               │
    │ ⑥ 上下文里读到 FINAL_ANSWER     │                                 │
    │ ⑦ followup_task(追加) ──► 唤醒新回合                             │
```

1. **spawn_agent 内部**：解析参数 → 按角色套配置 → 算子路径 `/root/auth_worker` → 过三层闸门（执行槽 / 常驻槽 / 总数槽）→ 按 `fork_turns="all"` 清洗历史 → 建新线程 → 投递初始消息（`trigger_turn:true`）唤醒子回合 → **立刻返回** 任务名与昵称，父回合不等待。

**补充说明（线程是 spawn_agent 工具创建的，不是 Spawn 消息创建的）**：子 agent 线程的创建、注册进注册表，全发生在**父 agent 回合里调用 `spawn_agent` 工具**的瞬间——handler 依次做"算路径 → 过三层闸门 → 建新线程（创建 + 登记进注册表）→ 投递初始消息 → 立刻返回"。**消息类型为 Spawn 的那封"首封信"，是投给已经创建好、已登记在册的线程的**，用来唤醒它开第一个回合（初始任务 NEW_TASK），而不是创建线程的触发器。所以**注册 ≠ 激活**：线程先存在并登记，收到首封信才开干；两者之间有一个极小的窗口——线程已在注册表里，但第一个回合还没跑。一句话：**触发创建的是 `spawn_agent` 工具调用，Spawn 消息只是"新线程开张后的第一封信"。**

2. **父不干等**：做不重叠本地工作，或继续 spawn 其他 explorer。
3. **子 agent 可选主动 send_message**：向父汇报/提问（MESSAGE，不打断父；`send_message` 允许发 root）。
4. **wait_agent**（仅当被结果阻塞）：订阅父邮箱活动，本回合暂停，其他线程照常。
5. **子终态 → 自动 FINAL_ANSWER**：运行时拦截子回合完成事件，以 `trigger_turn:false` 投进父邮箱，`wait_agent` 返回等待完成。
6. **父读到结果**：FINAL_ANSWER 片段在父下一回合构建上下文时注入。
7. **followup_task 追加**：唤醒子 agent 新回合；若已被 LRU 驱逐，先从落盘的记录恢复再投递。

## 9. 并发一致性：多 agent 如何解决状态一致性与冲突

**设计哲学一句话**：**不在文件层做冲突检测**，靠"源头规避 + 串行化写入"；运行期共享状态用原子/锁/信号量；跨线程的图边与状态广播**接受最终一致**。逐层看：

### 文件系统层面：不做冲突检测

所有 agent **共享同一工作目录与容器文件系统**，无 per-agent 工作区隔离，谁都能看到并修改别人的文件。既然共享就得防冲突，但这里的做法是**不设防**：

- `apply_patch` 每次编辑前**实时读文件当前内容**，patch 是相对"此刻磁盘状态"的 diff
- **唯一的冲突信号**：patch 的 old lines 在当前文件里找不到就报错，agent 自己重试
- 没有版本号、乐观锁、文件锁——不存在"我改过之后别人也改过"的检测
- **冲突规避靠提示词**：worker 角色内置规则显式分配文件 **ownership**、并要求"不要回滚他人修改、调整实现适应他人改动"
- **权限门控**：执行策略给出 Allow / Prompt / Forbidden 三档判定，决定命令能否直接执行
- 线程回滚只重建对话历史、**不触碰文件**——因为文件层根本没有一致性快照，做不到"回滚到一致态"

**一个完整例子（apply_patch 怎么改一个文件）**：模型想改 `src/api/login.rs` 的 `issue_token`，不重写整个文件，只发一段 patch（`*** Begin Patch` 开头、`*** End Patch` 结尾）。

文件当前内容示意：`login.rs` 里有两个函数——`verify_credentials`（查库比对密码哈希）和 `issue_token`（签发 token，当前签名只带 `user` 和有效期）。

模型发的 patch：以 `*** Begin Patch` 起头、`*** End Patch` 收尾，声明 `*** Update File: src/api/login.rs`，然后一个 `@@` 块——空格行是**没改的上下文**（`issue_token` 的函数头），`-` 行删旧签名，`+` 行换成带 `TokenKind::Access` 的新签名。

工具的处理（解析 + 执行两步）：

1. **解析**：拆出要匹配的 `old_lines`（空格行 + `-` 行）与替换用的 `new_lines`（空格行 + `+` 行）；
2. **读文件**：实时读磁盘当前内容；
3. **定位**：从头扫，**连续找 `old_lines` 那 3 行**，找到就锁定位置；
4. **替换 + 写回**：算出新内容，整文件覆盖写盘。

结果：只有 `issue_token` 那行变成 `Token::new(user, 3600, TokenKind::Access)`，其余不动。它还能 **Add File**（新建）、**Delete File**（删除）、**Move to**（重命名）。

**关键：它靠"文本定位"而不是"行号"**——文件其他地方被改过、只要这 3 行还在，照样能改；`old_lines` 本身被改掉才报错（下面时序 2 会看到）。

**举例（两个 worker 同改一个文件）**：`apply_patch` 写回是**整文件覆盖**（用重算后的完整内容调写盘），且写回时**不做"文件是否已被别人改动"的校验**。于是三种时序各得一个结果：

场景（文件 v0）：文件里两段函数各占几行。Worker A 负责 `issue_token` 所在区段（45-47 行附近，要加一个 `refresh_token`）；Worker B 负责 `verify_credentials` 所在区段（40-43 行附近，要换成强哈希）。

1. **串行 + 区域不重叠 → 共存**：A 先写完，B 的 old_lines（40-43）原封不动 → 两处修改都落盘。这正是 ownership 提示词想引导的常态。
2. **串行 + 区域重叠 → 报错重试**：A 先改 40-43 并写盘，B 后读盘时已找不到自己的 old_lines → 报"找不到期望行"→ B 重读文件、把自己的改动重新 diff 到 A 的新内容上再试。运行时只给信号，**不自动 merge**。
3. **同时读旧版 → 静默覆盖**：A、B 都读到 v0，各自算出新文件，后写者整文件冲掉先写者 → **无任何报错**，先写者的改动丢失（lost update）。这就是下面"明确接受的竞态窗口"在文件层的体现。

**小结：靠什么兜底、接受什么**——主防线是**模型自律**：任务分解时分配 ownership（每份文件归谁管），并要求"不碰别人的文件；万一被改了，**别回滚，调整实现去适应**"。这是**双重约束**——不只是一开始别碰，还包括"碰到也别顶回去"。模型之外还有一道**机制兜底**：`apply_patch` 的 old lines 校验——模型若真操作了已变的文件，patch 对不上当前内容就报错、重读重试。所以是"**模型自律为主，工具乐观校验兜底**"。而"尽量"不是硬保证：时序 3 表明冲突仍可能发生，互相覆盖后没有检测、没有恢复，落盘即既成事实——这是设计取舍，用概率性的模型自律换掉"锁 + merge"的复杂度，赌 ownership 分好之后冲突足够罕见。

**为什么说它有 CAS 的意思（但差在原子性）**：old lines 校验思路**确实像 CAS**——乐观不预锁、写前对基线、不匹配就失败重试，全是"乐观并发控制"的手法。但**差在原子性**：

- **CAS 是单步原子**：比较 + 交换是一条指令，中间插不进别人，不存在"比较通过但写时被覆盖"。
- **apply_patch 的四步（校验在"算"之前，且写回前没有再次校验）**：读文件拿基线 → 用 old lines 匹配当前内容（**编辑前校验**，找不到即报错）→ 匹配成功才算出新内容 → 整文件覆盖写回。关键：**没有"提交时校验"**——算出新内容就无条件写回，写回前不会再次确认"文件还是不是我读的版本"。校验与写回之间隔着一整段匹配 + 重算，别人随时可插进来改文件；而"提交时校验"（真 CAS 有、apply_patch 没有）正是防"基于旧版覆盖"的那一环——缺了它，时序 3 静默覆盖就必然可能。

三种时序正好映射这个差别：时序 2（old lines 被改掉 → 报错重试）**最像 CAS**；时序 3（都基于旧版 → 校验都通过 → 后写者静默覆盖）**真 CAS 不会出现**——因为 CAS 比较与交换一体，apply_patch 校验与写回分开。另外，校验的是 old lines 的**存在性**而非"整文件还是原版"——别人改了别的区域、old lines 还在，照样通过（时序 1 共存即由此）。真要升级成真 CAS，需给文件加版本号、把"校验 + 写回"焊成单步——但那正是文档开头说的"复杂度不可控"。

### 内存共享状态：分层锁 + 原子计数

（三层并发控制的细节见第 5 节，这里侧重"一致性如何保证"。）

这一小节回答：N 个 agent 在同一进程里并发跑 turn，彼此**共享的那点内存状态**，各用哪种并发原语防竞争。

**能共享的状态其实很少**：每个 agent 的私有状态（对话 / 邮箱 / 当前回合）只有自己的回合循环会写，天然**单写者**，不需要跨 agent 加锁。真正被并发触碰的只有下面 5 个共享对象——"分层"就是对每个对象按访问特征选最合适的原语，而不是套一把全局大锁（那会直接杀掉多 agent 的并行度）。

| 共享对象 | 访问特征 | 原语 | 作用 |
|---|---|---|---|
| 线程注册表 `threads` | 读多（查线程）写少（注册/移除） | `RwLock` | 读并行、写独占 |
| spawn 总数 `total_count` | 极热，每次 spawn 都动 | `AtomicUsize` + CAS | 总量不超发 |
| 执行中数 `active` | 极热，turn 开始/结束都动 | `AtomicUsize` + RAII guard | 并发度不超限 |
| 每线程 `active_turn` | 私有，但多入口竞争 | `tokio::Mutex` check-and-set | 单线程单 turn（互斥，非计数） |
| `agent_status` | 通知型 | `watch` 通道 | 广播状态，接受短暂陈旧 |

逐个看：

- **线程表**：读写锁保护的线程查找表。查线程（消息路由等）很频繁，读写锁让多个读并行；注册/移除是写才独占。表里存的是线程句柄——锁只在"查指针"那一瞬持有，查完即放，线程本体照跑不阻塞。
- **spawn 上限**：先读当前值，达到上限即拒绝；否则用 CAS 试着换成 当前值+1，**失败说明有人抢先，拿新值重试**。两个并发 spawn 读到相同的当前值，但只有一个 CAS 赢——绝不超发。配 RAII 占位，中途失败结束时把计数减回去，防泄漏。
- **执行中上限**：计数器记录当前活跃子 agent 数，配置一次设定。回合开始前读计数看名额，无名额即拒绝（回合根本不启动）；有名额则占位加一，返回的守卫在**结束时自动减一**，计数必然归还。只对子 agent 生效。
- **单线程单 turn（最硬的一条保证）**：当前回合槽用异步互斥锁做 **check-and-set**：上锁后先检查、再占位，**检查与占位在同一把锁里故原子**。用户输入与邮箱邮件同时砸向同一空闲线程时只有一方通过检查，另一方被拒（消息留到下一回合）。这一条消掉了"同一 agent 内部并发写自己状态"的可能。
- **agent_status**：用 watch 通道广播，订阅者**接受短暂陈旧**——不追求每次读都同步。

**功能视角（大白话）**：把多 agent 看成一个小团队——root 是老板，子 agent 是员工，这 5 个共享对象就是"让团队正常运转的公共设施"：

- **名册（线程表）**：记着每个员工的工位与工号。老板要喊某个员工，先在名册上按名字查到工号，才能把话递到他的工位信箱；招人、找人、盘点谁在，都靠这本名册。没有它，消息就送不到人。
- **编制上限（spawn 总数）**：公司规定最多招 N 人。每次招人先占一个编制，招满了就拒招——防止员工无限招下属、团队变成无底洞；编制还要"占而不成就退回"，防止名额悄悄漏光。
- **值班名额（执行中数）**：工位上可以坐 100 人，但同一时刻只让 5 个人真干活，其他人待命。谁想开工先看有没有空名额，满了就排队等。它是"并发油门"：管的是同时干多少，不是一共有多少。
- **一人同时只做一件事（active_turn）**：老板刚派新活、消息又到了，员工一次只能接一件——先占住"我在忙"的牌子，第二件就拒收，放一边等做完再处理。防止一个人把自己搞乱。
- **状态公告板（agent_status）**：每个人的状态（空闲/干活中/做完了/出错）挂在公告板上，老板扫一眼就知道谁做完了、谁卡住了，不用挨个敲门问。允许稍微滞后，但换来"谁都不用等谁"。

**例子**：root 派 `auth_worker` 和 `db_worker` 两个员工做登录模块——
1. root 想给 `auth_worker` 发新任务：先在名册上把名字翻译成工号，消息投进他的工位信箱；
2. 招 `db_worker` 时先占编制、查值班名额，名额满了就得等别人干完；
3. 两个员工各自开工，每人同一时刻只做自己那一件活；
4. root 扫一眼公告板，看到 `auth_worker` 变"做完了"，结果自动送回来。

**两个计数 vs 三个非计数**：真"限阈值"的只有 `total_count`（**线程存量**上限，一个 session 最多派生多少）和 `active`（**执行并发**上限，同一时刻多少子 agent 在跑）——两者维度不同，存量 ≠ 并发度。其余三个不是计数：`active_turn` 是**互斥**（保每线程单写者）、RwLock 是**数据结构安全**、`watch` 是**通知解耦**。

**分层思路**：最热的计数路径用**无锁原子**（并发 spawn/开 turn 互不阻塞，靠 CAS 自己裁决）；中频注册表用**读写锁**；最关键的单线程单 turn 用**互斥锁 check-and-set**——它是整个并发模型的地基：一旦成立，每个 agent 自己的状态就都是单写者，跨 agent 竞争被压缩到仅剩的计数器和注册表上，各保一块。代价是放宽部分一致性（watch 陈旧、计数与 map 非原子一起更新），即下文"明确接受的竞态窗口"。

**为什么是这几种原语（选型逻辑，不是随机挑的）**：并发里没有"万能锁"——保护共享状态有四种不同诉求，各付各的代价：

- **极热、只做简单增减**（spawn 总数、执行中数）→ **无锁原子**（CAS / `fetch_add`）。付的代价是"可能白读一次、重试一把"，换来**谁都不排队**。若用锁，每次 spawn / 开 turn 都串行排队，直接扼杀并行度。
- **中频、读多写少**（线程表）→ **读写锁**。读者互不挡、只有写者清场独占；查得快、写得少，写者等读者的时间可忽略。
- **必须精确互斥**（active_turn）→ **互斥锁 check-and-set**。唯一会"排队等待"的原语，但拿锁区间只有"查一下、占个位"，极短；换来"同一线程绝不会同时跑两个 turn"这条最硬保证。
- **通知型、可容忍短暂滞后**（agent_status）→ **watch 通道**，根本不用锁。写方更新、读者看最近快照，谁都不等谁，代价是可能看到旧值——这正是它被放进下节"明确接受的竞态窗口"的原因。

**三条配套事实**：

- 无锁原子有两种风格：spawn 计数是"读 → CAS 试着 +1，失败拿新值重试"，配 RAII 防占后失败漏名额；执行中数是"查名额 → 占住 → 守卫自动归还"。
- active_turn 用的是 **异步锁**而非普通锁：check-and-set 要**跨 await 保持**，普通锁跨 await 不安全。
- 这是按**热度分层**的选型：最热的走无锁原子，中频走读写锁，唯一精确互斥的走互斥锁——不是一把全局大锁包打天下。

### 持久化一致性：串行化写入 + flush 屏障

**先拆词（这两个词到底在说啥）**：

- **rollout = 线程的流水账**。每个线程从出生到现在的全部记录——每条对话消息、agent 间通信、事件、元数据，按时间顺序一行行记进自己的历史文件。这份账本是线程历史的**权威正本**：内存里的对话只是运行副本，SQLite 表只是可重建的投影，都以它为准。
- **rollout 写入 = 记一笔账**。turn 每产生一条消息/事件，就往账本追加一条。但它是**两步**的：先记账（丢进后台队列，马上返回），后台 writer 再真正写进文件——**记了账 ≠ 落了盘**。
- **flush 屏障 = 一条分界线**。flush 命令后台 writer"把我前面排队的账全部写完刷盘"，再用一个确认通道等它回话，没回话就等着。它保证"分界线之前的所有账都已落盘"——把"异步、不确定的写入"变成"同步、确定的落盘"。没有它，进程一崩，队列里"以为写了其实没写"的账就全丢。

**补充说明（"投影"不是正文的备份拷贝）**：rollout 是对话正文的**唯一权威正本**；SQLite 表是"可重建的投影"——从流水账里**提炼 / 重算**出来的结构化派生态（线程元数据、派生边、会话索引、可查询摘要），目的是回答跨线程、关系型的查询（全局有哪些线程、谁派生谁、改名删除），**不是把正文再存一份**。正因为是派生的，**库里这份丢了，能拿 rollout 完整重建回来**；反过来 rollout 丢了，投影救不回来——它"丢得起"，才叫投影。一句话：**正文只在 rollout 一份，库里存的是从正文提炼出的关系索引，不是正文拷贝。**

- **rollout 写入**：回合只把条目推进后台写队列（容量 256），后台 writer 消费；**flush 用一次性确认做屏障**，调用方等确认才继续
- **writer 锁**：每线程一把写锁串行化进程内写入，再配跨进程锁文件防多进程同时写同一线程
- **fork 快照一致**：派生子线程前先把父历史刷盘落稳，子 agent 继承的是**已提交一致的父历史**，不是排队中的尾巴
- **派生关系图**：派生边写进 SQLite 时若已存在则覆盖——**最后写入者赢**
- **压缩**：历史压缩在该线程回合内**内联**执行，与回合天然串行

### 明确接受的竞态窗口（设计取舍，不是 bug）

- `watch` 订阅者看到的 agent_status **短暂陈旧**
- 派生关系图的 spawn 边**最终一致**，并发下靠"最后一次写"收敛
- `total_count`（原子计数）与活跃 agent 映射**非原子一起更新**，有短暂不一致窗口（CAS 只保证不超发）
- mailbox 驱逐保护"**队列为空才允许驱逐**"，但"查空"与"驱逐"间仍有极小窗口（可接受，驱逐保守、宁可不驱逐）
- 邮箱**纯内存**，进程崩溃即丢——一致性边界就是进程生命周期

### 小结

> 文件层不做冲突检测（多 agent 改同一份源码必然要 merge 语义，复杂度不可控），靠任务分解时**分配所有权 + 互不 revert**从源头规避；运行期共享状态用**原子计数/锁/通道**保证不超发、单线程单 turn；持久化靠**串行写 + flush 屏障**保证每线程自己的 rollout 一致，跨线程的图边和状态广播**接受最终一致**。

## 10. 关键澄清点

1. **spawn_agent 等是"普通工具形式 + 不普通的执行语义"**：工具调用只是入口，实际效果是启动一个并发的完整 agent 循环（独立 Session + 独立回合循环）。
2. **FINAL_ANSWER 自动回传不是子 agent 调 send_message**：是运行时在子回合终态自动完成，子 agent 无需任何操作；`send_message` 是子 agent 可选的**主动**通信工具，两者并存但机制不同。
3. **"spawn 之后 wait"不是写死的**：`wait_agent` 的阻塞行为是代码写死的，但何时调用由 **LLM 决策**（提示词建议少用、仅在关键路径被阻塞时）。父收结果通常走"继续干活 + FINAL_ANSWER 自动注入"，无需 wait。
4. **兄弟 agent 可直连但设计上倾向层级**：底层是同构的扁平异步消息总线，软约束压成树形消息流。
5. **通信本质 = "各自队列互塞 + watch 通知 + trigger_turn 语义 + 上下文注入"四件套**：队列（互斥保护的 FIFO）只是存储本体，入队时靠 watch 广播唤醒、`trigger_turn` 决定敲门与否、取出后渲染进上下文才算送达。并发限流 / AgentPath 树 / LRU / rollout 属于**编排与资源管理**，不是通信本身。
