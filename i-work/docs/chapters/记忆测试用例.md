## 记忆管理功能概览

> 把对话沉淀成可复用的记忆，让 AI「记得」之前聊过什么。四层模型：**原始对话（L0）→ 原子记忆（L1）→ 场景记忆（L2）→ 画像记忆（L3）**。每层解决不同问题、用不同方式召回。

### 四层模型

```
L0 对话记录（原始）  →  L1 原子记忆（结构化）  →  L2 场景记忆（情景）  →  L3 画像记忆（语义）
    核对原话/时间         精确召回事实             快速恢复情境            进入用户/团队语境
```

| 层 | 内容 | 回答的问题 | 注入方式 |
|---|---|---|---|
| **L0 对话记录** | 原始对话逐字存档（事实源） | 「当时原话是什么」 | 不直接注入，靠「对话搜索」工具按需查原文 |
| **L1 原子记忆** | 单条事实碎片（结构化） | 「和这条对话直接相关的具体事实」 | 按查询检索 top-N，拼到用户消息前缀（动态） |
| **L2 场景记忆** | 跨会话连贯叙事（情景） | 「有哪些进行中的情境、全貌」 | 全量注入「场景导航」，放系统提示词末尾（稳定） |
| **L3 画像** | 凝练的稳定身份（语义） | 「这个人/团队是谁、该怎么服务」 | 整份注入，放系统提示词末尾（稳定） |

### 核心概念

- **原子记忆（L1）**：从 L0 对话抽取的单条结构化事实（`persona` / `episodic` / `instruction`），双写到「按天追加的产出文档 + 检索库」；抽取前经质量门预筛、抽取后做冲突判断（store / update / merge / skip）
- **场景（L2）**：把方向一致的 L1 记忆**重写融合**成的 .md 叙事文档（不是清单、不是追加列表），文件头含 META（created / updated / summary / heat）
- **画像（L3）**：综合 L2 场景产出的稳定身份文档 `persona.md`，有硬性字符上限（对话模式 2000 字符 / 团队模式 1200 字）
- **召回**：每轮对话前把三层记忆预取好，拆成「动态部分（用户消息前缀）+ 稳定部分（系统提示词末尾）」两段注入

### 数据流闭环

```
会话 → L0 存档 → L1 抽取 → 记忆库 → L2 场景聚合 → L3 画像 → 下次会话召回 → 会话
```

### 观察标记 / 产物（设计级）

> 说明：**L1/L2/L3 不弹 UI toast**。以下观察对象基于设计文档描述（功能实现后逐一对齐），多数是数据目录里的文件与检索库记录。

| 观察对象 | 内容 | 位置 |
|---|---|---|
| L1 产出文档 | 按天追加的原子记忆记录（只追加不修改，事实源） | 数据目录 / 产出文档 |
| L1 记忆库记录 | 检索库中的原子记忆记录行 | 检索库 |
| 血缘日志 | 每条记忆来自哪批消息、执行了什么动作 | 数据目录 / 血缘日志 |
| 场景文件 | `scene_blocks/*.md` 叙事文档（含 META 头） | 数据目录 / scene_blocks/ |
| 场景索引 | 所有场景的文件名 / 摘要 / 热度 / 时间的清单 | 数据目录 / 场景索引 |
| 画像文件 | `persona.md`（画像正文 + 末尾场景导航） | 数据目录 / persona.md |
| 动态注入区 | `<relevant-memories>`（L1 相关记忆，拼到**用户消息前缀**） | `context_payload` |
| 稳定注入区 | `<user-persona>` + `<scene-navigation>` + `<memory-tools-guide>`（**系统提示词末尾**） | `context_payload` |

### 1.1 测试准备（必读）

| 项目 | 说明 |
|---|---|
| 启动服务 | `python -m uvicorn server.main:app --host 127.0.0.1 --port 8000` |

| 发消息 | `POST /sessions/{id}/messages`，请求体带 `content`（正文）、`mode`（本轮模式）等，返回 NDJSON 流 |

| 快速触发 L2 | L1 抽取完成后自动级联（设计默认延迟 10 秒）；最小间隔默认 900 秒是护栏，验证时可调小 |
| 快速触发 L3 | 冷启动（首次有场景无画像）立即触发；或让新增记忆达到阈值（默认 50 条） |

| 日志 / 产物 | 含义 |
|---|---|
| L1 抽取日志 | 本轮抽了多少条、游标推进到哪、抽取/去重结果 |
| L1 产出文档 | 按天追加的原子记忆记录（双写的事实源） |
| L1 记忆库记录 | 检索库原子记忆行：store 新增 / update / merge 版本递增、skip 无变化 |
| 血缘日志 | 每条记忆的来源消息批次与动作 |
| L2 场景日志 | 场景整合动作（UPDATE / MERGE / CREATE / 删除）、热度变化 |
| `scene_blocks/*.md` | 场景叙事正文 + META 头（created / updated / summary / heat） |
| `persona.md` | 画像正文 + 末尾场景导航 |
| `context_payload` | 每轮实际发给 LLM 的完整上下文，可看到三层注入的最终效果 |

### 1.2 L1 原子记忆模块

> L1 把 L0 新对话按游标增量读出来，经过「质量门 → 场景切分+抽取 → 截断 → 候选召回 → 冲突判断 → 双写落地 → 血缘 → 级联 L2」。全流程只有两处调用 LLM（抽取、去重）。

#### E2E-L1-01 轮次阈值触发抽取
- **前置**：新建会话；抽取阈值设为较小值以加速（如 N=2，可配置）。
- **步骤**：连续发送消息，累计轮次达到阈值。
- **预期**：达到阈值的轮次后触发抽取，日志出现 L1 抽取记录；产出文档与检索库出现新增记忆；游标推进，**每条消息只被抽一次**。

#### E2E-L1-02 空闲兜底抽取
- **前置**：会话内只发不足阈值轮次的消息（如 N=5、只发 2 轮）；空闲计时器默认 10 分钟。
- **步骤**：停止对话，等待空闲计时器到期。
- **预期**：计时器到期后自动补抽一次，把当前累积的消息抽掉；该会话已抽完时再次到期**直接跳过、不重复抽取**。

#### E2E-L1-03 会话冲刷抽取
- **前置**：会话内存在未抽取的尾部消息。
- **步骤**：明确结束会话（会话关闭 / 重置）。
- **预期**：会话结束时入队冲刷任务，把最后未抽的消息一次性收尾；冲刷后无残留未抽消息。

#### E2E-L1-04 存量级联抽取
- **前置**：一次性批量灌入大量历史消息（导入 / 迁移 / 恢复），L0 游标后积压数百条。
- **步骤**：触发首次抽取。
- **预期**：首次抽不完，抽取完成后发现仍有积压 → **立即再排一次**，级联连续抽取直到追平；日志出现多轮级联抽取记录。

#### E2E-L1-05 质量门滤结构噪音
- **前置**：对话中包含空消息、纯空白消息、框架内部噪音（引导语 / 会话重置）、斜杠命令（如 /new、/reset）、纯符号/纯问号的短消息。
- **步骤**：让这批消息进入抽取。
- **预期**：结构噪音与纯符号消息被规则预筛滤掉，**不进 LLM 抽取**（不产生记忆、不报错）。

#### E2E-L1-06 LLM 宁缺毋滥滤闲聊
- **前置**：对话中包含问候、闲聊、一次性操作指令（如「这次帮我翻译一下」）、纯主观感受。
- **步骤**：触发抽取，观察 LLM 输出。
- **预期**：闲聊 / 无意义内容按「宁缺毋滥」规则被过滤，不产出记忆；产出的记忆均为**可复用结论**（跳出当前对话依然成立）。

#### E2E-L1-07 场景切分+抽取结构化输出
- **前置**：对话中发生话题切换（如从「排查 Billing 超时」切到「规划旅行」）。
- **步骤**：触发一次抽取。
- **预期**：**一次 LLM 调用**返回合法 JSON 数组，每个元素含情境（场景名）与该情境下的记忆；话题切换被识别为多个情境；记忆字段含 `content` / `type` / `priority` / `source_message_ids`；`scene_name` 与 `content` 使用用户消息的语言。

#### E2E-L1-08 背景消息禁止提取
- **前置**：构造一批「背景消息」（仅供理解上下文）与「新消息」（唯一提取来源）。
- **步骤**：触发抽取，检查 LLM 输出。
- **预期**：所有记忆均来自新消息；背景消息中的信息**不产生记忆**（仅作理解上下文、推断关系/时间）。

#### E2E-L1-09 每会话条数截断
- **前置**：一轮抽取产出的记忆数量超过上限（默认 10 条）。
- **步骤**：触发抽取。
- **预期**：只保留前 10 条，超出部分被截断；检索库该会话记忆条数 ≤ 10。

#### E2E-L1-10 候选召回
- **前置**：检索库已有若干原子记忆；新抽取一条与旧记忆语义相似的记忆。
- **步骤**：抽取进入冲突判断之前。
- **预期**：算法召回相似旧记忆作为候选（默认 top 5，相似度从高到低）；**同批新记忆被排除**（自己和自己不比）、**不跨租户**；无检索能力（库为空且无能力）时跳过冲突判断、全部走 store。

#### E2E-L1-11 冲突判断 store（新增）
- **前置**：新记忆与候选无相似 / 无冲突。
- **步骤**：触发冲突判断。
- **预期**：LLM 输出 `store`；记忆作为新增写入，产出文档追加 + 检索库写入，版本号为 1。

#### E2E-L1-12 冲突判断 update（覆盖）
- **前置**：新记忆与旧记忆描述**同一事实/事件**且更优（更具体 / 更晚 / 纠错）。
- **步骤**：触发冲突判断。
- **预期**：LLM 输出 `update`，`target_ids` 指向旧记忆；**旧记忆被删除**，新记录版本号 = 目标最大版本 + 1；可保留旧记忆中仍正确的细节。

#### E2E-L1-13 冲突判断 merge（合并）
- **前置**：新记忆与多条旧记忆互补且不矛盾（同一事件不同阶段，或跨类型）。
- **步骤**：触发冲突判断。
- **预期**：LLM 输出 `merge`，可**跨 type**、可**多对多**（`target_ids` 数组）；合并成一条更完整记忆，target 旧记忆被删除，版本号递增。

#### E2E-L1-14 冲突判断 skip（忽略）
- **前置**：新记忆与候选重复，或更模糊 / 无增量。
- **步骤**：触发冲突判断。
- **预期**：LLM 输出 `skip`；不写入任何新记录，旧记忆保持不变。

#### E2E-L1-15 落地双写
- **前置**：一批抽取同时含 store 与 update/merge 两类动作。
- **步骤**：冲突判断完成后落库。
- **预期**：store 在产出文档追加 + 检索库写入；update/merge 从检索库**删除目标记忆**、产出文档追加新记录（旧行保留待定期对账清理）；**单侧写失败不阻塞另一侧**。

#### E2E-L1-16 血缘日志
- **前置**：完成一批抽取。
- **步骤**：查看血缘日志。
- **预期**：每条记忆记录了来源消息批次（source_message_ids）与执行动作，可追溯「记忆从哪批消息来」。

#### E2E-L1-17 级联 L2
- **前置**：L1 抽取成功完成。
- **步骤**：观察 L2 调度。
- **预期**：抽取完成后为该作用域调度 L2（默认延迟 10 秒）；同一作用域计时器**只提前不推迟**，保证尽快聚合新记忆。

### 1.3 L2 场景记忆模块

> L2 把 L1 中方向/主题一致的记忆整合进**同一个场景文件**，由 LLM 主动决策（UPDATE / MERGE / CREATE），重写融合成连贯叙事（明确禁止简单追加列表）；工程侧做确定性收尾。

#### E2E-L2-01 增量读取
- **前置**：L1 已产生若干记忆记录。
- **步骤**：L2 处理。
- **预期**：只读取游标之后新增的 L1 记录，且传给 LLM 的**只保留 content / created_at / id**（不带类型、优先级等结构字段）；已处理过的记忆不重复聚合；无新记录时**直接跳过、不推进游标**。

#### E2E-L2-02 作用域分组
- **前置**：不同隔离作用域（teamId + agentId）的记忆混合在一起。
- **步骤**：L2 读取后分组。
- **预期**：按「teamId + agentId」拆成独立组，每组独立聚合；刻意**忽略用户 / 会话 / 任务维度**（仅 teamId 缺省时退化到 userId 兜底）。

#### E2E-L2-03 UPDATE 整合（首选）
- **前置**：已有场景文件；新记忆与该场景方向一致。
- **步骤**：LLM 整合。
- **预期**：**默认策略是 UPDATE 不是 CREATE**；新记忆被**重写融合**进已有场景（不是简单追加列表），文件头 `heat = 旧heat + 1`、`updated` 更新为新时间。

#### E2E-L2-04 CREATE 新场景（最后手段）
- **前置**：新记忆与所有已有场景方向都不同。
- **步骤**：LLM 整合。
- **预期**：先 `read` ≥2 个最相似场景验证确实无法融入后才 CREATE；新文件 `heat = 1`，**每批最多新增 1 个场景**；文件名符合命名规范（无空格 / 括号等非法字符）。

#### E2E-L2-05 MERGE 合并
- **前置**：两个场景属同一叙事弧线（或超限强制合并）。
- **步骤**：LLM 整合。
- **预期**：合并成一个概括性更强的场景文件，`heat = 所有相关场景热度之和 + 1`；被合并的旧文件**必须写 `[DELETED]` 标记**；清理后旧文件消失、文件总数减少。

#### E2E-L2-06 场景数量上限与分级预警
- **前置**：场景数达到上限（默认 15）。
- **步骤**：LLM 处理新记忆。
- **预期**：红色预警（≥ 上限）：**必须先 MERGE** 把最相似的 2-4 个场景合并为 1 个并删旧文件，直到 < 上限再处理新记忆；橙色预警（= 上限 - 1）：**只能 UPDATE，不能 CREATE**；数量不无限膨胀（偶发超限由下一轮预警再要求合并）。

#### E2E-L2-07 热度管理
- **前置**：多次 UPDATE / MERGE 之后。
- **步骤**：查看场景文件 META 与场景导航。
- **预期**：新建 `heat=1`、更新 `heat=旧+1`、合并 `heat=sum+1`；场景导航按**热度降序**排序，热度分档（≥50 单火、≥100 双火、≥200 三火、≥500 四火、≥1000 五火）。

#### E2E-L2-08 确定性收尾
- **前置**：LLM 留下 `[DELETED]` 标记文件、空白文件、只有文件头没正文的残留文件、非法文件名。
- **步骤**：工程侧收尾。
- **预期**：软删 / 空白 / 残留文件被真正清理；文件名规范化（空格 → 短横线、去括号等）；**场景索引被全量重建**（索引只由工程侧维护）。

#### E2E-L2-09 场景导航更新
- **前置**：L2 完成，画像文件存在。
- **步骤**：查看画像文件末尾。
- **预期**：读最新索引生成「场景导航」（路径 / 热度 / 摘要），剥离画像里旧的导航后追加重写；画像文件不存在、或只剩导航没有正文时**跳过**，等画像生成。

#### E2E-L2-10 级联 L3 与画像信号
- **前置**：L2 完成；LLM 在文本输出中带了 `[PERSONA_UPDATE_REQUEST]` 标记。
- **步骤**：解析信号并观察 L3。
- **预期**：主动请求信号被解析写入检查点，供后续 L3 画像刷新**优先触发**；L2 完成后推进 L3 调度（L3 是否真正执行由画像触发器按优先级二次判断）。

### 1.4 L3 画像记忆模块

> L3 读 L2 场景做综合分析，产出一份凝练、稳定、有界的画像文档 `persona.md`（对话模式上限 2000 字符）。触发靠五级优先级，生成分首次 / 增量两种模式。

#### E2E-L3-01 触发 P1 主动请求
- **前置**：L2 抽取时 LLM 输出了 `[PERSONA_UPDATE_REQUEST]`（重大价值观转变 / 跨场景突破性洞察）。
- **步骤**：观察 L3 触发。
- **预期**：画像被**立即（插队）**触发更新；触发原因记录在画像生成的触发信息里。

#### E2E-L3-02 触发 P2 冷启动
- **前置**：已抽取过场景、从未生成过画像、且有场景文件。
- **步骤**：观察 L3 触发。
- **预期**：冷启动触发画像生成，模式为「🆕 首次生成」。

#### E2E-L3-03 触发 P4 阈值
- **前置**：自上次画像以来新增记忆数达到阈值（默认 50 条）。
- **步骤**：持续产生记忆直到阈值。
- **预期**：达到阈值触发画像增量更新；阈值计数在画像生成后被清零、重新累计。

#### E2E-L3-04 首次生成
- **前置**：无旧画像（画像正文为空）。
- **步骤**：触发首次生成。
- **预期**：基于当前所有变化场景从零提炼，输出完整模板文档（核心原型 + 基本信息 + 长期偏好 + Chapter 1-4）；对话模式**长度 ≤ 2000 字符**；内容只来自提供的场景数据（**禁止过度推测、禁止用非场景来源信息**）。

#### E2E-L3-05 增量更新
- **前置**：已有旧画像 + 变化场景。
- **步骤**：触发增量更新。
- **预期**：基于「旧画像全文 + 变化场景全文」迭代，自主选择**强化 / 补充 / 修正 / 重构 / 不改**；**不把每次变化追加成新条目**，保持「持续压缩、少而准」。

#### E2E-L3-06 后处理
- **前置**：LLM 写完画像但夹带了场景导航区块 / 注入边界标签 / 空内容。
- **步骤**：工程侧后处理。
- **预期**：LLM 写的导航被剥掉（只留正文）；正文里可能的**注入边界标签被转义**（防逃逸）；剥离 + 转义后正文为空 → **本次判定失败、不落地**。

#### E2E-L3-07 备份
- **前置**：已有旧画像。
- **步骤**：生成新画像之前。
- **预期**：旧画像先备份一份，默认保留最近 **3 份**；即使新画像写坏也能找回上一版。

#### E2E-L3-08 落地
- **前置**：画像生成成功（有正文）。
- **步骤**：查看画像文件。
- **预期**：画像文件最终形态 = **画像正文 + 最新场景导航**一体落地；召回注入时剥掉导航只取正文。

#### E2E-L3-09 检查点推进
- **前置**：画像生成（成功或失败）。
- **步骤**：查看检查点。
- **预期**：生成时间被推进、当前已处理记忆总量快照更新、新增记忆计数清零、P1 主动请求信号被消费；**无论成功还是失败检查点都推进**（避免对同一批数据反复重试）。

#### E2E-L3-10 稳定注入
- **前置**：画像已生成。
- **步骤**：观察多轮 `context_payload`。
- **预期**：画像整份（剥导航后正文）包在「用户画像」标签里，拼到**系统提示词末尾**稳定区；两次画像更新之间**字节级不变**（命中提示词缓存）；变化只发生在画像更新后。

### 1.5 三层召回模块

> 每轮 AI 开口前，宿主用当前用户消息当查询，把三层记忆（L1 相关记忆 + L2 场景导航 + L3 画像）一次预取好，拆成两段注入。

#### E2E-MEMREC-01 三层预取
- **前置**：已有 L1 记忆、L2 场景、L3 画像。
- **步骤**：发一条新消息，查看 `context_payload`。
- **预期**：一次召回同时带回三层——L1 相关记忆、L2 场景导航、L3 画像，一起注入上下文；预取是**同步**的（LLM 等这份记忆到位）。

#### E2E-MEMREC-02 动态/稳定拆分
- **前置**：同上。
- **步骤**：对比相邻两轮 `context_payload`（同一条用户消息前后切话题）。
- **预期**：L1 相关记忆拼到**用户消息前缀**，随问题每轮变化；画像 + 场景导航 + 记忆工具指南拼到**系统提示词末尾**，两轮之间字节级不变（命中缓存）；L1 检索口径为默认 top 5、相似度阈值 0.3、整体超时 5 秒。

#### E2E-MEMREC-03 主动工具兜底
- **前置**：注入的记忆不足以回答当前问题。
- **步骤**：引导 agent 需要更深入的信息（具体场景正文 / L0 原文 / 更多 L1 记忆）。
- **预期**：agent 可主动调用「记忆搜索」（L1）/「对话搜索」（L0）/「读场景文件」（L2 按路径读全文）；其中**两个搜索工具每轮合计限 3 次**，3 次后仍无结果则直接基于已有信息回复、不再搜。

#### E2E-MEMREC-04 失败不阻塞
- **前置**：召回服务异常 / 超时，或当前用户消息过短。
- **步骤**：继续发消息对话。
- **预期**：召回失败或超时**不阻塞对话**（非关键路径，仅在响应里带错误码，对话照常进行）；取不到当前用户消息、或查询清洗后不足 2 个字符时，本轮不召回。

### 1.6 注意事项（测试人员）

1. **功能尚未实现**：本文档为**设计级验收用例**，观察对象（产出文档 / 场景文件 / persona.md / 注入区标记）基于三份设计文档的描述，待功能落地后逐一对齐。
2. **记忆不弹 UI 提示**：L1/L2/L3 的产出是文件、检索库记录与上下文注入，不产生界面 toast；判断是否触发以日志、数据目录产物、`context_payload` 为准。
3. **触发有护栏，测试可加速**：L1 空闲兜底默认 10 分钟、L2 最小间隔默认 900 秒、L3 阈值默认 50 条——验证时可调低配置加速，验证通过后调回。
4. **抽取口径是「轮」与「游标」两套**：L1 按「轮」触发但按游标消费 L0 消息行；批量灌入历史数据会走存量级联连续抽；每会话抽取上限 10 条。
5. **场景上限靠 LLM 自觉遵守**：数量上限（默认 15）靠提示词里的分级预警约束 LLM，工程侧只做事后清理；偶发超限属预期，下一轮红/橙预警会再要求合并。
6. **比较注入用同一会话同一模式**：动态部分（L1）每轮变、稳定部分（画像 + 导航 + 指南）字节级不变；比对两轮差异时应确认稳定区一致、只动态区变化。
7. **L2/L3 的「LLM 沙箱文件工具」形态**：本文档按设计文档语义描述验收行为；实现侧可能采用「单次 LLM 输出、工程侧写文件」的等价形态，验收标准不变（文件产物、热度、导航、画像一致）。
