### 17.1 问题定义：Agent 幂等管什么、和传统请求幂等差在哪

传统幂等的对象是**一次请求**：客户端带幂等键发 N 次，服务端只处理一次、返回同一结果。判断标准简单——"同样的调用，重复执行与执行一次的最终状态一致"。

先停一下，把贯穿全文的词定住：**"副作用"指 agent 动作对外部世界造成的持久改变**——写文件 / 删除改名、调外部 API、执行 shell 命令、写库 / 写记忆等"做了就留下痕迹，无法靠撤销或简单重放来对齐"的动作。与之相对的是**只读 / 纯计算**（读文件、检索、生成文本）：重跑多少次结果都一样，无副作用，重试永远安全。判断一个动作有没有副作用，只需一问：**它是否改变了动作发生前的外部状态？**——覆盖写同内容算副作用（动了文件系统）但可安全重放（结果一致）；`>>` 追加算且不可重放（每次多一行）；发 HTTP POST 算且不可重放（可能下单两次）。正因为一条用户消息会派生**一串**这样的动作，且两串几乎不可能跑成一样（LLM 非确定），幂等问题才从"一次请求"退化成"一束会改世界的动作"——17.2 的三道防线与 17.3 / 17.4 的机制都围绕它展开。

Agent 系统的幂等对象是**一段会自我决定下一步的长进程**，用"重复执行与一次执行状态一致"去套立刻失效：同一用户消息交给 LLM 重跑两次，工具序列几乎不可能一致（非确定性），"最终状态一致"无从谈起。所以必须先把"幂等在这里管什么"拆成三个互相独立的承诺：

| 承诺 | 问的是 | 对照物 |
|------|--------|--------|
| **① 外部副作用至多一次** | 一次写文件 / 外部调用，会不会因重试或重跑被执行两遍？ | 传统 exactly-once 副作用 |
| **② 内部处理至多一次** | 同一条用户消息会不会被排两次队、同一结果会不会被消费两次？ | 传统请求幂等（入队侧） |
| **③ 恢复时对"已发生事实"诚实** | 崩溃后重启，能否说清"上次做到哪、哪些动作已生效"，而不假装一切从零？ | 传统事务的恢复日志 / 审计 |

三点里只有 ② 能借传统请求幂等的现成做法；① 是 Agent 特有的（动作由 LLM 发出、失败会自动换方案重试，副作用边界不清）；③ 是 Agent 长生命周期 + 中间状态多导致的**新增责任**——传统请求处理完要么成功要么失败，Agent 一条消息处理到一半崩溃，留下的不是"干净的回滚点"，而是一堆可能已落盘的工具副作用。

由此得到贯穿全章的两条地基：

1. **LLM turn 不可重放 → 恢复单元只能是"已持久化的执行"，不是"重新跑一遍推理"。** 若崩溃恢复 = 把消息重置成 pending 从头重跑，那 LLM 大概率发出不同的工具序列，等于重新开始而不是续跑；真正能保证的只有"不会把同一个已生效的动作再执行一遍"。所以本章所有方案都以 **"动作级可幂等" + "已发生事实可审计"** 为支点，而不是"整条消息可重跑"。

2. **幂等必须分级逐层解决，不存在一把万能锁。** 一条消息的完整旅程是：**客户端投递 → 服务端入队 → 引擎逐 turn 推理 → 逐个工具执行（副作用发生点）→ 结果注入 → 收尾/失败恢复**。不同段落的重复来源不同、解法不同，落在哪一层处理取决于"重复在哪个边界最容易发生"。这正是 17.2 要按"协议层 → 运行时防御 → 业务兜底"分层的理由。

> 与传统软件对比（承接 12.1 的表格）：传统"重试近乎免费、失败可复现"；Agent"每次重试烧 token、失败不可复现、副作用已发生无法感知"。因此 Agent 的幂等设计**宁可在"要不要自动重试"上保守（把不可逆写操作交给人工/LLM 换方案），也不可贪图流畅而放开自动重放**——一次重复的外部副作用比一次被打断的体验贵得多。

### 17.2 心智模型：三道防线（协议层 · 运行时防御 · 业务系统兜底）

按"一条消息旅程"去切层，早已在草稿里证明太细。这一节把幂等看成一件事上叠的**三道防线**——越靠外层越通用、越靠里越贴近动作本身：前一道拦不住，才轮到后一道；三道都判不出时，靠账本如实记录、把交代权交回用户。每道防线各在下面章节有落点。

**① 协议层 · 定规矩（先定义，后执行）**

把"哪些动作能安全重放"在动作发生前钉成工具定义上的既定事实，不在每次调用时现算：工具经 `server/tools/idempotency.py` 按名字派生 `idempotency`（read-only / idempotent / non-idempotent）与 `side_effect`（读 / 写），定义里可显式覆盖默认（`apply_to_tool_def` 尊重已有标注）；`requires_approval` 是另一路，不随定义写死，由 `permission.py` 在运行期按策略判定。这份分类决定后面每一档行为：②先不先落账、④是否先问人、⑦判不出时敢不敢自动重放。
→ 落点：**17.4.0 ① 先定义工具（分类前提）**。

**② 运行时防御 · 以状态为准的判断（不依赖重试方自觉）**

协议层只立规矩，不保证执行。真正挡重复的是运行时两处以状态为准的判断：

- **输入幂等键去重**：同一用户消息带同一 `client_message_id` 再投 → 命中唯一键返回已存在消息，不重复入队、不重复副作用（17.1 承诺②）。→ 落点：**17.3**。
- **执行账本状态判断**：每个工具动作先落 `issued` 再执行（先落意图），回投按 `invocation_id` 幂等收口为 `completed`，重复 / 迟到的回投被账本状态挡下、不二次生效；判不出执行与否时按幂等档分流——可安全重放 → `superseded` 交 AI 以新 invocation 重试，写类 → 停留 `issued`（ambiguous）如实记录（17.1 承诺①）。→ 落点：**17.4 主体（②–⑧、17.4.2、17.4.4）**。

**③ 业务系统兜底 · 工具/业务自身幂等（不依赖 Agent 外部）**

运行时防御判得出就已闭环；判不出"改没改"时，最后的兜底是**业务自己把动作做成幂等 / 可复核**：整文件覆盖写天然幂等（重复执行结果一致）、外部 API 带上自己的幂等键、写完后能 probe 读回复核。Agent 侧能承诺的只是账本如实记录、不自动回滚；业务答不出确定度时，落到 17.4.5 的 verified 分级（参考 · 未实现）。→ 落点：**17.4.5**；真做幂等要落在各工具实现侧，不在本章。

一句话收口：**协议层决定"敢不敢自动重放"，运行时防御决定"放不放行、记不记得住"，业务兜底决定"判不出时世界到底改没改"。** 三道防线如何被用户触发——重发 / 继续 / 重新生成三个键各穿透哪道防线——是末章 17.5 的主题。

### 17.3 摄入幂等：从"客户端再投一次"到"只入队一次"

**边界**：客户端 → 服务端入队。这是最接近传统请求幂等的一段。

**现状盘点**：

- ✅ **会话级已做**：session **有**唯一 id，且该 id 由**客户端生成**（`models/session.py:67`"客户端生成的 UUID v4"）——id 即幂等键。`create_session` 对同 id 已存在返回 `409`（`api/routes.py`），客户端超时重试创建时带**同一个 id**，就能被认出重复。
- ❌ **消息级缺失**：message **也有**唯一 id，差别在 **id 由谁生成、能否当幂等键复用**——`Message.id` 是服务端**收到 POST 后才** `uuid4` 生成（`models/message.py:144`），且 `MessageCreate` 请求体里只有 `content/scene_mode/workspace/model/mode/agent_id` 等业务字段、**没有客户端自定义幂等键的位置**。客户端无法在重发时带上"与上次相同"的键，于是两次相同内容得到两个不同 message id，服务端无法区分"同一条重试"还是"两条新消息"，可能排两次队、跑两遍。
- ✅ **出队侧已有"至少一次"地基**：`dequeue_next` 用 `SELECT ... FOR UPDATE SKIP LOCKED`（`storage/postgres.py`）原子出队——同一消息不会被两个引擎实例同时取走。配合消息状态机 `pending → processing → completed/error/cancelled`（`models/message.py`），**入队/出队这一段已经具备"至多一次消费"的前提**，只差入口的幂等键。

**为什么客户端会"再投一次"**：`POST /sessions/{session_id}/messages`（`api/routes.py` `send_message`）不是"发出去即收 ack"的普通接口——它**入队后直接挂一条 NDJSON 流**，消息 id / 排位在流首条 chunk 才返回；任何让客户端"拿不到已入队确认"的情形（读超时 / 确认前断连 / 客户端崩溃重启补发 / HTTP 自动重试 / 双击发送）都可能把同一条消息再投一次。五种触发与各自语义逐条放在末章 17.5《重发》入口，本节不再展开；这里只需记住结论：**投递的 ack 不可靠，所以入口必须有幂等键**。

**划清边界（为什么不能按内容去重）**：用户真把同一段话作为**新意图**再发一次，内容与上一条完全相同——但它是新消息，不该被去重。所以幂等键**不能用内容哈希**，必须是客户端在"按下发送"那一刻生成一次、整个重试往返复用的 `client_message_id`：同一意图的重试带**同一键** → 命中唯一约束返回已存在消息；新意图（哪怕同内容）分配**新键** → 正常入队。

**方案（待评估）——要不要 ack、ack 长什么样**：

**要 ack，但 ack 不是解药，三件套才是**——客户端幂等键 + 服务端去重 + ack 返回同一 `message_id`：

| 原语 | 解决什么 |
|------|---------|
| **客户端幂等键**（`client_message_id`） | 让服务端认出"这是上一条的重试"——没有它，多收一次就是多一条 |
| **服务端去重**（`(session_id, client_message_id)` 唯一） | 重复请求不再入队、不再重复副作用（audit / 设标题 / wake 引擎） |
| **ack 返回同一 `message_id`** | 客户端知道"成了、是哪条"才能停止重试——没有它，重试无终止条件 |

**病根在 ack 不可靠**：现状的 message_id 塞在长连接 NDJSON 流里，客户端拿不到"已入队"的可靠确认。所以方案本质是**把 ack 变成一次"轻、快、可靠"的往返**，再由键让这个 ack 在重试下仍返回同一条消息。

**解决形状：采用 A（提交与输出分离）**：

- **`GET /sessions/{session_id}/stream` 是会话级长驻流**（`reconnect_stream`：按 `since_seq` 回放 buffer → 实时消费，跨消息持续输出），客户端**在会话建立那一刻就开一条并长期保持**，断线按 `since_seq` 重连；**POST 只负责入队 + 拿 ack，不再背输出**。
- **流程**：会话建立 → 同时开 `GET /sessions/{session_id}/stream`（保持）。之后每条消息：`POST /sessions/{session_id}/messages {client_message_id, …}` → 服务端查 `(session_id, key)` 是否已存在 → **是**：返回已存在 `{message_id, queue_position, status}`（幂等）；**否**：插 pending → 202 `{message_id, queue_position, status:"pending"}`。引擎随即处理，输出经那条**早已开着的** `GET /sessions/{session_id}/stream` 回来——对每条消息**无额外连接往返**，首 token 速度与"POST 即流"持平（首 token 支配项是 LLM TTFT，本地多一跳 RTT 为毫秒级）。
- **代价 / 前提（不回避）**：首 token 不会被拖晚，因为 `GET /sessions/{session_id}/stream` 在会话开头（用户打字时）就已就绪。真正依赖回放兜底的是**唯一一个窗口：`GET /sessions/{session_id}/stream` 中途掉线 → 重连成功之间**引擎推的 chunk 按 `since_seq` 补——这和今天断线重连是同一场景。当前回放只有内存 StreamBuffer（环形 500 条）、`stream_events` 表是空壳（无人写），故需**连"回放可靠"一起做**（输出事件落 `stream_events` 表 / 加大 buffer），否则长掉线会丢中间 chunk。客户端契约变更：从"POST 即流"改为"会话一条常驻 `GET /sessions/{session_id}/stream` + POST 只入队拿 ack"。引擎活着时 `/stream` 掉线不是恢复场景、客户端无需动作（掉线只是订阅断，见末章 17.5）；本节只把 `/stream` 当作 A 层的输出通道机制，掉线重连就靠本条的 since_seq 回放兜底，不再展开成客户端交互。

**关键语义（A 方案内通用）**：

1. **去重短路在副作用前**：命中重复 → 直接返回已存在消息，**不再** audit / 改标题 / wake 引擎；这些只在首次插入时做。
2. **重复返回 200/202 + 同一 `message_id` + 当前状态**（不抛 409）：重试与首次成功走同一条 happy path，客户端无需特判。
3. **键存在消息行上**（`client_message_id` 列 + 部分唯一索引），不需要单独的"键→id"映射表 → 无表膨胀，保留期跟消息生命周期走。
4. **429 队列满**：该次未插入，客户端稍后带**同一键**重试仍幂等。
5. **别与 17.4 工具回投幂等混**：这里幂等的是"消息已入队"（键 = `client_message_id`）；17.4 账本幂等的是"工具结果已回传"（键 = `invocation_id`）——两层、两把键，不复用。
6. `MessageCreate` 增可选 `client_message_id`：客户端**按下发送那一刻**生成一次、整个"发送→收 ack"往返复用同一值（不随重试改变），见上文"划清边界"。

**A 层客户端契约（极简）**：A 层客户端只需做一件事——`POST /sessions/{session_id}/messages` 时带 `client_message_id`；未拿到 ack（POST 超时 / 连接错误 / 5xx）时以**同一键**重发即可。判断依据 = POST 是否返回 202 ack（形状 A 下提交与输出解耦，天然可分）：瞬时网络错误可先指数退避自动试 1–2 次，仍失败才亮"重发"按钮等用户点；无论自动还是手动都**复用同一 `client_message_id`**——即便上次实际已入队，服务端命中 `(session_id, key)` 唯一约束也只返回已存在消息、不重复入队/副作用。这里 ack 的是"消息已入队"，与 17.4 工具回投的 `invocation_id` 是两层两键（见上关键语义 5）。**客户端其余动作（继续 / 重新生成）不在本节，统一收在末章 17.5**。A 只回答"怎么让同一条消息只入队一次"。

**为什么入队后不再需要更多**：出队已 `SKIP LOCKED`，处理结果按消息 id 落状态机，只要入口去重，A 层就闭合。**A 层只解决"流程不重"，不解决"动作不重"**——一个工具动作至多生效一次是 17.4 账本的事；A 层拦不住的"重跑后 LLM 又发一遍写动作"，只能靠 17.4 的幂等档与恢复前导去挡。

### 17.4 工具执行状态机（四个账本状态，实现口径）

> **本节定位**：把 `tool_invocations` 工具调用账本的状态管理**按当前实现写清**，是工具执行幂等 / 副作用账本的**实现口径**。旧方案曾把"执行失败"拟成一个账本状态 `failed`，**实现里没有这么做**：工具"执行了但失败"一律记 `completed + result.success=false`；账本状态只保留四个值 `issued | completed | skipped | superseded`，其中原 `failed` 仅承载"明确未执行（用户跳过）"，已更名为 `skipped`。

#### 17.4.0 一次工具调用的端到端流程（九步总览：① 先定义工具，②–⑨ 落地一次调用）

先把 ① 的定义工具分类，到一次客户端工具调用（写文件 / 跑命令这类在客户端执行的工具）从诞生、落账到终态后续处理，九步连起来看一遍；字段、状态含义与迁移细则在 17.4.1–17.4.6 逐节展开；账本的**恢复消费**（重跑尾巴过账 / 前导）已上移到 17.5。

**① 先定义工具（分类前提）**

工具在进入调用流程前先拿到两类**工具级属性**：`side_effect`（读/写）、`idempotency`（`read-only / idempotent / non-idempotent`）。**先定义、后落账**——分类不是每次调用现算，而是钉在工具定义上的既定事实：

- 由 `server/tools/idempotency.py` 按工具名派生（客户端工具与 `SERVER_MEMORY_TOOLS` 服务端直执行共用同一套白名单）：
  - `read_file / read / glob / grep / recall / load_memory` → `read-only`：读操作，无条件安全重放；
  - `write_file / write` → `idempotent`：整文件覆盖写，重复执行结果一致，可安全重放；
  - **其余一律默认 `non-idempotent`**：写类/副作用，判不出时一律不自动重放（保守：只放行白名单）。
- `side_effect` 与 `idempotency` **同源派生**：`read-only=false`，其余为 `true`——幂等可重放的整文件覆盖写仍构成副作用。
- 工具定义里可**显式声明 `idempotency` 覆盖默认**（`apply_to_tool_def` 尊重已有标注）。
- `requires_approval` 是**另一路**：不随工具定义写死，由 `permission.py` 在运行期按 `permissions.yaml` 策略判定（见 ④）。

② 落账带的 `side_effect / idempotency`、④ 是否先问人、⑦ 判不出时敢不敢自动重放——后面每一档行为都以这份工具分类为准。

**② 先落意图再执行**

服务端先在 `tool_invocations` 插一条 `state=issued` 的记录，动作才真正下发。**先落账、再执行**是铁律；这条记录即一次受账动作的执行账：

```json
{
  "invocation_id": "2f4c…",           // 唯一调用键，= 下发给客户端的 request_id
  "session_id": "9a1e…",
  "message_id": "5b8d…",              // 归属消息
  "turn": 3,
  "attempt": 1,
  "tool_name": "bash",
  "location": "client",
  "state": "issued",
  "input": { "command": "echo hi" },
  "side_effect": true,                // 写类；read-only 工具为 false
  "idempotency": "non-idempotent",    // read-only | idempotent | non-idempotent
  "requires_approval": false,
  "result": null,
  "error": null,
  "created_at": "2026-09-08T10:00:00Z",
  "completed_at": null                // 终态落定时才填
}
```

字段语义见 17.4.1 字段表。

**③ 派活并等待**

服务端经 NDJSON 长流推一条 `client.tool_request` 给客户端，随后等待约 `tool_wait_timeout`；等待期间②的账保持 `issued`。发送结构：

```json
{
  "type": "client.tool_request",
  "request_id": "2f4c…",              // == ② 的 invocation_id，回投时凭它认账
  "tool_name": "bash",
  "input": { "command": "echo hi" },
  "message_id": "5b8d…",
  "tool_call_id": "tc1",
  "step": 1,
  "requires_approval": false,
  "policy": { "workspace": "/path/to/ws", "…": "…" },
  "idempotency": "non-idempotent"     // 幂等档，客户端据此判断能否自动重试
}
```

客户端据此执行，结果经 `POST /sessions/{id}/tool-result/{request_id}` 回投。

**④ 需审批则先问人**

`requires_approval=true` 的工具由客户端弹审批框：

- 用户**批准** → 进入 ⑤ 执行；
- 用户**拒绝 / 跳过** → 回投 `{skipped:true}`，账改 `skipped`（`error=user_skipped`），AI 得知该动作被跳过、改用别的手段，不硬重试。

**⑤ 真实执行**

批准或免审批后，客户端真正执行该工具。

**⑥ 回投收口**

执行完回传结果：

- 成功 → 账改 `completed`，`result.success=true`；
- 业务失败 → 同样记 `completed`，`result.success=false` + `error=真实错误`（工具确已执行、副作用范围可能不完整，不是独立状态，见 17.4.2）。

收口后服务端把 `result` 喂回 LLM（`append_tool_result`），由 LLM 决定继续 / 换参重试 / 换工具；**引擎不代自动重发**。

**⑦ 首段超时 → 对账窗**

约 `tool_wait_timeout` 没等到回投时**不判失败**，先推 `client.tool_reconcile`（带 `request_id / tool_name / idempotency`），再宽限一个对账窗：

- 客户端答 "executed + 补投结果" → 账改 `completed`（已执行不重跑）；
- 客户端答 `unknown` 或超窗 → 按 `idempotency` 分叉（细则见 17.4.4）：
  - 可安全重放（`read-only` / `idempotent`）→ 原账改 `superseded`（`error=uncertain_replayable`），以"结果不确定、可安全重试"喂回 LLM，LLM 自行发**全新** `issued` 重试；
  - 写类不可重放（`non-idempotent`）→ 账**停留 `issued`（ambiguous）**，如实记录"已下发、结果未裁决"：不自动重放，也**不推 `tool.reconcile_needs_confirm`、不强制人工确认**——结果以"不确定、已记录 + 核实引导"喂回 LLM（见 ⑧），消息正常收尾；迟到的真实回投仍可把它收口为 `completed`，ambiguous 尾巴只是如实记录、不再拦截该消息后续的重新生成。

**⑧ 全程结果回喂 AI**

除"跳过"分支外，每步终态的结果（成功 / 失败 / 不确定可重试 / 不确定已记 issued）都追加进 LLM 上下文（`append_tool_result`），AI 据此推进，直到 `end_turn` 收尾该消息。对"写类结果不确定、已记 issued"的引导：能用只读手段核实（read_file / glob / recall）就先核实再继续；核实不了就把"已发起、结果未回、可能已生效、未重试"如实写进回复，不阻塞本轮、不要求人工裁决。

**⑨ 回合后拉工具动作清单（含状态）**

消息终态后客户端 `GET /sessions/{id}/effects`，把本轮实际执行过的工具动作（读、写都含）展示给用户：

- 返回该会话（或指定消息）的**全部受账工具动作**：不限 `side_effect`（只读也进）、不限 `state`（`issued / completed / skipped / superseded` 四态都返回，见 17.4.6）；
- 每行带 `state` 与 `side_effect`：按 `state` + `result.success` 呈现 完成/失败/跳过/未知，用 `side_effect` 区分读/写——只有写动作才算副作用、才需"已执行、未回滚"的交代；
- 每行字段：`invocation_id / message_id / attempt / tool_name / location / state / side_effect / idempotency / input / result / error / created_at / completed_at`。

对应关系：字段表 → 17.4.1；四个状态各自"能确定什么" → 17.4.2；"结果未知"的三种落点 → 17.4.4；副作用确定度 → 17.4.5；对外呈现 → 17.4.6；账本的**恢复消费**（重跑前尾巴过账）→ 17.5。

#### 17.4.1 账的对象与记录时机

`tool_invocations` 表每行 = **一次"受账"工具动作的执行账**（ORM `OrmToolInvocation`，`db/models.py`；迁移 011 建表、012 加 `attempt`）。铁律是**先落意图、再执行**：工具动作一旦确定（LLM 输出 tool_use 且通过权限/hook），先插一条 `state=issued` 的记录（`query_loop.py:_record_issued`），之后动作才真正下发/执行，结果回来再按状态机迁移。

关键字段：

| 字段 | 语义 |
|---|---|
| `invocation_id` | 唯一调用键 = 下发给客户端的 `request_id`，唯一 `(session_id, invocation_id)` |
| `session_id` | 所属会话 |
| `message_id` | 归属消息；前端据此把工具动作挂回对应 assistant 气泡 |
| `turn` | 归属 turn 序号 |
| `attempt` | 前端工具动作运行分块序号：regenerate 开新块 / continue 复用当前（`_resolve_attempt`） |
| `tool_name` | 工具名 |
| `location` | 执行位置：`client \| server` |
| `state` | 状态：`issued \| completed \| skipped \| superseded`（见 17.4.2）；随 `GET /effects` 行下发 |
| `side_effect` | 是否写类（布尔）：read-only=false、其余=true；随行下发供展示侧区分读/写，当前不作过滤（见 17.4.6） |
| `idempotency` | 幂等档：`read-only \| idempotent \| non-idempotent`（运行期由 `tools/idempotency.py` 按工具名派生） |
| `requires_approval` | 是否需用户审批 |
| `input` | 入参 JSON |
| `result` | 工具返回（`completed` 时写，含 `success` 标志；业务失败 = `success:false`，见 17.4.2） |
| `error` | 状态机层"中止原因"：`user_skipped` / `uncertain_replayable`（见 17.4.4） |
| `created_at` | 落账（`issued`）时间 |
| `completed_at` | 终态落定时间 |

#### 17.4.2 状态集与"能确定什么"

| 状态 | 跑了没？ | 世界改没改？ | 一句话 |
|---|---|---|---|
| `completed` + `success:true` | 确定跑了 | 按工具语义应该生效了（成功返回） | 结果确定，成功 |
| `completed` + `success:false` | 确定跑了 | **不知道**（失败前可能已改一半） | 结果确定，失败；改没改另说 |
| `skipped` | 确定**没**跑 | 确定没改 | 明确没执行（用户跳过/审批未放行） |
| `issued` | **不知道** | 不知道 | 活儿派了、结果没回；账还开着 |
| `superseded` | **不知道** | 不重要（可安全重跑） | 查不清就作废，让 AI 安全重试 |


#### 17.4.4 "结果未知"的三种落点（别混）

结果回不来时，账停在哪里取决于"还能不能重放"：

| 账停在哪 | 弥补措施 |
|---|---|
| `superseded` | 前提：判不出执行了没，但工具可安全重放（read-only / idempotent）。可重放 → 原调用作废、LLM 可用全新 invocation 重试 |
| 停留 `issued`(ambiguous) | 前提：判不出执行了没，且是写类（non-idempotent）。弥补：不自动重放、不强制人工裁决——账如实记录"未裁决"；回喂 LLM 提示其用只读手段自核实，核不了则如实交代给用户；迟到的真实回投经 `submit_client_tool_result` 仍收口为 `completed` |
| `completed`(success:false) | 前提：判得出"执行了但失败"。执行与否确定；不知道的是副作用范围（clean/partial/applied） |


#### 17.4.5 副作用确定度（参考 · 未实现）：失败 ≠ 没生效——verified 四级

17.4 的账能答"跑没跑、账停哪"，但**答不了"这一次失败把世界改到了哪"**：`completed` success:false 只证明"执行了但失败"，副作用可能是干净（完全没改）、partial（改了一半）或 applied（其实已完成）。要精确到 `clean / partial / applied / unknown` 四值，需要**状态机之外的验证机制**——当前未实现，此处保留草案方向作参考（原则：**失败 ≠ 没生效，禁止默认重做**）：

1. **原子 / 只读**（失败必未生效，可放心重试）→ `clean`：只读读失败必无副作用；写文件若改成"同目录临时文件 + rename 原子替换"，失败只剩替换前的错误 → 原文件未动。
2. **快照 diff**（bash 这类任意命令）：执行前后各抓一次工作区快照对比，空差集 → `clean`；非空 → `partial`，附 `changed_paths` 如实喂 LLM / 人，不自动回滚。
3. **幂等键 probe**（外部 / MCP）：带 key 只读查询是否已应用；已应用 → 其实已完成、只是结果没回 → 转**补投结果**（`applied`，不重执行）；未应用 → 可重试。
4. **判不出** → `unknown`：不做任何自动重放，走 ⑦ 的分叉——可安全重放档记 `superseded`、写类记 `issued`(ambiguous)，如实交代（见 17.4.4）。

| `verified` | 含义 | 去向 |
|---|---|---|
| `clean` | 失败必未生效（只读 / 原子），或 diff 证无改动 | 当干净失败，按幂等档可安全重试 |
| `partial` | 已改动，附 `changed_paths` | 如实报告改动，交 LLM / 人补救，不自动回滚 |
| `applied` | probe 证副作用已完成、结果未知 | 转**补投结果**，不重执行 |
| `unknown` | 判不出 | 走 ⑦ 分叉：可重放 → `superseded`；写类 → 记 `issued`(ambiguous) |

> 一句话：`completed` 答"执行了"，**"改没改"由 `verified` 四值答**：clean 可重试 / partial 如实报 / applied 转补投 / unknown 按幂等档交代——失败后绝不默认重做。

#### 17.4.6 对外呈现（客户端工具动作视图）

`GET /sessions/{id}/effects`（`routes.py`）是当前对外视图：返回该会话（或指定消息）的**全部受账工具动作**——**不限 `side_effect`**（只读也返回）、**不限 `state`**（`issued / completed / skipped / superseded` 都返回），每行 payload 含 `state` 与 `side_effect`。语义从"已生效副作用清单"扩成"**工具执行账本视图**"：让用户看到 AI 本轮实际执行了哪些读/写动作、各自停在哪个状态，而非只挑写操作汇报。

语义要点：

- `side_effect` **不再作过滤条件**，只随行标注读/写：**只有写动作才构成副作用**，其中 `completed ∧ side_effect=true` 才确定是"已生效写"，需如实交代"已执行、未回滚"；只读动作只是过程记录，无副作用语义。
- 展示侧若只想要"已生效副作用"，可自己对 `state=completed ∧ side_effect=true` 再筛；将来对只读做折叠/限制也应在展示层做，账本侧不预设。

按 `state`（+ 并行维 `result.success`）的四色映射：

| 展示（色） | 状态 |
|---|---|
| 完成（绿） | `completed` success:true |
| 失败（红） | `completed` success:false（副文案宜注明"可能部分生效"） |
| 跳过（蓝） | `skipped` |
| 未知（黄） | `issued`、`superseded` |

### 17.5 中断与恢复：三个幂等入口（重发 · 继续 · 重新生成）

> 前几节是机制（17.3 摄入、17.4 账本），本节把它们收拢成**用户能按的三个键**。整章幂等平时不可见，靠用户触发才现身——每次按键都代表"同一个意图要跨边界再来一次"，三个键恰好各兑现 17.1 三个承诺中的一个：重发 / 继续 / 重新生成。
>
> **先划清非恢复场景**：没有 token 流级别的"继续"。引擎活着时 `/stream` 掉线只是订阅断，自动重连 / 刷新即全量（17.3），不构成动作，不在下列。
>
> **恢复场景判据**：回合**真正中断**（异常 / 进程死 / 遗留 `processing`）之后才是——此时该回合已是"半截"，需要"重发？继续？重新生成？"三选一。

#### 17.5.1 重发

- **触发**：消息**没拿到入队 ack**——读超时 / 确认前断连 / 客户端崩溃重启补发 / HTTP 自动重试 / 双击发送（五种触发逐条见 17.3）。
- **处理**：**复用同一 `client_message_id` 再发一次即可**——入队去重（`(session_id, key)` 唯一键，机制全在 17.3）兜底：同键重投命中已存在 → 幂等 ack 返回原消息；不在 → 才插 pending 跑。**不会双跑**。
- **边界**：引擎活着时 `/stream` 掉线不触发重发——订阅断，自动重连即全量（17.3），不是"没投递"。

#### 17.5.2 继续

**是什么 / 与另两键的差别**

- **继续** = **半截消息的恢复入口**——补中断的尾巴，不丢已完成的动作。触发 = 生成到半截中断（异常 / 进程死 / 遗留 `processing`）；库里停在 `processing` / `error` 即持久"中断"信号，前端据此亮"继续"。
- **≠ 重发**：这条消息已成功入队并开始生成过，是"半截"，不是"没提交"；
- **≠ 重新生成**：不把整条旧回复推倒重来，只把断掉的后半截续上。

服务端要撑得起"继续"，三个前提先立住（不满足则半截停在哪就是哪）：

1. **终态诚实**：`run()` finally 按路径写 completed / error / cancelled，不再无条件 completed；
2. **探针判活**：判"引擎死没死"一次内存读（`/state` 探针）；
3. **截得准**：`conversation_history` 行带 `message_id` / `turn` 标记，服务端才定位得到这条消息的 **commit 点**（DB 已把某个 turn 完整落库的边界：该 turn 的工具都 `completed`、结果进了 `conversation_history`）——续跑从它接着起，才不会把没落库的半截当已提交重跑。

**① 门槛：什么消息能亮"继续"（客户端）**

先判"末位 assistant 是不是一条能续的**半截**"，以下四条同时成立才亮"继续"：

- **位置**：末位 assistant，且已带服务端 `message_id`；
- **引擎空闲**：无在途回合——有在途则等它自然收尾，不并跑续跑；
- **停在非正常终态**：终态 ∈ `error | cancelled | interrupted`（下表逐个拆）；
- **半截只在客户端**：前半动作（用户行、此前的 completed turn）都在库，只有中断的半截正文 / 思考在客户端内存。

这三个"可继续"终态各自是怎么进来的（库中写的 / 推导的）：

| 停在哪 | 什么情况进入 | 亮"继续"？ |
|---|---|---|
| `error` | 生成到一半抛未捕获异常——执行超时（`execution_timeout`）、API / 认证失败等。引擎 `try` 兜到 `Exception` → `finally` 落 `error` 并记 `error_message` | ✅ 半截 |
| `cancelled` | 两类：① **未开跑**——消息还在 pending 队列就被用户移除；② **跑一半被取消**——软取消（build-abort / plan-reject / 取消检查点，循环返回 `"cancelled"`）或硬取消（`task.cancel()` / 解释器关闭抛 `CancelledError`），`finally` 一律落 `cancelled` | ② ✅ 真半截；① 无正文、不是半截（该走删除 / 重发） |
| `interrupted` | **推导态、非存库**：进程被 kill / 引擎 task 静默死亡，`finally` 没机会跑 → 消息一直停在 `processing`；重启后引擎不活，`/state` 把这些 processing 消息列为 `interrupted_candidates`，客户端据此判为中断半截 | ✅（只在引擎不活时出现） |

对照 **`completed` 不算中断、不亮"继续"**：end_turn / ask 单轮自然结束，已是完整结果，用户不满意该走"重新生成"，不是补半截。

**② 按下"继续"：客户端只置 processing、不动半截（客户端 → POST）**

- 半截正文只在本地（服务端从未落库），**留着不清**——万一被服务端拒绝（busy / needs_confirm）还能原样再点；
- 客户端置 processing，POST `/messages/{id}/continue`（body 带原 `client_message_id` 审计关联）。`continue` 与 `regenerate` 是**同一入口的两个截断点参数**；continue 的截断点 = **commit 点**。

**③ 核心判断：扫这条消息的 issued 尾巴 → 按幂等档放行（服务端）**

放行前服务端只做一句判断——**看这条要续的消息名下还有没有没结算完的工具账**（`state=issued` 的**尾巴**，即“已发起、结果没回、可能已生效”的账——裁决只看 `issued`，`skipped`（已明确不执行）、`superseded`（已作废）、`completed`（已收口）都已定论，不进裁决）。这就是"**查看最近消息的工具执行情况**"——但只查**这一条**消息的账（`list_issued_by_message(session_id, message_id)`），不是查整个 session；别的消息残留的半截尾巴各有自己的恢复入口，不在这里拦。扫到 issued，再**按工具的幂等档分叉**：

| 扫到哪种尾巴 | 处理 | 要问用户吗 |
|---|---|---|
| 没有 `issued` 尾巴 | 放行 | 否 |
| 只读 `read-only` | 放行 | 否 |
| 幂等写 `idempotent` | 放行| 否 |
| 非幂等写 `non-idempotent` | **先判得再放行**：判得 = **重问客户端**（工具在客户端执行，它本地执行账可答"已执行 / 没执行 / 不知道"）——答已执行 → 补投结果、标 `completed`、"别重跑"、进前导清单；答没执行 → 放行；**答不出（ambiguous）→ `needs_confirm` 反问用户**，返回 `ambiguous_tools` 交用户裁决，重跑不自动放行 | 判不出才问 |

> **表里的"放行"指什么**：服务端**不拦这次 continue，放它进入 ④ 的续跑**——已提交前缀照留、起点从 commit 点起、历史原样重给大模型。放行的是**整个继续请求**（这一条消息的半截被允许重跑），不是"某个工具现在立刻再执行一遍"——只读 / 幂等尾巴放行后，重跑阶段要不要真的发工具，由续跑的 LLM 自己决定。和"要问用户吗"列对着看：凡标"否"的行都是放行、不打扰用户；唯一例外是非幂等写的**判不出**那格，会 `needs_confirm` 把这次 continue 拦下反问，拦下就不进续跑。
>
> 对照你"若 issued → 看幂等 → 幂等就把历史重给大模型 / 非幂等就反问"的总结：方向对，两处收窄——(1) 扫的范围是**这条消息名下**的账，不是全局"最近工具"；(2) 非幂等是**先判、判不出才反问**——判得已生效 / 未生效的都自动收口，不一律反问。
>
> 实现注记：上表是**目标设计**；当前实现取更粗的"判不出即挡"——非只读的 `issued` 尾巴一律 `needs_confirm` 整轮拦截（`reprocess`），不自动裁决、无前导注入。运行期 C-2（工具超时对账）已实现幂等档分叉（见 17.4.0 ⑦）。

**例 · 同一个尾巴两种走法**

一条 user 消息："把 `/tmp/report.md` 末尾追加今天的结论，再读回来检查格式。" 首跑动作链：

| 轮 | 动作 | 结果 |
|---|---|---|
| turn1 | LLM 发 `read_file(/tmp/report.md)` | 结果回投 → completed，随 turn1 落库 ✅ |
| turn2 | LLM 发 `edit_file`（追加结论） | 落 `issued`、推 client.tool_request → 客户端执行完但回投前崩溃 → 结果没进上下文，引擎死，消息停在 processing ⛔ |

此刻 commit 点 = turn1 结束；**尾巴 = turn2 那只 `edit_file`（issued，side_effect=true）**。它没回投，completed 与落库都没发生 → 不在"已提交前缀"里（喂给 LLM 的历史只到 turn1），只作为一条 issued 账躺 `tool_invocations`。LLM 并不知道那半截执行了没 → 尾巴按幂等档分两路走：

- **尾巴是幂等操作（`idempotent`，如整文件覆盖 `write_file`）→ 放行**：即使实际已执行，重放一遍结果一致（可安全重放）→ 不打断、不进前导，直接续跑；
- **尾巴是非幂等操作（`non-idempotent`，如 `edit_file` 追加）→ 先判得再放行**：判得 = **重问客户端**（工具在客户端跑，它本地执行账能答）。于是三种回音：
  - 客户端答"已执行、结果如下" → 补投结果、标 `completed` + 注入前导"以下写动作已确认完成，勿重复执行：[edit_file 追加结论]" → 续跑的 LLM 看到已追加，直接去检查格式；
  - 客户端答"没执行" → 放行，续跑 LLM 重新追加一次（无碍）；
  - 客户端也答不出（断了 / 丢了本地账）→ **判不出 → `needs_confirm` 反问用户**，不自动放行。

> 对照：只读尾巴（read_file 类）没这危险——放行让续跑重读也无害（重读零风险），这就是它直接放行的理由。"判得 = 重问客户端"运行期 C-2（工具超时对账）已按这套走；恢复期（continue）的自动裁决 / 前导注入仍是目标设计（见本步注记）。

**④ 放行后：历史原样重给大模型，从 commit 点接着续（即"把之前的历史重新给大模型"）**

③ 放行落成动作就一句：**不 truncate、不重播**——把这条消息 DB 里已提交的部分原样当上下文，从断点之后的 turn 重新让 LLM 接着想。拆五条：

**起点：commit 点，不 truncate DB**

- `_resume_turn_start` = 该消息 DB 已落**最大 turn + 1**；
- 为何安全：DB 只落"完整提交"的 turn（assistant 正文在"调工具前 / 回合自然结束"两处落库），半截尾巴从未落库 → 起点天然对齐 commit 点，不会切在半截工具上。

**上送什么：已提交前缀整段保留**

- 用户行 + 此前已完成 turn（含**已记录**的工具结果）整段进重跑上下文；
- 效果：**"已提交 / 已记录副作用不重放"由上下文保留实现**——LLM 看到已做完，自然不重发。

**前导注入（仅当 ③ 判得"已确认生效的写"）**

上面"上送什么"是重放**历史**——已落库、重跑原样可见；前导注入补的是**历史里没有的一段**：写动作实际已生效，但结果没来得及进库/进上下文（③ 判得"已执行"的尾巴、"结果已回投但整轮未落库"的 `completed` 写都属此类）——LLM 靠历史看不见它，就可能换 id 再发一遍（重跑是新一轮、新 `invocation_id`，id 去重拦不住这种语义重复）。于是把这份清单单独拼成一条消息，注入重跑**首轮**：

- **装什么**：③ 判得"已执行、别重跑"的尾巴，＋"结果已回投、整轮未落库"的 `completed` 写——共同点都是**已生效、但不在对话历史里**；
- **怎么装**：做成一条清单消息注入首轮上下文，如"以下写动作已确认完成，勿重复执行：[tool、对象、摘要]……"；
- **和历史重放什么区别**：历史重放是"记录本来就在库里，原样再给一次"；前导是"这份记录从没写进对话行，靠注入补一张事后清单"。给 LLM 看到的效果相同（见已做完即不重发），来源不同。
- **例**：接上"例 · 同一个尾巴"的 turn2——`edit_file`（给 /tmp/report.md 末尾追加今日结论）已执行、结果没进上下文就崩，历史里没有它；客户端答"已执行"→ 标 `completed` 并注入"以下写动作已确认完成，勿重复执行：[已在 report.md 末尾追加今日结论]" → 续跑的 LLM 看到已追加，直接去"读回检查格式"，不再 append。

（目标设计，见 ③ 注记：当前 reprocess 仍为粗门禁，不做裁决、无前导。）

**客户端何时续接：收到 `message.start` 才截半截**

- 服务端推 `message.start{message_id, reason:"recovered"}` 为首事件；
- 客户端**收到它**才把本地半截正文 / 思考截到"末次已落库工具（commit 点）"处；
- 随后新流从这续接，与续跑内容不重叠——收到首事件前，② 欠下的"不清气泡"仍保持。

**续跑走账**

- 新工具 → 新 `invocation_id` → `issued` → `completed`（运行期 C-1 / C-2 不变）；
- D 副作用分块 `attempt` **复用当前块**（不新开，与 17.4.1 attempt 语义一致）。

**⑤ 收尾与如实交代**

- 终态按路径分流 `completed / error / cancelled`；续跑中再次中断 → 同样停在该终态，尾巴再交给下一次恢复；
- 仍判不出的 ambiguous 尾巴如实标注"已发起、可能已生效、未确认"，**不伪称已回滚**；
- 前端在终态 `GET /effects` 按 attempt 分块渲染副作用清单。

#### 17.5.3 重新生成

**触发**

完整结果已出但用户不满意、或 error / cancelled 后想重来。

- **不是新消息**：截到该消息**用户问题行**，丢弃整条旧回复（含全部工具痕迹），从头重跑出新回复；
- **不用幂等键**：有意重跑——要的是一条新结果，不是把写再做一遍。

**与继续的差别只在截断点**

- 继续 = commit 点（保前缀）；重新生成 = 用户问题行（丢整条，turn 从 0 重来）；
- 两者机械同构 = “按截断点执行”：服务端收敛成一个入口（两个按钮只是截断点参数不同），走同一条“**过账（把这条消息的账理清）→ 截断（到各自的点）→ 重跑**”流程；
- **不能**把同内容当新消息 POST——那会带着旧回复追加一轮而非替换。

**危险与对策**

- **为何更危险**：继续丢的只是未落库的半截、已提交 turn 的工具结果留在上下文；重新生成连**已提交 turn 里已生效的 `non-idempotent` 写也一起丢**；
- **对策一 · 前导喂回**：重跑前把该消息**已确认生效写清单喂回**（前导注入同继续 ④；范围更大 = 该消息 D 账 `list_effects` 里 `completed ∧ side_effect=true` 的全部，而不只 ③ 尾巴判得的那几只），让新 LLM 看到已做完；
- **对策二 · 判不出不放行**：`non-idempotent` 判不出的一律不自动重放（同继续 ③：判不出即反问）；
- **D 账分块**：`attempt` 开新块（与继续的复用相反）。
